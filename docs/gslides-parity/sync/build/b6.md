### 2. The copy script, as built

`SOURCE_BLOB_TOKEN` and `TARGET_BLOB_TOKEN` from the environment (sourced in a subshell), refused when either is missing or both are one value, never printed, written or passed on a command line; the SDK's `list({ token, limit: 1000, cursor })`, `head`, `get({ useCache: false })` and `put({ addRandomSuffix: false, allowOverwrite: false, contentType, cacheControlMaxAge })` from `@vercel/blob` 2.8.0 (the version the store package pins; the root `node_modules/@vercel/blob` resolves it); eight in flight. Resumable: the target is headed first and an object there with the source's etag is counted `already`; an object there with another etag is a conflict, listed and never overwritten; a put refused as existing is headed again (a race) and counted `already` or conflict. Verified: the put's etag is compared with the source's and, when they differ, the copy is read back and compared by the md5 of the bytes (`hashChecked`). `--dry-run` heads the target and writes nothing (`planned` counts). `--skip exports-older-than=<n>d|h,turboslide-sidecars` (the job records under `exports/.jobs/` are kept; an export without an upload time is copied). `--verify` re-lists both stores and compares the copied set per prefix by count and per object by etag, naming the skipped rules and the target objects outside the set it ignores. `--state <file>` writes pathnames and source etags (nothing else); `--delta` copies the entries whose source etag moved since the first pass over a target copy that still carries the first pass's etag (`ifMatch`) and lists a target copy rewritten since without touching it. The summary prints counts, bytes, elapsed time and the first twenty differing pathnames; `--json <out>` writes the same. Cost and time are section 3's estimates; nothing here measured a real store.

What the fake cannot show and a real run would: the SDK's `get` answering a weak validator (`W/"..."`) where `head` answers the strong etag (`normalizeEtag` strips both, as `blob-vercel.ts` `strongEtag` does); a multipart put's etag shape (the md5 fallback covers it); the 429 and 5xx of a busy store (the SDK's retries stay on in this script, since `VERCEL_BLOB_RETRIES` is not set here and the store package's reason for turning them off is a function's deadline, not a copy's); the public host's CDN lag (`useCache: false` reads the origin).

### 5. Findings for the integrator and Kevin

1. The WAF redirect and the path (R4): the documentation does not say the request's path survives a WAF redirect; the rehearsal's step 13 reads it on a scratch project. Until then the WAF rule of section 5 step 7 should be read as a coarse switch for the minutes before the static 308 lands.
2. The CLI's subcommand help: `vercel env pull --help` and every other `vercel <cmd> <sub> --help` print an error in 58.4.4; `vercel <cmd> --help <sub>` prints the subcommand's options. The audit's method section names `vercel blob list --help`; the form that works is `vercel blob --help list`.
3. `vercel env add` takes the value from the prompt or stdin; `--value` puts it on the command line and in the shell history, so the runbook uses the prompt for every secret and `--value` for the plain settings alone.
4. The `redirects` rule's `permanent: true` is a 308 (the redirects documentation); the WAF's `--redirect-permanent` is a 301 (the CLI's help) and the WAF default a 307. The static deployment is the 308 the acceptance names; the WAF rule is never the permanent one.
5. `vercel project speed-insights` and `web-analytics` enable only; the off toggles of section 7 are the dashboard's.
6. `vercel project update` has `--framework`, `--build-command`, `--output-directory` and `--auto-detect`, and no Root Directory flag; whether `--build-command ""` sets an override on and empty was not tried (it would change the project), so the dashboard is the path of record for the section 7 settings and the CLI's `--auto-detect` the way back at the rollback.
7. The plan's `turboslide deck info --to <url> <id>` is not a CLI command; `turboslide share get <id> --to <url>` is the authenticated read the runbook and the check name.
