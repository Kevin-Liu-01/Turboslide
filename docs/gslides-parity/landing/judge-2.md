# Landing judge 2: showing off the product

Judge 2 of three for the landing workflow. Kevin wrote on 2026-10-02: "make the landing much better inspired off of lovefrom and openai brand and make the landing much more interactive and showing off features featuring the best of graphic and motion design". My lens is the product shown off: does a seller understand within one scroll what Turboslide does that Google Slides does not, are the features real and demonstrated rather than claimed, are the interactions worth touching, and does the page lead to New Presentation and Open the Example Deck.

Written 2026-10-02 from 18:09 to 18:40 PDT in `/Users/kevinliu/repos/Turboslide-landing` on `landing/redesign` at `2108dad4`. I read the five research notes (`research-lovefrom.md`, `research-openai.md`, `research-product.md`, `research-motion.md`, `research-current.md`), the three direction notes, and every picture each direction listed (all 20 of A, all 26 of B, all 23 of C), plus the current branch's first screen (`current/pictures/branch-1440-light-first.jpg`) and two reference stills (`openai/stills-desktop-heroes.jpg`, `lovefrom/desktop-home-1440.png`). I opened each prototype from `file://` with the worktree's `playwright-core` and tried it as a seller would (section 8). No site was fetched for this note: claims about lovefrom.com and openai.com are the researchers' readings of 2026-10-02 with the URLs they cite. Nothing outside `docs/gslides-parity/landing/` was written, no git write ran, no server was started.

## 3. Direction A, quiet object: 39

- **Craft 8.** The most exact page of the three. The lighthouse develops through the Bayer screen at 2 px cells and reads as a photograph (`mood-develop-light.png`, `reduced-motion-mood-200ms.png`); the mark's seven bars assemble once (`close-mark.png`); the show turns the band to ink and back on the move curve (`present-show.png`, `judge-2/a-show-try.png`); nothing runs at idle and CLS is 0 at both widths (direction-a.md section 7). Against it: the 1440 first screen is a title and a two line subtitle on an empty sheet (`first-1440-light.png`), which reads as restraint to a designer and as nothing yet to a seller; the Tailor band's three slides are about 320 px wide, with body text near 8 px (`page-1440-light.jpg`, band 3); the agents band opens on an empty slide reading "The first command adds slide 6"; the buttons carry the chrome's 6 px radius where the branch's `/home` grammar says "no radius" (`apps/studio/src/components/home/grammar.css` line 8).
- **Inspiration 8.** LoveFrom's method is translated, not copied: one made object per band, built once and then still (`hero-intro.png`, LoveFrom rule 2); the typed subtitle behind a caret with LoveFrom's measured blink of 400 off and 510 on (`research-lovefrom.md` 4a); the photograph developing like the book's Polaroid but by tone mix (rule 13 and MOTION.md "Texture"); "Made in Turboslide. Set in Inter." signing the last slide (rule 17); a print still (rule 18); one subtitle per visit (rule 4). OpenAI's lesson of a working product in the first screen (`research-openai.md` rule 1) is there as the editable h1. OpenAI's big type and its staged demonstrations are not taken, which is why the first screen is quiet.
- **Features 6.** Five working demonstrations, all honest, in one deck the visitor carries from band to band, and the closing show replays the visitor's own edits (`judge-2/a-show-try.png`: "Onboarding plan for Initech", "3 / 7", notes naming Initech). That continuity is the strongest argument any direction makes. The score is held down by the order: the two features a seller cannot get from Google Slides arrive after two screens of parity, the agent run is a button pressed three times with hand written JSON (direction-a.md risk 4), export is a figure in a table, and the brand kit is absent.
- **Brand 9.** Inter only, paper and ink, the blue only on live selection, caret, guide and focus; ruled rows with Heroicons solid in key cells (`Turboslide today`); no eyebrows, loops, em dashes or exclamation marks; 345 words, the only page under the 350 of `decks.home.copy-rules`; reduced motion has zero animations. Small debts: the 6 px button radius above; the first paint waits up to 800 ms for Inter (a LoveFrom habit, risk 6); the lighthouse plate's sentence is GT's deck copy, not Turboslide's (risk 10).
- **Buildable 8.** 87 KB brotli in total with no picture files, 15.3 KB gzip of page script, no shader and no field engine, so the `ShaderMount` test stays; about 3 days of wall time across four lanes (direction-a.md section 8). The risks are the replica editor's drift from the product's selection grammar and recording the agent run at build, both bounded.

## 6. What to graft into A, in order

1. **Put the differentiator in the first scroll.** Move "Agents run the same actions" to band 2, directly under the hero, and Tailor to band 3; the lighthouse band follows. A's own principle (one object per band) is unchanged; only the order changes.
2. **B's gesture log, on A's lighthouse slide.** Every drag, resize and turn on the mood slide prints the command an agent would send for it (`slide to-canvas`, `block set <slide>#<block> /pos '{...}'`, `block rotate --to`), on the `#101010` panel beside the slide. This joins "Everything on a slide moves" and "Agents run the same actions" in one object and is the best proof in the round that the menus and the agents share one table.
3. **B's terminal input, in A's agent band.** Keep A's Run for the three recorded steps, and accept the same command forms typed by the visitor plus `help`, with C's sentence for anything else ("This page runs N of the commands. The CLI runs all 193."). The outputs are recorded from the CLI at build, as all three notes require.
4. **C's export seam, as a band of its own.** The lighthouse slide drawn twice under one seam, "One picture, 1600 by 900" against text boxes that stay text, with the 0.003 percent row from `facts.json` beside it. A has no export demonstration; B's self comparison must not be the one taken.
5. **C's agent console tabs.** CLI, MCP and HTTP showing the same write as `slide.new`, `tools/call` with the real tool name and `POST /api/actions/...`, from `mcp-tools.json` and `openapi.json`.
6. **B's feature table's menu paths, merged into "Turboslide today".** A's rows carry counts; B's carry where each feature lives (Tools > Tailor for a customer, Slide > Change theme, File > Version history, Insert > Animated pattern). One ruled table with both.
7. **C's brand kit, if a band is free.** Three kits that restyle every slide of the page's deck at once (`research-product.md` ranks it fourth). It is optional; it should not add a toolbar to the hero.
8. **C's Print This Deck**, replacing A's hero only print still, so printing the page prints the visitor's deck.
9. Keep from A: the closing band with both buttons, the show of the visitor's own deck, zero loops, the 350 word ceiling.

## 7. What not to carry into the build

- B's people band until production's realtime rows read green, and B's sentence "The PowerPoint file matches the screen pixel for pixel".
- B's chapter field strips (length and decoration without a feature).
- C's menus lead "Every row below changes the deck on this page" while any row only describes; if the menus come in at all, list only the rows the page runs.
- C's amber error colour; errors on the panel stay in the panel's ink.
- Any hand written JSON on a terminal panel: every answer is recorded from the CLI against the fixture deck at build.
- For A: the Northwind deck the visitor tailors is not the deck Open the Example Deck opens (direction-a.md risk 12). The fixture deck question of `research-product.md` section 8 has to be answered before the build, or the button's sentence has to say which deck it opens.
