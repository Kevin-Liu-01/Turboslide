## 1. Kevin's directive and the rule it sets

Kevin, verbatim, with a screenshot of the title row's right cluster (the Slideshow button, a separate chevron button beside it, then Share with a lock icon): "thigns that would be great to add: bring back boxes and tables and other stuff, all our formatting, bring back everything that worked actually well and make them work a lot better, also make separator lines between our ui rows better, and make the section in my image look a lot better too (and that slideshow and dropdown should look like 2 parts of one thing". His standing words: "remember this is actually going to be used by majority sales in our org"; "make sure to actually test our slide features and make sure they work"; "focus on the features we need, that work, and that work well with every interaction tested".

The rule, which is FOCUS.md section 8's rule for bringing a feature back with the two run rule and a computable parking rule added:

1. A parked feature returns to the default view when the return audits measured it working or nearly working on production, once every one of its interactions is a row in `core-matrix.json` with a stable id, a feature and a driver, and every row passes twice on the enforce preview built from the ship's commit and once more in the last run on production after the alias moves (FOCUS.md 6.2). Two runs on one deployment with no code change between them, both passing; a row that passes in one and fails in the other is flaky and holds what it guards. One run on production suffices because the flakiness check is the two preview runs on the same commit; a production failure holds the ship like a preview failure does.
2. What a red row (failed or not driven) holds is computed from the matrix file by `parkedFeaturesOf` and `shipVerdict` (`scripts/probes/core-matrix.mjs` 220 to 237 and 260 to 275), extended this round with two fields so the document says what the file computes:
   - A parkable feature is one whose every menu row and control carries the `advanced` flag or a stub sentence, so hiding the feature is one flag change: `shapes`, `lines`, `tables`, `charts`, `diagrams`, `wordart`, `formatting`, `view` and `inbox` (the features of section 5). A red row of a parkable feature parks the feature whole for that ship, as FOCUS.md section 8 says, unless the row carries `parks`.
   - An unparkable feature is one already in the default view with no flag to hide it: `surface` (as today, `UNPARKABLE_FEATURE`), `chrome` (the title row's split button, separators and right cluster; nothing hides them), and every core feature of FOCUS.md section 2 (`decks`, `slides`, `text`, `images`, `arrange`, `present`, `share`, `comments`, `versions`, `export`, `help`). `UNPARKABLE_FEATURE` becomes the list `UNPARKABLE_FEATURES`; `readParkedList` refuses every one of them; a red row of an unparkable feature blocks the ship, which is what `shipVerdict` already does for a red id whose feature is not in `parkedFeatures` (`core-matrix.mjs` 262 to 273). This names what FOCUS.md 1.4 left uncomputable: "parked" had no meaning for a core feature.
   - A row may carry `parks: ["<data-control id>", ...]`, the menu rows or controls that row alone guards. A red row with `parks` keeps those ids behind the `advanced` flag (or their stub sentence) for that ship and neither parks its feature nor blocks the ship; the committed parked list `ship-<commit>.json` gains `parkedRows: [{ "id", "parks" }]` beside `parkedFeatures`, rendered from the run and never typed. So a failed `export.jpg.current-slide` keeps `file.download.jpg` parked and the PDF and the PowerPoint downloads stay in the default view; a failed `inbox.*` row keeps the inbox plate parked and Share stays; a failed `chrome.split.enter-chevron` blocks the ship and parks nothing, because the split button cannot leave the default view.
3. A feature the audits measured as not working stays parked and is named in section 8 with the mechanism seen.
4. "Make them work a lot better" means the fixes named in section 2 land in the same round as the flag change, so a returning row is measured after the fix, never before it. A fix is owned by one area (section 6) and its mechanism is the one an audit or the drive saw and named with the file and line; a fix whose mechanism no audit saw is not written, and its rows stay red with the reason "mechanism not found".
5. A core defect the audits found in the default view (the cover title's formatting, the two step undo of a typed field, the split button's Enter and Tab, the deck's truncated name) is fixed in this round under the same rule: its row joins the matrix and must pass; its feature is unparkable, so a red row blocks the ship.
6. The GT brand grammar holds for the chrome: Inter, black and white, hairlines, sentence case, no decoration for its own sake (`tokens.css` `:root`, the one corner `--pt-radius` and the solid call to action's 8 px). Every colour a rule of section 4 names is a token in `tokens.css` (`TitleRow.css` line 7, "colors are tokens only"); this document adds the tokens the rules need, in both appearances, with their computed composites.
7. This rule binds the chrome, not the deck: a formatting row a seller uses on the slide (a shadow, an alt text) is not parked as decoration by rule 6; where this document parks a working deck row it is Kevin's decision, put to him in section 9 with a default.

## 7. The README section "What works today"

New feature paragraphs in `what-works-data.mjs`, each shown only while every row of its feature passes:

> **Tables.** Insert > Table places a table from a grid of columns and rows. Double click a cell to type, Tab to move to the next cell, Tab on the last cell to add a row.
