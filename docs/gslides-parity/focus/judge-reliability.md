# Judge: reliability

Judgement of `docs/FOCUS.md` (the focus round specification, 2026-09-15) against the eight production audits under `docs/gslides-parity/focus/`, the matrix file `core-matrix.json`, the probe `scripts/probes/editor-walk-probe.mjs`, `playwright.config.ts`, the specs under `apps/studio/e2e/`, and the sources at the production commit read with `git show ec61c6b:<path>`. Lens: engineering reliability. The questions asked of the document: is every core interaction in the matrix with a driver that can run against production; can the acceptance be gamed; is the Advanced tools switch one mechanism; do the fixes name mechanisms the audits saw; does the plan leave a severity 3 core row unfixed.

This judge ran no Playwright, touched no source file and ran no git write command. Every claim below names the file or the audit row that shows it.

## Verdict

Revise.

## What checks out

- The rendered table of section 6.4 matches `core-matrix.json`: 353 rows, the same ids in the same order, and no status differs between the table and the file.
- The counts of section 6.3 are the file's: 274 works, 40 broken, 21 flaky, 18 not driven; 12 rows at severity 3, 46 at severity 2, 21 carrying severity 1 (17 not green and 4 works rows that carry a severity 1 defect); the 18 not driven rows name a reason in their evidence cell.
- The mechanism citations of section 5 that this judge checked read as stated at `ec61c6b`: `apps/studio/src/server/authorize.ts` lines 178 to 184 and 228 to 236 return `ok: true` with the role `editor` on a denial in shadow mode; `packages/viewer/src/Editor.tsx` 1079 to 1082 stamp every `call` with `revisionRef.current`; `packages/schema/src/actions.ts` `block.align` snaps the shared edge unless `snap` is false; `packages/chrome/src/editor-shell.ts` `menuActionPlan` plans `slide.deleteSlide` with `slideId: facts.slideId` while `slide.duplicateSlide` and `slide.skipSlide` use `slideIds`; `packages/chrome/src/menus/model.ts` 1217 to 1237 carry the three named shape rows under a submenu whose effect is `shapeGrid('shapes')`.
- The probe citations of section 6.1 hold: the flags at lines 52 to 66, `record` and `step` at 79 to 107, `skip` at 108, the `finally` block from line 3164 with File > Move to trash, Delete forever and the 404 poll.
- The copy rules hold throughout: the document reports what the audits saw, and a step nobody drove is written as not driven.

## Rejections

1. Section 6.2 counts "the driven core rows" and section 6.1 makes `probe --core` exit 1 only "when any tagged step fails", so a core id with no step is recorded as not driven with the reason "no step" and the run still passes; the matrix has no `feature` field (every row in `core-matrix.json` carries only `id`, `interaction`, `driver`, `today`, `evidence` and `severity`), so rule 4 of section 1, "a core feature with a not driven row is parked for that ship", cannot be computed by the run and rests on the ship note's author.
2. Section 6.2 makes a row green "only when it passed on its first try in that run", but nothing bounds the number of runs or requires every run to be listed, and the flakiness the audits saw is between decks and runs, not between tries: `audit-images` row 6 passed on decks `qbf5` and `adfi` and broke on `3fma`; `audit-present` row 31 delivered in 2.4 s in run 2 and lost three edits in run 3; `audit-decks` row 37 failed three times on one card and passed on a fresh one; so a red row can be rerun on a fresh deck until it passes and that run attached as one of "both JSON tables".
3. Section 6.1 says "only tagged steps run" in `--core` mode, but the walk's steps depend on earlier ones (an object is inserted before its handles are dragged, the deck exists before File > Move to trash), and the section does not say how a failed untagged setup step is recorded against the tagged rows that depend on it; `audit-arrange` section 1 shows the cascade this produces (run 3's rows after the paste row failed because the stage held another slide, and every one had to be re-driven on a fresh deck).
4. Section 3.1 says `isPresent` is "the one place this is decided" and that the toolbar and "the palette's menu rows all already read or will read" it, but at `ec61c6b` `ToolbarHead.tsx` line 259 maps `TOOLBAR_HEAD` with no read of `when`, `ToolbarTail.tsx` line 163 draws `tailFor(kind)` with no filter (only `TOOLBAR_TAIL_END` at line 796 is filtered by `evaluate(control.when, ...)`), `packages/chrome/src/menus/finder.ts` lines 35 and 64 build Search the menus from `allItems()` filtered on `status === 'omit'` and never call `isPresent`, `BottomBar.tsx` line 38 draws the Grid view toggle from its own `ToolButton` outside the model, and the chord dispatcher that would leave a parked row's key unbound is not identified, so at least five surfaces need their own reader and the section names none of the changes.
5. Section 3.1 says the Later stubs "hide with the parked set too" but names no mechanism, and a rule on `status === 'later'` beside the `advanced` flag is a second predicate unless the document says every stub carries `advanced: true`.
6. Section 5 rank 1 and section 9 question 1 leave the two severity 3 rows `share.stranger-cannot-edit` and `share.view-link-cannot-edit` (`audit-present` rows 26 and 29) without a fix in the plan: the decision is handed to Kevin, and the alternative offered, a Share dialog that says every link can edit, leaves both rows red, so either the acceptance of section 6.2 cannot pass on production or rule 4 parks sharing, which section 2.7 lists as core.
7. Section 5 rank 3 names a hypothesis and not a mechanism for `slides.delete.canvas-focus-undo` and `slides.delete.undo-redo-saved` (severity 3; `audit-slides` rows 93, 95 and 96; section 2.2 item 1 of that audit says "that is a hypothesis"), and names no reproduction step, fix or fallback, so two severity 3 core rows have no path to green.
8. Section 5 rank 4 names no mechanism and no fix for `arrange.keys.backspace-empty-selection` (severity 3; `audit-arrange` row 48 recorded the focus on `div.ts-stagewrap.ts-sheet` and on `body`, and a console 400 on the last slide), and the document does not say which key handler removes the slide or what it will do instead.
9. Section 6.4 marks `shapes.move`, `shapes.resize.eight-handles`, `shapes.rotate`, `shapes.duplicate-delete-undo-redo`, `lines.insert.line-drag`, `lines.end-handle` and `surface.menus.open-close-escape` as "works" on the evidence of the hotfix 4 production walk, but that walk ran at 2026-09-15T10:15Z against production serving `e2e6307` (`hotfix-4.md` section 3.8), `ec61c6b` changed `packages/store/src/blob-store.ts`, `packages/store/src/comments-store.ts`, `packages/store/src/migrate.ts` and `apps/studio/src/server/bundle-core.ts` after it (`git diff --stat e2e6307 ec61c6b`), and the shapes audit recorded the same interactions as not driven on `ec61c6b` (`audit-shapes` rows 36 to 39, 43 and 45), so the column "Today on production" cannot read "works" for them.

Section 6.4 marks `collab.presence-chips` and `collab.rename-reaches-second-browser` as "works" while their interaction text names a check the audit saw fail (`audit-present` row 34: four chips for two other tabs, and chips of closed tabs stay; row 46: the second browser's tab title kept the old name), and a works row that carries a severity contradicts the document's own definition of works.
11. Section 2 lists core rows and gestures with no matrix row, so "every core interaction is a row" does not hold: the card menu's Download (`audit-decks` row 41), Copy link on the Present link row (`audit-present` row 21, which section 7 also claims), `file.makeCopy.entire` from the editor (no audit drove it), every object right click menu (`textBlock`, `textSelection`, `image`, `shape`, `line`) and the `emptyCanvas` target (sections 2.3 to 2.6; the matrix's only right click rows are the five `slides.*.context` rows on a filmstrip card), `slide.moveSlide.up`, `.down` and `.toBeginning` with Cmd+Shift+Up and Cmd+Shift+Down on a card, `view.showSpeakerNotes`, the View > Zoom > 50%, 100% and 200% rows, `format.text.size.decrease`, `format.spacing.single` and `.1_15`, the menu rows `format.alignIndent.center`, `.right`, `.increaseIndent` and `.decreaseIndent`, `format.image.imageOptions` as a menu row, `file.share.withOthers`, `toolbar.select`, `toolbar.textBox`, `toolbar.insertLink`, the toolbar and Insert menu routes to a comment on a working anchor, the background dialog's hex field (section 2.4 keeps it; no audit drove it), and a comment reaching the second browser (`audit-present` row 40, not driven).

## Additions

1. A `feature` field on every row of `core-matrix.json` naming the section 2 feature it belongs to, so the rule "a core feature with a not driven or red row is parked for this ship" is computed from the file by the run and the ship note's parked list is rendered, not typed.
2. The run exits 1 when any core id is not driven unless its feature is listed in a committed parked list for that ship; "no step" is a failure of the run, not a not driven row.
3. A run ledger in the ship note: every run started against the preview and against production, with its start time, deck id, counts and JSON path; a row is green only when it is green in the last run of each origin and no run of that origin on the ship's commit is left out; a rerun is allowed only after a code change or with a reason written in the ledger; `retries` stays 0 (`playwright.config.ts` line 28) and no core spec calls `test.describe.configure({ retries })`, and the report's retry count is asserted to be zero.
4. The rule for setup steps in `--core` mode: untagged steps run as setup; when one fails, every later tagged step that depends on it is recorded as not driven with the reason "setup failed: <step>" and the run exits 1.
5. A table in section 3.1 naming every surface that draws or runs a row (the menu bar and submenu parents in `Menu.tsx`, the right click menus in `ContextMenu.tsx`, the title row in `TitleRow.tsx`, `TOOLBAR_HEAD` in `ToolbarHead.tsx`, the tails and the tail end in `ToolbarTail.tsx`, Search the menus in `menus/finder.ts`, the palette's Insert group in `palette-data.ts`, the Grid view toggle in `BottomBar.tsx`, the chord dispatcher by file and line, the shortcuts dialog, the tooltip audit) with the line where each reads `isPresent` after the change, and a unit test in `menu-model.test.ts` that flips `advancedTools` and asserts every surface's visible set differs only by the rows carrying `advanced`.
6. One sentence on the Later stubs: either every stub carries `advanced: true`, or `isPresent` reads `status === 'later'` under the switch; not both.
7. A fix, not a question, for every severity 3 row: for rank 1 the decision (enforce mode with the access record, or a server enforced read only address, or sharing parked with the ship note saying so by matrix id) and the rows that prove it; for rank 3 the reproduction step (the refusing instance's document revision against the revision it acknowledged, read from the server function's answer or a header) and the fix or the fallback (the undo write rebased on the server's document before it is retried); for rank 4 the handler and the rule (Delete and Backspace remove a slide only while the filmstrip has focus); for ranks 5 and 6 the fixes the images audit names (stamp `asset.add` with the room's server revision or queue it with the other writes, show the refusal in the snackbar, create the deck before the first picture write) written as the plan with their rows.
8. Mechanisms for the severity 2 rows that carry none: rank 23 (`ToolbarHead.tsx` imports `ZOOM_LADDER`, `clampZoomPercent`, `effectiveZoomPercent` and `zoomStepFrom` from `editor-shell.ts`; the step function's input when the zoom is `fit` or a preset), rank 16 (the redo stack after an undo issued straight after a duplicate), rank 11 (autofit grow on a text box), rank 13 (the outbox replaying a `text.splice` against the text before the refusal), rank 10 (the toolbar button taking focus before the mark is applied), rank 15 (the stage owning the paste only while it holds the focus), rank 26 (the hero figure over the form).
9. Matrix rows for every gap of rejections 11 and 13, each with today's state from the audit row that saw it, or not driven with the reason.
10. The seven rows of rejection 9 become not driven on `ec61c6b` with the walk cited as the last observation, and `--core` drives them in this round.
11. Section 7 is rendered from `core-matrix.json` rows whose last production run is green, or is held until the ship; today its text claims Cmd+K links a word, upload, drop and paste land a picture, Replace image swaps the file, Share copies a present link, and shapes carry a fill, a border and text, all of which are red or not driven in the matrix.
12. Rules for `core/*.spec.ts`: no import from `node:fs` except to read a file the browser downloaded, no deck seeded, no environment variable read other than `PLAYWRIGHT_BASE_URL` and `VERCEL_OIDC_TOKEN`, every observation through the page, `window.turboslide.studio.describe()`, the network and the download, and every deck created from `/new` by the test itself.
