## Cycle 3 stream fix round

### 1. The diagnosis: the stale base is the absorbed marker, not the slide prop

C3-F8: `apps/studio/e2e/realtime.spec.ts:374` "undo in A never reverts B's later change" failed
four of four runs on the memory tier with one shape, 500 characters expected and 506 received,
`B drag` appended, and failed before its undo ran (b7.md FR3.8, runs of 02:12Z, 02:45Z and 03:02Z
on 4387). FR3.8 read the op on the wire: tab B's `VV` typed at the start travelled as one
`text.splice` at 0 removing 492 characters and inserting 500, a replacement of the whole run
against a base two remote writes old (the 492 characters both tabs converged on in the 200
keystroke test), applied to the 498 character document (`U` plus the 492 plus ` drag`), which left
the last six characters standing after the insert. FR3.8 placed the base at `Editor.tsx` line 1445,
`committedText.current = readRunText(slideNow, …)` from `slideRef.current` at the session's open.

That line is not the mechanism. `slideRef.current` is the render's `doc.slides[slideId]` and the
double click that opens the session runs long after the document's last remote change re-rendered
the Editor; nothing in the Editor holds a slide fresher than its props. The base that was two
writes old came from `InlineText.tsx`'s absorbed marker:

1. `absorbedBases` is a module level `Map` keyed by `runKey(slideId, blockId, pointer)`. A
   collaborator's change to the run being edited reaches the session through
   `TEXT_CHANGED_EVENT`; `onTextChanged` calls `noteAbsorbed(key, text)` and then `absorbRemote`,
   which puts the document's markup with the unflushed keystrokes into the editable. The next
   burst's `textBurstMutation` takes the marker (`takeAbsorbed`) as its base, so the diff is the
   local keystrokes alone (SPEC-3 3.5). That is the design, and it is right while a burst follows.
2. When the change lands after the session's last burst with nothing local unflushed, no burst
   follows: `absorbRemote` sets the editable to the remote text and schedules a burst only when
   `next.text !== remote`. The Editor's document effect runs `sessionReconcile` (verdict `resend`),
   waits `RECONCILE_RESEND_MS` and calls `writeText` with the document's text as `from` and the
   editable's text as `to`; the two are equal, and `textBurstMutation` returned on `from === to`
   before it reached `takeAbsorbed`. Escape then ends the session with the same equal pair. The
   marker stays in the Map, keyed by the run, with the document's text as of that moment.
3. The next session on that run, whenever it opens, takes the marker on its first burst. In the
   spec, tab B's session of the 200 keystroke test (`:234`) absorbed tab A's last characters after
   its own last burst and ended with the 492 character marker in place; A's ` drag` (`:312`) and
   `U` (`:374`) changed the run with no session open in B, so nothing touched the marker; B's `VV`
   in `:374` diffed `VVU…B drag` (500) against the marker (492): no common prefix (`V` against
   `A`), no common suffix (`…B` against `…drag`), remove all and insert all, exactly the bytes on
   the wire. The shape is deterministic because the spec's order is, which is why the three runs
   agreed to the byte.

The marker also fits the verifier's `:234` divergences of earlier cycles named in FR3.8 (B's text
with A's characters at other offsets): a session opened on a run whose marker an earlier session
left behind sends the whole run back at stale offsets. It does not explain the merge's `:515` (the
persisted queue's tail landing twice), which FR3.8 folded into the same reading: run 2 below
failed that row with the fix in place, and its trace shows a different mechanism, a `mutations`
array shared between the controller's typing group and the room client's pending op (request
S2-R1 in section 6, with the POST bodies).

The two `forgetAbsorbed` calls are belt and braces around the reorder: `startEdit` alone closes
the leak, because a marker left by any earlier session is dropped before the new base is read
(so a session ended by `unmount` on a slide that changed under it, whose `endEdit` reads the new
slide's id, leaves nothing the next session on the old run would take).

The undo itself was never reached by the failing assertion and is sound on this tree: the inverse
the reducer answers at A's commit (`text.splice` at 0 removing one character) is moved past every
entry that landed since by the controller's `stepMutations` (`room.transformSince` over the recent
remote entries, `transformPast` with the schema's `transformMutation`), so after B's `VV` lands at
the same offset the undo removes `U` at offset 2 and B's characters stay. The schema test below
pins that shape, and `:374` passes end to end in the ledger.

### 2. The change

- `packages/viewer/src/InlineText.tsx` `textBurstMutation`: `takeAbsorbed` runs first, before the
  `from === to` return and the slide field branch, so every burst consumes the run's marker,
  including one with nothing to send. The comment names C3-F8 and FR3.8.
- `packages/viewer/src/InlineText.tsx`: `forgetAbsorbed(key)` drops a run's marker without reading
  it; the Map's comment states the marker's life (as long as the session that noted it).
- `packages/viewer/src/InlineText.tsx` `onTextChanged`: returns when `done.current` is set. The
  session's listeners leave one tick after `finish` (the deferred teardown), and a change announced
  inside that tick used to note a marker for a session that had ended.
- `packages/viewer/src/Editor.tsx` `startEdit`: `forgetAbsorbed(runKey(slideNow.id, run.blockId,
run.pointer))` before `committedText.current` is read from the slide. A new session's base is the
  document's text and nothing an earlier session absorbed.
- `packages/viewer/src/Editor.tsx` `endEdit`: after the final `writeText`,
  `forgetAbsorbed(runKey(slideIdRef.current, current.blockId, current.pointer))`. The final write
  consumes any marker the session held (the reorder above); one it did not reach (no slide to write
  against) dies with the session.

No change to `keys.ts`, to `reduce.ts` or to any file outside the list. The click model A1 is
untouched: the entry paths (`clickEntry`, `entryCaret`, the pending insert) and the exit paths keep
their behaviour; the two calls sit on either side of the session's base.

### 6. Requests (Cycle 3 stream fix round)

- **S2-R1** (S1 the client while disconnected, with the integrator; `packages/realtime/client/room-client.ts` `apply` and `apps/studio/src/editor/controller.tsx` `commitAs`; `realtime.spec.ts:515` "a closed tab's pending queue is offered on the next open and Apply lands it", severity 3, the row the integrator recorded at the cycle 3 merge and FR3.8 attributed to the text session's base): the mechanism is a shared array, not the session. `commitAs` passes one `mutations` array to `room.apply(mutations, label)`, which stores the reference in the pending op (`pending.push({ …, mutations, … })`), and to `history.push({ mutations, … })`, which stores the same reference; a burst that folds into the typing group inside `TEXT_UNDO_GROUP_MS` runs `group.mutations.push(...mutations)` and grows the array the first pending op still carries. Online the first POST is serialized before the next burst, so nothing shows; offline, or on any resend, the first op travels with every later burst's splice appended and the later ops travel as their own entries. Read from run 2's trace (`<scratchpad>/s2-playwright-run2/realtime-a-closed-tab’s-pe-32a73-…/trace.zip`, the ops POST bodies): the offline POST at 07:31:19.690Z carried `[splice@513 "1"]`; the resend at 07:31:19.980Z carried `[splice@513 "1", splice@514 "2"]` and `[splice@514 "2"]`; the resend at 07:31:20.185Z carried `[splice@513 "1", splice@514 "2", splice@515 "3"]`, `[splice@514 "2"]` and `[splice@515 "3"]`; the new tab's Apply POST at 07:31:23.053Z carried the same three entries with the new client id and the server admitted them at seq 2026, 2027 and 2028, which is `late12323` in tab B. The same sharing reaches the blob tier's resend of a lost POST (`settleLostPost`, C3-F1), a doubled edit in another person's tab. The fix is a copy at either boundary: `room.apply` storing `[...mutations]`, or `commitAs` handing the history its own copy (`history.push({ mutations: [...mutations], … })` and the group appending to that copy). A unit test in `room-client.test.ts` pins it: apply two ops on one run, grow the first array after the apply, flush, the POST body carries each op's own splice once. Not this lane's files; nothing of the text session is involved, and the row stays red on this tree until it lands.
