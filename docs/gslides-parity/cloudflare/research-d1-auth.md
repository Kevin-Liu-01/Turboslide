## 0. The five answers

1. **better-auth against D1 from a Vercel function.** There is no supported path. The D1 binding exists only inside a Worker: "To interact with your D1 database from your Worker, you need to access it through the environment bindings provided to the Worker (env)" (https://developers.cloudflare.com/d1/worker-api/d1-database/). better-auth's own documentation says "Cloudflare D1 can only be queried through a Cloudflare Worker, so the CLI cannot access it directly" (`docs/content/docs/concepts/database.mdx` line 68 of `better-auth/better-auth` at `main`, read raw from GitHub). The installed adapter `@better-auth/kysely-adapter` 1.7.4 ships a D1 dialect, and it wraps the binding's `prepare().bind().all()` (`dist/d1-sqlite-dialect-D4qp4-wW.mjs` 66); it is not an HTTP client. The D1 HTTP API exists (`POST /accounts/{account_id}/d1/database/{database_id}/query`, token permission "D1 Read" or "D1 Write", https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/query/), Cloudflare describes it as the control plane ("REST API primarily interacts with the control plane, and allows you to create/manage your D1 database", https://developers.cloudflare.com/d1/best-practices/query-d1/), no Kysely dialect over it exists on npm (2.3), and it sits under the global API limit of "1,200 requests per five minute period per user" (https://developers.cloudflare.com/fundamentals/api/reference/limits/), which is 4 requests a second across every instance. No page states a per query latency; the facts that exist are in 1.3 and they put one statement at tens to hundreds of milliseconds. With T2 4.1's 4 to 7 statements per authenticated request, one HTTP call per statement is a ceiling near one authenticated request a second and an added 4 to 7 round trips per request. The HTTP API is a migration, backup and admin path. The auth routes and the identity reads run on a Worker, or the account database is not D1.

2. **A Worker on `workers.dev` and the cookie on `www.turboslide.com`.** No. A cookie without `Domain` "is returned only to the host that sent it" and `Domain` "cannot be a public suffix" (https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie); `workers.dev` is line 12707 of the Public Suffix List (https://publicsuffix.org/list/public_suffix_list.dat, 334,832 bytes on 2026-10-01). better-auth's `crossSubDomainCookies` shares across subdomains of one root ("Setting it to your root domain (e.g. `example.com`) makes the cookie accessible across all subdomains", https://www.better-auth.com/docs/concepts/cookies), which `workers.dev` and `turboslide.com` do not share. A custom hostname on the Worker needs "An active Cloudflare zone" (https://developers.cloudflare.com/workers/configuration/routing/custom-domains/), that is `turboslide.com`'s DNS on Cloudflare, and the zone is at the registrar today (`dig NS turboslide.com +short` on 2026-10-01: `dns1.registrar-servers.com`, `dns2.registrar-servers.com`; `www` is a CNAME to `5661780b11730745.vercel-dns-016.com`). Cloudflare for SaaS gives "100" custom hostnames on the Free plan and "$0.10" each above that (https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/plans/) but still needs a Cloudflare zone on the SaaS side and a CNAME at the registrar. Every hostname route is a DNS change, and no agent moves DNS (`docs/hosting.md` HEAD 802 to 804). The one layout with no DNS change is the app proxying `/api/auth/*` to the Worker so the cookie is set first party on `www`: the installed h3 2.0.1-rc.31 relays upstream `Set-Cookie` headers with optional domain and path rewriting (`dist/proxy.mjs` 185 to 199) and forwards the request's cookies (209 to 227). Section 3 spells out what that layout costs; the short form is that the identity runtime, not only the sign in, ends up on the Worker.

3. **The free plan against Turboslide's numbers.** Sign ins are no load: 300 a month is 10 a day, 7 to 9 rows read and 5 to 8 rows written each on a first sign in (T2 4.2), under 100 rows read and 80 rows written a day against "5 million / day" read and "100,000 / day" written (https://developers.cloudflare.com/d1/platform/pricing/). The per request reads decide: 4 selects per authenticated request while the 5 minute cache cookie is fresh, 5 past it (T2 4.1), 1,600 to 2,200 `requestIdentity` calls per signed in editor hour, so 6,400 to 8,800 rows read an hour when each select hits an index, and the free 5 million a day is 570 to 780 signed in editor hours a day. That holds on a Worker with the binding. Over HTTP from Vercel the 1,200 per 5 minutes is the limit instead: 6,400 to 8,800 calls an hour is 1.8 to 2.4 a second per signed in editor, so two concurrent signed in editors reach the cap. Section 4 has the table, including the Workers Free request cap (100,000 a day, 45 to 62 signed in editor hours a day if the Vercel function asks the Worker once per request) and the KV line (1,000 writes a day) that matters only if sessions and the limiter move to KV.

4. **What wrangler needs.** A Cloudflare account, Node, and one of `wrangler login` (OAuth in a browser, `--browser`, `--callback-host`, `--callback-port` flags) or `CLOUDFLARE_API_TOKEN` with `CLOUDFLARE_ACCOUNT_ID` ("can be used for authentication for situations like CI/CD, and other automation", https://developers.cloudflare.com/workers/wrangler/system-environment-variables/). The token comes from the dashboard ("go to My Profile > API Tokens for user tokens. For Account Tokens, go to Manage Account > API Tokens. Select Create Token", https://developers.cloudflare.com/fundamentals/api/get-started/create-token/) with the account permissions "D1 Read" and "D1 Edit" (https://developers.cloudflare.com/fundamentals/api/reference/permissions/). Then `npx wrangler d1 create <name> --location=enam`, the `d1_databases` block, and `wrangler d1 migrations create | list | apply --remote` or `d1 execute --remote --file`. Section 5 has the commands and the one account fact: Cloudflare's "Sign in with Google" creates a new account only when no account exists for that address, and "A Cloudflare account has already been created with your Google account's email: This option is unavailable at this time" (https://developers.cloudflare.com/fundamentals/user-profiles/login/). D1 is on the Free plan and nothing read today forces Workers Paid for this database.

5. **A Postgres compatible free database on Cloudflare reachable from Vercel.** None. Hyperdrive is on the Free plan ("Hyperdrive is included in both the Free and Paid Workers plans", https://developers.cloudflare.com/hyperdrive/platform/pricing/) but is "a service that accelerates queries you make to existing databases" (https://developers.cloudflare.com/hyperdrive/), brings no database, and every access path on its pages is the Worker binding `env.HYPERDRIVE.connectionString` (https://developers.cloudflare.com/hyperdrive/configuration/connect-to-postgres/). PlanetScale Postgres can be created from the Cloudflare dashboard since 2026-06-18 and "PlanetScale usage appears on your Cloudflare invoice each billing period as a dollar total at PlanetScale's standard pricing" (https://developers.cloudflare.com/changelog/post/2026-06-18-planetscale-databases-cloudflare-billing/); PlanetScale's pricing page shows no free plan, the cheapest Postgres being a single node PS-5 at $15 a month with high availability or $5 a month without (https://planetscale.com/pricing). D1 is SQLite, and the tree already runs better-auth with `type: 'sqlite'` on a checkout (`better-auth.ts` 171), so D1 is the fit on Cloudflare and Postgres is not. The free Postgres in the research notes is Neon's own free plan (`research-hosting.md` 29), with or without the Marketplace; that is outside this note.

### 1.2 The binding API

`prepare()` "Prepares a query statement to be later executed"; `batch()` "Sends multiple SQL statements inside a single call to the database", which "reduces latency from network round trips to D1" and "guarantees that each statement in the list will execute and commit, sequentially, non-concurrently"; `exec()` "Executes one or more queries directly without prepared statements or parameter bindings"; `withSession()` "Starts a D1 session which maintains sequential consistency among queries" with `first-primary`, `first-unconstrained` (the default) and a bookmark (https://developers.cloudflare.com/d1/worker-api/d1-database/). The result's `meta` carries `duration` ("the duration of the SQL query execution only, in milliseconds"), `rows_read`, `rows_written`, `served_by_region`, `served_by_primary`, `changes`, `last_row_id`, `size_after` and `timings.sql_duration_ms` (https://developers.cloudflare.com/d1/worker-api/return-object/). Read replication: replicas in "ENAM, WNAM, WEUR, EEUR, APAC, OC", "sequential consistency", "you don't pay extra storage or compute costs for read replicas" (https://developers.cloudflare.com/d1/best-practices/read-replication/); whether it is on the Free plan the page does not say. The binding got "up to a 60% end-to-end latency improvement due to the removal of redundant network round trips" on 2025-01-07 (https://developers.cloudflare.com/changelog/post/2025-01-07-d1-faster-query/); no absolute number is published.

### 1.3 The HTTP API

- Endpoint and shape: `POST /accounts/{account_id}/d1/database/{database_id}/query`, body `sql` (a string, "supporting multiple statements joined by semicolons") and optional `params` (an array of strings), answer `result[]` of `{ success, results, meta }` with the same `meta` fields as the binding; permission "D1 Read" or "D1 Write" (https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/query/). The page says nothing about latency, rate limits or production use.
- Position: "REST API primarily interacts with the control plane, and allows you to create/manage your D1 database" (https://developers.cloudflare.com/d1/best-practices/query-d1/). The D1 FAQ answers nothing about external access (https://developers.cloudflare.com/d1/reference/faq/).
- Rate limit: "The global rate limit for the Cloudflare API is 1,200 requests per five minute period per user", then "HTTP 429 - Too Many Requests" for five minutes; the exceptions named are Cache Purge, GraphQL, Rulesets, Lists and Gateway Lists, not D1 (https://developers.cloudflare.com/fundamentals/api/reference/limits/). This note treats the limit as applying to `/query`, as T2 open 2 does.
- Latency, what exists: Cloudflare's changelog of 2025-05-29, "50-500ms Faster D1 REST API Requests", moved "D1 authentication at the closest Cloudflare network data center that received the request" and says the gain is "50-500 ms depending on request location and database location", "the REST API" only (https://developers.cloudflare.com/changelog/post/2025-05-30-d1-rest-api-latency/). The `d1-api` package README (0.1.0, published 2023-11-10, registry record) says "The D1 HTTP API has significate overhead which results in about half a second of latency on every query. This is intended and is not planned to be fixed by Cloudflare"; that sentence predates the 2025 change. Floor measured here: five unauthenticated `POST` requests to the query path from this Mac at 19:53 UTC answered error 7003 in 50, 53, 64, 70 and 116 ms total, TLS complete at 26 to 39 ms, from `2606:4700:300a::6813:c11d`; the edge answered without reaching a database, so a real statement from Vercel's `iad1` to a D1 primary adds at least the edge to primary leg. No measurement from a Vercel function exists in the tree or the notes (`research-hosting.md` 55 for Redis; T2 open 3 for D1).
- Clients outside Workers, found on the registry on 2026-10-01 with the searches `kysely d1`, `d1 http`, `d1 rest api client`, `cloudflare d1 node`: `d1-api` 0.1.0 (2023-11-10), `cloudflare-d1-http-knex` 1.3.2 (2025-01-21), `dsh-d1` 0.1.0 (2026-09-03, a tooling harness), `@cretezy/cloudflare-d1-backup` 0.2.1 (2023-12-21). No Kysely dialect over the HTTP API appeared. Drizzle Kit speaks HTTP for schema work only: "Drizzle Kit lets you run `migrate`, `push`, `introspect` and `studio` commands using Cloudflare D1 HTTP API" with `driver: 'd1-http'` and `accountId`, `databaseId`, `token` (https://orm.drizzle.team/docs/guides/d1-http-with-drizzle-kit); the runtime driver on its D1 page is the binding (https://orm.drizzle.team/docs/connect-cloudflare-d1). Drizzle's proxy driver takes a callback `(sql, params, method)` returning `{ rows }` (https://orm.drizzle.team/docs/connect-drizzle-proxy, the Postgres tab was what rendered), so a Drizzle over HTTP path can be written; the tree uses Kysely, not Drizzle (`db.ts` 13).

### 1.4 Placement

A location hint "is an optional parameter you can provide to indicate your desired geographical location for your primary database instance": `wnam`, `enam`, `weur`, `eeur`, `apac`, `oc`; set with `wrangler d1 create new-database --location=weur` and not changed afterwards; without a hint "D1 will automatically create your primary database instance in a location close to where you issued the request to create a database"; "D1 automatically creates a read replica in every available region" (https://developers.cloudflare.com/d1/configuration/data-location/). The app's functions run in `iad1` (`research-hosting.md` 79), so `enam` is the hint if a Vercel function ever reaches the database; a Worker reads from the nearest replica either way.

## 2. How better-auth reaches D1

### 2.1 The installed adapter already has a D1 dialect

`@better-auth/kysely-adapter` 1.7.4 is installed beside `better-auth` 1.7.4 (`node_modules/.pnpm/@better-auth+kysely-adapter@1.7.4_*/`; `pnpm-workspace.yaml` 51 pins `better-auth: 1.7.4`, 57 `kysely: 0.29.5`). Its `createKyselyAdapter` classifies the `database` option (`dist/index.mjs` 24 to 96): a `{ db, type }` object is taken as is (32 to 37), a `{ dialect, type }` object is wrapped in a Kysely (38 to 43), and a raw object with `batch`, `exec` and `prepare` is recognised as a D1 binding (21, 84 to 88) and given `D1SqliteDialect` plus an index introspector, with `transaction = false`. The dialect (`dist/d1-sqlite-dialect-D4qp4-wW.mjs`) runs every statement as `database.prepare(sql).bind(...parameters).all()` (66), maps `meta.changes` and `meta.last_row_id` (67 to 69), refuses transactions ("D1 does not support interactive transactions. Use the D1 batch() API instead.", 48 to 56) and refuses streaming (75). It is not exported (`index.mjs` 698 exports `createKyselyAdapter`, `getKyselyDatabaseType`, `kyselyAdapter` and schema helpers only). The documentation's example is `database: env.DB` with `import { env } from "cloudflare:workers"` and migrations through an endpoint calling `getMigrations` (`concepts/database.mdx` 67 to 100); the callout says "`getMigrations` only works with the built-in Kysely adapter (SQLite/D1, PostgreSQL, MySQL, MSSQL)" (63). The tree runs `getMigrations` at boot already (`better-auth.ts` HEAD 17; T2 1.1), so the CLI limitation does not bite. Workers need `nodejs_compat` because "Better Auth uses `AsyncLocalStorage`" (`integrations/hono.mdx` 61); compatibility dates of 2026-08-04 or later enable it by default (T2 section 6).

The tree passes `database: { db: deps.db.db, type: ... }` (`better-auth.ts` 171), a Kysely it built itself over `pg` or `node:sqlite` (`db.ts` 84, 88). On a Worker that Kysely needs a D1 dialect of its own, because the adapter's dialect is private and because Turboslide's five tables (`ts_alias`, `ts_api_key`, `ts_profile`, `ts_mail`, `ts_quota`; `schema.ts` 137 to 143) are created and read through that same Kysely (`schema.ts` 148 to 210; `db.ts` 93 to 94). The choices: `kysely-d1` 0.4.0 (published 2025-04-19, peer `kysely: *`, 125,919 downloads in the week 2026-09-23 to 2026-09-29, README constructs `new D1Dialect({ database: env.DB })`; registry record and https://github.com/aidenwallis/kysely-d1), `@8x/kysely-d1` 1.1.0 (2026-08-21, "insertId support and typed atomic batches"), or a dialect in the shape of the tree's own `sqlite-dialect.ts` (one connection, the statement kind read from the SQL, booleans and dates bound by hand, 1 to 8, 23 to 39), which is the shape the adapter's private dialect also has. better-auth's dialects page lists "Cloudflare D1" among the community dialects and says "Any dialect supported by Kysely can be utilized with Better Auth" (https://www.better-auth.com/docs/adapters/other-relational-databases). A third party article shows the combined form in use, `{ db: new Kysely({ dialect: new D1Dialect({ database: ctx.cloudflare.env.DB }), plugins: [new CamelCasePlugin()] }), type: "sqlite" }` (https://dev.to/atman33/setup-better-auth-with-react-router-cloudflare-d1-2ad4, 2025-07-10); that is data about one person's setup, not a vendor statement. What D1's `bind()` accepts for booleans and dates was not read today (section 9); the tree's `bindable` mapping (`sqlite-dialect.ts` 29 to 39) would be kept in front of any D1 dialect until it is.

### 2.2 Transactions, which closes T2 open 5

On the tree's `{ db, type }` form the adapter's `transaction` is `db.transaction`, which the tree does not pass (`index.mjs` 36; `better-auth.ts` 171), so the adapter option at 677 to 685 resolves to `false` and no `db.transaction()` is opened. The three `db.transaction().execute(...)` sites in the adapter are inside `config?.type === "mysql"` branches (338 under the MySQL insert fallback; 618 to 624; 643 to 653). On `type: 'sqlite'` the library never opens a transaction, which is what D1 requires. Nothing in Turboslide's own auth code opens one either (T2 open 5, the grep).

### 2.3 Over HTTP from a Node process

Possible, unsupported and slow. The pieces that exist: the endpoint of 1.3; an API token in a Vercel environment variable; a Kysely dialect of about the size of `sqlite-dialect.ts` (115 lines) whose `executeQuery` posts `{ sql, params }` and maps `results` and `meta`. Kysely's driver interface executes one compiled statement at a time, so every select is one HTTPS request, and the four reads of an authenticated request (T2 4.1) are four requests. The budget consequence is in section 4. No package does this for Kysely; `cloudflare-d1-http-knex` does it for knex (1.3.2, 2025-01-21), and Drizzle's proxy driver would do it for Drizzle (1.3).

### 2.4 Secondary storage on a Worker

better-auth's secondary storage holds "session data, verification records, rate limiting counters, and other short-lived auth data" (T2 2.2, https://www.better-auth.com/docs/concepts/database). The tree's adapter is Redis shaped (`secondary-storage.ts` 9 to 16, six ioredis methods). On a Worker the candidates are Workers KV, with Free "100,000 / day" reads, "1,000 / day" writes and "1 per second" writes to one key (https://developers.cloudflare.com/kv/platform/pricing/, https://developers.cloudflare.com/kv/platform/limits/), or D1 itself with no secondary storage, in which case the session row is in the `session` table and `findSession` is one indexed select (T2 2.3). `better-auth-cloudflare` 0.3.1 (2026-07-23) packages the KV route: "Optionally use Cloudflare KV for secondary storage (e.g., session caching)" and "Support for D1 (SQLite), Postgres, and MySQL databases via Drizzle ORM, or native D1 without Drizzle", for "any framework that runs on Cloudflare Workers" (https://github.com/zpg6/better-auth-cloudflare). The tree does not need it; the adapter of 2.1 is in the installed library.

Why A'' becomes C: every authenticated request to the Vercel function runs `requestIdentity` (13 call sites, T2 4.1), which reads `user`, `ts_profile` and `ts_alias` and, past the cookie cache, the session (T2 4.1). Those reads need the account database. On a Worker placement the Vercel function has three ways to them: the D1 HTTP API (layout B's cap), a request to the Worker (layout C, one hop, inside the Workers Free 100,000 a day until 45 to 62 signed in editor hours a day), or a per instance cache of the account facts keyed on the session token for the cache cookie's 5 minutes, which would cut the per request reads to the session check alone. The third is a design choice this note only names. Either way the sign in alone does not move; the identity reads move with it.

Two more facts for A'' and C. First, the Worker sees the proxied request's `Cookie` header, so the `__Host-ts_id` anonymous cookie does reach the callback and `linkAnonymous` can run in the hook (`REALTIME.md` 4.2) if the Worker holds the principal store and the alias table; otherwise the fallback link on the next request with both (T2 3.5 A' and `identity.ts` 605 to 611 as T2 cites them) does the work on Vercel. Second, the CSRF filter on `/api/auth/*` reads `Sec-Fetch-Site`, `Origin` or `Referer` (T2 3.3); behind a proxy those headers are the browser's and still name `www`, so the filter can stay where it is or move with the routes.

## 7. Findings, one line each

1. The installed `@better-auth/kysely-adapter` 1.7.4 already contains a D1 dialect, chosen when the `database` option is a raw binding with `batch`, `exec` and `prepare` (`dist/index.mjs` 21, 84 to 88); `kysely-d1` is needed only for Turboslide's own tables, or the tree writes a dialect in `sqlite-dialect.ts`'s shape.
2. On the tree's `{ db, type }` form the adapter opens no transaction (`index.mjs` 32 to 37, 677 to 685); the three `db.transaction()` sites are MySQL branches (338, 624, 653). T2 open 5 is closed.
3. D1 cannot be queried from a Vercel function by any supported means; the HTTP API is the control plane by Cloudflare's own description and sits under 1,200 requests per 5 minutes per user, which caps a per statement design at two concurrent signed in editors.
4. No per query latency for the HTTP API is published; a 2025-05-29 changelog removed 50 to 500 ms from it, a 2023 client README called it half a second, and the unauthenticated edge floor from this Mac was 50 to 116 ms.
5. A session cookie set on a `workers.dev` host cannot serve `www.turboslide.com`: host-only cookies, a public suffix host, no shared root for `crossSubDomainCookies`; a custom hostname means a DNS change at the registrar or the zone on Cloudflare.
6. The only no DNS layout is the app proxying `/api/auth/*` to the Worker, and the installed h3 relays `Set-Cookie` (`proxy.mjs` 185 to 199); it moves the identity reads with the sign in, so the Worker ends up answering `requestIdentity`, or the function caches account facts for the cookie cache's 5 minutes.
7. D1 Free holds for sign ins by three orders of magnitude and for per request reads up to 570 to 780 signed in editor hours a day, as long as the principal records stay off D1.
8. The first free line a Worker placement crosses is Workers' 100,000 requests a day, at 45 to 62 signed in editor hours a day in layout C; Workers Paid at $5 a month is the fix if that load arrives.
9. wrangler needs an account, Node and either a browser OAuth login or `CLOUDFLARE_API_TOKEN` plus `CLOUDFLARE_ACCOUNT_ID`; the D1 token permissions are D1 Read and D1 Edit; `d1 create --location=enam` fixes the primary near `iad1`.
10. Cloudflare's Google sign in creates an account only for an address with no Cloudflare account; GT already has a Worker (`gt-cloud/apps/edge/wrangler.toml`), so the account exists under some login.
11. There is no free Postgres on Cloudflare; Hyperdrive is a Worker only pooler for a database you pay for elsewhere, and PlanetScale through Cloudflare starts at $5 a month.
12. The tree's `node:sqlite` import at module load (`db.ts` 11) and the `env.VERCEL` reads on the auth path (T2 3.4) are the code changes any Worker placement needs before the first request.
