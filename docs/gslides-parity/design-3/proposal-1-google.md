# Proposal 1: Google faithful

Round three design proposal, designer 1 of 3, written 2026-09-13 against `main` at `61b16e4` (after Google Slides parity round two) and the eleven research reports under `docs/gslides-parity/research-3/`. The angle is Google faithful: every collaboration, comment, sharing and identity behaviour of Google Slides that a standalone product can reproduce is reproduced with Google's labels, positions, shortcuts and rules, one standalone mechanism substitutes for each Google service, and the parts Google does not expose (the realtime engine, security, layout shift, dithers) are designed to Google's quality bar.

Kevin's directive for this round, verbatim: "make sure its 'multiplayer' too with all collab features with optional logins and avatar creation. address all layout shifts and prevent cyberattacks and introduce rate limiting. also add more features like being able to add images in background and apply dithers over those, those are some huge features we like".

Rules followed: plain technical English, sentence case, no em dashes, no metaphors, no trailing periods on headings, full sentences in body. No Google icon or artwork is copied; Google Slides is the reference for structure, labels, positions and behaviour. No account was signed in. No web page was fetched for this proposal: every Google fact and every platform fact comes from a research report of this round or round one, cited by report number and section, and section 14 lists the URLs those reports read with the date they read them. Every Turboslide fact was read from the code at `61b16e4` on 2026-09-13.

## 0. The decisions in one page

1. Google's model, no locks. Every editor's change lands on one shared copy, propagates to every open tab within the stream's latency, and is merged without a lease, a dialog or a conflict card for humans (report 01 section 1, section 11). Leases stay for agents only (SPEC 6.7), bound to the agent's presence heartbeat. The conflict card of round one is retired for text and property conflicts and stays only for a `reject`.
2. The change feed is an operation stream in front of the revision log, and the one addition to the hosted backend is Redis. Vercel Blob cannot carry it: a Pro store allows 75 advanced operations per second for the whole deployment and one write is five (report 02 1.3), an overwritten public blob is served stale for up to 60 seconds (report 02 1.3), and Blob has no publish and subscribe. Upstash Redis through the Vercel Marketplace on the fixed 250 MB plan ($10 per month, unlimited commands) is the ordering authority, the fan out and the presence store (report 02 2.5, report 10 F33). Without Redis the same code runs a reduced tier over Blob with a 1 second poll and no cross instance presence; on a checkout it runs in process (report 02 7.7).
3. Transport is Server-Sent Events down and POST up on every tier, because TanStack Start's server layer does not upgrade a WebSocket and the dev server does not run Nitro (report 02 2.3, F1). WebSockets are a flagged swap for the presence channel in round four.
4. Merging is server serialized: text operations inside one Text are transformed at admission (the client server form of operational transformation, which is what Google's own posts describe by title, report 02 3.1), every other JSON pointer is last writer wins by server order, structural operations re-anchor, and an operation that cannot be placed is returned to its author with its content and never dropped (report 02 7.5). No CRDT replaces the document.
5. Presence has Google's four surfaces and no more: the avatar row in the title row with Follow, the filmstrip marker, the caret and the optional live pointer on the canvas, and chat (report 01 section 2). Names are shown for people the owner invited; everyone else is a generated label, never an animal (report 11 section 4). Follow is refused for anonymous people and for people without edit permission, as Google refuses it (report 01 section 2).
6. Colour is a session channel only. Six hues that pass 3:1 against `#070707`, `#ffffff` and `#f2f2f0` colour the remote caret, pointer, selection outline and Following ring; every stored surface (comments, version history, Show changes) is monochrome with the principal's mark (report 11 decisions 1 to 3).
7. Comments are a sidecar per deck (`decks/<id>/comments/`), never document data, with Google's six anchor kinds, replies, `@` and `+` mentions, one assignee with Done, emoji reactions, resolve and reopen, a link per comment, the panel with For you, search and a type filter, the four display modes, Google's shortcuts and the three notification levels (report 01 section 3, report 08). Comment operations ride the same stream as edits.
8. Share roles are Google's: Owner, Editor, Commenter, Viewer, with Restricted and "Anyone with the link" plus a link role, the two gear switches, per person expiry, Remove access, Transfer ownership, Request access with the dot on Share and the Review banner, and Publish to web with Stop publishing (report 01 section 5, report 09). Enforcement is one server function, `authorize(ctx, deckId, capability)`, at the top of every server function and route.
9. Identity is anonymous by default and optional to upgrade. Every browser gets a server sealed `__Host-` cookie carrying a v4 UUID (report 03 B2); the first write asks "How should others see you?"; sign in is better-auth 1.7.4 with magic link and a typed code in one mail, passkeys once the production domain is decided, and GitHub when its two variables are set; no passwords, no Google (report 03 J). Identity tables live in Neon Postgres, sessions and counters in Redis, avatars in the public Blob store under a per person random key (report 03 D2, report 10 F43).
10. Security lands as the plan of reports 04 and 10 in their order: identity and authorization on every server function (F1, F2), rate limits in three layers with the numbers of section 5, the `html` block sandboxed and sanitized with DOMPurify, uploads re-encoded through sharp with SVG refused hosted, `safeFetch` with pinned DNS, the CSRF filter widened, security headers and a nonce based CSP, two Blob stores (private documents, public files under an unguessable key), the hosted asset write path fixed (F49), client uploads above 3 MB (F51), agent API keys, structured logging.
11. Layout shift is gated to zero measured entries on every route, state, width and appearance by `scripts/layout-shift-audit.mjs` as `pnpm check` step 26, with the nine rules of report 05 section 4 applied to every new surface (fixed slots, `cqw` placeholders, fixed width flags and count chips, absolute overlays).
12. A dither is a property of a picture object: `PictureDither` on `picture` and `shot` (pattern, tone, cell, strength, ink and paper points, midtones, invert, light theme, advanced filters), rendered from a materialized variant file in every export and from a canvas overlay only while editing, with a Dither toggle on the Change background dialog's Image row and a Material row that places a shader frame at the bottom of the stack (report 06). Defaults reproduce the GT deck's look: Bayer 8 by 8, ink and paper, cell 2, strength 100.
13. Everything a person can do is an action. Forty six actions join `packages/schema/src/actions.ts` (presence 4, sync 1, comments 12, notifications 3, activity 1, versions 2, share 19 including publish, account 6, dither 4), each with CLI, MCP and window handlers, working on a checkout with no server and hosted behind the bearer or an API key.
14. Existing links keep working. Every deck created before this round is `open: editor` until its owner claims it, then `open: viewer`; the Prototemplate embed of `gt-brand` stays open; new decks start Restricted as Google's do (report 09 1.4, SPEC 0.25).

## 1. The multiplayer architecture

### 1.1 Two paths: the operation stream and the revision log

The document stays the JSON block document written through the fifteen mutation ops of `packages/schema/src/mutations.ts` and applied by `applyWrite` (report 02 1.1). What changes is what sits between a keystroke and `versions/<n>.json`.

The operation stream is one ordered sequence of admitted operations per deck. Each entry carries `seq`, the revision it followed, the author (derived on the server from the session or the API key, never from the body, report 04 F2), a server issued `clientId` bound to the session (report 10 F26), the client's `opId` (`clientId:counter`), the kind (`edit` or `comment`, report 08 2.4) and the mutation list as transformed at admission. Hosted it is a Redis stream `deck:<id>:ops` with a head counter `deck:<id>:head`, fanned out through one publish and subscribe channel per deck, trimmed after every checkpoint to 10,000 entries or 24 hours, whichever is larger, and 16 MB (report 02 7.1, report 10 F35). On a checkout it is an in process array fed by the editor and by `fs.watch` when the CLI writes beside the dev server.

The revision log is the existing `deck.json`, `slides/<id>.json`, `versions/<n>.json` and `snapshots/<md5>.json` on Blob (SPEC-2 8.2), written by a checkpointer that takes the stream's entries since the last checkpoint, coalesces them into one `Write` per author run (consecutive `text.replace` on one run into one operation, consecutive `block.set` of one pointer into the last value, a drag's `pos` sets into the final box), applies them through `BlobStore.write`, and announces `{ type: 'checkpoint', revision, fromSeq, toSeq, snapshot }` on the stream. It runs on the instance that admitted the latest operation after 2 seconds without operations, every 10 seconds during continuous activity, when the retained bytes pass 1 MB, and at once for an agent write, a `version.restore`, a `version.save` and a share change, under a Redis lock `deck:<id>:ckpt` with a random holder token, a 2 second TTL and a heartbeat a waiter breaks after 3 seconds (report 02 7.1, report 10 F34, F36). `VersionRecord` gains `ops?: { fromSeq: number; toSeq: number }` so a version names the stream range it coalesced. Three active decks at 0.1 checkpoints per second are 1.5 advanced Blob operations per second against the 75 per second cap; the History panel reads as bursts, not keystrokes.

Acknowledgement has two levels. `seqAck` means the operation is in the stream; `revAck` means a checkpoint on Blob covers it. The client keeps every operation until `revAck`. If Redis loses the stream, clients resend their un-checkpointed operations against the Blob document, transformed against whatever landed, so an accepted keystroke is never lost; only its position may move (report 02 7.1).

### 1.2 The room protocol

Messages down the stream, each with an `id` the browser echoes as `Last-Event-ID`:

- `hello { seq, revision, clientId, clients[], role, pointersVisible }` on connect. The server issues `clientId` here as a random 128 bit value bound in Redis to the session and the deck for 320 seconds, refreshed by presence (report 10 F26).
- `ops { seq, entries[] }` for the operations since the client's position, or `resync { revision }` when the position is older than the retention window or more than 2,000 entries behind, in which case the client reloads the document at `revision` and continues. Replay reads are capped at 2,000 entries and 1 MB per open (report 10 F25).
- `op { seq, rev, kind, author, clientId, opId, mutations | commentOp }` for each admitted operation, including the author's own, so the author replaces its pending copy with the admitted form.
- `checkpoint { revision, fromSeq, toSeq, snapshot, author, note, comments: { revision, threadIds } }`.
- `presence { clientId, clock, state }`, `leave { clientId }`, `chat { clientId, at, text }`.
- `inbox { unread }` for the connected principal (report 08 5.2).
- `reject { opId, reason, mutations }` where `reason` is one of `stale`, `invalid`, `forbidden`, `too-large`, `locked` (report 10 F29).
- a comment line every 15 seconds as the heartbeat; the `retry` field set to a random 1,000 to 4,000 ms; the server closes every stream at a random point between 240 and 290 seconds so tabs never reconnect together (report 10 F24).

Messages up, a POST per batch:

- `POST /api/decks/:id/ops { clientId, base: { seq }, entries: [{ opId, kind, mutations | commentOp }] }`, at most 64 entries and 256 kB, `base.seq` at most 500 behind the head (report 10 F27, F28).
- `POST /api/decks/:id/presence { clientId, clock, slideId, selection, pointer, follow }`, one per 80 ms per client, coalesced; the identity fields come from the session and are refused in the body as `unknown_field` (report 10 F31).
- `POST /api/decks/:id/chat { clientId, text }`, at most 500 code points, 10 per minute per client; never stored (report 01 section 2: messages are not saved).
- `lease` and `release` for agents through the existing `slide.lease` action.

A viewer role receives checkpoints, presence and chat, never raw operations; a commenter receives operations for the slides it may read with notes fields stripped; the stream re-checks the role at connect, every 60 seconds and on every `access:<deckId>` message, so a removed editor loses the stream within a second (report 09 9, report 10 F25).

### 1.3 Admission and transformation at the server

The function that receives an `ops` POST (report 02 7.3):

1. Loads the document at the last checkpoint from the instance's `/tmp` mirror and applies the stream entries since it from Redis (`XRANGE`), cached per instance by `seq`, so a warm instance does this incrementally and admission stays under 10 ms.
2. Checks `authorize(ctx, deckId, 'write')` (or `'comment'` for a comment entry) and refuses a slide outside the author's role with `forbidden` before any transform (report 10 F29).
3. Transforms each incoming operation from `base.seq` to the head: `text.replace`, `text.style`, `text.case`, `text.insert` and comment `text` anchors by the transform functions of 1.4; `after` anchors of `slide.insert`, `block.insert`, `block.move` and `slide.move` re-resolved; everything else unchanged.
4. Applies it through `applyMutation`, validates the touched slide (`validateSlide`) and the deck caps (500 slides, 400 blocks per slide, 200 KB per slide document, 5 MB per `html` block, 25 MB per deck; report 04 7.5), and answers a failure as `reject` with its content.
5. Appends atomically. A Lua script compares `deck:<id>:head` with the head the function transformed against; on a match it appends with `XADD`, increments the head and publishes; on a miss it returns the count and the new head only (never the entries, report 10 F34) and the function reads the gap with `XRANGE`, transforms once more and retries; after two misses it takes a 200 ms lock and retries under it.

The admitted operations reach every instance's subscribers through one Redis subscription per instance per deck, never per stream (report 10 F24), and each instance writes them into its open streams.

### 1.4 Conflict rules per operation

The rules are report 02 7.5, adopted without change; the table is repeated so the builders have it in one place.

| Operation                                                                        | Two concurrent writers                                                                                              | Rule at admission                                                       | Undo rule                                                                |
| -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `text.replace` (insert or delete in one Text)                                    | both kept, offsets transformed; equal position ties broken by server order                                          | transform against the operations since base, in plain text offsets      | the inverse is transformed against later operations before it is applied |
| `text.style`, `text.case`, `text.insert`                                         | ranges shifted and split around concurrent inserts and deletes                                                      | transform as range operations                                           | same                                                                     |
| whole Text `block.set` or `slide.set` (an agent, a paste, `slide.replace`)       | last arrival wins the string; the other side's pending inserts are re-anchored by `textDiff`                        | last writer wins                                                        | applied only if the pointer still holds the value this author wrote      |
| `block.set` of any other pointer (`pos`, colour, `dither`, `adjust`, chart data) | last arrival wins the pointer; different pointers never conflict                                                    | last writer wins per pointer                                            | same                                                                     |
| `block.insert`, `slide.insert`                                                   | both inserted; a removed `after` resolves to the end of the slot or section                                         | re-anchor                                                               | the inverse removes the inserted id if it still exists                   |
| `block.move`, `slide.move`                                                       | last arrival decides the position; `z` last writer wins                                                             | re-anchor `after`; keep `z`                                             | same                                                                     |
| `block.remove`, `slide.remove`                                                   | the removal wins; concurrent edits to the removed target are rejected to their author with content                  | the target must exist                                                   | the inverse re-inserts at the recorded anchor, re-anchored               |
| `slide.replace`                                                                  | last arrival wins the slide; pending operations on it are re-anchored by id where the block survives, else rejected | last writer wins                                                        | as whole Text                                                            |
| `section.set`                                                                    | last arrival wins the order; slides added since are appended to their section                                       | last writer wins with reconciliation of ids                             | same                                                                     |
| `asset.set`, `asset.remove`, `deck.set`                                          | last writer wins per asset id or pointer                                                                            | last writer wins                                                        | same                                                                     |
| `version.restore`                                                                | admitted as one operation; everyone rebases on the restored document                                                | forces a checkpoint                                                     | it is itself a version, undoable as today                                |
| comment `add`, `reply`                                                           | both land, in server order                                                                                          | append only; a duplicate ULID is a `reject`                             | no undo stack; delete is a tombstone with a 30 day restore               |
| comment `edit`, `move`                                                           | the author's later arrival wins                                                                                     | author only; `expectedUpdatedAt` refused with 409 when the thread moved | none                                                                     |

The text transform module lives in `packages/schema/src/transform.ts`: the two primitive case of operational transformation (insert against insert, insert against delete, delete against delete) over plain text offsets, with the range operations shifted and split. One change to the mutation language follows: `text.replace` ranges count plain text characters like `text.style` already does (report 02 1.1 records the two offset systems), with the marks of the run the caret is in carried by `insertAt`. Records already written keep their meaning because a record's `mutations` are replayed against the document as it was. Property tests run random concurrent insert, delete, style and case operations on the fixture deck's Texts and assert convergence; the interleaving anomaly two concurrent inserts at one offset can produce is accepted and documented, as Google's operational transformation shares it (report 02 3.3, E17).

Undo is per author and never reverts another author's later change: an inverse `block.set` is applied only if the pointer still holds the value the author's operation wrote, otherwise the step is skipped with the snackbar "That change was already changed by someone else" (report 02 section 5, the Figma and Liveblocks rule).

### 1.5 The client

The controller in `apps/studio/src/routes/edit.$deckId.tsx` keeps the local document, a queue of pending operations (un-acked at `seq`) and the set of operations acked at `seq` but not yet covered by a checkpoint (report 02 7.4). On a local gesture it applies the mutation through `applyMutation`, records the undo entry with its inverse and sends the operation on the next flush: at once for structural operations, coalesced at 50 ms for `pos` sets during a drag, at 100 ms for typing so one `text.replace` carries the characters since the last flush; the undo grouping keeps its own 400 ms rule. On an incoming `op` from another client it transforms its pending operations against it, applies the incoming operation and re-renders the touched slides through `setDocument`. On its own admitted `op` it drops the pending copy and adjusts the local document by the difference when the server transformed it. On `reject` it removes the operation from the document and shows the inline recovery with the content. On `checkpoint` it moves the covered operations out of the retained set, appends the version to the History panel and updates `serverRevision`.

The save words of the title row (SPEC 2.0) gain the sync state: "All changes saved" when `pending` and `retained` are both zero, "Saving…" otherwise, "Offline. Changes save when you reconnect" while the stream is down and the last POST failed (Turboslide's words; Google's exact offline sentence is not on any page read), and "Couldn't save, retrying" on a refused checkpoint. A tab with `pending > 0` warns on `pagehide` (report 10 F36).

### 1.6 The presence channel

The state per client (report 02 Part 4): `clientId`, `clock` (increasing), `slideId`, `selection` (slide id, at most 64 block ids, and for a caret the Text pointer and plain offset or range), `pointer` in sheet units when live pointers are on, `follow` (the followed `clientId`). The server writes the identity fields into the roster from the session: principal id, label, trust state, kind human or agent, the mark spec, the hue slot (report 11 3.1: `sha256(principalId) mod 6` preferred, the least used slot with the lowest index otherwise, granted for the roster entry's life). Hosted the roster is a Redis hash and a sorted set per deck with a 120 second expiry, heartbeat every 5 seconds, stale after 30 seconds; presence never touches Blob or the version log. Live pointers are published for the first 20 clients by join order and only for roles that may edit, as Google caps and restricts them (report 01 section 1). Presence is off on `/deck`, `/embed`, `/present`, `/print` and the published player, and hidden in present mode.

### 1.7 What the CLI, MCP and the window API see

- Every hosted agent write (`POST /api/actions/<id>`, `/mcp`) is admitted through the room like an editor's and forces a checkpoint, so the answer carries a revision and the write appears in every editor within the stream's latency (report 02 7.9). The `baseRevision` conflict rule becomes "a slide you touched, or the deck level, changed since your base"; `strict: true` on the input keeps the exact revision check. The 409 body keeps `current`, `currentRevision`, `since` and `holder`.
- `sync.status` (window, CLI, MCP, HTTP) answers `{ seq, revision, pending, retained, transport: 'sse' | 'poll' | 'memory', tier: 'redis' | 'blob' | 'memory' }`; `window.turboslide.studio.describe().state` gains `presence` and `sync`.
- `presence.list`, `presence.follow`, `presence.unfollow` (report 11 7.3 gives the shapes: `Participant { clientId, principalId, kind, label, trust, mark, slideId, selection, pointer, following, presenting, idle, lastSeenAt }`), and `presence.pointer { on: boolean }` for the toolbar toggle.
- `deck.watch { since, timeoutMs }` is the polling form for transports without a stream and replaces `watchDeck` for agents; `GET /api/decks/:id/events?since=<revision>` is the SSE form behind the bearer or an API key, carrying checkpoint events and, with `?ops=1`, the operations.
- The MCP server declares `resources: { subscribe: true, listChanged: true }` and sends `notifications/resources/updated` for `deck://<deckId>`, `deck://<deckId>/comments` and `deck://inbox` on every checkpoint or comment write (report 02 Part 6 item 2, report 08 3.1); over stdio the notification comes from `fs.watch`.
- The attached studio session registry moves from `globalThis` to Redis, so `deck_goto_slide` over `/mcp` reaches the page whichever instance holds its poll (report 02 1.5).
- An agent session appears in the roster with the dashed agent mark and its token's registered name, the `runId` as a monospaced suffix limited to 32 characters of `[A-Za-z0-9._-]` (report 10 F45, report 11 3.3); its lease expires 60 seconds after its last heartbeat instead of ten minutes.

### 1.8 Offline, reconnection and the local checkout

Google's offline editing needs Chrome and an extension and its merge behaviour is undocumented (report 01 section 1). Turboslide's substitute: the editor keeps working while the stream is down; pending operations stay in memory and are mirrored into IndexedDB under the deck id and the `clientId` so a tab that reloads while offline recovers them; on reconnect the client sends `Last-Event-ID`, receives `ops` or `resync`, transforms its pending queue against what landed and re-posts it; a pending operation whose target is gone comes back as `reject` with its content in the inline notice. Round four adds "Available offline" pinning; round three ships nothing that claims to work without ever having loaded the deck.

The local checkout: the `memory` implementation of `RealtimeChannel` serves `pnpm dev`, the tests and `node-server`; `fs.watch` on `decks/<id>` feeds CLI and MCP stdio writes into the stream so the editor beside them shows the change within a second; two browsers on one checkout are two anonymous identities with two cookies and two hue slots, which is the intended multiplayer test setup (report 10 F48). `turboslide deck follow <id> --from <studio>` subscribes a checkout to a hosted deck's events since the local revision and applies each version record forward through the `FileStore` with the record's `createdAt`, checking the result against the record's `snapshot` md5, so the local `decks/<id>` tracks the host byte for byte; `--push` sends local records the host lacks as writes under the per touched slide rule and prints both sides on a conflict with `--force` and `--theirs` (report 02 Part 6 item 4). `deck pull` and `deck push` stay for whole deck transfer and gain `comments/` (report 08 7.1).

### 1.9 Sequences with numbers

Round trip values are typical public internet figures from report 02 7.10, not measurements; report 02 7.12 lists what the preview run measures first.

1. A keystroke from A reaches B, both in the US East. A types "x" at t0; the flush at t0+100 ms posts one `text.replace`; the POST reaches the function at t0+120 ms; admission (mirror apply, transform against zero entries, the Lua append, the publish) takes 3 to 8 ms; the instance holding B's stream writes the `op` at t0+130 ms; B's tab applies it at t0+150 ms. From Europe the same path is about 250 ms. Today the same keystroke reaches B in 1.5 to 3 seconds hosted (report 02 1.4).
2. A and B type in one paragraph at once. A inserts "ab" at offset 4 with base seq 100; B inserts "cd" at offset 4 with base seq 100; A's POST is admitted first as seq 101; B's arrives with base 100, is transformed against 101 (its offset moves to 6, server order breaks the tie), lands as seq 102; A receives 102 and applies it after its own 101; B receives 101, transforms its pending copy of "cd" (already admitted as 102, so the pending copy is dropped) and both documents read "...abcd..." at offset 4. Neither typed character is lost; the checkpointer coalesces 101 and 102 into two version records, one per author run.
3. An agent writes `block.set` through `POST /api/actions` while A drags the same block. The agent's operation is admitted at seq 200 and forces a checkpoint at revision r+1 within about 600 ms (four sequential Blob puts, report 02 1.3); A's `pos` sets at 50 ms cadence land at 201 to 204 and win the `pos` pointer by last writer wins; the agent's answer carries r+1 and the record; A's title row shows "All changes saved" after the next checkpoint at most 10 seconds later.
4. A stream reaches its life. At 240 to 290 seconds the server closes the stream with a `retry` of 1,000 to 4,000 ms; the browser reconnects with `Last-Event-ID`; the server answers `hello` and the `ops` since that id (in the normal case zero to a few entries); no operation is lost and no reconnect storm forms because every tab's close time and retry are jittered (report 10 F24).
5. A tab goes offline for three minutes with two pending operations. The title row reads the offline sentence; the person keeps editing (12 more operations); on reconnect `Last-Event-ID` is 5,000 entries behind on a busy deck, the server answers `resync { revision }`, the tab reloads the document at that revision, transforms its 14 pending operations against the reloaded Texts by `textDiff` where their base is gone, posts them in one batch, and receives 13 `op` events and one `reject` for a block a colleague removed, shown inline with its text.
6. Redis is unreachable. Admission fails with a connection error; the instance logs `redis.unavailable` and falls to the `blob` tier: the client's next POST is applied through `BlobStore.write` with 400 ms coalescing at one write per second per deck, `subscribe` polls `head('deck.json')` once per second per instance, presence is per instance only, and the title row shows "Presence and live cursors need a Redis store on this deployment" for the deployment admin and nothing for others. Every un-checkpointed operation clients still hold is re-sent against Blob under `revAck`.
7. `version.restore` while three people edit. The restore is admitted as one operation and forces a checkpoint; every client rebases: pending operations on blocks that survive are re-anchored by id, the rest come back as `reject` with content; the filmstrip and the canvas repaint from the restored document; the History panel shows the restore as a version by its author.

## 3. Comments, notifications, activity and share roles

### 3.1 The comment model

Threads are a sidecar per deck, never document data (report 08 section 2): `decks/<id>/comments/index.json` with its own `revision`, `comments/<threadId>.json` per thread (a 26 character ULID), `comments/authors.json`. The reasons are decisive: a per slide `ext.comments` list is one JSON pointer under last writer wins, so two people commenting on one slide inside one checkpoint window would lose a comment; comments must not be undo steps, versions, snapshot noise or standalone build content. On Blob the folder sits in the private store with `index.json` as the `ifMatch` commit point; on a checkout the FileStore writes it under its lock and `.gitignore` gains `decks/*/comments/` because the repository is public and comments name people; `deck push` and `deck pull` carry it, `deck pack` only with `--comments`, `slide.import` never, `deck.copy` only with "Copy comments" ticked (Google's default is off, report 01 section 3).

The types (report 08 1.1): `CommentAnchor` is one of `deck`, `slide`, `block`, `text` (block, Text pointer, `[start, end]` in plain text offsets, `quoted` at most 200 code points), `cell` (table block, `[row, column]`), `notes` (slide); these are Google's six anchors of the Drive API mapped onto the block document (report 01 section 3, T19 and D1). `CommentBody` is plain text with `{@n}` tokens naming `mentions[n]` (a principal id or an invitation id), at most 4,000 code points and 20 mentions; a URL in the body renders as text with an "Open" affordance that passes the link scheme check. `Thread` carries the first comment, `replies` (at most 100), `resolved`, `assignee` with `done`, stamps and the comments revision that last touched it. Reactions are a set per emoji from a fixed palette of 24, keyed by principal. Anchors are resolved at read time by one pure function, `resolveAnchor(document, anchor)`, so a removed block orphans its threads without deleting them and undo, `version.restore` and `slide.replace` with the same ids revive them; text ranges shift through the same transform functions the stream applies to `text.style`, emitted as `comment.shift` entries on the stream (report 08 1.2).

### 3.3 Mentions without accounts

Present people and past commenters are mentionable by anyone who can comment; grantees and raw email addresses are mentionable by editors and the owner, because naming a grantee reveals the share list and a raw email creates an invitation, which is a share action (report 08 4.1). The stored form is a principal id or an invitation id, never a display string; the client sends the mention record, the server checks it and refuses the comment with `invalid_input` at `/body/mentions/<n>` when the caller may not name that party. A mention emails the mentioned person only when they hold a grant on the deck and have an address (report 10 F38); a mention of an address with no grant sends nothing and shows "Invite them from Share" to a caller who may share.

### 3.4 Notifications inside the app, email and the three levels

Google routes comment notifications to Gmail and documents no centre in the editor (report 01 section 3). Kevin asked for notifications inside the app, so the inbox is Turboslide's own design with Google's per file settings adopted verbatim: "All comments", "Comments for you", "None" under Tools > "Notification settings", also reachable from the comments panel's foot and from every mail's "Notification settings" link; Slides has no edit notifications and neither does Turboslide (report 01 section 3, report 08 5.4). The default is Comments for you for everyone but the owner, who defaults to All comments (Google's default for the owner is unverified).

The inbox: one record per event kind (`mention`, `reply`, `assigned`, `resolved`, `reopened`, `reaction`, `accessRequest`, `granted`, `versionNamed`, `comment`), coalesced per thread inside a 15 minute window, at most 500 per principal; Redis with a 30 day TTL for anonymous principals, the identity database for signed in ones, one `Inbox` interface with a JSON mirror under `.turboslide/inbox/` on a checkout (report 08 5.2). The plate in the title row updates through the `inbox` stream event; the panel "Notifications" (`PanelId 'inbox'`) lists rows of a fixed height (the actor's mark, one sentence, a tabular time) and "Mark all read". Email goes only to signed in principals through Resend: mailable kinds are mention, reply, assigned, resolved, access request and granted; digests per person per deck over a 15 minute window (2 minutes for a direct mention); at most 10 mails per person per day, then one end of day summary; every mail carries `List-Unsubscribe` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click` with an endpoint that sets email to None (report 08 5.5, report 10 F38).

### 3.5 Share roles and the Share dialog

The roles are Google's (report 01 section 5, report 09 section 2): Owner (everything), Editor (view, comment, edit, share and change permissions unless the owner turns it off, never the owner), Commenter (view, comment, download by default), Viewer (view, download by default). The link visitor holds the link's role and is never named in a grant; an agent acts as its token's owner intersected with the token's scopes. Two documented departures from Google, both for the sales workflow (research/10 C2): speaker notes are read by editors and owners only, and skipped slides are hidden from viewers.

The access record `decks/<id>/access.json` (report 09 1.1) holds `owner`, `pendingOwner`, `generalAccess { mode: 'restricted' | 'link' | 'open', role }`, `links[]` (hashed tokens with a role, label, expiry, revocation), `publish` (one hashed token), `grants[]` (principal or email, role, inviter, stamps, expiry, message), `requests[]`, `settings { editorsCanShare, viewersCanDownload, allowHtmlBlocks }`, `assetKey` (the deck's random public prefix, section 5.8) and `revision`. It lives in the private Blob store beside `deck.json`, cached in Redis for 60 seconds with invalidation on write, and at `decks/<id>/.turboslide/access.json` on a checkout, gitignored. A deck with no record synthesizes `open: editor` with no owner; "Claim" in a banner makes a signed in person the owner and moves the deck to `open: viewer` so every existing view link and the Prototemplate embed keep working (report 09 1.4).

### 3.6 Link tokens, the exchange route and the embed

Two research reports disagree on where a link token travels: report 09 puts it in the query as `?k=`, report 10 (F40) exchanges it once at `/s/<token>` and redirects without it, following the W3C TAG's finding that capability URLs leak through Referer, logs and history. This proposal takes the exchange for share links and the query for the published player:

- "Copy link" copies `https://<host>/s/<token>`. The route validates the token against the hashed link records, writes a `linkGrant` (the link id and its role) into the session, sets `Referrer-Policy: no-referrer`, renders nothing but a redirect to `/deck/<id>` (viewer and commenter links) or `/edit/<id>` (editor links), and never shows the token in the address bar again. Revoking or rotating the link kills every session grant that names it on their next request.
- The published player and the embed keep the token in the query (`?p=`) because a published URL is public by definition, an iframe inside Prototemplate has no first party cookie in Safari, and `X-Robots-Tag: noindex` covers every tokenised response. The `gt-brand` deck stays `open: viewer` for the existing `/embed/gt-brand` iframe until Kevin changes the snippet.
- Tokens are 16 bytes from `crypto.getRandomValues`, stored as SHA-256 hashes; a dead token answers the same 404 page as a missing deck (report 09 3.2, 8.2).

### 3.8 Enforcement on routes and actions

One function, `authorize(ctx, deckId, capability)` (report 09 8.1), with the capabilities `read`, `readSkipped`, `readNotes`, `comment`, `write`, `history`, `export`, `exportNotes`, `share`, `settings`, `rename`, `copy`, `trash`, `restore`, `remove`, `publish`, `transfer`, `presence`, `follow`, called first in every server function of `write.ts`, `decks.ts`, `download.ts`, `bundle.ts`, `render.ts`, `sessions.ts`, `agent-actions.ts`, in the stream, ops, presence, chat and comment routes, in `handleActionRequest` and in the MCP tool wrapper. Deny by default; 401 without identity on an agent route, 403 with identity and no right (`{ "error": "forbidden", "capability": "write" }`), 404 when the deck must not be shown to exist, 409 on a stale record revision, 410 on a revoked publish token, 429 over a limit with `Retry-After`. Menus hide rows a role cannot use, never disabled (report 09 2.3); the hiding is a convenience and the server call is the check.

The home page reads a per identity index (`users/<principalId>/decks.json` in the private store, heads cached in Redis) instead of syncing every deck, with the views Owned by me, Shared with me, Recent and Trash; Delete forever and Empty trash act on owned decks only (report 09 section 5).

## 4. Optional accounts, sessions and the avatar builder

### 4.1 The anonymous identity

Google shows uninvited people as anonymous animals; Turboslide's majority user opens a deck from a link and will not sign in to edit a slide (report 03 B1). The substitute:

- The first request without an identity cookie gets a `__Host-ts_session` cookie, `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, sealed by h3's `seal` under `TURBOSLIDE_SESSION_SECRET`, carrying a v4 UUID as the principal id; the browser mirrors the label and avatar choice in `localStorage` for instant paint (report 03 B2). `?author=` leaves the editor; the CLI keeps `--author` for the file store.
- `Author` gains `principalId?: string` (report 03 E2); every write, lease, comment and presence record carries it; the server derives the author from the session or the API key and refuses a body author on the browser transports as `unknown_field` (report 04 F2).
- The first write, comment or lease opens a one field dialog, "How should others see you?", prefilled with the generated label ("Titanium 471": a word from a closed list of 64 materials and elements and a number 100 to 999 with a deny list, derived from the principal id, report 11 section 4), a Continue button and a "Sign in" link. Decline keeps the label. A typed name is validated by the rules of 4.5.
- Three trust states, each shown as what it is (report 11 5.2): a label reads as a label; a typed name carries " · guest" in `--pt-ink-2`; a verified account carries the check badge glyph and the email in the tooltip. The word "guest" is Figma's and Notion's word for an outsider.
- Roles bind to accounts or links, never to an anonymous id (report 03 B4); an anonymous owner is a cookie, so the editor shows "Not signed in. Sign in, or copy an edit link, to get back to this presentation from another browser" on a deck the anonymous session owns (report 09 5.4).

### 4.2 Sign in

better-auth 1.7.4 through its official TanStack Start integration (`auth.handler` on `/api/auth/$`, `tanstackStartCookies` last), the only maintained library with that integration and a built in anonymous to account link (report 03 C4). Methods, in the order the dialog lists them:

1. 2. "Use a passkey": the passkey plugin over SimpleWebAuthn 14 with `rpID` fixed to the production host, autofill on Safari 16.1+, Chrome 108+, Edge 122+ and Firefox 122+, the QR cross device flow. 3. "Continue with GitHub": present only when `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` are set; for engineers and agent operators (report 03 C3).

No passwords and no Google sign in. Sessions: 7 days idle, refreshed daily, a `cookieCache` so a burst costs no Redis command; the profile lists sessions with browser, platform, coarse location and last activity, "This browser", Sign out per row and everywhere else; adding a passkey or linking GitHub needs a fresh session (`freshAge`); share settings changes and Delete forever need a re-authentication within 10 minutes (report 03 Part F, report 04 8.1). Storage: identity tables (`user`, `session`, `account`, `verification`, `passkey`, `apikey`, device codes, aliases) in Neon Postgres through better-auth's Kysely adapter hosted and `node:sqlite` under `.turboslide/auth.sqlite` on a checkout; sessions, verification rows, challenges and rate limit counters in Upstash Redis as `secondaryStorage` hosted and memory on a checkout; avatars and profile documents on Blob (report 03 D2). Agents hold API keys with the scopes `read`, `comment`, `write`, `export`, `share`, `admin`, stored hashed with a `ts_` prefix, shown once; `turboslide login --to <url>` runs the device authorization flow (RFC 8628 through better-auth's plugin) and stores the key in `hosts.json`; the MCP session binds to the key at initialize (report 09 6.2, 6.4).

### 4.3 The avatar builder

One dialog in the Prototemplate look, 560 by 640, four tabs in the order a person is most likely to want them, each showing the result at 24, 32, 64 and 256 px in light and dark chrome in a fixed 2 by 4 preview strip (report 03 I3, report 11 8 row P8):

- Initials: one or two letters of the display name in Inter 500 on a square plate with a 1 px `--pt-edge` border; a 2 bit hash picks the plate's Bayer density among 1/8, 2/8, 3/8 and 4/8 so two people with one initial sit on two greys; the letters stay ink so they read at 24 px (report 11 6.1). The default for everyone.
- Glyph: a 5 by 5 grid of cells inside a 22 px plate, each empty or one of five glyphs the theme owns (a dot, a dash, a slash, a square, the GT mark's stroke), mirrored left to right, from the hash; "Another" rerolls a salt kept in the profile.
- Dither: a Bayer dithered ramp whose centre, angle and curve come from the hash, at 2 px cells; "Another" as above.
- Picture: a file input for JPEG, PNG, WebP or GIF (first frame), a square crop the person drags, a client side resize to at most 1024 px, then the server sniffs the bytes, decodes with sharp under `limitInputPixels` and `failOn: 'error'`, rotates by the orientation tag, crops, resizes to 32, 64, 128 and 256 px WebP and one 256 px PNG, strips metadata, and stores under `u/<avatarKey>/<sha256>-<size>.webp` on the public store where `avatarKey` is a random 128 bit value per person rotated on every change and the old prefix deleted; the original is never kept; SVG is refused (report 03 I4, report 10 F43).

One function renders every mark: `markSpec(identity)`, `renderMarkSvg(spec, size, theme, { halo, live })`, `renderMarkBits` and `renderMarkPng1` through `encodePng1` with the two entry palette, `labelFor(principalId)`, `hueFor(slot)`, in a new browser safe package `packages/identity` (report 11 7.1). The CLI prints `turboslide account me --avatar-png me.png`. Agents' marks are the 50 percent Bayer field with a centred square and a dashed border, never a hue.

### 5.4 The html escape block and the standalone export (P4)

Three layers, all three (F4):

1. Isolation at render time: each `html` block renders into `<iframe sandbox="" srcdoc="...">` with no `allow-scripts` and no `allow-same-origin`, sized to the block's box, carrying the theme CSS the block needs and a `<meta http-equiv="Content-Security-Policy" content="default-src 'none'; img-src 'self' data: https://<store>; style-src 'unsafe-inline'; font-src 'self'">`, in the studio, the viewer, print, present and the standalone HTML file (a file opened from disk has a `file://` origin where a same origin script is more dangerous, not less). 2. 3. A scheme check on every link: `run.link` and `BlockLink` accept `https:`, `http:`, `mailto:`, `tel:` and the slide link forms in the schema and again in `renderRuns`, rendered with `rel="noopener noreferrer"`.

## 7. Background images with dithers, and shader materials as backgrounds

Google's background is a stretched picture fill that cannot be selected, and its only tonal effect is Recolor (report 06 section 2). ### 7.1 The field

`PictureDither` joins `pictureToolFields` in `packages/schema/src/blocks.ts`, so `picture` and `shot` take it (report 06 4.1):

```ts
export type PictureDither = {
  pattern: 'bayer8' | 'bayer4' | 'blue64' | 'random';
  tone?: 'two' | 'three' | 'original';
  steps?: number; // 2 to 7, tone 'original'
  cell?: 1 | 2 | 3 | 4; // sheet pixels; 2 is the deck's cell
  strength?: number; // 0 to 1; 1 is the pure two tone
  black?: number;
  white?: number;
  gamma?: number; // the deck's tone LUT
  invert?: boolean;
  polarity?: 'auto' | 'dark-ground' | 'light-ground' | 'same';
  blur?: number;
  minFilter?: number;
  channel?: 'gray' | 'r' | 'g' | 'b';
  seed?: number;
};
```

Defaults when absent: tone two, steps 4, cell 2, strength 1, black 0, white 255, gamma 1, invert false, polarity auto, blur 0, minFilter 0, channel gray, seed 0. The Dither toggle is the presence of the field: on writes `{ pattern: 'bayer8' }`, off removes it; `block.resetImage` removes it with `trim`, `mask` and `adjust`. The field never rewrites the asset's twins; the GT deck's 16 committed two tone treatments stay as they are, and a block level dither over an asset with a two tone treatment and no `sourceFile` is refused with "the asset has no continuous source (sourceFile); the committed twins are already dithered" until `asset.add --replace-source` attaches one (report 06 6.3). Zod ranges bound every number (blur at most 8, minFilter at most 9, seed a 32 bit integer).

`Asset.variants?: Record<string, AssetVariant>` records materialized files: `{ key: sha256(source digest, resolved dither, cell, screen size), twins, size, scale: 1 | 2, metrics?, producedAt }`, named `assets/<asset>.dither-<key12>-light.png`, `-dark.png` or `.png` for `same` polarity, 1 bit or palette PNGs of about 4 KB at cell 2 (report 06 4.5, 6.1).

### 7.2 The pipeline and the renderer path

One browser safe function, `ditherPicture(source, box, view, dither, theme, adjust?)` in `packages/effects/src/dither.ts`, shared by the studio's worker, the headless sheet page and Node (report 06 4.2): the cover fit of the trimmed region to the screen size (`w / cell` by `h / cell`) through the pinned Lanczos3 after gray or one channel, invert, min filter and blur (cached as `toneBase`); autocontrast 0.5 and the tone LUT; brightness and contrast of `block.adjust` folded into the LUT; the threshold against `bayer8` (the deck's table), `bayer4`, `blue64` (a CC0 texture pinned by sha256) or `random` (a 32 bit hash of `(x, y, seed)`), or the ordered posterise for tone `original`; polarity by the lit fraction; paint in the theme's ink and paper, three tones with titanium as the middle, or the posterised colours, at `cell` sheet pixels per cell by nearest upscale (`twoToneAtScale`'s rule at export scales); strength under 1 composites the plane over the continuous picture. With `bayer8`, tone two, cell 2 and strength 1 the stages are the deck's pipeline unchanged, and a parity test pins that the recorded Rosetta parameters regenerate the committed cells.

The live preview is under 100 ms because the slow stages are cached: a slider event re-runs the LUT, the threshold and the paint over 360,000 cells in the worker, requests carry ids and stale ones are dropped, the section posts on every input event and writes `block.set /dither` on pointer up (report 06 4.3).

The renderer writes the effect as data and prefers a variant: `<div class="picture" data-dither='…' data-dither-key="sha256:…" data-dither-state="variant|live">` with `img.picture-img` pointing at the variant twins when `deck.assets[asset].variants[key]` names them, else at the continuous twin with a `canvas.picture-dither` overlay (absolute, `inset: 0`, `image-rendering: pixelated`) that the runtime draws only in a live render. The standalone build, the CLI render, the PDF page and the Perfect raster read the variant and need no script (report 06 4.4).

## 12. Risks

1. Redis as a new dependency in the write path. Mitigations: the `blob` tier as the automatic fallback, the two level acknowledgement so no accepted keystroke is lost, the fixed plan so a command flood is a 429 and not a bill, eviction off, per identity command budgets (report 02 7.11 risk 2, report 10 F33, F35). The preview run of report 02 7.12 measures the Lua contention and the command latency before enforcement.
2. Transform correctness. The text transform module is small (insert, delete, range shift) but the property tests must run before two people type in one Text on production; the interleaving anomaly is accepted and documented.
3. Scope. Six builders at 438 agent-hours plus the integrator and verifier is the largest round yet. The cut line, in order, if day 6 shows it: chat, the activity panel's comment trend bar, `version.delete`, the Glyph and Dither avatar tabs (Initials and Picture stay), GitHub sign in, the material background's Play button. Every cut leaves its menu row present and disabled with a clause that says what to do instead.
4. Passkeys and the domain. `turboslide.vercel.app` is on the public suffix list, so a passkey made there dies with a later move to a General Translation subdomain; passkeys stay behind a flag until Kevin decides the domain, and magic link plus code is the first method (report 03 C1).
5. Email deliverability and abuse. Sending from General Translation's domain needs SPF and DKIM and a person with DNS access; a mention or invitation flood would spend the free quota and risk suppression. The design sends mail only to grant holders, caps per person and per day, digests, and ships `List-Unsubscribe` (report 10 F38). `TURBOSLIDE_MAIL=capture` keeps previews from sending anything.
6. The two store migration on a live deployment. Documents and emails must never land on the public store; the private store is created before the access record exists (report 09 R2), and the public twins are copied under the keyed prefix while the old paths still serve through the asset route. A failure mid copy leaves both paths valid.
7. The html block sanitizer against the GT deck. The four imported escape blocks must render identically after DOMPurify and the sandboxed frame; the canvas fidelity gate and compare-to-shoot are the check, and a block that changes pixels is fixed by extending the allowlist, never by weakening the frame.
8. Layout shift as a hard gate. A zero tolerance gate on a production preview can fail on a machine under load (VERIFICATION-2 finding 24 records a load sensitive step). The script runs against `vite preview` with the machine otherwise idle, records the frame sampler per run, and a flaky row must be isolated to a cause before it is declared an exception in the script.
9. Anonymous owners. A person who creates a deck without signing in and clears cookies loses the owner role; the editor says so on every such deck and the admin can assign an owner (report 09 5.4).
10. Name impersonation and confusables. The rules of 4.5 refuse the obvious cases; a typed name colliding with a named collaborator by skeleton is refused only inside the decks the identity is present in, so a determined impersonator moves to another deck. The trust word and the check badge are what a reader must learn to look for; the profile sentence says it.
11. The SSE stream on TanStack Start's dev server. Streaming from a server route is documented (report 02 F4) but the 300 second life and the heartbeat under HTTP/1.1 intermediaries are measured on a preview first (report 02 7.12 item 1); the long poll stays one release as the fallback.
12. Google facts this proposal builds on that no public page states (section 13). Each is marked in the text; the verifier lists them for Kevin, as rounds one and two did.
