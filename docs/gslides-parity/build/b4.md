## 3. Decisions taken where the SPEC was silent, and deviations

1. **Right-click inside an editing session is the browser's own menu.** SPEC 4.3's text selection menu lists the browser's spelling suggestions first; a custom menu cannot list them (the browser exposes them only in its own menu), and the sales user's typo fix is that menu. So a right-click inside the editable run is not intercepted; Link is Cmd K and Format options is on the toolbar tail. The `textSelection` rows stay in the model for Search the menus. Recorded as a deviation for Kevin (SPEC 15.11).
2. **The chip prints the block's plain name.** SPEC 1.1 says the chip no longer prints `type · id`; SPEC 13.7 wants a block's accessible name to be its type in plain words. The chip reads Text box, Image, Table, Title, Subtitle and so on (`blockDisplayName`), and `type · id` only while Tools > Advanced > Show slide and block ids is on (`showIds`).
3. **The arrange bar leaves the stage.** Google has no floating arrange bar; align, distribute and order live in the Arrange menu and the right-click menu (SPEC 4.3) and the `EditorHandle` carries them. `overlay-component.test.tsx` encoded the bar and was updated (section 1 of MILESTONES B4's rules).
4. **Several dragged cards write one `section.set`.** SPEC 4.1 says "one `slide.move` per moved slide in one write"; no action takes several `slide.move` mutations in one write, and `section.set` is the one write that carries the whole order. One card stays one `slide.move`, so the version log reads as Google's move for the common case.
5. **Deleting several cards is several `slide.remove` writes.** No action removes several slides in one write; the snackbar's Undo runs the page's undo once per removed slide.
6. **New slide after a Section header is Title and body**, like after a Title slide (SPEC 0.27), because a second header would open a second section (B1's rule for an opener).
7. **The frame edges are the drag surface on a freeform slide.** On a grammar slide a block still drags by its body outside its text (the chip's `block-move`); inside text a click places the caret, as Google does.
8. **Bare letters are consumed while a block is selected.** The stage stops propagation of a bare character key when a block is selected (SPEC 0.28), so a stray keystroke never reaches a shell key. With nothing selected the key owner of the shell decides (B3's `useEditorKeys`).
9. **Cmd C, X and V ride the browser's clipboard events**, not the keydown: the `copy` and `cut` events write the envelope through `clipboardData.setData` (no permission prompt) and the `paste` event reads it; the menu's Copy and Paste go through `navigator.clipboard` with the in-page copy as the fallback. The stage's keydown listener only stops the chord's propagation (never its default) so the shell's key table cannot swallow it. `text-editing.spec.ts` grants `clipboard-read` and `clipboard-write` to read the envelope back through `navigator.clipboard.readText()` in headless Chromium.
10. **`Row added` and the second write of Tab in the last cell.** The typing's last burst and the appended row are two writes: the row is computed from the slide as it stands after the burst (`slideAfter`), never from the stale record, so the typed cell text survives; one Undo removes the row, a second the typing.
11. **The Editor counts revisions across the writes of one tick** (`revisionRef`): the page's reducer applies a write before React re-renders the document prop, so a second write in the same tick would otherwise carry a stale `baseRevision` and be refused.

### 7.2 Finding 18: the chip's order key and the direction of block.move

The cause was two things, both in B4's files.

1. `orderBlock` in `Editor.tsx` inverted its sign in this round's first cut: `move === 'forward' ? 1 : -1` where `14da621` had `-1 : 1`. `nudgeMutation`'s `block-move` case treats a positive delta as one place down the slot (`gestures.test.ts` pins it), so the chip's ArrowDown (`'backward'`, delta -1) on the first block computed an index of -1 and `nudgeMutation` returned null: no write, which is what the spec measured. The same inversion made Cmd Up (Bring forward) move a block down its slot and Bring to front send it to the last place.
2. The chip's chord was Alt with an arrow, and the chip's tooltip named it in the default view.

The SPEC reading. Finding 18 says SPEC 10.2 does not retire the chord. It does: the row "Alt+Up and Alt+Down | reorder a block or a slide row | Google moves a paragraph | Dropped; Cmd+Up and Cmd+Down do both jobs by focus (the filmstrip moves the slide, the canvas orders the block)", and the section closes with "The Turboslide only keys that remain in the editor's default view: none". So the fix follows the SPEC instead of restoring the Alt chord; this is not a deviation, and the existing spec was updated because SPEC 10.2 changes the behaviour it encoded.
