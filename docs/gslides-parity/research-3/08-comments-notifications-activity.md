# Comments, mentions, notifications, activity and version history by author

Report 08 of the Turboslide Google Slides parity round three, written 2026-09-13 against commit `61b16e4` (main after the round two production table). It designs the data model, the storage, the sync, the transfer, the export, the notification model and the action table for comments, mentions, in app notifications, the activity feed and version history by author. Report 01 recorded Google's behaviour (sections 3, 6, 7, 9, 10, 11); report 02 designed the operation stream, the checkpointer and the presence channel; report 03 designed the principal id and the alias table; report 04 stated the security requirements; report 05 the layout shift rules; report 07 inventoried the disabled stubs. Nothing those reports verified is repeated here; it is cited by report number and section.

Every Turboslide fact is read from the code at `61b16e4` and cited with file and line. Every external fact carries its URL and the date read (2026-09-13 unless stated). Facts that could not be verified from a public source are marked and repeated in section 12.

## The decisions in one page

1. Comments are a sidecar per deck, never document data. Threads live under `decks/<id>/comments/<threadId>.json` beside `deck.json`, with `comments/index.json` carrying their own revision counter. They do not enter the mutation log, the version records, the snapshots, the undo stack or the canvas fidelity gate. Section 2 has the comparison; the deciding fact is that a per slide `ext.comments` list would be one JSON pointer, and the round three merge rule for one pointer is last writer wins (02 7.5), so two people commenting on one slide at once would lose a comment.
2. A thread has one anchor of six kinds (slide, block, text range, table cell, notes, deck), resolved against the document at read time, never stored as dead or alive. A removed block orphans its threads without deleting them; undo, `version.restore` and `slide.replace` with the same ids revive them. Text ranges are plain text offsets, the offsets `text.style` already uses (`packages/schema/src/actions.ts:271-276`), shifted by the same transform functions the stream applies to `text.style` ranges (02 3.3, 7.5).
3. Comment operations ride the operation stream of 02 7.1 as a second entry kind and are checkpointed to the sidecar, not to version records, so a comment reaches every tab within the stream's 60 to 250 ms and the History panel never shows one. On a checkout the FileStore writes the sidecar under its write lock and `fs.watch` carries the change; over `turboslide mcp` on stdio the same functions run with no server.
4. Every comment operation commutes or has one winner: add is append only, edit is author only and last write of the author wins, resolve, reopen and assign are last writer wins with the server's order, delete is a tombstone that keeps the replies, reactions are a set keyed by principal. No comment operation ever produces a conflict card.
5. Mentions store a principal id, an agent principal id, or an invitation id, never a display string. Present people and past commenters are mentionable by anyone who can comment; grantees and raw email addresses are mentionable by editors, because naming a grantee reveals the share list and a raw email creates an invitation, which is a share action (report 09's interface `access.invite`).
6. Notifications are a per principal inbox: Redis with a 30 day TTL for anonymous principals, the identity database of 03 Part D for signed in ones, one shape for both. The title row gets a fixed inbox plate beside the comments glyph (05 rule 4). Per deck settings are Google's three levels (All comments, Comments for you, None) and Slides has no edit notifications (01 section 3). Email goes through Resend for signed in people only, coalesced into digests, with `List-Unsubscribe` and one click unsubscribe, capped at 10 mails per person per day.
7. Version history groups the coalesced records of 02 7.1 by day and by 15 minute window, colours each author from the principal mark interface report 11 owns, and Show changes runs `version.diff` (a data form of `diff.run`) between two records and outlines the touched blocks on the canvas in the author's colour. Anonymous principals are attributed per principal id, not collapsed, because each anonymous browser has a stable id (03 B2); a principal nobody can resolve renders as the stored label.
8. The activity feed is the security event stream of 04 8.11 filtered by deck plus the comment and version events, readable by editors. Turboslide records no views and has no Viewers tab; the privacy baseline of 03 Part G decides it.
9. Comments travel in the bundle as a new manifest group with digests, are copied by `deck.copy` only with `copyComments: true` (Google's default is off, 01 section 3), never cross decks with `slide.import`, and are exported to PPTX as native `p:cmLst` and `p:cmAuthorLst` parts written by hand in the OOXML post process, because pptxgenjs 4.0.1 has no comment API. PDF, print, TXT and the standalone HTML never carry comments.
10. Eighteen actions join `packages/schema/src/actions.ts` with CLI, MCP and window handlers (section 8). The window handlers of every comment, notification and activity action run server side through `runDeckAction` (the path `deck.copy` takes, `apps/studio/src/server/agent-actions.ts:39-50`), because the sidecar is the store's, not the page's.
11. The comments panel sorts open threads by last activity, newest first, resolved threads after them, with a "Slide order" toggle for a review pass; Google documents no sort (01 Unverified) and Figma's default is by date with an unread sort (section 9).
12. Every list the round adds (comments, inbox, activity, versions by author) follows 05 rules 4 to 6: fixed slots, tabular count chips with `min-width`, `cqw` placeholders or no `content-visibility`.

## 1 The data model

### 1.1 The types

The schema package's style is a `z.strictObject` per type with `annotate` for inspector metadata (`packages/schema/src/annotate.ts:40-44`) and a `satisfies z.ZodType<T>` clause (`packages/schema/src/mutations.ts:159-163`). The comment types go in a new `packages/schema/src/comments.ts`; nothing in `deck.ts`, `blocks.ts` or `mutations.ts` changes, because comments are not document data (section 2).

```ts
// packages/schema/src/comments.ts (new)
export type CommentAnchor =
  | { kind: 'deck' }
  | { kind: 'slide'; slideId: SlideId }
  | { kind: 'block'; slideId: SlideId; blockId: BlockId }
  | {
      kind: 'text';
      slideId: SlideId;
      blockId: BlockId;
      path: string;
      range: [number, number];
      quoted: string;
    }
  | { kind: 'cell'; slideId: SlideId; blockId: BlockId; cell: [number, number] }
  | { kind: 'notes'; slideId: SlideId };

/** Who wrote something: the principal of 03 E2 plus the label at the time. */
export type CommentAuthor = { principalId: string; label: string; kind: 'human' | 'agent' };

/** A mention inside a body: a principal, an agent, or an invitation report 09 issued. */
export type Mention =
  { kind: 'principal'; principalId: string } | { kind: 'invite'; inviteId: string };

/** The body is plain text; `{@n}` tokens name `mentions[n]`. Never markup. */
export type CommentBody = { text: string; mentions: Mention[] };

export type Reaction = { emoji: string; principalIds: string[] };

export type Comment = {
  id: string;
  author: CommentAuthor;
  createdAt: string;
  editedAt?: string;
  body: CommentBody;
  reactions?: Reaction[];
  /** A tombstone keeps the slot and the replies; the body is gone from every read. */
  deleted?: { at: string; by: string };
};

export type Assignment = {
  principalId: string;
  by: string;
  at: string;
  done?: { at: string; by: string };
};

export type Thread = {
  id: string;
  deckId: string;
  anchor: CommentAnchor;
  /** The first comment is the thread's own; `replies` follow in order. */
  comment: Comment;
  replies: Comment[];
  resolved?: { at: string; by: string };
  assignee?: Assignment;
  createdAt: string;
  updatedAt: string;
  /** The comments revision that last touched this thread (section 2.4). */
  revision: number;
};
```

Zod: `threadIdSchema` is a 26 character lower case Crockford base32 ULID (time ordered, so a `list` sorted by id is sorted by creation without a second field; generated with `crypto.getRandomValues` for the random half, the same source 04 F22 asks for share tokens); `commentBodySchema` is `z.strictObject({ text: z.string().max(4000), mentions: z.array(mentionSchema).max(20) })` with a refinement that every `{@n}` token names an existing mention and no other `{` sequence appears (so a body can never smuggle markup or an unresolved token); `emoji` is one grapheme cluster from a fixed list of 24 (the palette is data, not free text, so a reaction cannot carry a string); `label` is at most 40 code points with control characters and bidirectional overrides removed, the rule 03 B3 sets for display names. The anchor's `range` is `[start, end]` in the plain text of the Text with one character per paragraph break, the exact words of `textRange` (`packages/schema/src/actions.ts:271-276`); `quoted` is the plain text the range covered when the thread was made, at most 200 code points, so a reader sees what was commented on after the text moved (the Drive API's `quotedFileContent` in 01 section 3 is the reference).

The six Google anchor kinds of 01 section 3 map as follows.

### 1.2 Anchors under concurrent edits

An anchor is data about the document, and the document moves under it. The rule is one function, `resolveAnchor(document, anchor): Resolved | { orphaned: true; reason }`, pure, in `comments.ts`, called at read time by the panel, the markers, the exporter and `comment.list`. Nothing stores an `orphaned` flag, so every path that brings an id back revives the thread without a write.

| Document change                                                                       | Effect on a thread anchored there                                                                                                                                                                        | Why                                                                                                                                                                                                             |
| ------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `block.remove`, `slide.remove` (`reduce.ts:144-162, 229-288`)                         | The thread stays in the sidecar; `resolveAnchor` reports `orphaned`; the panel lists it under its slide (or under "Removed slides" when the slide is gone) with the quoted text; no marker on the canvas | Google's anchors "are lost when the object is deleted" and the Drive API treats an unresolvable anchor as unanchored (01 section 3); Turboslide keeps the words because a review comment is still worth reading |
| Undo of the removal                                                                   | The inverse is a `slide.insert` or `block.insert` with the same id (`reduce.ts:147-162, 261-288`), so the anchor resolves again                                                                          | Ids are the identity (`packages/schema/src/ids.ts:1-4`)                                                                                                                                                         |
| `slide.replace` (`reduce.ts:198`)                                                     | Threads on blocks whose ids survive stay anchored; the others orphan; the text range is re-checked against the new Text and clamped to its length                                                        | The source drawer's Apply and the canvas conversion both keep ids (`docs/freeform.md:88`)                                                                                                                       |
| `block.move` into or out of a group (`block.group` writes `pos.group` on each member) | Unchanged                                                                                                                                                                                                | A group is a tag on the members, not a new block (`position.ts:28-29`)                                                                                                                                          |
| `version.restore` (`reduce.ts:383-392`)                                               | It is a `diffDecks` of ordinary mutations, so removed ids orphan and restored ids revive, and text ranges shift through the same path as any `text.replace`                                              | No special case                                                                                                                                                                                                 |
| `slide.import` from another deck                                                      | Colliding ids are renamed (`actions.ts:1049-1082`); the source deck's threads never come along (section 7.3)                                                                                             | Google does not carry comments across files (01 section 3)                                                                                                                                                      |
| `deck.copy`                                                                           | Thread ids and slide ids are kept in the copy, so anchors resolve in the copy                                                                                                                            | Section 7.2                                                                                                                                                                                                     |

Text ranges under concurrent `text.replace`: report 02 3.3 makes `text.replace` a plain text offset operation transformed at admission, and 7.5 shifts `text.style` ranges "around concurrent inserts and deletes". A `text` anchor is exactly such a range with no mark, so it shifts through the same function: an insert before `start` moves both ends, an insert inside grows the range, a delete before shrinks the offsets, a delete overlapping the range trims it, a delete covering the whole range collapses it to `[start, start]`, which `resolveAnchor` reports as `orphaned: text removed` while keeping `quoted`. The shift is applied where text operations are admitted: in the stream's admission step (02 7.3) the server loads the slide's threads from the index and emits one `comment.shift` entry per changed anchor on the same stream (section 3); on a checkout, `FileStore.write` runs the same `shiftAnchors(threads, write.mutations)` inside its lock after `applyWrite` succeeds (`packages/store/src/file-store.ts:243-261` is where the log entry is written) and rewrites the touched thread files. A whole Text rewrite through `block.set` or `slide.set` (an agent, a paste) is last writer wins for the string (02 7.5); anchors on it are re-placed by `textDiff` when the diff finds the quoted text once, else orphaned with the quote kept.

### 1.3 Sizes and caps

Measured on the shapes above with canonical JSON (the store writes `canonicalJson`, `packages/store/src/versions.ts:62`): a `block` anchor is about 90 bytes, a `text` anchor about 220 bytes with a 60 character quote, an author about 110 bytes (a 36 character UUID, a 20 character label, the kind), a comment with a 120 character body and no reactions about 330 bytes. A typical thread (one comment, two replies, no reactions) is about 1.2 KB; a thread with the caps below reached (4,000 character body, 100 comments, 24 reactions with 20 principals each) is about 480 KB, which is why the caps are where they are.

| Cap                 | Value                                                        | Reason                                                                                                                                                                                        |
| ------------------- | ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Body length         | 4,000 code points                                            | Above any review sentence; Liveblocks caps a metadata value at 4,000 characters, the nearest published number for comment sized strings (L4); Google's limit is not published (01 Unverified) |
| Mentions per body   | 20                                                           | A review rarely names more than the room                                                                                                                                                      |
| Replies per thread  | 100                                                          | Google's number is unknown; Liveblocks groups at most 50 activities per inbox notification (L5), a comparable scale                                                                           |
| Threads per slide   | 200                                                          | Keeps a slide's index entry list under 40 KB                                                                                                                                                  |
| Threads per deck    | 5,000                                                        | At 1.2 KB typical that is 6 MB, under the 25 MB of documents per deck 04 7.5 sets                                                                                                             |
| Reactions           | 24 emoji from a fixed palette, any number of principals each | The palette is data                                                                                                                                                                           |
| Quoted text         | 200 code points                                              | Enough to recognise the passage                                                                                                                                                               |
| Comments per minute | 10 anonymous, 30 signed in, 60 agent                         | 04 7.5's row, unchanged                                                                                                                                                                       |

### 2.2 The sidecar's layout

```
decks/<id>/comments/index.json          { revision, updatedAt, threads: [{ id, slideId?, kind, open, updatedAt, count, assignee? }] }
decks/<id>/comments/<threadId>.json     one Thread, canonical JSON
decks/<id>/comments/authors.json        principalId to the last label and kind seen (the export's author list, section 7.4)
```

The folder is a first class deck folder like `slides/` and `versions/`: `listDeckFiles` (`packages/store/src/bundle.ts:123-154`) gains a `comments` group (section 7.1), `isMirroredDocument` (`packages/store/src/blob-store.ts:148-157`) already accepts any safe key that is not an asset, a snapshot, a lease or `.turboslide/`, so the mirror pulls it; `localDocuments` (`blob-store.ts:199-215`) gains `comments` beside `slides` and `versions`.

Git. The repository is public and the deck folders are committed (`decks/gt-brand`); a comment names people by label and says what they thought of a slide. Decision: `.gitignore` gains `decks/*/comments/` in this repository, so a checkout's comments stay local by default, and `AGENTS.md` records that a private checkout of decks may remove the line. The folder is not `.turboslide/` state, because state is derived and never travels (`docs/deck-transfer.md` section 1), while comments are authored and must travel by `deck push` and `deck pull` (section 7.1). The alternative, committing comments, is a one line change a team with a private deck repository can make.

Blob. The private store 04 P9 asks for is where `comments/` belongs once it exists; until then the files sit under the deck's prefix on the public store as `deck.json` does today, which 04 F1 already rates as the exposure to fix first. Keys: `decks/<id>/comments/index.json`, `decks/<id>/comments/<threadId>.json`, `decks/<id>/comments/authors.json`. `ifMatch` is used on one key, `index.json`, as the commit point, the pattern of `deck.json` (`blob-store.ts:672-675`); thread files are overwritten in place after it (the CDN's stale body window of 02 1.3 is closed by the same proof the mirror uses for slides: the thread file's etag is the md5 of the bytes the index names in `threads[].etag`). A reader that finds a stale thread body re-fetches with `useCache: false`; on the public store that flag does not bypass the CDN (02 1.3), so the reader replays from the stream instead, as `pull()` replays version records today (`blob-store.ts:322-338`).

### 2.3 The write path on both stores and the Blob operation count

FileStore (a checkout, `turboslide mcp` on stdio, the tmp overlay): a comment action loads `index.json` and the thread under the deck's `.turboslide/write.lock` (`file-store.ts:136-173, 202`), applies the operation with the rules of 3.2, bumps `index.revision`, writes the thread file and `index.json` last (the order `writeSlideFiles` then `writeManifest` uses, `file-store.ts:249-261`), and `fs.watch` reports `comments/<threadId>.json` and `comments/index.json` (`packages/store/src/watch.ts:56-62`; nothing under `comments/` is ignored).

BlobStore (hosted): the operation is admitted through the room of 02 7.2 as an `op` with `kind: 'comment'`; the checkpointer of 02 7.1 takes the comment entries since the last checkpoint, applies them to the mirror's `comments/` folder, then pushes the changed thread files (one `put` each), `authors.json` when a new label appeared, and `index.json` with `ifMatch` last. A single comment costs 2 advanced operations (thread, index); a burst of n comments inside one checkpoint window costs at most n plus 2. Against the cap 02 1.3 records, 75 advanced operations per second on Pro for the whole deployment, a review session of ten people leaving one comment every ten seconds is 0.2 operations per second, and a checkpoint every 2 to 10 seconds keeps a deck under 1 operation per second in any burst. Cost: at $5 per million advanced operations (02 V5), 10,000 comments a month is about 2 to 3 cents.

Without Redis (the `blob` tier of 02 7.7) a comment action writes the sidecar through the BlobStore directly, one `put` for the thread and one for the index with `ifMatch`; a precondition failure re-pulls the index and re-applies, and because every comment operation commutes or has a defined winner (3.2), the retry always lands. The checkout needs neither.

### 2.4 How the checkpointer treats comment operations

One stream per deck (`deck:<id>:ops`, 02 7.1) carries two entry kinds: `kind: 'edit'` (the mutation lists 02 designed) and `kind: 'comment'` (one `CommentOp` of 3.2 per entry, with the thread id, the author and the op's payload). One stream, not two, so a tab receives edits and comments in one order and a `comment.shift` (1.2) follows the text operation that caused it. The checkpointer coalesces edits into version records as 02 7.1 says and comment entries into sidecar writes; it never writes a version record for a comment, and `index.revision` is the comments' own counter, independent of `deck.revision`. `VersionRecord` gains nothing. The `checkpoint` message of 02 7.2 gains `comments: { revision, threadIds }` so a client knows which threads to refetch or, since the entries carry the full ops, has already applied them.

### 2.5 The version log, Copy comments, undo of a delete, and the deck level actions

The log stays free of comments by construction (2.4). "Copy comments" on Make a copy (01 section 3) is `deck.copy { copyComments: true }` (section 7.2): `copyDeck` copies the `comments/` folder after the slides, keeps thread ids (the copy is a new deck id, so ids cannot collide with anything), filters threads whose `slideId` is not in `slideIds` when a subset is copied, and drops `notes` anchored threads when `removeNotes` is set (`packages/store/src/templates.ts:467-522` is where the copy is assembled). Undo of a deleted comment is not an inverse mutation but a tombstone with a 30 day restore window: `comment.delete` writes `deleted: { at, by }` and moves the body to `deletedBody`, readable only by the deleting principal and the deck owner, so the snackbar's Undo and `comment.delete { restore: true }` bring it back; after 30 days a sweep removes `deletedBody` and the tombstone stays with the replies (the Drive API's "Deleted comments keep only a deleted flag", 01 section 3).

### 3.2 Conflict rules per comment operation

The rules follow the shape of 02 7.5. `CommentOp` is the payload of a `kind: 'comment'` entry; every op names `threadId` and carries the author from the session, never from the body (04 F2).

| Operation                                                                                       | Two concurrent writers                                                                                                                                       | Rule at admission                                                                                                                                                                                                                                                                                                                                        | Effect of `comment.shift` |
| ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------- |
| `add` (a new thread)                                                                            | Both threads exist; ids are ULIDs minted by the client and checked for uniqueness at admission                                                               | Append only; a duplicate id is a `reject` with the reason                                                                                                                                                                                                                                                                                                | none                      |
| `reply`                                                                                         | Both replies exist, in server order                                                                                                                          | Append only to `replies`; the `updatedAt` is the server's                                                                                                                                                                                                                                                                                                | none                      |

| `delete`                                                                                        | A tombstone; a concurrent reply to the deleted comment still lands in the thread                                                                             | Author or deck owner; deleting the first comment tombstones the thread's comment and keeps the replies (Google deletes the whole thread on the first comment, 01 section 3; Turboslide keeps the replies because they are other people's words, the choice Liveblocks makes: "Deleting a comment doesn't remove the comment object from the thread", L1) | none                      |

The conflict card of round one never appears for a comment.

### 3.3 What a reader in Viewing mode or with a viewer role sees

Viewing mode (View > Mode > Viewing, `packages/chrome/src/menus/model.ts:825-838`) is a per browser toggle on an editor's own deck; it hides handles and Format options and now also hides the Add comment controls while keeping the panel, markers and replies readable and reactable, since the person still has edit access (the Mode menu is about the risk of moving things, 01 section 4). A viewer role sees the markers, the filmstrip counts and the panel with resolved threads folded, cannot open the reply box, sees no reaction picker, and `comment.list` answers without `deletedBody`. Commenting mode is a third state of the same toggle: edit gestures refused, comment controls present.

Why the split by role: the autocomplete list is a disclosure. A commenter who can see every grantee learns the share list, which Google shows only in the Share dialog to people who may share (01 section 5, "Editors can change permissions and share"). A mention of an invitee produces the invitation email through report 09's path, and the notification of section 5 is written to the invitee's inbox the moment the principal exists.

### 4.2 Triggers, storage and rendering

The `@` and `+` triggers of 01 section 3 both open the autocomplete after a word boundary; `+` is kept because Google documents it, and both insert a token. The body stores `{@n}` where `n` indexes `mentions`; the text around it is plain. The client never sends the display string, only the mention record (04 8.1: "mentions in comments store identity ids, not names"); the server checks each mention against the cases above and refuses the comment with `invalid_input` at `/body/mentions/<n>` when the caller may not name that party. Rendering resolves each mention at read time and emits a React text node inside a `<span class="ts-mention">`, never `innerHTML` (04 F4 rule 3 for links applies to mentions: no scheme, no href, a click opens the person's chip in the roster). A body with a URL in its text renders the URL as text with a "Open" affordance that goes through the link scheme check of 04 F4 (https, http, mailto, tel), never as a raw anchor. Copy, TXT export and the PPTX comment text render mentions as `@` plus the current label.

## 5 Notifications inside the app

Google routes comment notifications to Gmail and documents no centre inside the editor (01 section 3, "In app notification centre: None found"). Kevin asked for notifications inside the app, so this is Turboslide's own design; the reference models read for it are Liveblocks' inbox notifications, which group "new comments in a thread" into one notification with a `readAt` timestamp and up to 50 activities per notification (L2, L5), Linear's Inbox with read and unread, snooze and a 2,000 open notification cap (L6), Notion's Inbox with Archive and per page levels "All updates", "All comments", "Replies and @mentions" (L7), and Figma's in app notifications for mentions (L3).

### 5.2 The inbox and where it lives

One record shape: `{ id, principalId, kind, deckId, threadId?, slideId?, actors: principalId[], count, createdAt, updatedAt, readAt? }`, at most 500 per principal, the newest kept. Two homes behind one `Inbox` interface in `packages/store`:

- Anonymous principals: Redis, `inbox:<principalId>` as a sorted set scored by `updatedAt` with the record as the member, `inbox:<principalId>:unread` a counter, `EXPIRE` 30 days refreshed on every write. An anonymous person whose cookie is gone loses the inbox with the identity, which is the anonymous animal's fate 03 Part G accepts. On a checkout the same interface runs in process memory with a JSON mirror under `.turboslide/inbox/<principalId>.json` so `turboslide notification list` works with no server; the file is derived state and never travels.
- Signed in principals: the identity database of 03 Part D (Neon Postgres hosted, `node:sqlite` on a checkout), table `inbox_notification` with an index on `(principalId, readAt, updatedAt)`, and the Redis counter for the unread badge so the title row never queries Postgres per poll. Linking (03 E2) moves the anonymous sorted set into the table once.

Delivery to an open tab: the presence channel of 02 7.6 carries a `inbox { principalId, unread }` event to that principal's connections, so the plate updates without a poll; a tab that reconnects reads `notification.list { since }`.

Read state: `readAt` per record; opening a thread marks its notifications read, and marking a notification read opens nothing (Liveblocks' two way rule, L2, is adopted in one direction: thread to notification). "Mark all read" is `notification.markRead { all: true }`. Records are never deleted by the person; they age out at 500 or, for anonymous principals, at 30 days. Snooze is not built; Linear's `H` (L6) is noted as the reference if it is asked for.

### 5.3 The plate in the title row

05 rule 4 requires a fixed slot. The title row (`packages/chrome/src/TitleRow.tsx:279-312`) gains an inbox `ToolButton` between the comments glyph and Slideshow, in a slot sized for the glyph plus a two digit count (`--pt-inbox-w`), present whether the count is zero or not; the count chip uses tabular figures with `min-width` for two digits and reads `99+` beyond (05 rule 5). The button opens the inbox as a right panel (`PanelId` `'inbox'`, title "Notifications", `packages/chrome/src/editor-shell.ts:340-350`), one frame with the refit (05 rule 8). Each row: the actor's mark, one sentence ("Maya replied on slide 4", "Kai mentioned you"), the relative time in a fixed tabular width, and a click that runs `comment.link`'s target (section 8). A "Notification settings" row at the panel's foot opens the per deck dialog, the position Google gives it (01 section 3).

### 5.4 The per deck setting

Google's three levels under "Comments" are adopted verbatim: All comments, Comments for you, None (01 section 3; research/10 A12). No "Edits" section, since Slides has none. The setting is per principal per deck (`notification.settings`), stored beside the inbox; the default is Comments for you for everyone except the deck's owner, who defaults to All comments. Whether Google's default for the owner is All comments is not on the pages read (section 12). The dialog is reachable from Tools > Notification settings and from the inbox panel's foot, and every email carries a "Notification settings" link to it (01 section 3 lists that link in each mail).

### 5.5 Email

Email goes only to signed in principals (an anonymous principal has no address, 03 B2), through the Resend account 03 C2 chose, with the same three levels and a per kind rule: `mention`, `reply`, `assigned`, `resolved`, `accessRequest` and `granted` may mail; `reaction`, `versionNamed` and `comment` under "All comments" never mail but do reach the inbox. Resend "doesn't manage contact lists for transactional emails", so the `List-Unsubscribe` header is added "when sending emails" through the `headers` parameter, with `List-Unsubscribe-Post: List-Unsubscribe=One-Click` and an endpoint that answers a POST from the same URL with 200 or 202, and the person must "stop receiving email within 48 hours" (R1, read 2026-09-13). Turboslide's unsubscribe URL carries a signed token for the principal and sets every deck's level to None for email while leaving the inbox on; the same page offers the per deck levels.

Coalescing: a burst is one message. Per principal per deck, the first mailable event opens a 15 minute window; every later event in the window joins the digest; the mail goes at the window's end with one line per thread and one line per mention, and the subject names the deck. A direct mention shortens its own window to 2 minutes so a "look at this now" arrives now. An event on a thread the person opened in the app during the window is dropped from the digest (the inbox record is read).

### 5.6 The numbers

Redis commands per notification: `ZADD` the record, `ZREMRANGEBYRANK` to keep 500, `INCR` the unread counter, `EXPIRE` twice (set and counter), `PUBLISH` to the principal's connections, and one `SET NX PX` for the digest window when email applies: 6 to 7 commands per recipient. A reply that notifies two people is about 14 commands. A ten person sales team leaving 200 comments a working day with two recipients each is 400 notifications, about 2,800 commands a day, 62,000 a month: a fraction of Upstash's 500,000 free commands (02 T7), and small beside the presence traffic 02 7.10 counts.

Email against Resend's free tier of 100 a day and 3,000 a month (03 R1): 400 notifications a day, half of them mailable kinds, coalesced per person per deck into 15 minute digests, is in practice one digest per active hour per person per deck. Ten people reviewing two decks over a four hour session is at most 80 digests, under 100, and the cap below keeps it there; 22 working days at 60 to 80 mails is 1,300 to 1,800 a month, under 3,000. The cap per person per day is 10 mails; the eleventh event of the day joins one end of day summary at 18:00 in the person's time zone, so a team of ten can never send more than 110 mails a day. When the account's daily count reaches 90 the remaining digests wait for the next day and the inbox carries them meanwhile; the Pro plan (03 R1) removes the constraint if the team grows.

## 6 Version history by author, Show changes and activity

### 6.1 Grouping the records

What exists: `VersionsPanel` groups records by day, newest first, with "Only show named versions", "Restore this version", a More menu with "Name this version" and "Make a copy", and a "Show changes" row stubbed Later (`packages/chrome/src/VersionsPanel.tsx:71-85, 87-106, 165-325`); a record's author prints as its label unless it is `studio` (`VersionsPanel.tsx:255-257`); the Last edit clock names the current tab's author, not the record's (`TitleRow.tsx:169-190`; 07 3.3). The per author mark is one interface report 11 owns and this report consumes: `resolvePrincipal(principalId | Author) → { label, colour, avatar, kind, deleted?: true }`, backed by the alias table of 03 E2 so a record written before sign in renders as the person, and by the stored label when nothing resolves. ### 6.2 Show changes as data

`version.diff` (section 8) is `diff.run` (`packages/schema/src/actions.ts:1664-1711`) with two additions: the output groups the mutation list by touched block (`touchedSlides` names the slides, `packages/store/src/store.ts:136-163`; the block ids come from each mutation's `blockId`) and attributes each group to the author of the record that carried the mutation, so the panel can colour outlines per author. `from` and `to` are record numbers or revisions; `staged` keeps its meaning. The panel's "Show changes" checkbox (Google's is at the bottom of the panel, 01 section 6) selects a record and runs `version.diff { from: previous record of the window, to: selected }`; the editor draws an outline in the author's colour around each touched block in the stage's overlay layer (05 rule 4: an absolute overlay, no flow change), a filled rail beside a touched slide in the filmstrip, and a "removed here" ghost box from the inverse mutations for blocks the version deleted. Text changes inside a block show the block outline only; a per run diff is out of scope. Turning the checkbox off clears the overlay; selecting another record re-runs the action. The `VersionsPanel` stub row `version.showChanges` (`VersionsPanel.tsx:100-105`) and the foot sentence (`:315-324`) flip to Now; SPEC-2 12's row "Show changes" is discharged.

The Comment trend is the one tab with data Turboslide holds: `activity.list { kind: 'comment', since }` gives the counts, and the panel draws a small bar of new threads, replies and unresolved threads per day from it. The Tools row reads "Activity" and its Viewers section is omitted with the clause "Turboslide keeps no record of who viewed a presentation".

## 7 Transfer and export

### 7.1 The bundle

The bundle manifest carries `documents` and `assets` as maps from a path relative to the deck directory to `{ bytes, sha256 }`, `bundleVersion` 1, and the reader refuses any entry not listed and any listed entry that is missing or whose digest differs (`packages/store/src/bundle.ts:28-39, 83-111`; `unpack.ts:85-121`). Comment files are JSON documents under the deck directory, so they fit the `documents` group as they stand: `listDeckFiles` gains a `comments` folder walk beside `slides` and `versions` (`bundle.ts:131-140`), gated by `options.comments` (default off for `deck pack`, on for `deck push` and `deck pull`), and `bundleVersion` stays 1, so a studio at `61b16e4` unpacks a bundle that carries comments byte for byte without reading them (`unpack.ts:237-248` writes every document under its path). `inspectBundle` gains one validation pass when `comments/` entries are present: `index.json` parses with `commentsIndexSchema`, every thread it lists is present and every `comments/<id>.json` is listed, each thread parses with `threadSchema` (the body cap, the mention cap, the label rule of 1.1), `authors.json` parses, and a thread whose `slideId` is not in the deck is kept (it is an orphan, 1.2), never a refusal. The manifest gains an informational `counts.comments`.

Why `deck pack` defaults off: a bundle is what the `/decks` page hands anyone who can reach it (`docs/deck-transfer.md` section 5), and comments name people. `deck push` and `deck pull` move a person's own work between their checkout and their studio, so they carry comments unless `--no-comments`. The hosted routes: `GET /api/decks/:id/bundle` includes `comments/` only for a bearer holder or a ticket minted for an editor or owner (04 8.1 roles; the ticket already binds a purpose and a subject, `deck-transfer.md` section 3) and when `?comments=1`; `POST /api/decks/bundle` accepts them from anyone who may create a deck, since the bundle's comments become the new deck's comments under the uploader's ownership.

### 7.2 `deck.copy` and `deck.pull`

`deck.copy { copyComments?: boolean }` copies the folder as 2.5 says; the CLI flag is `--copy-comments`; the Make a copy dialog (`packages/chrome/src/dialogs/MakeCopy.tsx`) gains the "Copy comments" checkbox under "Remove speaker notes", unticked, Google's dialog order (01 section 3). `deck.pull --as <id>` keeps thread ids and rewrites nothing inside them: a thread's `deckId` is rewritten to the new id in canonical form the way `deck.json`'s id is (`unpack.ts:238-246`).

### 7.3 `slide.import`

Google does not carry comments across files (01 section 3). `slide.import` copies slides and renames colliding ids (`actions.ts:1049-1082`); it never reads the source deck's `comments/`, and its output gains nothing. A reviewer who wants the discussion moves the deck, not the slides.

### 7.4 PPTX

pptxgenjs 4.0.1, the version installed (`node_modules/.pnpm/pptxgenjs@4.0.1/node_modules/pptxgenjs/package.json`), exposes `addNotes` (`types/index.d.ts:2650`) and no symbol containing "comment" anywhere in its type definitions (a case insensitive search of the installed `types/index.d.ts` finds none; read 2026-09-13). Its issue tracker's one entry on the subject, #33 "Support for adding comments/notes to a slide", was closed in February 2017 (G1); the feature that came of it is notes. So the exporter writes the comment parts itself in the OOXML post process it already runs after pptxgenjs (`packages/export/src/pptx/build.ts:9-12, 26-38`; `docs/pptx.md` "The OOXML post-process and the package validation"), with `openPackage`, `readPart`, `writePart` and `writePackage` (`packages/export/src/ooxml/zip.ts:9-63`).

The parts, from ISO/IEC 29500 as Microsoft's Open XML SDK reference quotes it (O1, O2, O3, read 2026-09-13):

| Part                                                      | Root                                                                                                                                                                                                           | Content type                                                                           | Relationship                                                                                                                                      | Owner                             |
| --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------- |
| `ppt/comments/comment<N>.xml`, one per slide with threads | `p:cmLst`, "a list of comments for a particular slide" (O1)                                                                                                                                                    | `application/vnd.openxmlformats-officedocument.presentationml.comments+xml` (P1)       | `http://schemas.openxmlformats.org/officeDocument/2006/relationships/comments` from the slide part (P1; O4 names `SlideCommentsPart` as the part) | the slide's `.rels`               |
| `ppt/commentAuthors.xml`                                  | `p:cmAuthorLst`, "a list of authors with comments in the current document. Each comment in a document shall refer to an author in this list"; an author matches when "name and initials shall both match" (O2) | `application/vnd.openxmlformats-officedocument.presentationml.commentAuthors+xml` (P1) | `http://schemas.openxmlformats.org/officeDocument/2006/relationships/commentAuthors` from the presentation part (P1; O5)                          | `ppt/_rels/presentation.xml.rels` |

Each `p:cm` carries `authorId` ("refers to the ID of an author in the comment author list"), `dt` ("the date and time this comment was last modified") and `idx` ("unique within a list of all comments by this author in this document. An author's first comment in a document has index 1"), with children `p:pos` and `p:text` (O3). `authors.json` (2.2) is the author list: one `p:cmAuthor` per principal that wrote a comment in the exported slides, `name` the current label through `resolvePrincipal`, `initials` derived from it, `clrIdx` the principal's colour index, `lastIdx` the count. Each thread is one `p:cm` whose text is the first comment's body; each reply is a further `p:cm` by its own author whose text is prefixed "Re: " and the thread's first eight words, because the classic comment list has no threading element in ISO/IEC 29500 itself; PowerPoint's later threading extension inside `p:extLst` is a candidate the build verifies against a PowerPoint saved file before writing it (section 12). A resolved thread is written with "[Resolved] " before the text; a mention renders as `@` plus the label; a tombstone is skipped. `p:pos` is the block's top left from its `pos` or its measured box in the unit PowerPoint writes; the page read gives an example (`x="10" y="10"`, `x="1426" y="660"`) without naming the unit, so the unit is verified in the build and listed in section 12.

Both modes write the same parts: the Perfect (flatten) file is a raster per page plus invisible text and the parts are package level, not drawing level, so the page raster stays pixel identical; the Editable file adds them beside its native shapes. Comments travel only when the caller may see them: `export.run` gains `includeComments` (default true for an editor or owner, false and refused otherwise, the role check 04 F21 asks for on `includeNotes`), and a hosted export for a viewer never carries them. The residual gains one line per file: `comments: 14 threads on 6 slides as PowerPoint comments (authors 3, replies flattened, resolved marked)` or `comments: none` or `comments: omitted by request`.

Verification: `validatePackage` (`packages/export/src/ooxml/validate.ts`) already asserts that every part has a content type and every relationship resolves, so the two overrides and the relationships are checked on every export. python-pptx knows the part's content type and relationship type as constants (P1) but its Slide API exposes no comments property (its documented properties are `background`, `element`, `follow_master_background`, `has_notes_slide`, `name`, `notes_slide`, `placeholders`, `shapes`, `slide_id`, `slide_layout`, P2), so the interpreter step of `export check` (`packages/export/src/check.ts:72-89`, `from pptx import Presentation`) gains a second pass with the standard library only: open the file with `zipfile`, parse `ppt/commentAuthors.xml` and every `ppt/comments/*.xml` with `xml.etree`, count `p:cm` per slide part through the slide `.rels`, and assert every `authorId` names an author; the counts join the check's JSON and the read back line. LibreOffice's PDF conversion in the verify loop ignores comment parts, which is what the pixel comparison needs.

### 7.5 PDF and print

Google Docs offers "Print comments"; the Slides print settings of round one (`apps/studio/src/routes/print.$deckId.tsx:83-94`: slides with or without notes, handouts Later) offer nothing of the kind, and the PDF path already states "notes never travel" in its residual (`packages/export/src/pdf/build.ts:284`). Decision: the PDF and print routes never carry comments, and the PDF residual line becomes `notes and comments never travel`. A reviewer who wants a printed thread list uses TXT.

### 7.6 Standalone HTML and TXT

`build.run` reads the document and the assets and never the sidecar; the standalone file ships no comment and no author, and its report says `comments: never travel`. `export.text` (`actions.ts:1974-1996`) gains `includeComments` (off by default, `--include-comments` on the CLI): after a slide's notes it appends `Comments:` and one line per comment, `<label> (<time>): <text>`, replies indented by two spaces, resolved threads marked `[Resolved]`, tombstones omitted; the output shape gains `comments: number`.

## 10 Rules applied

Layout shift (05 section 4): the comments glyph, the inbox plate and their count chips sit in fixed slots of the title row that exist at zero (rule 4); the comment count on a thumbnail and the unread count use tabular figures with a two digit `min-width` (rule 5); the comments panel, the inbox panel and the activity panel are the right panel of 320 px (`packages/chrome/src/Panel.tsx:10-16`), one frame with the refit (rule 8); a card on the canvas and every marker are absolute layers in the stage overlay (rule 4); the lists set `content-visibility: auto` with `cqw` placeholders derived from the panel width, or set neither (rule 6); relative times in the panel and the inbox are tabular and fixed width (rule 5); the version history's window rows carry the author marks in a fixed width strip sized for four marks and a "+N" (rule 4); a "follow" or a `comment.link` jump changes the active slide and scrolls the filmstrip, never a track (rule 9).

Security (04): a body is plain text with mention tokens and renders through React text nodes, never `innerHTML` (04 8.1, F4); labels are capped at 40 code points and sanitized (03 B3); bodies are capped at 4,000 code points, mentions at 20, replies at 100, threads at 200 per slide and 5,000 per deck (1.3); URLs inside a body are text with an "Open" affordance that passes the scheme check of 04 F4 (https, http, mailto, tel) and `rel="noopener noreferrer"`; comments per minute follow 04 7.5 (10, 30, 60) and every refusal is a 429 with `Retry-After`; every comment, notification and activity route is a server function or a server route under the CSRF middleware, a POST for every state change (04 8.2); the author is the session's or the token's principal (04 F2); `comment.list` never returns `deletedBody` to anyone but the deleting principal and the owner; the activity feed is the security log filtered by deck and read by editors (04 8.11); the unsubscribe endpoint validates a signed token and never takes an address from the query (03 C2's URL token rules); mention autocomplete discloses grantees to editors only (4.1).

Privacy (03 Part G): an anonymous principal's comments live as long as the deck and render by the stored label once nobody can resolve the id; a signed in principal who deletes the account keeps the comments in the deck under the label "Deleted account" with a neutral mark, the body untouched, because the thread is the deck owner's record of a review and the person can delete their own comments before the account (`comment.delete` is author or owner); the inbox of a deleted account is removed with the sessions in `afterDelete`; an anonymous inbox expires 30 days after its last write; no view is ever recorded (6.5); logs name principal ids, never emails, and the comment bodies never enter a log line.
