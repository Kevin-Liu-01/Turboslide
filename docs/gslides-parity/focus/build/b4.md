## 1. What landed

### 1.1 The probe's `--core` mode (6.1)

`node scripts/probes/editor-walk-probe.mjs --core --base <origin> --json <path> [--matrix <path>] [--parked docs/gslides-parity/focus/ship-<commit>.json] [--only <areas>] [--shots <dir>] [--headed]`.

- The flag `--core` beside `--base`, `--json`, `--shots`, `--quick` and `--headed`. With it the probe hands its helpers (the human pace, the product reads, the menus and controls) to `scripts/probes/core-walk/index.mjs` and runs the core walk instead of the parity walk; without it the parity walk runs as before, byte for byte in behaviour (the hook sits before the parity walk's browser launch and returns through `process.exit`).
- The core walk is its own walk over the same helpers, pace, scratch deck from `/new` and finally block, rather than tags on the parity walk's 800 steps: the parity walk drives every kind the Insert menu offers (icons, materials, tables, charts, diagrams, groups, the theme panel), which are parked features, and would take the better part of an hour to prove rows the matrix does not hold. The decision is recorded in section 5.
- `toolkit.mjs`: `step(id, name, expected, fn)` writes the row id as `id` in the JSON row; a row with several tagged steps (the eight handles, the two appearances) passes only when every step passed, else it is failed when any failed, else not driven. `setup(name, ...)` is untagged; when it fails it throws `SetupFailed` and `section(area, ids, fn)` records every declared row not yet driven as not driven with the reason `setup failed: <step>` (the cascade of 6.1). An exception outside a step is a failed untagged row and the remaining rows of the section are not driven with its message.
- "No step": after the walk, every probe row with no tagged step reads `no step` in the table and fails the run whatever the parked list says. `scripts/probes/core-walk.test.mjs` asserts before any run that every probe row is declared by exactly one area (or the finally block) and that no area declares a row another driver carries.
- The exit code: `shipVerdict(results, parked, probeRows())` over the probe's rows alone (the matrix module's `shipVerdict` and `parkedFeaturesOf` took an optional `rows` argument for this), plus 1 on any `no step` or on a failed untagged step that is not a setup step. `--parked` reads `ship-<commit>.json` through the new `readParkedList` (the `surface` feature refused).
- The JSON: `mode: 'core'`, the rows with their ids, and `core: { rows, passed, failed, notDriven, noStep, results, table, verdict, untaggedFailures, exitCode }`. `--matrix <path>` writes the table of every probe row (id, feature, today, result, reason, steps).
- The finally block proves `decks.editor.move-to-trash` (File > Move to trash, the address moves to `/decks`, the card is not listed) and `surface.cleanup` (Delete forever on `/decks/trash`, then 404 on `/edit/<id>` and `/deck/<id>` within 20 s), with the actions API as the fallback for the record and the 404 asserted either way. A partial run (`--only`) tears its deck down quietly and exits 1 on the `no step` rows, so it is never mistaken for a gate run.

### F3: `core-gate.mjs` crashed after the specs on every run

The mechanism: line 315 read `value('matrix')` while the file defines `arg`; the `--matrix` option had been added by the integrator's edit with a helper the file never had. The crash came after `core-gate.json` was written and before `core-matrix.md`, the ledger copy and the verdict line, so every gate run exited 1 by the exception whatever the rows said.

The fix, in `scripts/probes/core-gate.mjs`: `MATRIX_OUT` is read once at the top with `arg('matrix', null)` beside the other options. The tail is now testable without a browser: `--report <dir>` runs no driver and renders the merge, the table, the ledger copy and the verdict from a finished run's `core-walk.json` and `specs.json` (the two readers `readProbe` and `readSpecs` are the run functions' own tails, factored out). `scripts/probes/core-gate.test.mjs` (new, in the root vitest project `scripts`) runs the gate over a stub Playwright JSON report three times: every spec row passed (exit 0, `core-gate.json`, `core-matrix.md` with every row id, the `--matrix` copy byte equal to the JSON, the verdict line `verdict ok; retries zero`), one `decks` row failed (exit 1, the row listed under "Failed rows" with its reason, `failing the gate: <id> (failed)` printed, `decks` in `wouldPark`), and one row nobody drove (exit 1, `## No step`). ### F7: the core walk broke at row 142 and never recovered

The mechanism, two parts. (1) `toolkit.mjs step()` recorded a thrown step as failed and moved on with the page as the step left it: `menuPath` had opened the Format menu and timed out on a submenu, nothing closed the menu, and every later click landed on the scrim. (2) `text.persistence.reload` (and `text.layout-runs.type`, `shapes.reload-and-viewer`) navigated to `/edit/<id>#s/<slide>` from an `/edit/<id>` address, which is a same document hash change the app handles without a load (13 to 48 ms in the verifier's runs), so the "reload" never reset the page and its facts were read from the broken state.

By hand on the preview (`repro-preview-fs.json`): the Size submenu opens on a list block made by the toolbar with the walk's own approach path (the pointer starts 20 px left of the Size row, over `menu.format.image` of the parent menu, and moves in six steps) three times of three, so the row's first failure at row 142 is not reproduced by the approach alone. Under the gate on this lane's 4364 server (the ledger below) rows 142 and 143 (`text.format-menu.size-increase`, `.size-decrease`) failed again with the Size submenu never drawn within 6 s of either hover, in the state rows 131 to 141 leave (a bulleted list box after the toolbar, menu and chord list rows, the indent rows, two link rows, Clear formatting and Format > Text opened once), and row 144 (`text.format-menu.align-left`) passed right after: the walk recovers and the cascade of F7 is gone. What the Size submenu meets in that state is still open and is the two rows' own question (the same rows fail on the preview by the verifier's runs and pass by hand on a fresh box); a screenshot of the failed state lands with `--shots` for the next look.

The fix, in `scripts/probes/core-walk/toolkit.mjs` and the areas: `step()` calls `t.recover(row, threw)` after every step that did not pass. With `--shots` the failed state is captured first (`<n>-<id>-failed.png`; F16 wrote nothing because no area called `shot`). A menu or a right click menu left open is closed with Escape (up to three); a step that threw also closes a dialog and a text session it left open, since its flow never reached the point where it would have; a judged failure (`ok: false`) keeps its selection, so a later check of the same row still finds its object. `menuPath` hovers a parent row once more from the row's own left edge when its submenu has not opened in 6 s, and fails the row when the second hover shows nothing. `text.persistence.reload`, `text.layout-runs.type` and `shapes.reload-and-viewer` reload through `t.reloadTo` (about:blank first, then the address, then `editorReady`). Two driver faults b3.md 7.1 handed to this lane are fixed on the way: `lines.tail.colour-weight-dash-ends` and `lines.context.line` read the stored fields `lineStart` and `lineEnd` (either spelling), and `shapes.default-look` reads the ground from the first painted ancestor of the transparent `.pt-slide`.

### F8: `core/share.spec.ts` failed every row at `closeShare`

The mechanism, reproduced by hand on the preview (`repro-preview-2.json`, scenario `share-copy`): on a freshly opened Share dialog the focus sits on the first field (`dialog.share.emails`) and Escape closes it at once (three trials, 1 ms); after a Copy link the focus has left the dialog (`document.activeElement` is the body: the copy re-renders the rows while the link is minted and the clicked button loses focus) and Escape then reaches nothing, because the Dialog's key handler is `onKeyDown` on its card (`packages/chrome/src/Dialog.tsx`). The dialog stays open until Done or the X is clicked. The spec's `copyRow` pressed Escape after every copy, so `share.dialog.open` hung 5 s and every row behind `readLinks()` failed with it.
