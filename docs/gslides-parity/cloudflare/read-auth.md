## 1. What the database is for and which engines the code runs

### 1.1 The tables

The identity database holds two sets of tables (`apps/studio/src/server/auth/schema.ts` 1 to 20, 124 to 134):

- better-auth's own: `user`, `session`, `account`, `verification`, and the device authorization plugin's device code table, migrated by the library itself (`better-auth.ts` 383 to 386 `getMigrations(auth.options)`; `identity.ts` 301 to 303 runs it at boot and every database read awaits `runtime.ready`, 141 to 142).
- Turboslide's own, migrated by Kysely's schema builder so one statement set serves SQLite and Postgres (`schema.ts` 146 to 213): `ts_alias` (anonymous id to user id, `alias.ts` 1 to 6), `ts_api_key` (the agent tokens, `tokens.ts` 1 to 7), `ts_profile` (the admin flag, the avatar choice, the avatar key, the deletion stamp, `profile.ts` 1 to 5), `ts_mail` (the captured mail under `TURBOSLIDE_MAIL=capture`, `mail/mailer.ts` 143 to 148), `ts_quota` (counters with a reset time, `quota.ts` 1 to 6). Booleans are integers and dates ISO strings in every Turboslide table on both engines (`schema.ts` 19 to 20).

Two things the account surfaces need are not in the database:

- The principal records (the typed name, the avatar choice, the link grants, the notification level, the live pointers, with a 90 day sliding TTL) live in Redis hosted and in a JSON file per principal under `.turboslide/principals/` on a checkout (`packages/identity/src/principal.ts` 1 to 13, 182 to 229; `apps/studio/src/server/auth/principal.ts` 1 to 6, 56 to 110). Since this round the hosted store follows the Redis binding the room module sets at boot and falls to the file store while none is bound (`identity.ts` 182 to 236; `room.ts` 276 to 280). Before this round the hosted principal store was a file per instance on every tier (`identity.ts` 187 to 189).
- The avatar picture files live on the public Blob store on the blob tier and under `<stateDir>/users/` otherwise (`avatar-tier.ts` 13 to 29); they are produced by `sharp`, a native addon reached on the server only (`avatar.ts` 19 to 20, 25).

### 1.2 The engines

`selectAuthDb` decides from the environment alone (`db.ts` 44 to 66): Postgres when `DATABASE_URL` is set (48 to 49), SQLite when `TURBOSLIDE_AUTH_DB` names a file (50 to 61), none otherwise (62 to 65). The SQLite choice is refused with a TypeError when `env.VERCEL` is set (52 to 55), because a hosted filesystem does not outlive the instance (41 to 42).

- Postgres: Kysely's `PostgresDialect` over `pg.Pool({ connectionString, max: 4 })` (`db.ts` 87 to 88). The pool is per instance; `docs/security.md` 403 records it as 4 connections per instance.
- SQLite: `node:sqlite`'s `DatabaseSync` with `journal_mode = wal`, `busy_timeout = 5000` and `foreign_keys = on` (`db.ts` 80 to 83) under the tree's own Kysely dialect (`sqlite-dialect.ts` 1 to 8): one connection, one statement at a time (84 to 93), the statement kind read from the SQL (23 to 25), booleans and dates bound by hand (29 to 39), no streaming (64 to 67).
- The raw SQLite handle is exported on the `AuthDb` for synchronous reads (`db.ts` 71 to 72): `tokens.ts` resolves a bearer without an await because the routes call `requireAgentAuth(request)` synchronously (`tokens.ts` 9 to 13); on Postgres the same store answers from a cache of every live key refreshed every 5 s and after each write in the process, so a revocation on another instance lands within 5 s (`tokens.ts` 37 to 38, 190 to 227). Any engine with no synchronous read takes the cache path.
- Versions installed: `better-auth` 1.7.4, `kysely` 0.29.5, `pg` 8.23.0, `ioredis` 6.0.0 (`apps/studio/package.json` 45 to 48 through the catalog; `node_modules/.pnpm/` listing).

### 1.3 Without a database

`runtime.auth` stays null (`identity.ts` 243, 268, 283), the Sign in row is absent with the sentence `NO_DATABASE_NOTICE` (`db.ts` 23 to 25; `better-auth.ts` 111 to 126 `available: databaseConfigured`), `/api/auth/*` answers 404 with that sentence (`apps/studio/src/routes/api/auth.$.ts` 16 to 25), and the key, alias, profile and quota stores fall to memory or no-op stores per instance (`identity.ts` 269 to 272). Production today is this state: no `DATABASE_URL` on either project (`research-hosting.md` 9).

## 2. What better-auth needs from a database and from secondary storage

### 2.1 The database option

The library takes a Kysely instance and a type (`better-auth.ts` 251: `database: { db: deps.db.db, type: 'sqlite' | 'postgres' }`). Its documentation says "getMigrations only works with the built-in Kysely adapter (SQLite/D1, PostgreSQL, MySQL, MSSQL). It does not work with Prisma or Drizzle ORM adapters" and, of D1, "Cloudflare D1 can only be queried through a Cloudflare Worker, so the CLI cannot access it directly. Instead, you can run programmatic migrations through an endpoint" (https://www.better-auth.com/docs/concepts/database, fetched 2026-10-01). The tree already migrates programmatically at boot (`identity.ts` 301 to 309), so the CLI limitation does not bite. The dialects page lists "Cloudflare D1" as a community dialect at https://github.com/aidenwallis/kysely-d1 and says "Any dialect supported by Kysely can be utilized with Better Auth" (https://www.better-auth.com/docs/adapters/other-relational-databases, fetched 2026-10-01). The npm registry record of `kysely-d1` read on 2026-10-01: latest 0.4.0, published 2025-04-19, peer dependency `kysely: *`; its README constructs `new D1Dialect({ database: env.DB })` from a Worker binding and says nothing about transactions (https://github.com/aidenwallis/kysely-d1, fetched 2026-10-01). The installed Kysely adapter of better-auth 1.7.4 contains no `transaction` string (`grep -rn transaction node_modules/.pnpm/better-auth@1.7.4_*/node_modules/better-auth/dist/adapters/kysely-adapter/*.mjs`, empty), and the tree's own migrations are single `createTable ... ifNotExists` statements (`schema.ts` 147 to 212). D1's binding wraps `batch()` in a transaction ("Batched statements are SQL transactions"; "If a statement in the sequence fails, then an error is returned for that specific statement, and it aborts or rolls back the entire sequence", https://developers.cloudflare.com/d1/worker-api/d1-database/, fetched 2026-10-01) and documents no interactive `BEGIN`. The tree's SQLite driver issues `begin`, `commit`, `rollback` as raw statements (`sqlite-dialect.ts` 95 to 105) but nothing in the auth folder calls `db.transaction()` (grep over `apps/studio/src/server/auth/*.ts` for `transaction(`: no hit).

What the library needs the database for, by its own capability check: a session store is "database or secondaryStorage", an account store is "database" alone (`better-auth/dist/context/store-capabilities.mjs` 2 to 7). So sessions can live in a key value store alone; users and accounts cannot.

### 2.2 Secondary storage

The tree's adapter is five methods over an ioredis shaped client with an `auth:` prefix (`secondary-storage.ts` 9 to 51): `get`, `getAndDelete` (Redis `GETDEL`), `increment` (with the TTL set on the first count), `set` (with `EX` seconds), `delete`. The documentation says "Secondary storage in Better Auth allows you to use key-value stores for managing session data, verification records, rate limiting counters, and other short-lived auth data" (https://www.better-auth.com/docs/concepts/database, fetched 2026-10-01). What the installed library moves when it is configured:

- Sessions: with `secondaryStorage` and `storeSessionInDatabase` false (the default, "Store session in database when secondary storage is provided (default: false)", https://www.better-auth.com/docs/reference/options, fetched 2026-10-01) the session row is not written to the database; the session lives under the key `<token>` as `{ session, user }` and the user's list under `active-sessions-<userId>` (`better-auth/dist/db/internal-adapter.mjs` 252 to 311; `executeMainFn: storeInDb` at 310). `findSession` reads the key and returns null when it is missing (321 to 324).
- Verification values (the magic link token, the OTP, the OAuth `state`): `verification:<identifier>` with the row's TTL (701 to 712); the state's life is 600 s (`better-auth/dist/oauth2/state.mjs` 31).
- The rate limiter's counters, when `rateLimit.storage` is `secondary-storage`, which the tree sets exactly when a secondary storage exists and `memory` otherwise (`better-auth.ts` 278; `better-auth/dist/api/rate-limiter/index.mjs` 195 to 199 needs `increment`).
- The device authorization plugin uses it too (`better-auth/dist/plugins/device-authorization/routes.mjs` imports `secondaryStorage`).

The tree wires it only from `input.redis` at runtime build (`identity.ts` 291 to 293), and `identityRuntime()` builds without a `redis` input (321 to 327); the room binds Redis for the principal store afterwards (`room.ts` 280; `identity.ts` 191 to 193), not for better-auth. So on this tree, even with `REDIS_URL` set, better-auth runs without secondary storage unless a caller rebuilds the runtime with `redis` (`setIdentityRuntime`, 330 to 335). That is a seam for whoever wires the redis tier, not a Cloudflare fact, and it is recorded here because it changes which store the counts of section 4 hit.

### 2.3 What breaks without each

- Without a database: everything of section 1.3. The library cannot start without a user and account store (2.1).
- Without secondary storage: the sessions, the verification rows and the device codes are in the database and shared by every instance that shares it (`internal-adapter.mjs` 341 to 357, `findSession` joins the user row). The sign in limiter counts per instance (`better-auth.ts` 278 `memory`; `start.ts` 114 to 119 logs the degraded quotas once on the platform). Nothing else of the library changes. The per instance problem this round names (`realtime.departed-guest.name-stable`) is the principal store's, which is Redis or a file per instance regardless of better-auth (`identity.ts` 182 to 189).
- A sentence to correct: `design-google-login.md` 223 says that without Redis "after that a signed in person on an instance without the session row reads as signed out". With `DATABASE_URL` set and no Redis the session row is in Postgres, which every instance reads (`internal-adapter.mjs` 341 to 357), so a signed in person is signed in on every instance; the cookie cache (`better-auth.ts` 267, 5 minutes) only saves the read. Redis before Google is still the right order for the limiter and the principal records, not for the sessions.

### 2.4 The cookie cache

`cookieCache: { enabled: true, maxAge: 5 * 60 }` (`better-auth.ts` 267). While the signed `ts.session_data` cookie is fresh, `getSession` answers from the cookie with no store read (`better-auth/dist/api/routes/session.mjs` 39 to 49, 72 to 110); past 5 minutes it reads `findSession` once and rewrites the cache cookie (153, 222); once per `updateAge` (24 h, `better-auth.ts` 66) it writes `updateSession` and a new session cookie (179 to 205). The cache cookie's own maxAge is 300 s (`better-auth/dist/cookies/index.mjs` 50).

## 3. The cookie and origin rules

### 3.1 The anonymous identity cookie

`__Host-ts_id` carries `v1.<payload>.<mac>` where the payload is `anon_<uuid>.<issuedAt ms>` and the mac is HMAC-SHA256 under `TURBOSLIDE_SESSION_SECRET` (`session.ts` 1 to 12, 21 to 27, 73 to 91). Attributes: `Path=/; Max-Age=34560000` (400 days, 23 to 24); `HttpOnly; SameSite=Lax`, and `Secure` under the `__Host-` name (174 to 188). On plain http off localhost the name falls back to `ts_id` without `Secure` (14 to 17, 168 to 171). The cookie is minted by the request middleware on the first request without one and without a bearer (`middleware.ts` 30 to 46; `session.ts` 226 to 244) and read on every request (`identity.ts` 603 to 604). A `__Host-` cookie cannot carry a `Domain` attribute by the prefix's definition, so it is host-only wherever it is set. The secret comes from the variable, else a generated file under the state folder on a checkout, else a value derived from `TURBOSLIDE_TOKEN` when hosted, with hosted read as `env.VERCEL` (`secret.ts` 27 to 68, the `VERCEL` test at 40).

### 3.2 better-auth's cookies

`cookiePrefix: 'ts'` and `useSecureCookies: deps.hosted` (`better-auth.ts` 270 to 271). The library names its cookies `<prefix>.<name>` with the `__Secure-` prefix when secure cookies are on, `secure: true` then, `sameSite: 'lax'`, and no `Domain` unless `crossSubDomainCookies` is configured (`better-auth/dist/cookies/index.mjs` 23 to 35). On production the names are therefore `__Secure-ts.session_token` (maxAge 7 days, 49), `__Secure-ts.session_data` (300 s, 50) and `__Secure-ts.dont_remember` (52). A `__Secure-` cookie may carry `Domain`; the options reference says `crossSubDomainCookies` lets cookies be "shared across subdomains" (https://www.better-auth.com/docs/reference/options, fetched 2026-10-01). The TanStack Start cookie plugin runs last so cookies set in server functions are written (`better-auth.ts` 5 to 6, 350).

### 3.3 The origin rules

- Base URL: dynamic per request. The request's Host is accepted when it matches `TURBOSLIDE_AUTH_HOSTS` or the five defaults `www.turboslide.com`, `turboslide.com`, `turboslide.vercel.app`, `localhost:*`, `127.0.0.1:*`; otherwise the hosted fallback `TURBOSLIDE_PUBLIC_ORIGIN`; otherwise a refusal (`better-auth.ts` 41 to 56, 132 to 155, 249; the library's refusal at `better-auth/dist/utils/url.mjs` 206 to 215). `x-forwarded-host` is honoured only under the library's `trustedProxyHeaders` (`url.mjs` 76 to 80), which the tree does not set.
- The OAuth redirect URI is `${baseURL}/api/auth/callback/google`, so it follows the Host of the request that started the sign in (`better-auth/dist/api/routes/sign-in.mjs` 228; `basePath` at `better-auth.ts` 62, 246).
- `trustedOrigins` is a function answering the request's own origin and nothing else (`better-auth.ts` 253 to 262). The library validates `callbackURL` and the `Origin` header against that list and refuses a `callbackURL` off it with `INVALID_CALLBACK_URL` (`better-auth/dist/api/middlewares/origin-check.mjs` 48 to 59, 112 to 115). The client's `callbackURL` is the page's own origin, path and search (`apps/studio/src/editor/EditorRoot.tsx` 299 to 301, 1017 to 1024).
- The client reaches the library with same origin JSON POSTs to `/api/auth/<path>` and assigns `window.location` to the answered `url` (`EditorRoot.tsx` 1017 to 1024, 1064 to 1065); the OAuth callback is a top level GET from `accounts.google.com`, which carries the `SameSite=Lax` anonymous cookie (`docs/REALTIME.md` 4.2; the row at `better-auth.test.ts` 234).
- The CSRF middleware validates `Sec-Fetch-Site`, `Origin` or `Referer` on `/api/auth/*` and `/device`, with top level GET navigations exempt for the magic link's verify URL and `/device` (`apps/studio/src/server/headers.ts` 374 to 397; `docs/security.md` 285 to 293).
- Rate limits: Vercel's WAF rule R8 counts `/api/auth/` at 10 per 60 s per IP with a 15 minute deny (`firewall/rules.json` 405 to 417); the library's rules at `better-auth.ts` 274 to 291 include the two new `/sign-in/social` and `/callback/google` rows at 10 per 60 s. The client address for the application's own limits is read from `x-vercel-forwarded-for` or `x-real-ip` only when `env.VERCEL` is set, else from `x-forwarded-for` under `TURBOSLIDE_TRUST_PROXY` (`headers.ts` 43 to 57); the library's own address header is `x-forwarded-for` (`better-auth.ts` 272).

### 3.4 The hosted flag is Vercel's

`isHosted()` is "the store selection is not `file`" (`apps/studio/src/server/root.ts` 192 to 194), and the store selection reads `TURBOSLIDE_STORE`, else `VERCEL` with `BLOB_READ_WRITE_TOKEN` for blob and without it for tmp, else `file` (`packages/store/src/select.ts` 5 to 6, 57 to 59, 67 to 91). Six more reads of `env.VERCEL` sit on the auth path: `middleware.ts` 24 (the secret's source), `secret.ts` 40, `db.ts` 52 (the SQLite refusal), `headers.ts` 51 (the client address) and 244, `start.ts` 118 (the per instance quota warning). A process on a Cloudflare Worker sets none of them: with `TURBOSLIDE_STORE` unset it would read as a checkout, mint a checkout token (`identity.ts` 275), look for a state folder for the secret (`secret.ts` 41 to 51), set the library's cookies without `Secure` (`better-auth.ts` 271) and allow the SQLite path (`db.ts` 50 to 61) on a runtime where `node:sqlite` is "a non-functional stub" ("A stub can be imported or required, but does not provide a working implementation of the underlying Node.js API", https://developers.cloudflare.com/workers/runtime-apis/nodejs/, fetched 2026-10-01). Any design that runs this code off Vercel needs one explicit hosted switch in place of the `VERCEL` reads.

### 3.5 What the rules imply for two topologies

Topology A, the auth routes on a Worker at `<name>.<account>.workers.dev` while the app stays on `www.turboslide.com`:

1. The session cookie the Worker sets is host-only on the Worker's host (3.2), so the Vercel function's `sessionOf(runtime.auth, request)` (`identity.ts` 605 to 607) never sees a session; every account surface of the app reads anonymous.
2. The anonymous cookie is `__Host-` on the Vercel host (3.1), so the Worker's callback request carries no `anon_<uuid>` and `onSessionCreated` cannot link (`identity.ts` 442 to 445; `better-auth.ts` 303 to 313). The fallback link on a later request that has both the session and the cookie (`identity.ts` 605 to 611) never fires either, because of item 1.
3. `trustedOrigins` as written answers the Worker's origin, so a `callbackURL` on `www.turboslide.com` is refused (`origin-check.mjs` 59); the app's `authPost` is a same origin fetch (3.3) and would need CORS with credentials on the Worker; the CSRF filter on `/api/auth/*` wants an `Origin` it trusts (3.3).
4. `workers.dev` is on the Public Suffix List (`public_suffix_list.dat` line 12707, fetched 2026-10-01 from https://publicsuffix.org/list/public_suffix_list.dat; `vercel.app` at 16269), so no `Domain` cookie can span a workers.dev host and anything else, and browsers treat two workers.dev subdomains as two sites.
5. Google's redirect URI rules are satisfied by the host's TLD ("Host TLDs must belong to the public suffix list", "Redirect URIs must use the HTTPS scheme", https://developers.google.com/identity/protocols/oauth2/web-server, fetched 2026-10-01); whether the consent screen's authorized domains accept a `workers.dev` host is unsettled (section 7).

Conclusion for A: the auth routes and the app must share one origin. A Worker can own the auth routes only by owning the whole origin, which on `www.turboslide.com` is a DNS change (`dig NS turboslide.com` on 2026-10-01: `dns1.registrar-servers.com`, `dns2.registrar-servers.com`; `www` is a CNAME to `5661780b11730745.vercel-dns-016.com`), and no agent moves DNS (`docs/hosting.md` 976 to 978).

Topology A', a same site subdomain such as `auth.turboslide.com` for the library and the app on `www`: the `__Secure-ts.session_token` cookie can be shared with `crossSubDomainCookies` (3.2), the app's `requestIdentity` would then read the session and link the anonymous cookie on the next request (`identity.ts` 605 to 611), `trustedOrigins` would need the `www` origin added, and the dialog's POSTs would need CORS or a redirect. It still needs a DNS record, so it is not an agent's step either.

Topology B, the database reached over HTTP from the Vercel function, cookies and origins unchanged: what changes is the latency per statement multiplied by the counts of section 4, and a cap. The D1 HTTP endpoint is `POST /accounts/{account_id}/d1/database/{database_id}/query` under an API token with D1 Read or D1 Write (https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/query/, fetched 2026-10-01); the D1 guide says the "REST API primarily interacts with the control plane" (https://developers.cloudflare.com/d1/best-practices/query-d1/, fetched 2026-10-01); the Cloudflare API's global limit is "1,200 requests per five minute period per user", "cumulatively regardless of whether the request is made via the dashboard, API key, or API token", with a 429 for the next five minutes past it (https://developers.cloudflare.com/fundamentals/api/reference/limits/, fetched 2026-10-01). 1,200 per 300 s is 4 requests a second across every instance; with the 5 to 7 statements per authenticated request of section 4 (batched to one HTTP call at best), that is a ceiling near one authenticated request a second, and near four a second only if every request is one batch. Hyperdrive, the free pooled path to a Postgres, is a Worker binding (`env.HYPERDRIVE.connectionString`, https://developers.cloudflare.com/hyperdrive/examples/connect-to-postgres/postgres-drivers-and-libraries/node-postgres/, fetched 2026-10-01) and is not reachable from a Vercel function. So B over D1 is capped, and B over Hyperdrive does not exist; a Worker in front of either, answering a private API for the function, adds one HTTP hop per statement or per batch.

## 4. The writes per sign in and per request

### 4.1 Per request

`requestIdentity` (`identity.ts` 513 to 713) is called at 13 sites: `write.ts` (5), `actions.ts` (2), the stream, ops and presence routes (`decks.$deckId.stream.ts` 89, `decks.$deckId.ops.ts` 67, `decks.$deckId.presence.ts` 74), `s.$token.ts`, `share.$.ts`, `notify.$.ts`, `access.$.ts`, `assist.ts`, `sessions.server.ts`, and `room.ts` 1427 (`sessionIdentity`). The store traffic per call, by branch:

| Branch | Statements on the identity database | Operations on the principal store | Lines |
| --- | --- | --- | --- |
| Account, cache cookie fresh | 1 select `user`; 1 select `ts_profile` (plus 1 insert the first time); 1 select `ts_alias` by anonymous id (plus 1 insert once); 1 select `ts_alias` by user: 4 reads | 1 get and 1 set (`touch` writes the record on every call) | `identity.ts` 605 to 645; `accountFacts` 371 to 379; `profile.ts` 63 to 86; `alias.ts` 27 to 55; `packages/identity/src/principal.ts` 216 to 223; `principal.ts` (studio) 81 to 88 |
| Account, cache cookie past 5 minutes | the 4 above plus 1 session read (`findSession`: a key get, or a select `session` joining `user`), and once a day 1 session update | the same | `session.mjs` 153, 179 to 205; `internal-adapter.mjs` 321 to 357 |
| Anonymous with a cookie | 0 | 1 get and 1 set | `identity.ts` 649 to 668 |
| Fresh visitor | 0 | 1 put | `identity.ts` 684 to 700 |
| Bearer (API key) | the key read is synchronous (SQLite) or from the 5 s cache (Postgres); `lastUsedAt` written at most once a minute per key; 1 select `user`; 1 select `ts_profile`; 1 select `ts_alias` by user | 0 | `identity.ts` 519 to 566; `tokens.ts` 211 to 227, 283 to 292 |

Rendering other people (`resolveIdentity`, `identity.ts` 725 to 760) costs per principal id 1 principal get, and for an anonymous id 1 `ts_alias` read plus, when aliased, the 2 reads of `accountProfile` and 1 principal get; the room caches a resolved identity for 5 s (`room.ts` 2538 to 2539) and drops it on the bus (300).

Per editor hour, `research-options.md` 105 counts 144 ops, about 1,440 caret and selection messages and 576 heartbeats, "about 2,200 messages sent"; the ops and presence POSTs each pass `requestIdentity` (the routes above), the heartbeats ride the open stream. For one signed in editor that is on the order of 1,600 to 2,200 `requestIdentity` calls an hour: 6,400 to 8,800 database reads and 1,600 to 2,200 principal store writes an hour; for an anonymous editor 1,600 to 2,200 principal store reads and as many writes. These are the code's counts on this tree, before any batching a design might add.

Set against the free tier limits fetched on 2026-10-01: Workers KV allows 1,000 writes a day on the Free plan (https://developers.cloudflare.com/kv/platform/pricing/), which the principal `touch` would pass in about half an editor hour; D1 Free allows 100,000 rows written a day and 5 million rows read a day (https://developers.cloudflare.com/d1/platform/pricing/), which the principal writes alone would reach at about 45 to 60 editor hours a day; a SQLite backed Durable Object on the Free plan has the same 100,000 rows written and 5 million read a day, and 100,000 requests a day (https://developers.cloudflare.com/durable-objects/platform/pricing/). The authenticated request's 4 database reads are rows read, not statements, when the selects hit indexes (`ts_alias_user`, `ts_api_key_user` exist, `schema.ts` 154 to 159, 177 to 182; `ts_profile.userId` is the primary key, 186).

### 4.2 Per sign in

A Google sign in on this tree, in order:

1. `POST /api/auth/sign-in/social`: `generateState` writes one verification value with a 600 s life (`sign-in.mjs` 220; `state.mjs` 31; `internal-adapter.mjs` 701 to 712, to the key store when there is one, else the `verification` table). One write.
2. The callback `GET /api/auth/callback/google`: the state is read and deleted (1 read, 1 write); the code exchange at Google's token endpoint (network); `findAccountOwnerByKey` (1 read, `link-account.mjs` 20) and `findUserByEmail` (1 read, 59); then either a new user and a new account (2 writes, 215 to 224), or a link to an existing verified user (1 write, 99, plus `emailVerified` set when needed, 128), or a token refresh on a known account (1 write, 165). `createSession`: without secondary storage 1 insert `session`; with it, a get and a set of `active-sessions-<userId>`, 1 select `user`, and a set of the token key (`internal-adapter.mjs` 280 to 305). The session cookie and the cache cookie are set (`callback.mjs` 248).
3. The session create hook `onSessionCreated` (`identity.ts` 431 to 448), sequential awaits inside the callback request: `accountFacts` (2 reads, plus 1 `ts_profile` insert the first time); `principals.touch` (1 get, 1 set); `setAdmin` when the address is listed and not yet flagged (1 read, 1 update, `profile.ts` 87 to 95); `linkAnonymous` when the cookie came along (1 `ts_alias` read and 1 insert once; 2 principal gets and 1 put; then the `onLinked` hooks, the deck index and inbox merges on the deck store, `identity.ts` 100 to 101, 427); `bindInvitations` when the address is verified (447).

Totals for a first Google sign in in a browser with an anonymous history: about 7 to 9 database reads, 5 to 8 database writes, 4 to 8 key store operations and one call to Google; a repeat sign in about 5 reads and 2 to 3 writes. The e2e email path is two POSTs (`accounts.spec.ts` 209 to 227) and three to four verification writes (the OTP stored hashed, its attempt counter, its deletion) around the same session and hook work.

The hook runs inside the callback before the redirect, so a remote database at L ms per statement adds about 15 × L to the callback: 75 ms at 5 ms, 450 ms at 30 ms, 1.5 s at 100 ms. Per authenticated request the add is 4 to 7 × L. Nothing here measured L; the research notes measured none either (`research-hosting.md` 55: "No measurement from a Vercel function exists yet").

## 7. Open

1. Google's authorized domains rule for a `workers.dev` host. The two Google pages fetched (https://support.google.com/cloud/answer/15549257 and https://support.google.com/cloud/answer/6158849) point to the Branding page for "how to manage authorized domains" and state no rule; the redirect URI page's "Host TLDs must belong to the public suffix list" is satisfied by `.dev`. Whether `<account>.workers.dev` can be an authorized domain of the consent screen is not settled by any page read today.
2. Whether the D1 HTTP query endpoint falls under the global 1,200 per 5 minutes limit. The limits page names the global rule and lists exceptions (Cache Purge, GraphQL, Rulesets, Lists, Gateway Lists); D1 is not among the exceptions, so this note treats the limit as applying, unmeasured.
3. The latency of one D1 HTTP call, one Hyperdrive statement from a Worker, or one Worker hop from `iad1`. Not measured anywhere in the tree or the research notes.
4. better-auth 1.7.4 over `kysely-d1` 0.4.0. The documentation names D1 in the `getMigrations` sentence; nobody on this tree has run the library's migrations or its session and account paths against D1. The `type: 'sqlite'` setting (`better-auth.ts` 251) is the one the D1 dialect would take.
5. Transactions on D1: the Kysely adapter folder has no `transaction` string and the tree's auth code calls none, but a full statement inventory of the library's device authorization and verification paths was not made.
6. Whether `sharp` (`avatar.ts` 25) runs on Workers. Not checked; the Node compatibility page read today does not mention native addons.
7. The e2e harness over any engine a Node script cannot open (section 5, last item). Not designed.
8. The sentence at `design-google-login.md` 223 about sessions per instance (section 2.3). This note reads the Postgres session path as shared; the lane that wires the redis tier should confirm with a two process run.
9. The secondary storage wiring: `identityRuntime()` never passes `redis`, so better-auth runs without secondary storage on every tier today (section 2.2). Whether this round intends `setIdentityRuntime` with a Redis client or leaves sessions in Postgres is not written in `docs/REALTIME.md` 3.6 or 4.1.
