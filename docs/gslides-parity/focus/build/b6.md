## 2. What was broken, the mechanism, and the fix

### 2.1 Rank 1, severity 3: `share.stranger-cannot-edit`, `share.view-link-cannot-edit` (with `share.view-link-lands-viewer`, `share.edit-link-lands-editor`, the four `share.copy-*` rows and `share.dialog.open`)

What the audit saw: a second browser with no link opened `/edit/<id>` of a deck never shared and got the full editor; a browser that came by the View link changed `/deck/` to `/edit/` and edited too; the Share dialog on production was the round one dialog with three plain addresses and no role, General access or Stop sharing control (`audit-present` rows 17 to 19, 25, 26, 29).

The mechanism, read from the tree:

1. The access record is written at the deck's first write already (`apps/studio/src/server/write.ts` `writeDeckFn`: `createStoredDeck` then `recordNewDeck(deckId, identity.ctx)`, restricted with the creating principal as owner, `newDeckRecord` of `packages/schema/src/access.ts`). What production showed was not a missing record but a page that never read it: the `/new` route pins the address to `/edit/<id>` through the native `History.prototype.replaceState` and keeps the draft payload (`routes/new.tsx`, by design, so the undo history survives), so `snap.access.record` stays null and `input.access` is undefined until a reload, and the dialog fell to its round one form.
2. Production runs `TURBOSLIDE_AUTHORIZE=shadow`, where `authorize()` answered every denial with `ok: true, role: 'editor'` (`authorize.ts` `roleOf(...) ?? 'editor'`), so `readEditorDeck` shaped the stranger's and the viewer's payload as an editor's and the editor opened in Editing mode on any address.
3. The View, Present and Edit links were plain addresses; a plain address grants nothing under a restricted record, so the three rows could not carry a role.
4. Found by the enforce run: `requestContext()` in `authorize.ts`, the identity path of every server function that authorizes through `authorizeRequest` and of `getDeck` on `/deck/<id>`, read the cookie alone (`authContextFor` of `auth/session.ts` answers `linkGrants: []`), while `room.requestIdentity` reads the principal record's link grants for the room routes. In enforce mode the View link's landing on `/deck/<id>` was refused as `not_found` for the very viewer the link admitted (the enforce log: `deck.view` denied for the link holder), and a link editor would have been refused every server function write; shadow mode's floor hid both.

The fix, in this lane's files:

- `apps/studio/src/server/authorize.ts`: `shadowStanding(record, ctx, now)` is the role a denied caller is handed in shadow mode: the standing the record gives when it gives one (an editor refused `remove` keeps `editor`, a viewer refused `write` keeps `viewer`), the legacy open editor for a deck with no record (unchanged: every deck without a record stays as it was), and otherwise the floor `viewer`. The server still refuses no write in shadow mode; the payload and the editor's mode now follow the role the record grants, whatever the address. `withLinkGrants(ctx, load)` loads the caller's link grants from the room's principal store when the context carries none (a stranger and a bearer pass through), and `requestContext()` runs it, so a link holder is the same person on `/deck/<id>` and on the server functions as on the room routes. `authorize.test.ts` pins the floor through `authorize()` for the stranger, the viewer by link and the editor refused `remove`, and the grants turning a 404 into the viewer role in enforce mode (two tests added, one assertion added to the existing shadow test; nothing weakened).
- `apps/studio/src/routes/api/access.$.ts`: the answer carries `authorize: 'shadow' | 'enforce'` beside the record, the role and the capabilities, so the Share dialog says which mode the deployment runs and a driven row records the mode it ran in.
- `packages/chrome/src/dialogs/Share.tsx`, rebuilt around the SPEC-3 dialog with every existing control id kept:
  - Three link rows, View link (viewer), Present link (viewer, opens as a show), Edit link (editor), with Copy link on each (`dialog.share.view`, `.present`, `.edit`, `.<row>.copy`; ruling 2). On a deck with a record, Copy link mints a share link with the row's role and label through `share.createLink` and copies its `/s/<token>` address (the Present row's carries `?present=1`). The address is remembered on the minting browser under `localStorage` `ts-share-links` by deck and link id, so a second Copy link sends the same address instead of rotating the link (a rotation would stop the address the seller already sent); a browser that never minted the link mints another one with the same label, and the earlier address keeps opening until it is revoked from the links list or by Stop sharing. The links list shows each minted link with its label, role and date, with Rotate and Revoke.
  - A deck with no record (a legacy open deck, a checkout) keeps the plain addresses, which are the truth for such a deck, with the sentence "Anyone with the address can open and edit this presentation." and no note promising a read only address; the words "Read only, opens on slide 1" left with the round (rank 1).
  - The dialog reads `GET /api/access/<deckId>` on open when the page carries no record (the `/new` page after its first write), so the record and the role appear without a reload; the same read gives the deployment's mode, said in one footer sentence (`dialog.share.authorize`, `data-mode`): "Sharing is not enforced on this deployment: the roles here are shown and logged, anyone with the address can open the presentation, and a change from any browser is accepted." in shadow mode; "Sharing is enforced on this deployment: only people with access or a link can open the presentation." in enforce mode. The footer Copy link's tooltip says the same in shadow mode instead of promising a restriction.
  - Every share write bases on the freshest revision the dialog knows (the page's, the route's, the last write's answer) and on a conflict re-reads the record through the route and retries once (SPEC-3 6.4 "re-read and retry"); before this the dialog based on the page's copy alone and showed the 409 sentence.
  - An unsaved draft shows one sentence, "Links appear once the presentation is saved. The first change saves it.", since nothing exists in the store to share.
- `apps/studio/src/routes/s.$token.ts`: `withPresent(location, request)` carries `?present=1` from the link's address to a `/deck/` landing, so the Present link opens the show; an editor or commenter link lands in the editor whatever the address carried.
- `packages/chrome/src/dialogs/share.css`: the rows, the mode sentence, the draft and loading states at fixed heights.

What the rows read now, on this lane's dev server in both modes (section 5): the View link lands on `/deck/<id>` with no editor chrome; the same browser on `/edit/<id>` opens in Viewing mode with the View only button and the role `viewer` in `describe().state.access`, a double click opens no text session, and a document write through the room's ops route answers 403 in enforce mode; the Edit link lands in Editing mode and a typed word reaches the owner within 5 s; a browser with no link meets the You need access page and a 404 in enforce mode and a read only editor with the role `viewer` in shadow mode.

### 2.2 Rank 19, severity 2: `comments.on-title-placeholder` (with `comments.toolbar-and-menu-routes`)

What the audit saw: with the title placeholder selected the submit answered "the anchor names nothing on the current document (block removed)" three times of three (`audit-present` row 35).

The mechanism: the blank template's one slide is a `title` slide whose heading and lead are slide fields, not blocks (`packages/viewer/src/Editor.tsx` at the run editing: "a title or statement slide's text run is a slide field, not a block"); the selection names the field as `blockId`, `anchorAtSelection` (`packages/chrome/src/comments/comments-model.ts`) made a block anchor of it, and the schema's `resolveAnchor` (`locateTopBlock`) finds no such block on a title slide.

The fix, in this lane's files: `slideHasBlock(slide, blockId)` in `comments-model.ts` applies `locateTopBlock`'s rule (a slot block of a content slide, a plate block of an opener, mood or closing slide; nothing on a title or statement slide), and `anchorAtSelection(slideId, selection, quote?, slide?)` anchors on the slide when the slide is given and the selection's block is not one of its blocks. The call site in `packages/chrome/src/EditorShell.tsx` (the surface lane's) passes no slide yet; request R2 asks for the one argument. Until then the belt in `packages/chrome/src/comments/CommentCard.tsx` holds: a new comment whose `comments.add` is refused with that one sentence is placed again on the slide (`slideFallbackOf`, `isUnplacedAnchorRefusal`), so the seller's comment lands where they wrote it either way. `comments-model.test.ts` pins the rule (one test added). Driven: the title placeholder selected, Cmd+Option+M, a comment lands as the slide's marker; the toolbar's Insert comment and Insert > Comment each land another on the same slide, whose one marker counts 2 then 3.

### 2.3 Rank 36, severity 1: `comments.resolve`

What the audit saw: the first click on the tick did nothing within 1.5 s and the second resolved the thread (`audit-present` row 39).

The mechanism is the read after the write: the tick's state is the thread view the controller recomputes from `comment.list` after a 60 ms debounce, and on the blob tier the instance that answers the list may sit behind the instance that landed the resolve until the channel's poll delivers the entry, so the card kept reading Resolve while the server had resolved the thread. The fix in `CommentCard.tsx`: the tick settles as soon as the server accepts the resolve or the reopen (`settled` state, `data-resolved` on the tick, the class and the label follow it) and the thread view confirms it when the refresh lands; a thread whose view moves resets the state. The panel's row follows the refresh as before. The server side of the latency is rank 3's (the server lane). The same file returns the focus to the card when the reply box closes (cancel or submit), so the chords of section 14 (`u` leaves, `e` resolves, `j` and `k` step) keep working after an Escape in the reply field; before, the focus fell to the body and the `u` chord of `comments.spec.ts` reached no card.

### 2.4 Rank 26, severity 2: `decks.access.paint`

What the audit saw: in one browser that had used the editor on the light appearance the light figure was drawn over the form and the sign in line (`audit-decks` row 57; the shot shows the notfound twin drawn at full size behind and over the page's text). The mechanism, reproduced on this lane's dev server by `roles.spec.ts`: the route's view transition. A navigation from an editor page to `/edit/<unknown>` runs the document's view transition; while it runs the outgoing page's snapshot is composited over the incoming You need access page (the spec's screenshot at that moment shows the editor's menubar and filmstrip around the form) and `document.elementFromPoint` at the Request access button answers the root element. A frame taken in that window is the audit's picture; a click in that window lands nowhere. The page itself draws no figure (`routes/-access-page.tsx`, `YouNeedAccess.tsx`); the outgoing snapshot does. The transition is the surface lane's (`__root.tsx`, the routes and transitions of round four); request R12 asks that a 404 landing run no view transition, or a short one. In this lane's file `packages/chrome/src/YouNeedAccess.css`, `.ts-access` paints on its own paper ground, positioned with `z-index: 2` and `isolation: isolate`, so the form reads over whatever else the document holds once the transition ends. The row in `roles.spec.ts` uses the editor on the light appearance first, opens `/edit/<unknown>`, waits for `:active-view-transition` to clear and every animation to end, and asserts the Request access button is the element at its own centre, the page's ground is opaque and no figure is in the document; it passes in both modes.

## 4. What flipping `TURBOSLIDE_AUTHORIZE` to `enforce` on production changes

For the integrator's ship note and for Kevin, read from `authorize.ts`, `packages/identity/src/access.ts` `decide()` and the record path:

1. Decks with no access record (the seeded `gt-brand`, decks made before `recordNewDeck` landed, decks whose first write ran with no identity): `decide()` reads them as the legacy open deck (`TURBOSLIDE_MISSING_RECORD` unset means `open`), so anyone with the address keeps editing them. The flip changes nothing for them; `TURBOSLIDE_MISSING_RECORD=notFound` would.
2. Decks with a record (every deck made from `/new`, `deck.create` or `deck.copy` since the record landed, restricted with the creating anonymous principal as owner): after the flip only the owner's browser (its sealed cookie), the grantees and the holders of a live link open them. A stranger receives the You need access page and a 404 on `/deck/`, `/edit/`, `/present/` and `/print/`, and 401 or 403 on the write functions and routes.
3. The plain addresses copied from the round one dialog (`/deck/<id>`, `/deck/<id>?present=1`, `/edit/<id>`) that sellers have already sent stop opening for anyone who is not the owner, a grantee or a link holder. The seller mints the View or Edit link from the rebuilt dialog and sends it again.
4. A seller whose anonymous cookie is gone (a cleared browser, another browser, another device) is a stranger to their own decks. Nothing in the record path recovers this without an account: the seller signs in and claims, or an admin bearer reassigns the owner (`admin.assignOwner`). This is the one consequence that costs a seller their deck, and it exists in shadow mode too since this round's floor shows them Viewing mode; before the flip Kevin should decide whether sellers sign in first (`DATABASE_URL`, the account rows of SPEC-3 7) or accept the risk.
5. Link grants exchanged before the flip stay on the principal records and keep working, and with item 4 of 2.1 they now count on `/deck/<id>` and on the server functions as well as on the room routes; without that fix the flip would have broken every View link at its landing. The published player and its 410 after unpublish are unchanged; the agent bearer keeps the admin standing.
6. In shadow mode after this round the editor already shows the role the record grants (a stranger and a viewer see Viewing mode), the server accepts every write, and the dialog says so; the flip makes the server refuse what the editor already withholds and turns the stranger's read only editor into the You need access page.

### 2. What was broken, the mechanism, and the fix

#### 2.1 One mechanism under three findings: the record read through the CDN (F-share-copy, F-share-404, F-missing-record)

What the verifier saw (pass 2, section 5): the Share dialog's second Copy link in a session refused as "the access record is at revision 0, not 1; re-read and retry"; a minted Edit link answering 404 to a fresh browser for a while; a deck whose record read as absent opening as a legacy editor deck to a browser with a cookie under enforce mode.

The mechanism, read from the tree and measured on the enforce preview. The access record, the link hash index and the per identity deck index are read through `BlobClient.get`, which on the public store (`vercelBlobClient`, `access: 'public'`; production and the previews run one public store) fetches the body at its public url. `packages/store/src/blob-store.ts` `pull()` records the three facts about Vercel Blob this round's deck reads already live by: `head()` answers the store's version at once, `list()` lags by up to a minute, and the body a public url serves can be the CDN's copy from before the last overwrite (the SDK's `useCache: false` bypasses that for private stores only), or a cached miss for a path written since. `deck.json` is proven against the head's etag and falls back to an immutable snapshot; `access.json` was not. So:

- The share writer (`apps/cli/src/records/access.ts` `write`) loads the record through `hostedAccessHooks.load` (drop, then `read`, one `get`), compares `record.revision` with the dialog's `baseRevision` and refuses. On the enforce preview this lane's probe (`scratchpad/b6/preview-probe.mjs`, the actions API with the bearer) minted a link and minted a second one 155 ms later: the second answered 409 "the access record is at revision 0, not 1", the plain read having served the record from before the first mint. That is F-share-copy at the server; the dialog's `baseRevision()` and `noteAnswer` were right (the mint's answer carries `record.revision`), and its retry re-read the same stale copy through `/api/access/<id>` and repeated the refused base.
- The exchange's lookup (`server/access.ts` `findShareLink`, bound in `start.ts`, `fresh: true`) reads the link index then the record; a record served from before the mint does not name the link, so the lookup falls to the scan of `listStoredDecks()`, which lags by up to a minute and does not list a deck made a moment ago: 404 to the visitor (F-share-404, b4 FR6). The verifier's reading of "no identity hook" was not the mechanism; the hook is bound on every server process by `bindServerSeams()`.
- A record whose path was fetched before it was written (the `/new` page's reads before the draft's first write) can read as a cached miss for a while, so `decide()` synthesizes the legacy open record and admits any browser with a cookie as an editor (F-missing-record).

Measured 2026-09-16 with `scratchpad/b6/cdn-probe.mjs` against the store under a scratch path (written, overwritten, read, deleted): from this machine's edge the overwritten body read fresh at once and `head()` answered the new etag; the function's edge on the preview served the old body 155 ms after the overwrite (the probe above). A url with a query string is keyed apart by the CDN (a new query is a MISS to the store), so a body can be read past a stale copy without a second write.

The fix, in this lane's files:

- `packages/store/src/access-store.ts`: `provenGet(client, pathname, options)` reads `head()` first (null means the store holds nothing, whatever the CDN cached), then `get()`; a body counts only when its md5 is the head's version, else the url is read again with `?v=<hex>` (`fetchFreshByQuery`), then the client is asked again after a short wait (two retries, 120 ms); when nothing proves the body the last body the client gave is answered under its own version, so a write based on it is refused as stale rather than committed over a newer record; a version that is not an md5 (a client reporting the upload time) takes the client's body. `blobAccessStore`, `blobIndexStore` and `blobLinkIndex` read through it and take `ProvenReadOptions` (the url read and the sleep are injectable for tests). The cached store in front keeps its TTL, so the extra `head()` costs one round trip per cache miss.
- `packages/store/src/access-cache.test.ts`, the group "the proven read (pass 2)": the fake client's `holdGet()` is the CDN. The record the mint wrote is read while the plain read still answers the record from before it; with nothing to prove the body the store answers the last body under its own version and a write on it is refused; a missing path is null and a non md5 version takes the client's body; the link index and the deck index read through the same proof; a shared row is written once per deck, role, via and link (five tests added; nothing weakened).

#### 2.2 The link grant across instances (F-share-404, the second half; b4 FR6)

Read from the tree: the exchange writes the grant on the principal record (`runtime.principals.put`), and `selectPrincipalStore` without Redis is a file store under the instance's state folder (`apps/studio/src/server/auth/principal.ts`), so on the blob tier (production, the previews) the grant exists on the instance that served `/s/<token>` alone; the landing, a server function or a room route served by another instance reads no grant and refuses the visitor the link admitted (the verifier's hand run: a View link's visitor landed read only once and met You need access once). This lane's curl probe on the preview (`scratchpad/b6/link-probe.sh`: mint through the actions API, exchange and eighteen landings with a cookie jar, a stranger, teardown) answered 303 and 200 every time and 404 to the stranger, so under that traffic one instance served the visitor; the reading stands as the mechanism a busy deployment meets.

The fix, in this lane's files: `server/access.ts` `noteLinkGrant(principalId, grant, now)` writes the grant on the principal's deck index (`users/<principalId>/decks.json`, a `shared` row with `via: 'link'` and the new optional `linkId`), which lives on the Blob store every instance reads; `linkGrantsFromIndex(principalId)` reads those rows back behind a 5 s process cache. `authorize.ts` `linkGrantsFor(principalId, record)` is the union of the principal record's grants and the index's, one entry per link id, and `requestContext()` reads it (`withLinkGrants`), so `/deck/<id>`, `/edit/<id>` and every server function see the grant wherever the request lands; an index that cannot be read adds nothing. `auth/links.ts` `exchangeShareToken` takes `deps.noteGrant` and calls it after the principal put for every identity kind (a failure never fails the exchange); `routes/s.$token.ts` passes `noteLinkGrant`. The `shared` row's `linkId` lets `standingOf` keep honouring revocation and rotation: the grant names the link, and a revoked link grants nothing. The room routes (`room.requestIdentity`, b7's) still read the record alone; request R1 below asks for the one line.

Tests: `apps/studio/src/server/link-grants.test.ts` (new, the index mocked: the union, the index alone, the index unreadable), `auth/links.test.ts` (three tests added: the note with the principal id, the grant and the stamp; a failing note leaves the redirect and the record grant standing; a dead token notes nothing).

#### 2.3 The reply that was not listed (F-comments-reply, with b7)

What the verifier saw: a reply submitted from the card was not listed within 20 s on the preview while the add, the resolve and the reload's listing held. Through the actions API on the preview this lane's probe added a comment, replied and listed: the reply was listed at once (one instance, `liveThreads` folding the room's pending entries). The mechanism this lane's files carry: `packages/store/src/comments-store.ts` `pullSidecar` read every sidecar file through `client.list(prefix)` (lags) and `client.get` (the CDN's copy); a reply pushed by one instance overwrites the thread file and `index.json`, and another instance whose `head(index.json)` differed from its local copy pulled the thread from before the reply and listed no reply, while the plain read kept answering that copy. The fix: `pullSidecar` reads the index through `provenGet`, reads each thread by the index's rows (never the listing) through the same proof, writes the index last (the commit point of 08 2.2) and removes local files the index does not name; `applyAndPush` forwards the read options. `comments-store.test.ts`, the group "the proven pull (pass 2)": a reply pushed by one mirror is listed by another whose plain reads still answer the thread from before it; a local thread the store does not name is removed and a store with no sidecar answers null (two tests added; nothing weakened). The other half of the reply's path (the checkpointer's pending entries per instance, the stream) is b7's; request R4.

#### 2.4 Escape after Copy link (b4 FR1)

After a Copy link the button re-rendered through the busy state and the focus fell to the body, where the Dialog's `onKeyDown` on the card never saw the Escape (`core/share.spec.ts` closes with Done for this reason). In `Share.tsx` `copy()` now ends by focusing the Done button when the focus is not inside the card (`focusDone`), so Escape closes the dialog after a copy as it does on a fresh one. The Dialog's document level listener (b3 R19, b1's file) would cover every dialog; this is the Share dialog's own belt.

#### 2.5 The retry base of a refused share write (F-share-copy, the dialog's half)

`conflictRevision(error)` reads the revision the 409 sentence names ("is at revision N, not M") or a `currentRevision` on the error; `write()`'s retry bases on the highest of that, the route's re-read and the dialog's own count, so a dialog behind another browser's write retries on the server's revision at once, and a dialog ahead of a stale server copy never lowers its base (a lower base would be refused by the store's `ifMatch` anyway). `share-conflict.test.ts` (new) pins the three readings.

#### 2.6 b3 R23, the copied deck on a tmp store (with b7)

Read this cycle: the loader's `readEditorDeck` and the room routes read the same principal (`readPrincipal` of `auth/session.ts` on both paths, one cookie name per scheme), `deck.copy` writes the record with the cookie principal as owner (`decks.ts` 455, `creatorOf`), the tmp store's `copyDeck` copies no `.turboslide/` folder, and `?author=` in the address is accepted and ignored by the editor. So the identity is not the mechanism and the record path in this lane's files is one store per process. See the run table for what the repro on this lane's server read; the finding stays with b7 for the stream's recheck and `refreshAccess` if the repro shows the copy's record granting the copier nothing.

The preview run of the comments rows on cycle 1's code (`core/present.spec.ts -g comments` against the enforce preview, 2026-09-16 21:44Z to 21:48Z, no lock; `scratchpad/b6/preview-comments.log`): `comments.on-slide`, `comments.on-object` and `comments.toolbar-and-menu-routes` passed; `comments.reply` and `comments.resolve` failed in `threadsLoaded` with no thread listed for 15 s after the reload, three threads having been created by the rows before; `comments.on-title-placeholder` failed with 3 threads where 2 were expected because its baseline was read right after the reload, before the comments had loaded. The baseline is the driver's (request R5).

#### 2.1 C2-F28, `collab.presence-chips`: the roster is per instance, and a leave lands on one instance alone

The blob channel's presence is the memory channel's (`blob.ts` `presence: local.presence`): a `Map` in the function instance that received the presence POST. Under fluid compute a tab's stream, its presence posts and its leave beacon are separate requests and land on whichever instance is free, so the first browser's stream (instance X) listed the second browser's chip only when the second browser's post happened to land on X, which is the run of record's half of the finding (0 chips where 1 was expected within 10 s), and the closed tab's leave (`?leave=1`, and the stream's own cleanup) removed the row from the instance it landed on while X kept its copy until `PRESENCE_EXPIRY_MS` (120 s), which is the rerun's half (1 chip where 0 was expected past 30 s; FOCUS.md rank 36's reading). The hello's roster (`room.channel.presence.roster`) and `overEditingCeiling` read the same per instance map. The driver's bounds are Google's shape (a chip within a few seconds, gone within seconds of the tab closing); 10 s and 30 s are not the mechanism.

The fix is the shared roster record the cycle 3 prompt names as in scope: `packages/store/src/presence-store.ts` `sharedPresence()`, one record per deck at `decks/<id>/.turboslide/presence.json` (under the state folder the mirror never pulls and a deck removal deletes with the prefix). Each instance keeps the rows its own posts wrote, merges its changes (a set or a leave per client) into the record with `ifMatch` on the version it read (a retry through a fresh read when another instance wrote first; the test "lands both rows when two instances write at once"), and while a stream of the deck is open on the instance polls the record every 2 s and announces the rows of other instances to its listeners as the same `presence` and `leave` frames the memory tier sends, so the stream route, `rosterEntryForReader`, `filterEventForReader` and the client change nothing. A shared row lives at most 30 s without a refresh whatever ttl the route gave (`PRESENCE_SHARED_TTL_MS`; the client's heartbeat is 5 s), so a tab whose beacon was lost leaves every roster inside the matrix's 30 s bound; a leave writes a tombstone `{ clientId, at }` for the client and a set whose time is at or before the tombstone never lands, so a set pushed late from another instance cannot bring the chip back (the test "buries a set pushed late"). The record is written with an immutable copy under its md5 first (`.turboslide/presence/<md5>.json`) and read through `provenGet` (access-store.ts) with that copy as the read that holds, because the public store's url serves an overwritten body stale for a while (the cycle 2 fix round's measurement); an instance deletes the copies it wrote once they are a minute old, so the garbage is bounded to a minute of writes per instance. The live pointer is stripped from the shared rows (`PRESENCE_OMITTED_FIELDS`): a cursor moving at the poll's cadence would jump, and the same instance's tabs keep it as before. A heartbeat that moves the clock and nothing else is not pushed until the shared row has under half its life left, so the cost per active deck per instance is one `head` every 2 s, two puts at most every 2 s while a state changes and two puts every 15 s at rest; `head` is a simple Blob operation, the puts are advanced ones against SPEC-3 0.2's 75 per second for the deployment. The hello's `roster()` reads the record when this instance has not read it for a poll interval, so a fresh instance's first stream lists everyone (the test "keeps the live pointer on the instance that received it and lists every instance in a fresh roster read"). Every call meets the store's deadlines (`boundedBlobClient`), so a hung fetch cannot hold a presence post or the deck's push queue, the mechanism B7 read under C2-F24.

The wiring into the channel is eleven lines of `blob.ts` (a `shared` dependency, `presence` from it with `bind` and `owner` left on the memory channel since the client id's MAC decides across instances, the poll started with the first subscriber and stopped with the last, `close`) and one construction in `room.ts` `buildChannel` over `exportBlobClient()`; both files are B7's, so the change is R1 (section 4), a patch verified as described there.

#### 2.2 C2-F28, `comments.reaches-second-browser`: a comment moves no revision, so the other instance never learns of it

On the blob tier a comment entry is written to the sidecar inside the append (`room.ts` `applyComments` through `commentsApplierFor` and `applyAndPush`) and moves no deck revision; the append publishes the `op` to the writer's instance's listeners alone. The blob channel's only cross instance signal is the store's watch, which fires when the manifest's revision moves (`blob-store.ts` `watch`, `blob.ts` `announce`), so a tab streaming from another instance was never told and kept the threads it had; the second browser's `comment.list` (which since the cycle 2 fix round reads the store's index by `head()` and pulls proven bodies) would have listed the thread, but nothing scheduled it. That is the verifier's reading in C2-F28 ("the second browser's pull cadence or its instance's index still lag") made precise: there is no cadence, the refresh is event driven and the event never crosses instances.

The fix is `watchSidecarIndex()` in `comments-store.ts`: a poll of the head of `comments/index.json` every 2 s while a stream of the deck is open on the instance, which takes its position first (what is stored is not announced), skips the versions this instance pushed itself (its mirror's index carries the etag, `localIndexEtag`), reads a moved index through `provenGet` (the immutable copy `pushSidecar` stores is the read that holds while the url lags; the test "reads a moved index through its immutable copy") and hands over the revision and the thread ids whose row changed. The blob channel turns that into the checkpoint frame with `comments` the memory tier's checkpointer sends (`CheckpointEvent.comments`), at the revision the instance announced last so no tab's revision moves, and every tab answers it with `comment.list` (`controller.tsx` `scheduleCommentsRefresh` on `event.comments`). The wiring is in the same R1 patch. Beside it, `pullSidecar` no longer reads a thread whose file on disk hashes to the etag the index names for it (`pushSidecar` writes the etag beside each row it pushes), so the second browser's `comment.list` on a deck with many threads costs the index and the changed threads instead of a proven read (a `head` and a `get`) per thread; the test "pulls the index and the changed thread alone" counts the reads.

#### 2.3 C2-F28 and C2-F25, `collab.slide-added-appears`: the manifest poll is three seconds, not one

The row asks a slide added in the second browser to reach the owner's filmstrip within 5 s, three times of three; it passed in the run of record and failed in the rerun (2 cards where 3 were expected). The path is the blob channel's: the writer's instance commits (after the channel's 1 s write spacing per deck per instance), the reader's instance's store watch polls the manifest, pulls, and `announce` reads the record and publishes the op. `openBlobStore` polls every `options.pollMs ?? 3000` ms and nothing passes `pollMs` (`hosted.ts`, `root.ts`), so the poll is three seconds, not the one second `blob.ts`'s header, `select.ts` and VERIFICATION C2-F25 describe. The chain's worst case is the spacing (up to 1 s) plus the poll (up to 3 s) plus the pull (a `head`, the record's `get`, the slide's `get`, together 0.3 to 1 s) plus the frame and the tab's apply: over 5 s at the tail, around 3 s on average, which is a row that flips between two runs with no code change, the shape C2-F25 recorded. `collab.edit-from-second-browser` and `collab.edit-from-owner` run the same path with a smaller record and passed both runs, which is the same distribution read at its middle. A second mechanism sits in the pull: `blob-store.ts` `pull` probes `versions/<n>.json` for the next record by number with a plain `client.get` on every poll before the record exists, and the public store's edge can hold that miss ("a cached miss for a path written since", the proven read's own comment), so when the record lands the probe can still answer null; `announce` then publishes an external checkpoint and the tab reloads through `readEditorDeck`, which on another instance inside the 750 ms sync window answers the document from before the slide. Google delivers a new slide within about a second, so a longer driver bound is not a fix. Both mechanisms are in `blob-store.ts` (B7's): the request is R2 (section 4), with a one second poll and a `head()` before the record's `get` (or the proven read for a record whose `head` names it). Not driven here: no dev server has the poll.
