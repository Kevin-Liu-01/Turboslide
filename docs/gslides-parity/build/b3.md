## 2. Decisions

1. **One `runItem`.** Every menu row, toolbar button, key chord, finder row and right-click item
   runs a model item through `EditorShell.runItem`, which resolves the effect: `action` through
   `menuActionPlan` and the dispatcher, `dialog` and `panel` by title, `route` by path, `toggle`
   by setting, `client` by handler. Nothing draws or runs an item that is not in the model.
2. **The renderer arrives as a prop.** `packages/chrome` does not depend on `@turboslide/render`
   (no `pnpm add` this round), so the layout tiles and the theme thumbnails take
   `EditorShellInput.renderSlide`; without it a tile shows the layout's name on the plate. The
   route has `renderSlide` at hand.
3. **`deck.set` goes through `commit`.** No action carries a deck level mutation apart from
   `deck.rename`, so the Themes panel, Slide numbers and Alt text use the route's `commit(mutations,
label)` (the editor's own write with a history entry). Section 5 asks for an action.
4. **The chrome appearance.** `ts-chrome-appearance` holds light, dark or match; when nothing is
   chosen a stored `gt-theme` counts as the reader's explicit choice (the chrome lint and the
   tooltip audit set it), else the chrome matches the deck (SPEC 1.4).
5. **Stubs stay in the tab order.** A Later control is `aria-disabled`, never `disabled`, so its
   tooltip shows on hover and focus and reads the stub sentence (SPEC 13.1).
6. **Cancel is opt-in.** The dialogs that write (Make a copy, Delete forever, Slide numbers, Name
   current version, Download, Open, Link, Image by URL) show Cancel first; the information dialogs
   (Details, Share, Publish, Agent access, Help) show Done alone, as Google's do.
7. **Find and replace's Replace.** Prev and Next step through the slides that carry a match
   (`view.goto`); Replace runs `text.replaceAll` on the current slide alone; Replace all runs it
   over the deck. A single occurrence write needs a run level `text.replace` the window API does
   not expose; recorded, not hidden.
8. **The Hide the menus chevron** sits at the far right of the toolbar row (SPEC 3.1 row 18, R02
   4.1 row 20), not of the menu bar row as SPEC 1.1's table says; one chevron, one place.
9. **The Layout button and the Apply layout row** open the same `LayoutGrid`; the New slide arrow
   opens it for a new slide and remembers the pick under `ts-last-layout` (SPEC 5.3).

## 3. The route's input

`deckId`, `document` (the `DeckDocument`), `slideId`, `revision`, `dispatch`. Everything else is
optional with the default stated in the type's comments. What the route wires, and where it comes
from in `apps/studio/src/routes/edit.$deckId.tsx`:

builds the input from it (document with the deck and no slide bodies, dispatch, revision,
onNotice), so the rows already show on `/edit/gt-brand`; the bridge knows the slide's place from
the manifest but not its content, so the tail is the default one and the layout tiles carry names.
Once the route passes `editor`, the bridge is dead code and can go.

## 4. What is not proven yet, and what was cut

- The `editor` input is not wired in `edit.$deckId.tsx` (the integrator's file): the dev server
  runs the bridge. The contextual tails (text, shape, image, line, table), the panels' data
  (versions, findings, history), Undo and Redo from the menu, the clipboard rows, the Download
  dialog's progress and the Slideshow handlers are exercised under jsdom with a stub input, not in
  a browser.
- The route's own keydown handler (`EditorRoot` in `edit.$deckId.tsx`: Cmd+/, Cmd+L, Cmd+Z, Cmd+S,
  Shift+D, E) still fires on `/edit`: on the dev server Cmd+/ opened the source drawer over the
  shortcuts dialog. The integrator removes it when wiring `editor` (SPEC 10.2 retires those keys).
- `scripts/tooltip-audit.mjs` walks the page and the surfaces of the old shell (`insert.open`,
  `export.open`, `palette.open`, `.pt-orow-more`); it does not open the ten menus or the dialogs.
  `editor-shell-render.test.tsx` covers the File menu's rows and the dialogs under jsdom; the audit
  itself is a request (section 5).
- The lint driver (`packages/headless/src/shell.ts`) drives the states with the bare letters `[`,
  `g` and `b`, which the editor retires; `lint --chrome` on `/edit` therefore runs with `--states
""` (the rest state) until the driver gains editor states (section 5). `/decks` has no shell root
  the driver recognises (`.pt-viewer, .ts-studio, .viewer`), so its audit times out.
- Cut this round, recorded rather than hidden: the Presenting keys in the shortcuts dialog are
  data (B6 binds them); Paint format arms nothing without B4's `onPaintFormat` (the snackbar says
  what to do); `Text fitting` is the Later row only; the finder does not list the right-click only
  items beyond Alt text and Text fitting (they are menu items already).

### 7.2 Deviations recorded, not patched

1. **A Title slide has no place for a block.** The grammar's `title` and `statement` kinds carry
   fixed fields and no slot (`slideBlocks` is empty, `insertionSlot` is null), so on the draft of
   `/new` and on the audit's scratch deck (one Title slide) Insert > Text box arms the tool and a
   click on the sheet writes nothing (the stage's `toolInsertMutation` returns null), and the
   Table, Icon and Material pickers show "Table needs a layout with a body. Apply Title and body
   or Blank first" instead of a write. Google accepts a text box on every slide. Making the fixed
   kinds take blocks (a floating layer over the title fields, or turning the slide into Title and
   body on the first insert) is a grammar decision for Kevin, not a fix; until then the sentence
   names the two layouts that take blocks. The audit's `block.insert` rows therefore still read
   "no write" on the scratch deck; they pass on a deck whose first slide has a body (section 7.4).
2. **The Table picker is a dialog, not Google's in-menu hover grid.** SPEC 2.4 asks for "a grid
   picker (hover picks columns by rows, up to 20 by 20)"; the grid, the hover, the caption and
   the 20 by 20 cap are there, in the one Dialog primitive (focus trap, Esc, focus return) rather
   than as a dynamic submenu plate. The menu row keeps `action('block.insert')` in the model, so
   the audit, Search the menus and the shortcuts dialog are unchanged.
