## 5. Deviations and decisions, recorded

1. Every fetched family is under the OFL 1.1 in google/fonts (Roboto is under `ofl/` there, not Apache), so `FONT_LICENCES`' `Apache 2.0` has no member this round; the script and the catalog admit it for a later face.
2. The woff2 files are format conversions alone, so the ten families whose OFL text declares a Reserved Font Name (Lato, Merriweather, Playfair Display, Lora, PT Serif with "PT Sans", "PT Serif" and "ParaType", Libre Baskerville, Raleway, Source Sans 3's "Source", IBM Plex Sans and IBM Plex Mono's "Plex") keep their names: B7's reading of the OFL FAQ is that repackaging the same font data in another container is not a Modified Version that triggers the renaming rule, while subsetting or instancing would be. This is B7's reading, not a verified text; the catalog records the name per family (`reservedFontName`) so Kevin's row (A7, the membership) can drop a family if he reads it otherwise, and the standalone inlining of day 6 will therefore inline whole files for those ten and may subset only the sixteen without a Reserved Font Name.

### 15.4 Deviations and decisions

24. The clear when the last participant leaves (SPEC-5 10) is not made on the blob tier: the roster's truth across instances is eventual, and a clear on a roster one instance reads as empty would lose a live conversation. The deck's removal deletes the chat folder with the state folder, and a message leaves `chat.list` when its revision leaves the 2,000 entry window the action reads. The memory tier's behaviour (`chat.spec.ts`) is unchanged. Recorded for Kevin; a chat retention row on the blob tier (a delete of files older than a day on the poll) is one line in `pollShared` if he wants it.
25. A chat entry on the blob tier carries `seq` equal to the revision it was sent at, so it sits in the stream beside the record of that revision (after it in a page). The room client applies it as a remote entry with no mutations and hands it to `onEvent`; a chat sent at revision N and delivered to a tab already past N is dropped by the client as a duplicate of position N, which costs nothing since the panel reads `chat.list` every two seconds (`packages/chrome/src/panels/Chat.tsx`). A seq above the head would make the client buffer the entry and count the position wrong, so the revision is the seq.
26. The presence shard functions B7 exported in section 10 (`putPresenceShard`, `readPresenceShards`, `deletePresenceShard`, `PresenceShard`, `PRESENCE_SHARDS_DIR`, `BlobChannel.presenceShards`) are gone; no file outside `blob.ts`, `blob.test.ts` and B7's two documents named them (grep over the tree). The state file functions and `sharedRoster` replace them (15.2).
27. The two instance behaviour was not driven end to end on a checkout: a checkout selects `file`, `tmp` or `blob` (a Blob token) and no disk backed Blob store, so two dev servers cannot share one store. The proof is the unit tests over one fake client with two channels (the fake stages the listing lag and the CDN lag the deployment showed), and the pass 2 preview is the verifier's; the request below asks for the three probe runs the finding names.
28. A presence post that writes the roster file pays a head, a body and a put inside its request (one post per second per deck per instance at most; the rest ride the timer or the next request), and a leave waits up to the spacing (1 s) for its write; a stream open with a retire list waits the same per retired id before its hello. The client posts presence without waiting on the answer, so the cost is invisible to the tab.
29. A superseded stream (a second stream of one tab on one instance) posts no leave; the stream's lifetime close (240 to 290 s) still does, followed by the tab's reconnect and its presence post, which is the behaviour before the fix round with one roster write more.
