## 1. The answer in five sentences

Email sign in works locally end to end: the code exchange signed a person in 1.02 s after Verify, the anonymous deck stays theirs through the alias, and a second signed in browser reads the badge 1.33 s after the sign in started. Three defects stop "auth works perfectly" before any account exists on production: the provider callback of GitHub and Google is refused 403 by the studio's CSRF filter, the account menu's Sign out does nothing, and a signed out browser still renders as the account with the badge. The Profile dialog never receives its sessions, its keys or Delete account, and every code refusal says "That code did not match". Production has no database, so a seller sees no Sign in anywhere while two surfaces tell them to sign in. The missing pieces, in order, are the callback fix (an agent), the accounts database on D1 (the realtime round), the Google client (Kevin in the console), the `/privacy` and `/terms` pages (an agent writes, Kevin approves the text), a mail sender (Kevin's choice and a DNS step), and passkeys (an agent, after Kevin fixes the domain).

## 4. The defects

Each defect names its lines, its picture or reading, and its state on the realtime branch.

1. **The provider callback is refused by the CSRF filter.** `/api/auth` is a CSRF route (`apps/studio/src/server/headers.ts` 360) and the only GET exemptions are `/device` and `/api/auth/magic-link/verify` (`headers.ts` 405 to 408). A browser returning from github.com or accounts.google.com sends `Sec-Fetch-Site: cross-site`. Reading on the local server: `GET /api/auth/callback/github?code=fake&state=fake` answered 403 with `sec-fetch-site: cross-site` and with `none`, and 302 with `same-origin`; `GET /api/auth/callback/google` answered 403 `{"error":"forbidden"}` with `cross-site` (picture 19 is the `none` case). So no GitHub or Google sign in can complete on any deployment. Realtime branch: unchanged (`headers.ts` 429 to 432 on the branch), and its four Google rows stop at the aborted leave, so none of them reaches the callback.
2. **The account menu's Sign out does nothing.** The row is `action('account.signOut')` (`packages/chrome/src/menus/model.ts` 906). The plan falls through to `{ action: effect.id, input: {} }` (`packages/chrome/src/editor-shell.ts` 3356 to 3357). The server action finds no session for an undefined `sessionId` and answers `{ signedOut: 0 }` (`apps/studio/src/server/auth/actions.ts` 480 to 495). The working path, `EditorAccount.signOut()` with no argument (`apps/studio/src/editor/EditorRoot.tsx` 985 to 990: `sign-out` then a reload), is never called by the menu. Reading: six seconds after the click the session still answered and the page still read signed in (`facts-probe3.json` p3; picture 23). Realtime branch: the same row (`model.ts` 911) and the same action (`actions.ts` 500).
3. **A signed out browser still renders as the account.** Sign out leaves the anonymous cookie in place, and that anonymous id is aliased to the account, so `resolvePrincipal` renders it as the account (`packages/identity/src/resolve.ts` 215 to 220; the rule of `apps/studio/src/server/auth/alias.ts` 1 to 6). Reading after `POST /api/auth/sign-out` and a reload: A's own state read `trust: verified, signedIn: false`, and B's state read A's chip as `verified` (`facts-probe4.json` p4 `aOut`, `bSeesOut`; picture 24). On a shared computer the next person's edits render as the previous person with the badge. Realtime branch: unchanged.
4. **The Profile dialog is not wired.** `EditorAccount` has `sessions`, `tokens`, `revokeToken` and `deleteAccount` (`editor-shell.ts` 562 to 563, 582, 584); the account the route builds sets none of them (`EditorRoot.tsx` 930 to 998). So the Sessions box is always empty, "Sign out everywhere else" never shows, the API keys never list, and Delete account is disabled (`packages/chrome/src/dialogs/Profile.tsx` 251). The server has the data: `account.sessions` answered two sessions for one account in two browsers (`facts-probe4.json` p5). Picture 10. Realtime branch: no `sessions:` in `EditorRoot.tsx`.
5. **Every code refusal says the code did not match.** `SignInDialog.verify` maps every failure to `ACCOUNT.signInDialog.failed` (`packages/chrome/src/dialogs/SignIn.tsx` 60). Reading: after three wrong codes the right code answered 403 `TOO_MANY_ATTEMPTS` (`facts.json` c3), and the dialog would say "That code did not match. Try again or request a new one". An expired code reads the same. Realtime branch: unchanged (`SignIn.tsx` 74).
6. **An invalid address shows the validator's text.** "not-an-address" produced the error row "[body.email] Invalid email address" (`facts.json` a4; picture 04), the library's message passed through `authPost` (`EditorRoot.tsx` 277 to 286).
7. **The address quota withholds mail with no word.** Five requests for one address in a minute all answered 200 and three mails were written (`facts.json` c2; `better-auth.ts` 61 to 62, 140 to 143). The dialog says the message "is on its way" each time. The equal answer is deliberate (no account enumeration); the code step has no resend control and no countdown.
8. **A used magic link lands with an error nobody reads.** The second click landed on `/decks?error=INVALID_TOKEN` and the files page said nothing (picture 18). The realtime branch reads `?error=` in the editor only.
9. **Sign in exists only inside the editor.** The access page says "If you were invited by email, sign in with that address from your presentations" (`apps/studio/src/routes/-access-page.tsx` 80) and its comment calls the files page "where the account chip's Sign in row lives" (24 to 27), while `apps/studio/src/routes/decks.index.tsx` has no account chip and no Sign in (pictures 18, 22). The chrome's dialog cannot mount outside an editor (`-access-page.tsx` 26). Production shows the same two sentences with no sign in anywhere (`facts-production.json` prod3 at 01:55:15Z, prod5 at 01:55:33Z; pictures 32, 34).
10. **A revoked session stays signed in for up to 300 s.** The session cookie cache is on for 300 s (`better-auth.ts` 187). Reading: after `revoke-other-sessions` the second browser's `get-session` still answered signed in at 30 ms, 5 s and 20 s. "Sign out everywhere else" and a per session Sign out therefore take up to five minutes to reach the other browser.
11. **The label changes at sign in and the title row keeps the old one.** The browser was "Glass 257" before the sign in and the account was "Cobalt 516" after (`facts.json` a1, a8). The title row then read "Last edit just now by Glass 257" (picture 08), because it prints the stored author's name (`EditorRoot.tsx` 1610) while `resolve.ts` 117 to 119 says an aliased id and its account are one word.
12. **The passkey row is a dead control first in the list on main.** It sits above GitHub with the note "Passkeys arrive once the address is final" (`SignIn.tsx` 132 to 156; pictures 03, 21). The realtime branch moves it last and keeps it.
13. **A tmp store server counts as hosted, so the test switch is ignored.** `isHosted()` is `selection.kind !== 'file'` (`apps/studio/src/server/root.ts` 192), and the limiter ignores `TURBOSLIDE_AUTH_RATE_LIMIT=off` when hosted (`better-auth.ts` 195). Reading: the eleventh code exchange from one IP address within 10 minutes answered 429 (`facts-probe2.json` p4 `signIn: [200, 429]`). The limiter keys on `x-forwarded-for` (`better-auth.ts` 192), which Vercel sets; on a Worker the header to read is `cf-connecting-ip`.
14. **The sign in mail is plain and carries the code in its subject.** The subject is "Your Turboslide sign in code is <code>" (`apps/studio/src/server/auth/mail/templates.ts` 62), so the code shows on a lock screen. The HTML twin has the browser's blue link and no wordmark (`templates.ts` 30 to 32; picture 06).
15. **The Google button on the realtime branch breaks Google's branding rule.** It is text only, with an ink fill when primary (r4.md request R4-INTb; picture `docs/gslides-parity/cloudflare/build/r4/sign-in-d1-mail-off-light.png` on the branch). Google's guideline, fetched 2026-10-01 from https://developers.google.com/identity/branding-guidelines, says: "you can't change the size or color of the Google "G" logo. It must be the standard color version", with the fills #FFFFFF (light), #131314 (dark) and #F2F2F2 (neutral).
16. **The dialog is off the brand deck.** The buttons have an 8 px radius and the methods are bordered boxes (`facts.json` a3 `btnRadius: 8px`; picture 03b). The brand deck allows no rounded corners and draws lists as ruled rows (`/Users/kevinliu/repos/Prototemplate/deck/DECK-GRAMMAR.md` 39), and puts Title Case on buttons (22 to 23), where the row reads "Use a passkey".
17. **One account in two browsers reads as two people.** B's state held two entries with the same `usr_` principal, each with its own chip (`facts-probe4.json` p5; picture 26).
18. **Production lists every presentation to a stranger.** A fresh anonymous browser on `/decks` read "Every presentation on this Turboslide is listed here" above other people's decks, among them "Perf audit scratch" and "General Translation brand deck" (`facts-production.json` prod4 at 01:55:16Z; picture 33). This belongs to the access model more than to sign in; it is recorded here because accounts are what would scope the list.

## 6. The missing pieces, in order, with who does each

1. **The callback exemption.** Add `/^\/api\/auth\/callback\/[a-z]+$/` to `NAVIGATION_GET_PATTERNS` (`headers.ts` 405 to 408) with a unit row for `cross-site` and `none`; better-auth checks the `state` and the PKCE verifier on that route. Who: an agent, in the realtime branch before its Google hand row. Without it the Google client below cannot be used.
2. **The accounts database on production.** D1 `turboslide-accounts` through the Worker (`docs/CLOUDFLARE.md` 4.1 to 4.4). Who: the realtime round's orchestrator and lanes; production has none today (`/api/auth/*` 404 at 01:38:13Z).
3. **The Google client.** The project `Turboslide`, Branding, Audience External, Publish app, the Web client with the four origins and the four redirect URIs (`docs/gslides-parity/cloudflare/build/google.md` step 3, B1 to B9). Who: Kevin in the Google Cloud console (the harness blocks agents there), then the pipeline sets `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`. The facts fetched 2026-10-01: an app that asks for the name, the email and the profile alone shows no warning and has no test user cap ("your users do not need to be in the trusted user list, they will not see a warning message, and their authorizations will not expire after 7 days", https://support.google.com/cloud/answer/15549945); without brand verification "only your application domain will be visible to users" (https://support.google.com/cloud/answer/15549049).
4. **The `/privacy` and `/terms` pages.** Both answer 404 today (`curl https://www.turboslide.com/privacy` and `/terms` at 01:38:01Z and 01:38:02Z; `https://turboslide.com/privacy` answers 308 to the www host). Google's Branding page says of the home page, privacy and terms links: "These links are required for all external production apps. You will not be able to submit your app for verification if it is missing these links", and "The homepage must be hosted on a verified domain you own" (https://support.google.com/cloud/answer/15549049, fetched 2026-10-01). The basic scopes need no verification, so the client can be published with the links empty (google.md B4); the pages are needed for brand verification, which puts "Turboslide" and the logo on the consent screen in place of the domain. Who: an agent writes the two routes; Kevin approves the text, since it is a legal statement for General Translation; the brand verification needs a domain proof (a DNS TXT record or an HTML file), which is Kevin's DNS step.
5. **A mail sender.** Production runs `TURBOSLIDE_MAIL=off`, so the email method is hidden on the realtime branch and Google may be the only method. The two options as fetched 2026-10-01:
   - Resend (https://resend.com/pricing): Free is $0 a month with "3,000" emails a month, "100 emails a day" and "3 domains"; Pro is $20 a month for 50,000. "You must add and verify at least one domain to send emails with Resend" (https://resend.com/docs/dashboard/domains/introduction); no DNS provider is required.
   - Cloudflare Email Service (https://developers.cloudflare.com/email-service/): sending is "Email Sending Beta ... Available on Workers Paid plan"; "3,000 included per month, then $0.35 per 1,000 emails", and Workers Free is "Not available" for sending to arbitrary recipients (https://developers.cloudflare.com/email-service/platform/pricing/); "You must be using Cloudflare DNS to use Email Service" (https://developers.cloudflare.com/email-service/get-started/send-emails/). It has a REST API callable from Vercel.
   - `turboslide.com` uses `dns1.registrar-servers.com` and `dns2.registrar-servers.com` and has no MX and no TXT record (`dig` at 01:58:33Z). So Cloudflare's service needs the nameserver move and the Paid plan; Resend needs records added at the registrar.
   Who: Kevin chooses and does the DNS step; the pipeline sets `RESEND_API_KEY`, `TURBOSLIDE_MAIL_FROM` and `TURBOSLIDE_MAIL=resend`. At 100 mails a day a sign in by email covers about 100 sign ins a day, since one mail carries both the link and the code (`better-auth.ts` 239 to 249).
6. **Passkeys.** Install `@better-auth/passkey` at the version matching better-auth 1.7.4 and set `TURBOSLIDE_PASSKEY_RPID` (`better-auth.ts` 35). The rpID cannot move once credentials exist (`better-auth.ts` 6 to 8), so it waits for Kevin to fix the domain (`turboslide.com` covers the www host as a registrable suffix). Who: Kevin names the domain; an agent builds. Until then the row should be hidden instead of greyed.
