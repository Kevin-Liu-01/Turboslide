# Focus audit: slides, layouts and the filmstrip

Production, https://turboslide.vercel.app, 2026-09-15 (the deck ids carry the UTC date 2026-09-16). The deployment serves commit `ec61c6b` (`describe().version` 1). Driven by headless Chromium through `playwright-core` 1.62.1 from the repository root, viewport 1440 by 900 at device scale 1, at human speed: the mouse moves in steps with a pause between them, keys land 40 to 90 ms apart, double clicks are the browser's own, drags hold the pointer from down through the move stream to up, and Shift and Cmd are held on the keyboard while the mouse clicks. Every observed value is read from the DOM and from `window.turboslide.studio` (`describe().state`, `slide.get`, `slide.list`). Nothing in the repository was changed; the scripts import nothing but `playwright-core`.

The table in section 3 has one row per interaction: the feature, what a person does, the result (works, broken, flaky, not driven), the evidence, a screenshot under `audit-slides/`, a severity (3 the seller cannot complete a top task, 2 a wrong or lost result, 1 cosmetic; 0 on a row that works), the need (core, useful, park, judged against `research/07-sales-users.md` sections 2, 3 and 8) and one sentence why. A failed first attempt was repeated up to three more times inside the same row; where the same interaction was instead run as three separate trials on fresh slides the trials are separate rows, and the summary states how many of the three passed.

### 2.2 What is broken, with the mechanism seen

1. Undo or redo of a saved slide delete is refused by the server in some runs while the tab shows the change applied (severity 3, core, flaky: 2 of 6 controlled trials plus one uncontrolled occurrence). Run 7 trial 6: with the canvas focused, Delete removed the last slide (revision 15, server revision 15), Cmd+Z put it back in the tab, the revision stayed at 15, the title row read "Couldn't save, retrying", and a dialog "A change was not applied. Slide "split-5" already exists" listed the refused `slide.insert` with the mutation's JSON and the buttons Continue and Dismiss; after a reload the server held five slides, so the seller's undo was lost (`203-canvas-delete-undo-3.png`). Run 7 trial 8: Delete on the focused card, Cmd+Z, then Cmd+Shift+Z; the redo's `slide.remove` was refused with "No slide "split-5"" while the tab showed the slide gone; after a reload the server held six, so the seller's redo was lost. Run 2 row 7 (excluded, uncontrolled) met the same dialog with two refused inserts, "2 changes were not applied" (`65-grid-shift-select.png`). The same undo passed in run 7 trials 4, 5 and 7, in run 6 rows 4 to 9 and in run 1 rows 17, 19 and 20, one of which (row 19) logged a 409 from the server and still landed after the retry. The refusals are the `RangeError`s of `packages/schema/src/reduce.ts` ("Slide "x" already exists", "No slide "x""), thrown when the mutation is replayed against a document that already reflects, or does not yet reflect, the write before it. The tab's revision and server revision agreed before each refused write, so the document the refusing instance held did not match the revision it had acknowledged; the blob tier's per instance state under fluid compute is the likely cause (build-4/hotfix-4.md section 3.7 recorded a redo refusal of the same shape on this tier), but that is a hypothesis. What was measured is the refusal, the dialog, the retry message and the lost undo.

2. Apply layout carries a layout's own empty placeholders, sample content and the starter picture into the next layout (severity 2, core, broken: 3 of 3 trials in each case). Run 4 trials 1 to 3: a fresh empty Title and body slide (3 blocks) given Section header and then Title and body again ends with 4 blocks; the fourth is the Section header's starter picture, which stays on the slide through every later layout (`121-carry-picture-1.png`). Trials 4 to 6: Ruled statement list then Title and table leaves the four empty list rows under the table (`124-carry-list-1.png`). Run 3 shows the accumulation over 21 applies on one slide: by Figure the slide holds the title, a body, the list, the 4 by 3 table and the figure (`96-layout-figure.png`), and by Closing it carries the Status board's three "Live" rows, the Matrix's number grid, two extra paragraphs and the picture credit (`102-layout-closing.png`). The mechanism is `packages/schema/src/apply-layout.ts`: the function keeps "your content" by extracting every block of the old slide and filling or appending it into the new layout, and it does not tell an untouched placeholder or a layout's sample rows apart from content the seller typed. A seller who tries two or three layouts on a new slide ends with prompts, tables and a picture they never placed. With typed content only (run 4 trials 7 to 9) the move is correct.

3. Slide menu > Delete slide and Edit > Delete remove one slide when several are selected (severity 2, useful, broken: 3 of 3 trials each). Run 6 rows 7 to 9 and run 9 rows 8 to 10: two cards selected by Shift click, the menu row clicked, "Slide deleted", six to five. The Delete key on the card and the right click Delete remove all selected (2.1). `packages/chrome/src/editor-shell.ts` `menuActionPlan`: `slide.deleteSlide` plans `slide.remove` with `slideId: facts.slideId` alone, while `slide.duplicateSlide` and `slide.skipSlide` plan on `slideIds`, the selection; Edit > Delete runs the same plan. Duplicate and Skip from the menu act on both selected cards (run 9 rows 2 to 7).

4. A grid tile does not drag to a new place (severity 2, useful, broken: 4 of 4 attempts). Run 5 row 7: the second tile pressed, wiggled, moved to the left half of the first tile and released; the order was unchanged every time, while the same gesture on a filmstrip card reorders (run 1 row 25). The tile's `onMouseDown` is `pressWithoutFocus`, which calls `event.preventDefault()` (`packages/viewer/src/GridView.tsx`); a prevented mousedown stops the browser from starting the native drag the tile's `draggable` and `onDragStart` expect. The bottom bar's tooltip reads "Every slide as a tile; drag to reorder".

5. The applied layout snackbar counts empty placeholders as blocks that did not fit (severity 1, useful, broken: 3 of 3). Run 4 trials 11 and 12: Title slide applied to a fresh, untouched Title and body slide raises "Applied Title slide. 1 block did not fit this layout" with Undo; Main point on a slide with only a typed title raises "2 blocks did not fit" (run 4 trials 8 and 9). Nothing the seller typed was dropped.

6. A plain click on a grid tile opens the slide and leaves the grid (severity 1, useful). Run 5 row 4: the click on tile 3 made it current and closed the grid; the intended double click landed on the canvas. `GridView.tsx` `pick` runs `onSelect` on a plain click and `EditorRoot.tsx` sets the mode to `slide` in `onSelect`; only Shift and Cmd clicks select inside the grid. Google's grid selects on a single click and opens on a double click.

7. Cmd+M adds no slide (severity 1, park). Run 1 row 8: a card focused, Cmd+M pressed, six slides before and after, no snackbar. The product binds Ctrl+M as Google does on the Mac too and the menu prints ^M; nothing tells a seller who tries Cmd+M.

8. Not driven: the two tile Delete and Undo in the grid (my scripts, section 1), and a chrome slide counter with a go to field, because none exists in the editor; the footer counter and the card numbers are the counters a seller has (run 9 row 1).

Observations outside the brief, for the other auditors: the refusal dialog shows the mutation's JSON to the seller with the buttons Continue and Dismiss (`203-canvas-delete-undo-3.png`); a deck that sits in the trash still serves its full editor at `/edit/<id>` (200) and `/present/<id>` (200) while `/deck/<id>` answers 404 (`scripts/check-deck.mjs` on run 1's deck before it was deleted forever); the trash page lists a newly trashed deck only some seconds after the move (section 1).

### 2.3 What a seller needs here

The filmstrip is the seller's tailoring surface and the core of it works: add, duplicate, delete, skip, select, reorder, notes, the hash and the layouts all behave at human speed, including the undo that stands in for confirmation dialogs. Three things stand between that and "works well with every interaction":

1. The undo and redo of a saved delete must land every time (2.2 item 1). A seller who deletes a slide and presses Cmd+Z can read "Couldn't save, retrying" and a JSON dialog while the deck on the server differs from the deck on the screen. This is the one severity 3 finding and it sits on the most trusted action in the filmstrip.
2. Apply layout must move only what the seller typed (2.2 item 2). Trying layouts is how a seller uses the picker, and today two picks leave a slide with a picture, a list or a table to clean up by hand; the research's design rule 30 asks for the opposite, a reset to the layout's placeholders.
3. Delete from the menus must act on the selection the way the Delete key and the right click do (2.2 item 3), so a seller who selects three slides and picks Slide > Delete slide is not left with two.

The grid tile drag (item 4) is worth fixing because it is the grid's stated purpose, but a seller finishes with the filmstrip drag. Items 5 to 7 are cosmetic. Nothing in this area needs removing; the shapes and drawings Kevin named are outside it.
