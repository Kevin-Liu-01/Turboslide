### Decisions

1. The variant key is the sha256 hex digest, 64 characters and no prefix, of `JSON.stringify([source, resolved, screen])`: `source` is the file identity of the continuous source (`asset.sourceFile`, else the light twin, else the neutral file), `resolved` is the field with every default of SPEC-3 10.1 filled in and its keys in one fixed order, `screen` is `[round(w / cell), round(h / cell)]` in cells. The bare hex form is what B1's in progress `ASSET_VARIANT_KEY` (`/^[0-9a-f]{64}$/`) keys `Asset.variants` by, so a record written with this key validates without a request. The theme is not in the key (a variant lists both twins or one neutral file for `same`). The source identity is a path rather than a byte digest because the string renderer has the document and nothing else; SPEC-3 8.5 makes the asset files digest named, so a replaced source changes the path and the key. The digest runs in plain TypeScript (`sha256.ts`) so the browser and Node compute one value; the test pins it against `node:crypto`.
2. The overlay canvas is emitted only in a live render (research-3 06 4.4 "only in a live render, RenderOptions.live"). Every non live surface reads the variant or, in state `live`, shows the continuous twin; the standalone build refuses a live picture with "materialize first" (day five).
3. `readDither` and `variantFor` read the block's `dither` and the asset's `variants` structurally, because B1 lands the types the same day. B1's in progress `packages/schema/src/blocks/dither.ts` (`PictureDither`) and `assets.ts` (`AssetVariant`) match `PictureDitherLike` and `AssetVariantLike` field for field; at stage 2 the local types become imports and the two structural readers stay as the guard against a stale value.
4. The escape block's images are sized in the dispatcher (`render-block.ts`) before B4's renderer runs, since `html-escape.ts` is B4's file. When B4 moves the block into the frame the same `withImageSizes` result is what the frame source receives, so the frame document carries the sizes without another call.
5. The frame is behind `RenderOptions.htmlFrame` so no document changes until B4's frame module lands; the GT deck's imported escape slides keep their pixels.
6. The collaborator hooks live in `apps/studio/src/styles.css`, not in the theme's `stage.css`: `packages/theme/src/theme.test.ts` requires every theme rule to start with `.ts-sheet` and refuses `:root`, and the overlay, the title row and the filmstrip are chrome outside the sheet. A first attempt in `stage.css` failed that test and was reverted; the test was not touched. The hooks are geometry only; the hues, marks and type are B6's in `packages/chrome`.
7. `width` and `height` are the stored `asset.size` as written (SPEC-3 9.2 E12 says "from `asset.size`"), not the sheet pixel size at the asset's `scale`; every sheet rule fixes at least one dimension, so the values only carry the ratio.

### Decisions

1. Cross package imports of the new modules go through existing subpaths (`@turboslide/effects/pipeline` for `dither.ts` and `blue64.ts`, `@turboslide/effects/io` for `dither-io.ts`, `@turboslide/render/runtime` for `dither-runtime.ts`) because every `package.json` is the integrator's; the modules keep their own files and the re-export lines say so. Once the export lines land (request 1) the imports can move to the named subpaths without a code change elsewhere.
2. The chrome writes the field as `block.set /dither` (the dialog, the section, the Material section). SPEC-3 10.5 makes that the window transport's implementation of `picture.dither`; the editor's `on()` table (B2) and `picture.dither`'s store implementation (B1) have not landed, and this write works on every transport today. The menu row `format.image.dither` (B6) dispatches the action and needs B2's row (request 7).
3. The exporter's materialization pass writes files and records on a copy, never the deck's own record: the export package does not depend on the store, and the committed record is `picture.materialize`'s write, which the CLI and the studio run around an export (request 3 to B1). The merged report names the files the pass wrote.
4. A `material` block has no `dither` field in the schema (B1 put it on `picture` and `shot`, SPEC-3 10.1), so the Material section's Two-tone row becomes the Dither toggle for a picture object over a material frame (the Background dialog's Material row makes one) and stays the capture flag for a material block. B1 may add the field to `material` later; the section then gains the row for the block kind too.
5. A picture only page in Perfect mode is a palette PNG, not the 1-bit PNG SPEC-3 10.4 names, because the page carries the frame's hairlines beside the two tone picture; the raster policy keeps it exact under the perfect budget, and the 1-bit encoding is the variant file's (about 4 KB at cell 2, 16 KB at scale 2) and a page whose colours are exactly two. Recorded in docs/pptx.md.
6. The Background dialog keeps round two's Choose paths (the editor's handle, else the plan and `block.order`) when no dither is remembered, because B6's `dialogs-round-two.test.tsx` asserts them; the one write of 10.6 runs when the Dither toggle is remembered on a canvas slide (`slide.setBackgroundPicture` with the dither).
7. The blue noise texture is generated, not downloaded: the account boundary and the offline requirement made an owned void and cluster generator the safe route; the bytes are committed and pinned.
8. `slide.setBackgroundPicture` refuses a slide that is not a canvas with a sentence naming `slide.toCanvas` unless the deps carry a `dispatch`; the canvas conversion needs the measurer that lives in `apps/cli/src/store-actions.ts` (B1) and is reachable only through the dispatcher.
9. The `upload` form of `asset.add` and `slide.setBackgroundPicture` passes through to the intake's `readUpload` (B4's route reads the presigned object); without it the intake refuses, and the dialog's upload line stays reserved and empty on a checkout.
10. The Rust crate did not gain the new stages this stage: the TypeScript stages are the reference SPEC-3 10.2 names, the parity test pins them against `twoTone` on the sixteen recorded treatments, and the wasm path in the browser is optional; the crate is recorded for the fixer round or round four (the napi and wasm builds are untracked build outputs, nothing changes in the tree).
11. The CSP nonce reaches the page from this stage (SPEC-3 8.8; B4's build-3 request 2 named the integrator for `router.tsx` and `__root.tsx`, both B5's in MILESTONES-3): `getRouter()` reads the request context's `nonce` through `getGlobalStartContext` from `@tanstack/react-start` (the client stub answers nothing; a router built outside a request answers nothing) and passes `ssr: { nonce }`, which `HeadContent` and `Scripts` read for the framework's own inline scripts; `RootDocument` puts `useRouter().options.ssr?.nonce` on the theme boot script, the shell boot script and the block CSS `<style>` with `suppressHydrationWarning`, because the browser hides the attribute once the script ran. Before the change the dev server logged `script-src-elem` reports for both boot scripts and the framework's hydration script on every page, and the shell boot script never ran (no `data-boot-*` attribute could appear); after it the only reports are two `script-src` `eval` lines from `node_modules/.vite/deps/iso-*.js` (a pre bundled dependency chunk of the dev server, lines 262 and 1937), recorded for B4 under Requests.
12. `dither.spec.ts` waits for the room's confirmation after every dialog write before its page goes (`deck.info`'s `revision` moves on the server's entry; the local apply is optimistic). The first spec run passed the toggle test and failed the slider test on reopening the deck without the dither: the room client's ops POST answered 2 to 4 s after the click on the loaded dev server (structural ops flush at once, the answer waits on the server), the page closed first and the op went with it (the dev log's `AbortError: This operation was aborted` lines). The record on disk stood at revision 3, the picture's write, with no `dither` field.
