## HR-O#5: a release reads what the release after it wrote

What failed. Every document object is strict (`z.strictObject`) and `schemaVersion` stays 1 while rounds add fields, so after an Instant Rollback or the guard's promote back the older release refused every deck the newer one had saved with a new field, and the mutations in version records had no migration at all.

Reproduced on `origin/main` first (`packages/schema`, 2026-10-11 21:58, load 449): the worked slide `content-rule` with `schemaMinor: 1` and one new field `futureFrame` read as two `unknown_field` issues of severity 3 (`/futureFrame` and `/schemaMinor`), so the deck does not open; `schemaVersion: 2` read as `ahead`.

The mechanism.

- A minor beside the major. `SCHEMA_MINOR` (0) in `packages/schema/src/deck.ts` and an optional `schemaMinor` (an integer above 0) on `deck.json` and every slide file, and on version records. A release that adds a field raises the minor and stamps it on what it writes; a field renamed or removed raises `SCHEMA_VERSION` with a migration, as before. A file without the field is minor 0, and this release writes none, so the release before it reads everything this one stores.
- The tolerant parse (`parseTolerant`, `packages/schema/src/migrations.ts`). A parse that fails only on unknown keys, each inside an object whose nearest `schemaMinor` is above this release's, is parsed without them, and the keys are put back on the parsed value in their places and in the key order the file had, so a canonical file the newer release wrote serializes to the same bytes. A file of this release's own minor stays strict: a typo is still an `unknown_field`. Any other fault fails as before.
- Where it reads. `validateSlide` and `validateManifest` (each kept field is a severity 1 `kept` issue; a newer major is now `upgrade_pending`, the code the checkpoint route of HR-RT#9 answers), the reducer's slide parse of `slide.insert` and `slide.replace` (`parseMutationSlide`), and every version record parse (`safeParseRecord` in `packages/store/src/versions.ts`, used by `parseVersionRecord`, `versionRecordText` and the Blob store's `parseRecordBytes`).
- The mutations take the documents chain. `migrateMutations` runs the slide migrations over the slides a record's mutations and inverse carry, so a record written before a migration replays after it; the reducer runs the same chain on the slide it inserts or replaces.
- The rollback gate. `packages/schema/scripts/pin-previous-validator.mjs <ref>` takes `packages/schema/src` of a release out of git, bundles its `validate.ts` with zod, and writes `packages/schema/fixtures/previous-validator/validate.mjs` with `PIN.json` (sha, zod version, bytes, sha256). Pinned: f7e97039, the release production serves, 423,311 bytes with zod 4.6.1; two runs gave the same sha256. `src/previous-validator.test.ts` runs that validator over the documents this release writes (the worked deck, the GT deck, the GT template, the blank template, each validated and written as canonical JSON first): it reads all four with no severity 3 issue, and it refuses a manifest with an unstamped new field, so a push that adds a field without raising the minor fails here.

After (pins): `packages/schema/src/newer-minor.test.ts`, 10 tests: a slide and a manifest of a newer minor round trip byte equal with `kept` issues at `/futureFrame` and `/slots/left/0/futureShadow`; the fields survive a `block.set` through `applyMutations` and the validator, and the slide's bytes differ from the input only by the written text; an unknown field of this minor is still refused; a newer minor whose fault is not a field is refused; `schemaVersion: 2` is `upgrade_pending`. `packages/store/src/newer-minor.test.ts`, 6 tests over a FileStore: the deck opens with the two `kept` issues; a write to the slide keeps the fields byte equal; removing the slide writes a record whose inverse holds it whole, and the undo restores the file byte equal; a record with an unversioned slide in a `slide.insert` replays stamped; a record a newer minor stamped round trips byte equal; an unknown record field of this minor is refused.

## HR-O#6: a resent agent write is applied once

What failed. An agent that resent a write after a timeout met a 409 (its first attempt had moved the revision), read the deck again and wrote a second time, so the deck took the change twice; the API skill tells agents to do exactly that.

Reproduced and read on the lane's dev server (port 4866; `TURBOSLIDE_STORE=tmp`, `TURBOSLIDE_REALTIME=memory`, `TURBOSLIDE_LOCAL_OPEN=1`, `TURBOSLIDE_MAIL=capture`, `TURBOSLIDE_AUTH_RATE_LIMIT=off`; a scratch deck made by `deck.create` and removed by `deck.trash` and `deck.remove`; 2026-10-12 01:56, load 389 to 434). A request without a key takes the code path of `origin/main`.

| Step                          | Without a key                                                | With a key                                                      |
| ----------------------------- | ------------------------------------------------------------ | --------------------------------------------------------------- |
| `slide.new` at revision r     | 200, revision 1, `big-number-1`                              | 200, revision 3, `big-number-3`                                 |
| the same request again        | 409 "baseRevision 0 is stale; the document is at revision 1" | 200, `idempotent-replayed: true`, the first record (revision 3) |
| the agent's re-read and retry | 200, revision 2, `big-number-2`                              | not needed                                                      |
| slides in the deck            | 1 to 3                                                       | 3 to 4                                                          |

Two sends of one key at once: one 200 that wrote (revision 4) and one 200 replayed; the deck took one slide. A malformed key (`two words`): 400 `invalid_idempotency_key`.

The mechanism, one op id from the route to the record.

- `packages/agent/src/http/dispatch.ts`: `Idempotency-Key`, 1 to 255 visible ASCII characters, else 400 `invalid_idempotency_key` before the action runs; `idempotentOpId(caller, key, n)`, the op id of the nth write of a keyed request: `idem-` and 32 base64url characters of the sha256 of the caller and the key, and `-n` from the second write. Two callers' keys never meet, and the id fits the room's 64 characters.
- The route (`apps/studio/src/routes/api/actions.$action.ts`): a POST of a writing action with a key builds the deck dispatcher over `keyedStore` (`apps/studio/src/server/idempotency.ts`), which gives each write its op id as the write's `origin`, under the client id the room gives a server write for its author. The caller is the API key record, else the principal. Once the gate admitted the call, a resend whose first attempt is in the log is answered before the action runs (`replayedRecord`, `replayedResponse`): 200, `idempotent-replayed: true`, the record's n, revision, author, note and time. An action that picks a fresh id each time (`slide.new` without an id) is not run again.
- The tiers. Do (production): the room backed store hands the op id to `admitServerWrite`, which sends it to the object as `x-turboslide-op-id` (`ROOM_WRITE_OP_ID_HEADER`); the object answers the entry it holds under the write's client id and op id (`findEntry`) before the base check, and admits a new write under it, so the checkpoint's record names it in its origin. A header and not a body field: the body schema is strict, and an object of the release before ignores the header and takes a fresh id. Blob: the origin reaches the Blob store's write, which answers a write whose op id a record above its base names with that record (the contract it already kept). Tmp: the FileStore keeps the same contract when opened with `origins` (the tmp backend does; the Blob store's own FileStore does not, since the Blob store keeps it itself).
- Agents learn it from the contracts: the OpenAPI document declares the header once (`components.parameters.IdempotencyKey`) and names it on every writing action, the manifest's execution rules and `llms.txt` carry a Retries line, and `skills/turboslide-api/SKILL.md` tells an agent to send a new UUID per write and the same key on a resend.

What the key does not cover: the actions whose writes do not go through the deck store (comments, sharing, accounts, the deck collection's `deck.create`, `deck.copy`, `deck.trash`), and `version.save`. Their resend behaves as before.

Pins: `packages/agent/src/http/http.test.ts` (the key's form, the op ids per caller, key and write, the refusal before the action runs); `packages/store/src/file-store-origin.test.ts` (a resend answered with its record and committed once, also by a second store over the same folder; another op id and no op id commit; no origin read or stored without the option); `apps/studio/src/server/idempotency.test.ts` (two writes of one request with their own op ids; the resend answered by the store for both; the look up; another caller's key is its own write); `apps/realtime-worker/test/idempotent-write.test.ts` (the object admits the first send, answers the resend with the same seq and `replayed`, fans out one op, records one origin; another key and no key as before; a malformed op id is 400). The row `sync.agent.idempotent-retry` enters with HR-0.

## HR-O#8: the node-server build exits on SIGTERM

What failed. srvx closes the listener on SIGTERM and SIGINT and then calls Nitro's `close` hooks, but nothing ended the process: timers kept the event loop alive, a process manager waited out its kill timeout, and the entries the memory channel held in the process were lost with it.

Before. Read on this machine at 2026-10-12 02:00 (load about 380): seven node-server builds (`node apps/studio/.output/server/index.mjs`) of other sessions' scratch worktrees were alive with no listener, the oldest started 2026-10-11 06:32, about 19.5 hours earlier (pids 39135, 96307, 49685, 61944, 63725, 78525, 94316). Each had been sent SIGTERM by its script, closed its listener and stayed. The research reproduced the same three times (`research/perf.md` PERF-18: alive 30 s after SIGTERM with or without open connections, one for more than 10 minutes until SIGKILL). The build of `origin/main` installs no signal handler of its own, and srvx's ends nothing but the listener.

The mechanism. `apps/studio/src/server/plugins/shutdown.ts`, a Nitro plugin `vite.deploy.config.ts` lists for the node-server preset alone (and which does nothing when `VERCEL` is set), wires `createShutdown` (`apps/studio/src/server/shutdown.ts`): at the signal a deadline is armed (9.5 s); when the listener has closed (the `close` hook), or after 6 s when no `close` hook comes (srvx installs no signal handler under `CI` or `TEST`), the derived sweep in flight settles (`settleDerivedSweep` in `root.ts`), every room on the memory and redis tiers commits its tail and every room closes (`flushRooms` in `room.ts`; the do tier's object keeps its own tail and the blob tier has none), and the process exits 0, or 1 when the flush failed or the deadline passed.
