## 1. The asks and the decisions

### 1.1 Kevin's words, verbatim

"make turboslide super secure with data and authh, super performannt, and bullet proof and do a massive codebase cleanup, rewrite any backennd logic into rustm" (2026-10-08).

The standing rules that bind this round: "make sure turboslide is super optimized and super cheap to run while being fully featured and super performant"; "make sure to actually test our features and make sure they work"; one shared component or module for any cross cutting standard; plain technical English in every word a person reads; no word a person reads names another company's slides app.

### 1.2 What each ask means in this codebase

1. **Data and auth security.** Today production does not enforce its access model. Every decision runs in shadow mode (DATA-1), and every document sits on a public Blob store (DATA-2). The agent surface `/mcp` accepts any API key for any deck (AUTH-2). The CDN keeps thumbnails of restricted decks under URLs anyone can request (CRIT-M2). The assets route serves any deck's pictures to anyone (CRIT-M3). The web page export is a public copy of the deck (CRIT-M4). The Worker serves raw SQL over the accounts database behind one bearer shared by preview and production (AUTH-3), and that database holds session tokens and Google's tokens in plain text (CRIT-M5, SPEC-2). A slide's CSS could carry a script into every viewer's page until H1 landed (WEB-1, WEBV-1). The ask means five things. The access model is enforced at every entry point with one context builder. Documents leave the public store. Every cache rule follows the reader's standing. Every secret is per environment and narrow, and stored credentials are hashed or encrypted. Every sink that writes deck content into a page treats that content as untrusted.
2. **Performance.** Clicks and typing already measure well (perf.md section 6). The problems are elsewhere. Store cost grows with a deck's history (PERF-1 to PERF-3). The editor loader is a serial chain (PERF-4). Pages ship code they do not use (PERF-8 to PERF-12). Cold starts write 30 MB of fonts (PERF-6). The admission clones and validates the whole document for every typed entry (RUST-1). The ask means costs that stay flat as decks and histories grow, with each one pinned by a budget.
3. **Reliability: nothing a person makes is lost, and every failure is handled.** The normal path is durable (reliability.md "What holds"). The losses are on recovery paths: a checkpoint answer lost and committed twice (RELIABILITY-1), the three two-typer losses and the lost-answer residual R (RELIABILITY-2 to 4, CRIT-M1), the pending store's Apply (RELIABILITY-5, 6), the oversized change (RELIABILITY-7), the object's failed close and dropped tails (RELIABILITY-8 to 11). There is also no backup and no alert that reaches a person (RELIABILITY-13, 14). The ask means each recovery path keeps every word exactly once, and each failure produces a sentence for the person and a message someone reads.
4. **A large cleanup.** 70 percent of the tracked tree and 94 percent of its history is the evidence folder (CLEANUP-5). There are 48 dead exports and 508 needless ones (CLEANUP-9). Thirteen hand written constant time comparisons exist, and the render worker has a fourteenth plain comparison (CLEANUP-1, CRIT-M8). One job is often done two to four times (CLEANUP-11). Infrastructure Kevin ruled out still has code paths (CLEANUP-6). Five specs, the Worker's tests and the Rust tests run in no gate (CLEANUP-3). The ask means one module per job, nothing in the tree that nothing reads, and gates that catch drift.
5. **Backend logic in Rust.** Section 6 gives every module a verdict. The research overturns most of the orchestrator's starting position. The one CPU hot path is algorithmic and is fixed in TypeScript 300 to 470 times over. serde_json in wasm is slower than V8 at the boundary. One TypeScript source shared by the browser, the function and the Durable Object is what makes them converge. Auth stays on better-auth. The Rust work this round is the existing crate (phase 1). Kevin can overrule this (question 10).

### 1.3 The decisions

1. H1 is on `origin/main` (`8be64284`). H2 and H3 ship next (section 3). No lane edits a file listed for H2 or H3 until that hotfix is on `origin/main`, and every lane rebases onto `origin/main` once H3 is there.
2. K1 and K2 are the first lanes with a step only Kevin may take: creating a paid store, setting secrets, running a production migration. The code half of each lands before his step and after it, as section 4 lists.
3. Severity 4 and 3 security fixes go through the guard first, then severity 4 and 3 reliability fixes, then the rest by severity (section 5). SA#1 (one `safeEqual`, severity 2) goes first, because SD#5, O#1a and PS#11a use it.
4. One mechanism per push, and each push rolls back alone with the guard's promote back. Three limits bind that claim. (a) A push with a D1 migration (K2#3, SA#3, O#2c) only adds a table, which the older build never reads, so the older build runs on the newer schema. No migration in this round drops or renames anything. (b) A change to what the store writes lands as a reader first and a writer one release later (O#5; PS#12a, then PS#12b), so the release before the writer reads everything the writer stores. (c) Kevin's steps carry their own way back: before the cutover, `migrate-storage rollback` (`docs/hosting.md` section 10); after a rotation, a new rotation.
5. A security finding a verifier refuted is dropped as a finding. Any fix it still warrants rides with the finding that needs it (AUTH-1 with AV-1 in H2; DATA-3's residual in K1#5a, K1#5b and SD#3). Findings the verifiers, the critic and this revision found are registered (2.2) and assigned.
6. Rust: no backend port this round. Phase 0 is the TypeScript work that removes the measured cost (lane RT). Phase 1 is the crate (lane N). Phase 2 has triggers (section 6.4).
7. One shared module for each cross cutting standard this round touches: `safeEqual` (SA#1), the cron credential (O#1a), the error reporter (O#2a) and the alert sender (O#3), the deck listing (C#7), the rewrite rule (RT#3, RC#2), the limiter (SA#3), the CSP builder in `headers.ts` (W#3b uses it for the static pages), and the zip, sha256, `writeAtomic`, `requireSlug` and sign in modules (C#5, C#6).
8. Every fix is pinned by a test, a matrix row, a hosted smoke row or a budget (section 8). A pin that holds a push is a unit, route, Worker or store test, a matrix row that is not a measurement row, or a hosted smoke row. A measurement row and a timing are records. A lane runs the feature rows its push touches on a local server before it commits (section 9).
9. No push enters a matrix row before HR-0 is on `origin/main`, and HR-0 waits for the dropdown round's last push (8.1).

## 2. The findings

### 2.1 How the register was built

Every finding in the nine files is listed below with its final severity and where it is fixed. "Verdict" is the verifier's where one ran (auth, data, web). The other audits had no verifier, so their findings stand as reported with their evidence. The critic's points that are defects in the code (CRIT-M2 to CRIT-M5, CRIT-M8, CRIT-M9) and this revision's SPEC-2 are registered in the last table. Its points about the spec itself are answered in 2.5. Severity follows the round's scale: 4 means a person's data or account can be read, changed or lost by someone else or by a common failure; 3 is a serious weakness with a plausible path; 2 is a real defect or a missing defence; 1 is hygiene. The matrix's own scale stops at 3 (`core-matrix.test.mjs` 87 accepts 1, 2 and 3), so a round severity 4 enters a matrix row as 3. A dash in "Where" means the finding needs no work.

### 2.4 SPEC-1, read for this spec

`GET https://www.turboslide.com/home` at 18:50 UTC (load 131) answered from the CDN (`x-vercel-cache: HIT`, `age: 1233`) with these headers only: `accept-ranges`, `access-control-allow-origin: *`, `age`, `cache-control: public, max-age=0, must-revalidate`, `content-disposition`, `content-type`, `date`, `etag`, `last-modified`, `server`, the short `strict-transport-security: max-age=63072000`, `x-vercel-cache` and `x-vercel-id`. There was no `content-security-policy` of either kind, no `x-frame-options`, no `x-content-type-options` and no `cross-origin-opener-policy`. `GET /docs` at 18:59 UTC (load 143) had the same header set (`x-vercel-cache: MISS`). `/decks` and `/signin` carried the app's headers (`content-security-policy-report-only`, `x-frame-options: DENY`, `nosniff`, COOP). The cause: the prerendered files are served by Vercel's static layer, and `ROUTE_RULES` (`vite.deploy.config.ts` 252 to 272) give them `cache-control` alone. The security headers come from the request middleware, which never runs for a static file.

Each prerendered page carries its own build time nonce, the same for every visitor of that page. `/home` carried one value on 52 tags at 18:50 UTC. The critic read four pages at 19:29 UTC (load 152) and found four different values (`/home`, `/docs`, `/docs/reference/block`, `/docs/shortcuts`). There are about 70 such pages, so one route rule for `/docs/**` cannot name their nonces, and a `<meta>` CSP ignores `frame-ancestors`. The critic also found that route rules do reach static files: `/favicon.ico` answered the rule's day long `cache-control`, and `/` answered `x-robots-tag`.

So the landing and every docs page can be framed by any site, and they fall outside WEB-3's site-wide CSP plan, which only reaches responses the function writes. Severity 2, a missing defence on public pages that hold no deck content. Fix: W#3a puts the headers in the route rules for `/`, `/home`, `/docs`, `/docs/**`, `/favicon.ico` and `/robots.txt`: `x-content-type-options: nosniff`, `x-frame-options: DENY`, `cross-origin-opener-policy: same-origin`, `referrer-policy: strict-origin-when-cross-origin` and the long HSTS value. W#3b gives every prerendered page one nonce per build and a CSP header in the same route rules. The build mints the nonce once (`TURBOSLIDE_PRERENDER_NONCE`), the request middleware uses it during the prerender in place of a fresh one, and `headers.ts`'s policy builder writes the header with `frame-ancestors 'none'`. A static page holds no injected content, so one nonce per build carries no risk there. Pins: the rows `security.static-pages.headers` and `security.static-pages.csp` (8.2), `check-vercel-output.mjs` reading the headers in `.vercel/output/config.json`, and the hosted smoke rows `static headers /home`, `static headers /docs`, `static csp /home` and `static csp /docs` (8.3).

### 6.2 Phase 0, this round, in TypeScript (lane RT)

RT#3 (one rewrite rule), RT#5a and RT#5b (incremental admission), RT#10 (deck cap) and RT#16 (Text memo). The parity method for RT#5a: 2,000 seeded random mutation sequences (mulberry32 seeds recorded) on GT and on the 850 slide copy, comparing today's `landCandidate` with the new one for equal `ok`, `reason`, `message` and resulting document, with every base document deep frozen so a write through a shared reference throws (CRIT-M17). The flag is `TURBOSLIDE_ADMISSION=incremental|full|shadow`. `shadow` decides with `full`, runs `incremental` beside it, and counts disagreements on `/health`. RT#5a ships production on `full` and the preview on `shadow`. RT#5b makes `incremental` production's value after seven days on the preview read zero disagreements (CRIT-W10). The browser keeps `applyMutations` and its deep copy; only the admission calls `applyMutationsTouched`. The gain measured on the prototype: 16.3 ms to 0.051 ms per entry on GT, and 122 ms to 0.261 ms on 850 slides.

### 6.3 Phase 1, this round, the crate (lane N)

Scope: N#1 (napi out, wasm the crate's one output), N#2's CPU reading, N#4 (the native CI job), N#5 (the dither port if and only if a frame misses 16 ms of CPU), N#6 (DSSIM restructured) and N#7 (the export profile). The parity method is the crate's existing rule, made general. The TypeScript stays the reference. The Rust passes the same vitest suite through the backend selector (`packages/effects/src/select.ts`). A seeded comparison checks outputs byte for byte, or DSSIM within 1e-9. CI runs it with `TURBOSLIDE_NATIVE_REQUIRED=1`. The flag today is `TURBOSLIDE_EFFECTS_BACKEND=native|wasm|typescript|auto`, and `auto` tries native, then wasm, then TypeScript (`select.ts` 3, 18, 42 and 45). After N#1 it is `wasm|typescript|auto`; `auto` selects TypeScript in Node and the browser's worker keeps wasm through `backend.ts` (CRIT-W6). `describeBackends()` reports which ran. The measurable gain of phase 1 is a smaller build, a parity gate that runs on push, and a binary whose hash is checked. It makes no user-facing speed claim.

### 6.4 Phase 2, later, each with its trigger

- Image decode, resize, encode and SVG raster in the crate's wasm (`image`, `png`, `zune-jpeg`, `resvg`), replacing sharp where N-API is missing. Trigger: the app moves onto Workers (`docs/CLOUDFLARE.md` stage 2).
- The logo sanitizer on `roxmltree` in wasm. Trigger: N#2 finds a parser defect.
- An export stage in the crate. Trigger: N#7 shows a JavaScript stage (scene extraction or the pptxgenjs write) above 10 s of CPU on `gt-brand`.
- A document core in Rust (reducer, transforms, validator) compiled to wasm and run by the browser, the function and the object alike, never as a server-only copy. Trigger: a measured cost that phase 0 cannot meet on a mid range laptop or in the object, read at a load under 24 or as CPU time.

Never: auth, the Blob store, Chromium orchestration, the MCP server, SSR.

### 6.5 Where the research overturns the orchestrator's starting position

The starting position was that Rust buys speed and correctness in the admission and transforms, the schema's validation and migrations, export and image work, and that auth and runtime glue should stay. The research keeps the second half and the image work. It overturns the rest, for the reasons in 6.1: the admission's cost is algorithmic, the wasm boundary is slower than V8 for this document, export is not yet shown to be CPU bound in JavaScript (N#7 reads it), and a server-only Rust copy of the document core would be a second implementation the browser cannot share. The framing's statement that the crate is "loaded through napi in the Vercel function" is also incorrect: no Linux addon was ever built (CLEANUP-7, RUST-3). Kevin can overrule this with question 10.
