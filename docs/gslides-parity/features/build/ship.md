### 4.4 The banner after the tab's own server side write, and the fix

The ship agent's seller visible finding (severity 2, no row): on the blob tier the announce path's resync after `asset.add` and `logo.insert` showed the banner "Revision rN arrived from outside this editor and is shown. Reload" and cleared the undo history. Read at the code: `apps/studio/src/editor/controller.tsx` `serverSide(id, { announce: true })` runs the action on the server, and when the write has not come back yet on the blob tier it calls `room.resync()` at once instead of waiting for the channel's one second poll; `onResync` reads the reloaded document's revision against `latest().serverRevision`, the revision this tab acknowledged, and `resyncBroughtUnseen(fresh, known)` (`resync-history.ts`) read true because the tab had acknowledged nothing above its last write while the store had committed the action's revision, so the history and its clocks were cleared and `showExternal` named the tab's own write. The precedent in the same file: `version.restore` publishes `serverRevision: result.revision` before `room.resync(result.revision)`, and the assist accept path publishes `Math.max(serverRevision, answer.revision)` after its server side write.

The fix, one guarded change in the announce branch: before `room.resync()`, the tab counts the answer's `revision` as acknowledged (`publish({ serverRevision })` when it is a finite number above the known one), through the new pure helper `acknowledgeAnswered(known, answered)` in `resync-history.ts`, so a reload landing at the answered revision brings nothing unseen (the history stays, no banner) and one landing above it (another writer's entry with it) still clears and shows the banner. The memory tier's path (no resync; the stream brings the entry) is untouched, and `landed()` reads the document's own revision, so the wait is unchanged. `resync-history.test.ts` gains four cases: the own write answered r9 with the reload at r9 (no banner), another writer's entry with the reload at r10 (banner), an answer without a revision (`undefined`, `null`, a string, `NaN`) changes nothing, an answer at or below the known revision never lowers it. ### 7.1 `brand.logo.remove`: the walk's read

The walk's editor read in `scripts/probes/core-walk/areas/brand.mjs` (the `brand.logo.remove` step) counted any `.mark, [data-slot="mark"]` element with a client rect as a drawn mark. It now counts a mark as drawn only when the element carries content: it is an `img` or an `svg` itself (the kit's picture is the `img.mark.mark-picture[data-slot="mark"]` of `render/slide.ts` and `renderMark`, the default glyph an `svg.mark`), or it holds an `img` or `svg`, the way the same step's show read requires children. The empty `div.mark-block.is-none[data-slot="mark"]` R15 emits for a kit whose mark is `none` reads as not drawn.

### 7.2 The tab's own server side write on another instance: the resync at once

The mechanism of `assist.rewrite.card-accept-undo` (5.1): Accept's `POST /api/assist` answered 200 in 558 ms on one instance and the record reached the tab's stream about 7 s later, after `acceptAssist`'s 5 s wait for the entry (`controller.tsx`), because the tab's stream instance had no op of its own and ticked at the quiet cadence. The change: one helper in `apps/studio/src/editor/controller.tsx`, `settleOwnWrite(revision, landed)`, that every window transport write which runs on the server and answers goes through. It waits `OWN_WRITE_STREAM_WAIT_MS` (250 ms) for the stream to bring the entry, the time a commit on the tab's own instance takes; past it, on the blob tier, it counts the answered revision as acknowledged (part A's `acknowledgeAnswered`, so the reload lands at a revision the tab asked for, the undo history stays and no banner names the tab's own write as external) and calls `room.resync()` at once; then it waits for the entry up to `OWN_WRITE_LANDED_MAX_MS` (15 s). The memory tier keeps the wait alone (its follower streams the write within milliseconds; a reload there would cost a read for nothing). The rule is the pure `resyncsForOwnWrite({ landed, tier, waitedMs })` in `resync-history.ts` beside the two constants. The paths on it: the announce branch of `serverSide` (`asset.add`, `asset.dither`, `material.capture`, `logo.insert`; the 250 ms wait replaces the resync at once, so a commit on the tab's own instance no longer costs a reload), `acceptAssist` (the 5 s wait replaced; the history entry is pushed after the settle as before, and `ownAssistNotes` keeps the follower's banner off the assistant's own entry), and the `slide.import` handler (the 5 s wait and the unconditional reload replaced; the reload stays as the last resort when the entry never came, and the private `awaitRevision`, which nothing else called, is gone). `version.restore` (`commitServerFirst`) already publishes the answered revision and resyncs at once with `atLeast`, so it is untouched. `deck.tailor` is not a server side write: its handler plans in the page and commits through the room client (`apps/cli/src/store-actions.ts` `deckTailor` over `storeDeps`), so its entries are the tab's own ops and acknowledged by id; the server side write Tailor makes is Find the customer's logo, `logo.insert`, which is on the helper.

The B2 note's acknowledgement rule (`docs/gslides-parity/sync/build/b2.md` section 1: the room client settles a pending op by the record's `covers` and its own id, `settledOps` drops a repeated echo, a resync's `since` answer names the op ids the records above it carry) is untouched: the helper publishes the controller's `serverRevision` alone, only on the blob tier and only before a reload it asks for, as part A's announce branch did; the room client's acknowledged position moves as before. `asset.add`'s answer still carries no revision (`packages/materials/src/actions.ts` `commitAssetsAtHead`; the output schema in `packages/schema/src/actions.ts`), so its reload still lands one revision above what the tab acknowledged and its banner stays on Kevin's list (4.6).

`resync-history.test.ts` gains four cases: the reload on the blob tier once the wait ran out without the entry, no reload while the wait runs, never for an entry that landed or on the memory tier, and the bound pinned under a second and above zero with the landed bound above it.

Three changes, each small:

- `packages/store/src/presence-store.ts`: `readRemote` keeps the rows the instance holds and marks the copy unproven (`version: null`, `proven: false`, `sawRecord: true`) when the head names a record whose body no read answered, instead of an empty proven roster; `confirm` (the pulse did not move) does not count an unproven copy as fresh, so the next roster question reads again once the copy is older than `PRESENCE_POLL_MS`; the type gains `proven(deckId)`, whether the roster this instance holds is a reading of the record or of its absence. A push over an unproven copy already waited for a proven base (`pushNow`, b4.md C3T-R1), so an instance in the edge's window no longer tries to create over the record either.
- `packages/store/src/pulse.ts`: `PollTickInput` gains `rosterKnown`; `pollTickMs` answers the active tick while it is false, so a tab whose company is unknown is never counted alone; absent, the rule reads as before. `pulse.test.ts` gains the case (unknown active, known alone quiet, absent as before, company and an op active either way, under `POLL_CALLS_PER_MINUTE_MAX`).
- `packages/realtime/src/blob.ts`: `nextTickMs` passes `rosterKnown: shared.presence.proven(deckId)`; and a stream that opens while the deck's pulse poll already runs on the instance wakes it (`DeckState.wake`, set by `startPulsePoll`): one read of the presence record now (`presence.poll`, the one extra store call of a stream open) and the tick re-armed from the fresh roster when it is sooner than the armed one. The new stream is company (`listeners - 1`), so a poll at the quiet pace returns to the active pace at the open instead of at its next quiet tick, up to 10 s away; a tick in flight arms the next wait from the same roster itself. Nothing periodic is added; the first stream on an instance already reads the record at its first tick (`readMoved`).

The costs: an idle tab alone still ticks at 10 s once its instance has read the record or its absence; while the edge withholds a fresh record's body, the instance ticks at 2 s and reads the record again at most every 5 s until a read proves it, bounded by the window; a stream opening on an instance that already polls costs one presence head (and a get when the record moved). `POLL_CALLS_PER_MINUTE_MAX` is pinned as before, and 8.1's cost rows read the ceilings again on the new preview.

A finding for Kevin, not changed here: `blob.ts` counts a roster row as the instance's own when this instance's presence route set it (`ownClients`), on the assumption that a tab's presence POSTs land where its stream is; the platform routes each POST on its own, so an editor's row can read as own on an instance where only a viewer's stream is open, and that instance would count the viewer alone. Two rows of company where one is misread is one edge; the fix is the stream telling the channel its client id at `subscribe` so own means a stream here, a change to `room.ts` and the channel contract for the round after.
