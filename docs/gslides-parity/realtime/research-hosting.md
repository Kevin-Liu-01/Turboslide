Two thirds of the sum is the seven command presence write. A Lua presence write (one `EVALSHA`) takes the hour to about 4,300 commands and the 50 hour scenario to $13 PAYG. Upstash bills each command inside a pipeline or `MULTI`/`EXEC` on its own (https://upstash.com/docs/redis/overall/billing.md); its documents say nothing about how `redis.call` inside a script is counted, and nothing about a delivered pub/sub message, so this estimate counts one `EVALSHA` as one command and a delivered message as zero. Upstash's own Realtime pricing page counts a server emit as the two commands `PUBLISH` and `XADD` and a client subscription as `SUBSCRIBE` and `XRANGE` (https://upstash.com/docs/realtime/overall/pricing), which is consistent with that reading. Operational commands (`AUTH`, `HELLO`, `PING`, `QUIT` and the like) are not charged (https://upstash.com/docs/redis/overall/pricing).

Redis Streams and pub/sub are both in Upstash's command set (https://upstash.com/docs/redis/commands/pub-sub/overview.md lists `PUBLISH`, `SUBSCRIBE`, `PSUBSCRIBE` and their inverses). `SUBSCRIBE` needs the Redis protocol over TCP, which is why `redis.ts` 1 to 3 names ioredis and not the REST API. Latency: Upstash states read latency under 1 ms and write latency under 5 ms from the same region (https://upstash.com/docs/redis/features/globaldatabase.md); Vercel's `iad1` is AWS `us-east-1` (https://vercel.com/docs/regions), and `us-east-1` is one of Upstash's primary regions, so a database created there sits in the function's region. ## 4. The Vercel constraints that decide the design

1. A function holds a connection for its maximum duration and no longer. Node runtime defaults are 300 s, the Pro maximum is 800 s, and 1,800 s is a beta that must be set per function (https://vercel.com/docs/functions/limitations). The max duration counts streamed responses (same page, "Max duration"). The SSE stream closes itself at a random point between 240 and 290 s (`packages/realtime/src/protocol.ts` 49) under the catch all's 300 s (`vite.deploy.config.ts` 275), and the heavy routes alone carry 800 s (138, 300 to 309). A WebSocket closes at the same limit and the docs ask the client to reconnect (https://vercel.com/docs/functions/websockets, "Handle disconnections and reconnects").
2. The task's premise that a function cannot hold a WebSocket is out of date. WebSockets in Vercel Functions entered public beta on 2026-06-22 on all plans; a connection is pinned to one instance for its life and a fluid instance handles several connections (https://vercel.com/docs/functions/websockets; https://vercel.com/kb/guide/do-vercel-serverless-functions-support-websocket-connections). Nitro, which the studio builds with (`apps/studio/vercel.json` `NITRO_PRESET=vercel`), has native support through crossws (the Nitro section of the WebSockets page). Vercel's own guidance keeps SSE for server to client data and WebSockets when the client sends a continuous stream of its own (the KB article above and https://vercel.com/kb/guide/publish-and-subscribe-to-realtime-data-on-vercel).
3. A held connection is a running invocation. Provisioned memory is billed for the instance's whole life until the last in flight request completes, including while it waits on I/O; active CPU is billed only while code runs (https://vercel.com/docs/functions/usage-and-pricing). A stream or a socket therefore costs memory and no CPU while quiet, and fluid concurrency lets one 2 GB instance carry many of them (`docs/SYNC.md` 4.3 shows the stream at 21 s of 2 GB per open as measured, 265 s when a tab is alone on its instance). This line is $73 of the $102.58 at 50 hours and does not move with the tier.
4. No two instances share memory. New connections may land on any instance, and after a deploy the old connections stay on the old deployment until they close (https://vercel.com/docs/functions/websockets, "Manage persistent state"). Rooms, presence and fan out live in an external store; Vercel names Redis Streams for messaging and a Redis sorted set with pub/sub for presence (https://vercel.com/kb/guide/publish-and-subscribe-to-realtime-data-on-vercel), which is the shape `redis.ts` already has.
5. File descriptors: 1,024 per instance shared across concurrent executions, counting sockets and database connections (https://vercel.com/docs/functions/limitations). Each open stream or socket is one; ioredis takes two per instance (the command client and the pub/sub duplicate, `redis.ts` 57 to 69); the Postgres pool is at most 4 (`db.ts` 87). Concurrency auto scales to 30,000 on Pro (same page).
6. Regions: functions run in `iad1` (`us-east-1`) by default and the team's default is `iad1` (`docs/HOSTING-MOVE.md` 1.4); the Blob store is in `iad1` (`docs/hosting.md` 331 to 334); Vercel asks that the database sit in the function's region (https://vercel.com/docs/regions, "Compute defaults"). Upstash and Neon both offer `us-east-1`. Requests from Kevin enter through the `sfo1` PoP and reach `iad1` over Vercel's network (`docs/HOSTING-MOVE.md` 1.2).
7. The Blob store's rate limits bound the write path whatever the realtime tier: Pro allows 7,200 simple and 4,500 advanced operations a minute (https://vercel.com/docs/vercel-blob/usage-and-pricing), which is the "about 15 one slide commits per second" of `docs/hosting.md` 679 to 680.
8. Payloads: a function's request or response body is at most 4.5 MB (https://vercel.com/docs/functions/limitations), which the ops batch cap of 64 entries and 256 kB (`docs/hosting.md` 707 to 709) sits well under.
