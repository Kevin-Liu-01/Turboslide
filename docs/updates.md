## 2026-10-01, the comments resolve hotfix and the ship rule

Kevin, 2026-09-30: "why does your deploys keep regressing? it genuinely keeps regressing, ur doing something wrong with turboslide". The people round's production table left three core rows red twice on production, named for their owners (`comments.resolve`, `images.insert.upload-while-pending`, `chrome.field.boundary-3-1`); the rounds shipped merges of 20 to 35 commits at once; the watcher deployed every push of `main` straight to `www.turboslide.com` with no check of the build that went live. This hotfix fixes the one regression read by hand, writes the ship rule that stops the next one (docs/FOCUS.md 6.2) and names the mechanism of each red row.

What changed in the default view, for a seller: Resolve on a comment card reads resolved at once on the card, in the comments panel and in `window.turboslide.studio.describe()`, the moment the server answered the action; a `comment.list` served afterwards by an instance that has not pulled the sidecar yet no longer moves the thread back to open (the list is folded over what the tab holds, by thread revision, and an answer behind the tab is read again up to four times 700 ms apart). On the server a comment action's identity read, its room open and its access record read leave together instead of one after the other, and the sidecar and the live document are read together inside the action; a caller slower than one second writes one line to the server log with where the time went. On the blob tier the threads a comment action and `comment.list` read are the stored sidecar alone: the append writes the sidecar inside the append there, and folding the pending entry over it a second time had moved the writing instance's `commentsRevision` one above every other instance's for one sidecar (read on production 2026-10-01: `rev 7` on the writing instance, `rev 6` on the others, for one resolve).

The three rows red twice on production after the people round's ship, with their mechanisms:

- `comments.resolve` (apps/studio/e2e/core/present.spec.ts). The production run of record (2026-09-30 16:11Z): the row's `comment.resolve` request answered 200 after 5183 ms, with the op's stamp (`resolved.at` 16:11:48.730Z) 4.6 s after the request arrived at 16:11:44.155Z, so the time went to the caller's identity read, its authorization and the room's open on the serving instance, which had not opened the deck (the request landed on one of about thirty instances; the deck had 17 records and three threads), before the op itself; the tab's `comment.list` 60 ms after the answer read the thread resolved at +5.7 s, past the row's 5 s. The once rerun narrowed to the row (`--only specs --rows comments.resolve`) failed in `threadsLoaded` on an empty list before its own setup write ran: the row depended on the `comments.on-*` rows of the same file, so its second red was the rerun's and not the row's; the spec now places a thread itself when the deck holds none. By hand on 2026-10-01 00:09Z: Resolve closed the card and the panel kept the thread under Open until a reload; the tab's list after the action was served by an instance behind the sidecar, and nothing read it again. The fix is this hotfix. Read on 2026-10-01 00:42Z through the browser path on production, before the fix: the same six rows green, `comment.resolve` at 770 ms.
- `images.insert.upload-while-pending` (apps/studio/e2e/core/images.spec.ts). Two uploads in a row; the row allows both pictures 10 s from the first upload. On production the second picture landed after the bound: the hosted `asset.add` of each upload takes about 4 s on an instance that has to open the deck (the row's own note, VERIFICATION.md C3T-F2: 4 s each, the second landing 5.2 s after its upload), and the two chains share the deck's write queue on the instance, so the second commit waits for the first; under production's instance spread each request may open the deck anew. - `chrome.field.boundary-3-1` (scripts/probes/core-walk/areas/chrome.mjs). The walk reads the border contrast of four fields; on production it read the font size field at 1.21:1 in both appearances (zoom 10.9, the Share fields 3.1 to 3.95, the /decks search 3.1). The walk selects the first run's block, a grammar field whose size control is disabled, and the disabled size field draws its border in `--pt-hair-soft` (packages/chrome/src/EditorToolbar.css `.ts-tb-size.is-disabled .ts-tb-size-field`), a token under 3:1 by design for a disabled control; the row's expectation and the disabled token disagree. The owner is the chrome lane; the fix is the row's expectation (a disabled field is read apart) or a border token at 3:1 for the disabled field.

## 2026-09-15, the focus round

The rule this release sets, and every later release keeps: a feature is in the editor's default view only when every one of its interactions works on production and is in the test matrix ([docs/FOCUS.md](FOCUS.md) section 1). The default view is what a seller does weekly: open a deck that exists, duplicate, delete, skip and reorder slides, retype a name and a few numbers, replace a logo or a screenshot, present over a call, and send a PDF or a link.

What changed:

- Tools > Advanced tools. One check row in the Tools menu, off by default and remembered in the browser. Off, the menu bar, the toolbar, the right click menus, Search the menus and the Keyboard shortcuts dialog show the core set and nothing else. On, every parked feature appears in Google's position exactly as before. The parked set, by menu, is FOCUS.md section 3 and the README section "Advanced tools".
- Parked, never deleted. A deck that carries a chart, a table, a diagram, an icon, a material, a code panel, a word art block or a gallery shape still draws it everywhere, and the block can be selected, moved, resized, ordered, aligned, duplicated and deleted through the rows of the default view. The keyboard shortcut of a parked row does nothing while the switch is off. The Font box on the text tail stays visible and disabled with its sentence.
- Shapes. The shape galleries drew every preset as its bounding rectangle, so a seller who picked a callout got a box. Insert > Shape keeps Rectangle, Rounded rectangle and Ellipse, and Insert > Line keeps Line and Arrow, as the minimal set; each is in the default view of a release only when every one of its matrix rows passes, and the rest of the galleries return with the geometry interpreter (FOCUS.md section 4). At the first ship of the round both sit behind Tools > Advanced tools: the verifier's second pass failed 4 of 20 shapes rows and 1 of 5 lines rows on the preview.
- The test matrix. Every interaction of the default view is a row with a stable id in `docs/gslides-parity/focus/core-matrix.json`, driven against the preview and against production at human speed before a release; a row nobody drove is not driven, never passed, and one not driven or failed row keeps its whole feature behind the switch for that release (FOCUS.md section 6). The README section "What works today" is rendered from that file.
- Sharing. A new deck's general access defaults to restricted, the owner alone, and the Share dialog's links grant the viewer, commenter or editor role. Sharing is in the default view only once a stranger and a browser that came by the view link cannot edit on production; until then the PDF is the safe send.
- Fixes to the core set. FOCUS.md section 5 ranks the broken and flaky interactions the production audits of 2026-09-15 found, with the mechanism each audit saw; the release note of the ship lists which passed.
- For agents nothing moves. Every action stays on the CLI, MCP, HTTP and the window API whether or not its menu row is in the default view; `GET /api/agent` lists them all, and the skills document the parked ones as advanced.

The evidence: the seven production audits and their screenshots under `docs/gslides-parity/focus/`, the two judgments beside them, and the build notes under `docs/gslides-parity/focus/build/`.
