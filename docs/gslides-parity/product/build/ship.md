### 3.6 The blob tier: the template index read through the CDN, and a store left inconsistent

The first enforce preview of this tree (`turboslide-rbnqx43st`, gate started 13:03Z) read `templates.card.rename-and-delete` and `templates.default.use-for-new` red, the same two rows pass 2 read red, and three rows red on `/new` alone (`charts.data.paste-rows`, `export.pdf.file`, `share.dialog.open`: the draft's first write never moved the address to `/edit/`, and the share row's page snapshot read "templates/core-spec-template-mubavl0o/assets/mood-earth-dark.jpg is not in the store"). Three mechanisms, all in `packages/store`, measured with the specs' traces and an HTTP probe against the preview and the public store host:

- **The body read lags the head.** `blob-vercel.ts` `get` calls the SDK's `get` with `useCache: false`, which the SDK honours for private stores alone (`if (options.useCache === false && access === "private")`); on this public store the body comes from the CDN, whose copy of a pathname overwritten in place lags the write for a few seconds, and a query string does not change the cache key (`?x=<random>` answers HIT; `?cache=0` answers 400). So a pull saw the new version in the head and read the old body: the gallery on a second instance listed a deleted template 1.1 s after the delete's 200 (the spec's trace: `deleteTemplate` 200 at 13:47:20.46, the gallery loader 200 at 13:47:21.60 with the card still drawn for the 20 s the spec waited), the `.default` mark never appeared after Use for new presentations, and the probe's `template.list` on one of six instances read a template absent 1.5 s after `template.create`. A push read the same stale body and put the index under its etag, so `ifMatch` failed three times in a row and the write answered 500 ("templates/index.json changed in the Blob store since it was read"). Fix: `BlobCallOptions.version` names the version the caller knows the body has (from the head, or from the index entry that lists each file's stored version); `blob-vercel.ts` `get` reads the CDN again every 250 ms until the copy carries it, for at most `CDN_LAG_MS` (6 s), then throws `BlobStaleReadError`; `blob-templates.ts` passes the head's version for the index and the entry's versions for a folder's files, skips a pull whose read never caught up (the mirror stands until the next pull), and a push heads the index first and reads the body under that version before `ifMatch`, waiting 300 ms times the attempt between lost races. The fake client (`blob-fake.ts`) honours the version against its held bodies the same way, so the two instance test drives the lag (`blob-templates.test.ts` "reads the index the head names").
- **A delete removed the folder before the index.** `push({ id, removed: true })` deleted the folder's files and then put the index; when the put failed (the stale read above, three times), the store held an index naming a folder that was gone. Every later pull on every instance threw at `fetchFolder` ("… is not in the store"), which is the 500 on `/new` and `/decks/templates` the first preview answered from 13:59Z on (the walk's later rows and the specs from `charts.data.paste-rows` on met it), and the three `/new` rows above. The ship step's own probe caused the state on the shared store (its `template.delete` of a template the brand spec left behind met the lag), so the production code at 67fb029, which has no pull, was not touched; the tree's code would have been. Fixes: the push puts the index without the entry first and deletes the folder after it; a pull that meets a folder the index names and the store lacks skips it (`LostFolderError`), leaves the other templates and the default landing (a default naming it falls back to blank), and remembers it so this instance's next push drops it from the index. Tests: "puts the index before it deletes the folder" and "skips a template the index names whose folder is gone".
- **The editor payload's default kit read without a pull.** `write.ts` read the default kit for the editor payload from the local folder alone; `defaultKitOfCollection` pulls first, as `readDefaultKitFn` does.

Not changed here and named for the owners (section 10): the deck store (`blob-store.ts`) reads `deck.json`, the slides and the version records through the same `get`, overwritten in place, so the same lag sits under the cross instance rows the ledgers call flaky; the manifest names each file's version, so the same hint would close it.
