### 3. Decisions and deviations, for the integrator and the verifier

1. The letters inside a comment card (`j`, `k`, `r`, `e`, `u`, Esc; SPEC-3 14) are bindings of a
   new `comment` key scope that never enters the editor map, the way present mode's letters never
   do. `shortcuts.test.ts`'s bare letter assertion, which exempted the present scope, now exempts
   both scopes through `OWN_MAP_SCOPES` and gains a second assertion the round did not have: no
   chord of `buildEditorKeymap()` is a bare key on either platform. The assertion the round one
   spec wanted (SPEC 0.28, the editor binds no bare letter) is therefore tested on the map the
   handlers read, which is stronger than before, and the exemption is recorded here as a change to
   an existing test.
2. The avatar builder's second tab is "Glyph" (SPEC-3 0.22, 7.6), and "glyph" is a forbidden
   default view word since round two. The label follows the spec; `default-view-words.test.ts`
   exempts the one key `ACCOUNT.avatar.tabs` and asserts the tabs verbatim. For Kevin: either the
   tab takes another word (the spec's own alternatives are none) or "glyph" leaves the forbidden
   list as a product label; the round ships the spec's word.
3. The roster shows an agent session as "Agent · <runId>" (SPEC-3 4.7, 15), and "agent" is a
   forbidden default view word. The sentence lives in `AGENT_SENTENCES.agentTrust` beside the
   CLI's "no continuous source" refusal of 10.1 and the standalone build's "materialize first", the
   block the default view words test names as its exemption beside the Agent access dialog. The
   word appears in the default view only while an agent is present in the room, by the spec's own
   text; recorded for the verifier's default view walk.
4. Rows a role cannot use are absent through `when` (13.4). The two identity rows of the own chip's
   menu (Sign in, Sign out) read the account facts rather than a role and are absent until the
   route passes `account`; a checkout with no identity therefore shows Change name, Change avatar,
   Forget this browser and Sessions, which is the 7.3 rule (no Sign in row without a database).
5. `tools.activityDashboard` opens its panel and carries the Viewers tab as its one Later child, so
   it is a split like the Slideshow button: its status is its own (`now`), not its children's;
   `menu-model.test.ts` names both splits.
6. `file.versionHistory.showChanges`, the two delete rows and `tools.activityDashboard.viewers`
   are `contextOnly` rows reached from a panel, not a right-click menu; the reachability test names
   them as `PANEL_ROWS`.
7. `title.presence` is the roster (Google's "Avatar row", fixture entry added from report 01
   section 2); its rows are `title.presence.follow` (`presence.follow`, `when: 'follow'`),
   `title.presence.goTo` (`client('goToClient')`), `title.presence.joinChat` (Later, 0.41) and
   `title.presence.me` (`client('accountMenu')`, the own chip's menu). SPEC-3 13.2 names them
   `presence.*`; the model's ids must start with their menu's head, so they are `title.presence.*`.
8. The inbox plate and Notification settings rows carry no icon yet: the sprite has no `bell`
   (request 2 below).
9. `--pt-inbox-w` is 60 px: the spec names the token and its contents, not the number.

### 3. Decisions and deviations

1. The mark is drawn in the chrome for now. MILESTONES-3 says the identity marks are drawn by
   `packages/identity` and nothing else; B3's stage 1 notes name the renderers (`renderMarkSvg`,
   `renderMarkBits`, `renderMarkPng1`) as their stage 2 files in `marks-render.ts`, and none was in
   the tree when the surfaces landed. `presence/mark-svg.ts` computes the cell grid by the rules
   of research 11 6.1 (2 px cells aligned to the plate's top left, d/8 Bayer densities, the
   mirrored glyph field, the seeded ramp, the agent's half field) and `IdentityChip` draws one
   `rect` per cell, so an SVG and a PNG of the same spec light the same cells once identity's
   renderer lands. Request 3 asks B3 to export it; `IdentityChip` then imports the package's
   cells and `mark-svg.ts` retires. Recorded as a deviation for the verifier.
2. `PlateMenu` is a second menu primitive. The model `Menu` draws label rows from `MenuItem`s;
   the roster and the account menu draw a chip, a name, a trust word and a role word per row and
   the emoji palette a grid, which `Menu` cannot. `PlateMenu` follows the same ARIA menu pattern
   and reuses `placeMenu`; the Join chat stub and the account rows keep their `data-menu-item`
   ids so the parity audit finds them.
3. The remote caret is measured in the chrome, not the viewer. MILESTONES-3 names
   `packages/viewer/src/RemotePresence.tsx`; the chrome cannot import a viewer file without an
   export line in `packages/viewer/package.json` (the integrator's file), so the measurement
   lives in `presence/remote-caret.ts` and the viewer's side of the seam is
   `EditorOverlayView.body`. B2's `InlineText.tsx` remote caret hooks, when they land, can feed
   the same function.
4. Shift+Tab belongs to the open menu. The document keydown owner (`useEditorKeys`) never sees
   Shift+Tab while a menu is open: `Menu.tsx` handles Tab first, so the roster is opened from the
   menu's own Tab case at the top level through `roster-hook.ts`, and the `key.roster` binding
   keeps working when no menu is open. Measured in `presence-slot.test.tsx` (the document
   listener saw no key before the change).
5. The `+N` chip counts beyond four and is drawn empty below; the empty slots keep their tracks
   at opacity 0, so the slot's grid never changes width (P1). The compact collapse of 4.2 is a
   width breakpoint left to the verifier's layout shift audit to measure; this stage draws the
   full slot at every width.
6. The flag's "guest" suffix follows a character rule (13 characters of text after the chip),
   not a measurement, so the words never change after paint (P2); a name longer than the width
   ellipsizes in CSS.
7. Delete of a comment shows the snackbar's Undo at once beside the tombstone (5.3): the
   snackbar carries one action, so Undo is `comments.remove(threadId, commentId, true)`.
8. The persisted queue notice (0.7) is a fixed plate over the stage with Apply and Discard, not
   a snackbar (which carries one action), reading `sync.persisted`.
9. Show changes marks a removed block only when its box is still measured (the version before
   the deletion is the one drawn); a text edit underlines the whole run's box for an insert and
   strikes it for a delete, from the diff's mutations, which is the run level of 0.44 without a
   per character measurement.
10. The account and share writes go through `input.dispatch` with the action id as a string cast
    (`share.*`, `deck.publish`, `notification.settings`); the ids are in `ACTION_IDS` since B1's
    stage 1, so the cast is over the chrome's `EditorDispatch` typing only.
11. `format.editHtml` is a new contextOnly row (the model's counts: format [29, 2, 0], 148 now
    over 188 rows in `menu-model.test.ts`'s tally, the context rows list gains it). The Edit HTML
    panel is a panel id (`editHtml`), not a dialog, as MILESTONES-3 calls it "the Edit HTML
    source panel".
12. The stale specs `canvas.spec.ts` and `text-styles.spec.ts` are unchanged: without a booting
    editor (section 6) their current misses cannot be reproduced, and changing counts blind would
    be weakening a test to pass.

### Finding 13: Shift+Tab opens the roster but focus stays on the menu title

Two causes, both the same class of bug: an element focused while it is still `visibility: hidden`.

1. `MenuList` renders `visibility: hidden` until its layout effect sets `position`; the mount
   effect's `root.focus()` for a pointer opened root list ran before that, so a menu opened by
   a click never took focus, the key stayed on `button[data-control=menubar.file]`, and Shift+Tab
   reached the shell's `key.roster` binding instead of the menu's own handler. The binding opened
   the roster and left the File menu open.
2. `PlateMenu` focused its first row in a mount effect while the plate was still hidden for the
   same reason, so the roster never took focus from any path (the pointer's `+N` click included).

Fix: `Menu.tsx` focuses a pointer opened root list once `position` is set (a keyboard opened list
keeps its row focus); its Shift+Tab case now runs at any level ("from any open menu", 0.42) and
closes with the new `MenuCloseReason` `'roster'`, which returns focus to nothing (`escape` and
`tab` still return it to the trigger; `MenuBar` and `ContextMenu` pass the reason through
unchanged). `PlateMenu.tsx` focuses its first usable row once placed. `roster-hook.ts` gained
`focusRoster` and `openRoster` focuses an already open roster instead of toggling it closed.
`EditorShell.tsx`'s `key.roster` case closes an open bar menu when it opens the roster, for the
path where the title button holds focus (a hover between titles leaves it there).

Tests: the existing Shift+Tab test in `presence-slot.test.tsx` now asserts the pointer opened File
list holds focus, the File menu is gone after Shift+Tab, the roster's first row (`presence.roster.c1`)
is `document.activeElement`, and Esc returns focus to the `+N` chip; a second test covers the key
owner's path with focus on the title button. `presence.spec.ts` asserts the same after its
Shift+Tab (the File menu at count 0, `activeElement` inside `#ts-menu-roster`, the `+N` chip
focused after Esc); that spec's row 2 did not reach this step on the verifier's run (finding 32)
and was not run here.
