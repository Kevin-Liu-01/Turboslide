1. A record that names its origin travels on the stream, in the replay and in `between` as an entry whose `clientId` is the writer's tab (no longer `store`), whose `opId` stays `store:<n>`, and whose `covers` lists every client op id the record folded, in posting order (blob.ts `entryOfRecord`; channel.ts `Entry.covers`). A record without an origin travels as before (`clientId: 'store'`, no `covers`). Today's `applyEntry` treats an entry whose `clientId` is the tab's as "mine" and looks for a pending op by `entry.opId`, which never matches `store:<n>`: when the echo arrives before the POST's answer it applies the fold to `server` without settling the pending ops, so the local fold doubles the text until the answer lands (under a second on a fast answer; for as long as the answer is late). 2. A resend whose op ids a record above the POST's base names is answered with one synthesized entry per covered op id at that record's seq, in the record's cover order, each carrying `clientId` the tab's, `opId` the op's, `covers` the record's whole list, and the record's folded mutations on the first sibling alone; the later siblings carry `mutations: []`. A client that applies the answer above its position therefore applies the fold once; `settleBehind` matches each by `entry.opId` as today. The fresh ops of the same resend are placed past the record and come back at the next seq as today. `entrySchema` (protocol.ts) accepts an edit with `covers` and an empty mutation list for this reason; without `covers` an edit still needs its mutations.
3. The transform of 3.3 means the answer's `entries[].mutations` are the placed form (the splice at the shifted offset), as the memory tier's always were, so the client's own transform and the server's agree and the session has nothing to repair.

### 2. Decisions inside the specification, recorded once

1. "The first slide's heading" of 3.4 is read as the deck's first title slide in section order, not the first slide of the deck: the GT brand deck opens with an opener and its title slide is second, and a divider title slide later in the deck never renames the deck. A converted title slide (canvas.ts keeps `grammar.kind` 'title') counts through its heading block, as the client's `titleHeadingOf` reads it.
2. The title follows on `text.splice`, `text.replace` and a `text.mark` case change of that heading, never on `slide.set /heading`: a `version.restore` is a diff of `slide.set` and `deck.set` steps, and a derivation on `slide.set` could make the restored document differ from the version it restores.
3. The field's `path` is the field's own pointer and the reducer refuses any other, so `sameText` on both sides compares one spelling and a `slide.set /heading` names the same pointer the splice does.
4. `rewritesText` in transform.ts keeps the whole slide rule for a `slide.set` of a pointer that is not a field's (`/notes`, `/layout`): the spec names the field paths alone and the client's own rule (B2, read 2026-09-21) reads it the same way.
5. The synthesized entries carry the record's fold on the first sibling and nothing on the rest, so today's client applies the fold once from an answer above its position and B2's client, acknowledging by cover, applies once too; `entrySchema` tolerates the empty list only beside `covers`.
6. "Another client" in the roster (3.10) is a row this instance's tabs did not set (`ownClients`, refreshed by every presence set here, dropped on leave or after `PRESENCE_EXPIRY_MS`), so two tabs of one person on one instance count as alone while idle and a colleague on another instance counts from their first row, whether or not this instance's tab has a row yet. An op announced to this instance's streams counts as landed here too (an agent writing on another instance keeps the reading tab at the 2 s tick while the writes flow).
7. The roster question in the tick runs after the tick's own read (the pulse head and, on a moved pulse, the presence poll; on a still pulse `confirm`), so the presence store's `roster()` reads its fresh copy and makes no store call; blob.test.ts asserts every call of the window is the pulse head or a read a moved pulse names.
8. The per instance admitted op memory is retired (3.2 says so); the same instance case now rides the record's origin like every other. Until the store writes `origin` (B3's switch), a resend is caught by the store's own origin check in `write()` only; the row `sync.resend.idempotent` reads a known mechanism on a tree where the switch is off.
9. The base window check on the blob tier applies its "behind" half only (a POST more than 500 behind the mirror). Its "ahead" half is left to the placement as before: a mirror the forced sync could not bring to the base places, meets the store's head and retries, which is the C3T-F2 path the tests keep.

### 0. Requests of the fix round, written first

**FR1, B2, `packages/realtime/client/room-client.ts` and `packages/viewer/src/InlineText.tsx` (finding 3, the tie of two inserts at one offset; the client's half of the rule this lane landed on the server). Land all four or none.** The server now ties two inserts at one offset by the two authors' client ids when the POST declares it (`OpsPost.insertTie: 'client-id'`, protocol.ts; `insertTieSide` in `@turboslide/schema/transform`: the lower id keeps the left; `landedOf` in room.ts applies it per landed record on both tiers), and keeps server order (`right`, today's) for a POST without the declaration, so nothing changes on the wire until the client declares. The client's four changes:

1. `flush` sends `insertTie: 'client-id'` in the POST body.
2. The transform of a pending op against a remote entry passes the tie: `transformMutation(mutation, against, 'right', insertTieSide(clientOfOpId(op.opId) ?? clientId, entry.clientId))`, so `transformPast`'s callback needs the entry's `clientId` (a record without an origin arrives as `store`, which every client id sorts before; the server reads the same `store` from `channel.since`, so the two ends agree there too). `defaultTransform` (room-client.ts 403) and every caller of `transformPast` in `applyEntry` (990) and `transformSince` (1809) are the sites.
3. The remote entry's mutations are carried forward through the earlier pending ops before the next pending op is transformed against them: for pending `p0, p1, …` in order, `p0' = T(p0, r, tie)`, `r1 = T(r, p0, opposite of tie)`, `p1' = T(p1, r1, tie)`, and so on (the model in `transform.test.ts` `twoAuthorsAtOneOffset` does exactly this). On the blob tier a POST is in flight about 700 ms and `p1` accumulates that long, so without this change the tie by id splits the lower id's word on every remote insert that lands mid flight, which is worse than today. With it the two words stay whole whichever id sorts first; the unit test pins both orders.
4. ### 2. Decisions inside the specification, the fix round

1. The tie is declared per POST rather than switched on server wide: the two ends must compute one answer for one op, and the only thing the server can know about a client's rule is what that client says. 3.
