# The realtime round

The specification of the realtime round, written 2026-10-01 in the worktree `Turboslide-realtime` (branch `realtime/round` at `f50b209d`, `origin/main`). It is the synthesis of the six research notes under `docs/gslides-parity/realtime/`: `audit-sync.md` (the sync architecture as built, its fourteen defects, the costs), `audit-people.md` (two people on one slide, measured on production with the drive `people-drive/drive.mjs` and its pictures), `research-options.md` (how Google Slides, Figma, Notion and Linear do it; four options including peer to peer), `design-google-login.md` (Google sign in with better-auth, the code, the linking rule, the production list) and `research-hosting.md` (what production lacks, who provides it, the prices). `research-costs-actual.md` (the Vercel bills read on 2026-10-01) is the sixth; section 1.1 and 5.4 carry what it changes. Every line number below is that tree's; every price carries the date it was read in the note it comes from; every claim about a product carries its URL in the note it comes from and is cited by note and section here. The build lands on `docs/SYNC.md` section 3's model (the log, the commit point, the idempotency by origin) and on `docs/PEOPLE.md` section 2's decisions (one id per person, the verified badge, the eleven defaults).

## 1. Kevin's ask and the answer to peer to peer

Kevin, 2026-10-01: "fix the syncing and people on the same slide issues. redesign or smthg. should it be peer to peer? check how google slides does it annd maybe we should implement google loginns and fully add it as well and set it up since we fully did oauth for mailroom too".

Should it be peer to peer: no. Google Docs and Slides run a central server that orders every operation with operational transformation and broadcasts the transformed operation; presence rides the same client to server channel and there is no peer path (`research-options.md` section 3, the Wave whitepaper and the Slides API's `batchUpdate`, whose `requiredRevisionId` is the shape of this codebase's `deck.trash {baseRevision}`). Figma runs one server process per open document that every tab connects to over WebSockets, with the server authoritative and last writer wins per property; Notion's CRDT operations flow through Notion's servers; Linear's sync log is server ordered (section 4). A server stays the authority here for four things a seller's deck needs one place for: a Viewer share link that refuses writes (`packages/identity/src/access.ts` role cells, `apps/studio/src/server/room.ts` `decideFor` 716), an agent that writes over HTTP and must land somewhere (`POST /api/actions/<action>`, `apps/studio/src/routes/api/actions.$action.ts` 112), a version log whose numbers are ordered so `deck.trash {id, baseRevision}` and Version history mean something (`versions/<n>.json`, `packages/realtime/src/blob.ts` 187 to 200), and undo per author, which transforms an inverse past an ordered history (`packages/realtime/client/room-client.ts` `transformSince` 1970 to 1983). y-webrtc itself still needs a signaling server and a persistence peer, and 10 to 25 percent of sessions go through a relay (section 5d). The two defects Kevin named are not caused by the server being in the path. They are caused by the Blob store being the path: a commit is a four round Blob write of about 650 ms, the other instance learns of it on a pulse poll of 2 s (10 s for a tab alone), and the roster goes through a shared record with a 5 s push spacing while the caret, the selection and the pointer never leave the instance (`audit-sync.md` 1.3 and 5.2; `audit-people.md` 1.6).

The recommendation is the redis tier that is already in the tree (`packages/realtime/src/redis.ts`, `lua.ts`, `select.ts`; `research-options.md` option 5a, `audit-sync.md` section 2): one Redis stream per deck ordered by one Lua compare and append, one pub/sub channel per deck that every instance with an open stream subscribes to, presence as a hash and a sorted set published at once, the version log written by the checkpointer as today's records. It keeps the transform, the version log, the agent surface and the share links as they are; its code change is the smallest of the four options; it takes the merge from a measured 2.6 to 4.6 s to an estimated 150 to 250 ms in one region and 300 to 450 ms across regions, and the chip from 2.6 to 9.9 s to the presence batch (`research-options.md` 5a and section 7; `audit-sync.md` 2.4). It has never run outside the in process fake (`audit-sync.md` 2.3), so the first gate of this round is its measurement on a preview. The second best, and the destination if the Vercel memory line or the latency floor becomes the problem, is a Cloudflare Durable Object per deck (or PartyKit on the GT Cloudflare account) running the same `room.ts` admission over hibernating WebSockets and committing records to Blob as today: an estimated 120 to 170 ms in region and 200 to 300 ms across regions, at $5 to $9 a month at 50 editor hours a day against about $45 for the redis tier, at the price of a second deploy surface, a bearer path from the Vercel routes to the object, the authorization decision moved into the object and a guard with no equivalent on the Worker (`research-options.md` 5b and section 8; `research-hosting.md` section 3 row D). A CRDT (5c) and peer to peer (5d) are refused for this round with the reasons of `research-options.md` section 8.

What each costs at 50 editor hours a day (1,500 editor hours a month), the realtime part alone, prices of 2026-10-01: the blob tier as it stands $12 to $41 a month by the production cost rows of 2026-09-22 (`audit-sync.md` 4.2; `docs/SYNC.md` 4.3 puts the whole app at $102.58 and about $22 after the sync round's savings); the redis tier $15 to $44 with the Upstash Fixed 250 MB plan at $10 and the Blob records falling to one per typing run (`audit-sync.md` 4.3; `research-options.md` 5a counts about $45 with the stream memory held alone; `research-hosting.md` section 2 counts the Redis line at $10 to $30); the Durable Object $5 to $9 with the Vercel stream memory and the presence invocations gone (`research-options.md` 5b). `research-costs-actual.md` reads the bills and finds that the money went to the pipeline's gates on previews (200 to 750 GB hours on a gate day against 6 to 27 on a quiet day) and that sellers' own use is a rounding error; its cut 5 names the Durable Object channel as the step that removes the per tab runtime. This document keeps that reading and orders the two steps: the redis tier this round, because the lag is the defect Kevin named and the tier exists; the Durable Object channel as a fourth `RealtimeChannel` implementation in the round after, only if the bill after cuts 1 to 4 of that note still says so (section 6).

Sign in is a separate decision from the transport. Google sign in needs a database and benefits from Redis (the sessions' secondary storage, the principal store), so it ships in the same round behind the same two Marketplace installs (section 4).

### 1.1 The bill and the pipeline rules it sets

Kevin, 2026-10-01: "check vercel, turboslide is turning out very expensive for me, we need to optimize a lot or use cloudflare workers or something". `research-costs-actual.md` reads both teams' usage pages and the usage API. Kevin's personal team ran the project `turboslide` at 3,758 function GB hours, 7.71 M requests and 41.7 M Blob operations since 2026-09-01, about $85 to $100 for the month before the $20 credit. The daily series puts the money on the pipeline, not on sellers: a quiet day costs 6 to 27 GB hours and a day with a whole matrix gate on a preview 200 to 750, because every editor tab of a gate holds an SSE stream in a 2 GB function and polls the deck's pulse at the Blob store; production's own traffic was 18 requests in three quiet hours. Three rules follow for this round and every round after, in force from this specification: (1) the whole matrix runs on the local memory tier, and the hosted run before a ship is narrowed to the rows only a deployment can read (the blob tier's classes, the access rules, the CDN, `cost.*`) plus the guard's seller path, with the production table read once after the alias moves; (2) one preview deployment per round, deployed by the integrator from the merged tree, reused by every fixer and by the verifier's second pass unless a source file changed; (3) a docs-only push runs the guard's smoke alone (landed in `gt-follow.sh` on 2026-10-01). The realtime channel of section 3 is cut 5 of that note: an idle tab on the redis tier costs the function and no store calls, and on a Durable Object nothing. A whole move to Cloudflare Workers is not this round's (section 6): the Chromium work, the native addon and the Blob store do not run there today, and with rules 1 to 3 the Vercel line at today's seller traffic is the Pro seat plus a few dollars on either team.

## 3. The design

### 3.1 The transport

The redis tier, selected the way `select.ts` already selects it: `REDIS_URL` set selects `redis` (`packages/realtime/src/select.ts` 79); an explicit `TURBOSLIDE_REALTIME` wins (61 to 78); `redis` forced without `REDIS_URL` is a TypeError at the first request (67 to 71). Production today forces `blob`, so the flip is the removal of that row once `REDIS_URL` exists (3.7). The three tiers stay: `memory` for a checkout and the tests, `blob` hosted without Redis and as the runtime fallback, `redis` hosted with it (`REALTIME_TIERS`, `packages/realtime/src/channel.ts` 10). The Redis is Upstash through the Vercel Marketplace in `us-east-1`, the function's own region, over the Redis protocol with `ioredis` (one command connection and one subscriber duplicate per instance, `redis.ts` 57 to 95; `room.ts` 154 to 166), because `SUBSCRIBE` needs the protocol and the REST API cannot block (`redis.ts` 1 to 4; `research-hosting.md` 2.1). The per tab channel stays Server-Sent Events plus the two POST routes as built (`apps/studio/src/routes/api/decks.$deckId.stream.ts`, `decks.$deckId.ops.ts`, `decks.$deckId.presence.ts`); the WebSocket on Vercel Functions (public beta since 2026-06-22) saves under a dollar a month and is section 6's.

### 3.2 The ordering and the transform

- The order is the deck's Redis stream `deck:<id>:ops` with ids `<seq>-0` and the head counter `deck:<id>:head`, appended by the Lua compare and append that refuses a stale base, appends the batch, sets the head and publishes once (`packages/realtime/src/lua.ts` `APPEND_SCRIPT` 18 to 41; `redis.ts` `append` 279 to 299; `keys.ts` 109 to 116). The admission is the memory tier's `admitOps` (`room.ts` 1693 onward), which transforms every fresh entry past what landed since its base before it places, runs the reducer and the validator, and retries from the original mutations after a miss with the append lock after two misses (`packages/realtime/src/admission.ts` `appendWithRetry` 167 to 233). `admitOnBlob` (`room.ts` 2094 to 2349) stays the blob tier's alone. Invariant 2 of `docs/SYNC.md` 3.11 holds on every tier.
- What moves from the blob tier's poll to the channel: the op fan out (one `PUBLISH` per append inside the script, one subscription per deck per instance, `redis.ts` `subscribe` 309 to 349, the gap filled from the stream by `XRANGE` 215 to 249); presence (3.4); the cross instance drops of the access record, the link index, the room's identity cache and the principal records (3.6). The pulse poll, the presence record and the per instance pushes (`packages/store/src/pulse.ts`, `presence-store.ts`) stay as the blob tier's code and run only there.
- What stays in the version log: `versions/<n>.json` on Blob, one record per author per contiguous run, written by the checkpointer after 2 s idle, every 10 s under continuous typing, at 2,000 entries or 1 MB, at once for an agent write, `version.restore` and `version.save`, under `deck:<id>:ckpt` (`apps/studio/src/server/checkpoint.ts` 11 to 37). The record carries `origin: { clientId, opIds }` as the sync round made it (`docs/SYNC.md` 3.2); on this tier a run is one author's, so one record names one client and its op ids. The manifest put with `ifMatch` stays the commit point of the store and `deck.trash {baseRevision}` compares store revisions; the stream's `seq` is the stream's own position and the entry's `rev` carries the revision it followed (`channel.ts` `Entry` 56 to 60). The stream keeps 10,000 entries behind the last checkpoint (`checkpoint.ts` `STREAM_RETAIN_ENTRIES` 37).
- The echo settle: on this tier the stream delivers the client's own entries with their own `opId`, so the tab settles by op id at `applyEntry` (`room-client.ts` 988 to 994) and `settleByCovers` (870 to 897) stays the blob tier's path. The answer's `between` and the position rules are unchanged (`docs/SYNC.md` 3.7).
- A text op is transformed on both sides (`packages/schema/src/transform.ts`; `room.ts` `transformEntry` 1485; `room-client.ts` `transformPast` 516 to 533); every other mutation is re-anchored or refused by the reducer. Nothing changes in the schema this round.

### 3.3 The agent surface's HTTP writes

A bearer's write (`POST /api/actions/<action>?deck=<id>`) flushes the room and enters the same order as a tab's POST: on every tier but `blob`, and for every mutation but `version.restore`, the server write goes through the room and not through `store.write` (`room.ts` 3287 to 3343), so it is appended to the stream, transformed past what landed, delivered to every tab as an `op` event and written to the log by the checkpointer at once (the agent trigger of `checkpoint.ts` 15). The banner's gate then needs the author: `announceAgentWrite` admits entries whose author kind is `agent`, whose client id is not the tab's own, and which carry mutations (`apps/studio/src/editor/controller.tsx` 1660 to 1670), and today a bearer whose identity carries no author falls to `{ kind: 'human', name: labelFor(principalId) }` (`apps/studio/src/server/actions.ts` `callerFactsFor` 720 to 726); only the checkout agent reads `x-turboslide-author` (677 to 690). ### 3.4 The presence channel

### 5.3 The merge order

R5 first (the rows and the drivers exist on day 0, so every lane measures against them), then R1 (the channel every other lane reads), then R2 (the client and the carets), then R3 (the surfaces, which read R2's model), then R4 (sign in, which reads nothing of the above but shares `EditorRoot.tsx` and `strings.ts`), then R6 (docs and scripts, which describe the finished tree). The ship follows FOCUS.md 6.2's rule 2 of 2026-10-01: a ship is one lane's work, so the round reaches main as one push per lane in the merge order, each push a lane's commits with the seam commits that serve it, each ridden through the guard (`deployed <sha>` in `gt-follow.log` before the next push), so a red on production names one change. Nothing of the round is read on production between the pushes; the production table of record is read once after the last push, and `realtime` stays unparkable because that table is the only hosted whole matrix run of the round (1.1 rule 1). R5's rows carry `today: broken` until the lanes land and are not read on production before the table.

### 5.5 The acceptance rule

FOCUS.md 6.2's rule as `docs/PEOPLE.md` 6.2 states it since the comments hotfix of 2026-10-01: every core row of every feature not in the committed parked list passes in the last run of each origin with `retries` zero; a row that passes only on a rerun with no code change is flaky and fails the ship; a core row red twice on production after a ship is a stop, fixed forward or reverted within the hour, never named for an owner and left in the production table. `realtime` is unparkable; a `cost` row over its ceiling on the preview holds the ship. The known mechanism class of `docs/SYNC.md` 6.2 holds: a row whose entry names two lanes, red on a tree where one is not merged, is written by id with the missing half named and never chased by a rerun of the same tree. Kevin's standing row `sync.title.concurrent-both-kept` is superseded by `realtime.title.two-typers`: when the new row is green on production's run of record, the ship note asks Kevin to retire the standing row, and until he answers both are read. Every scratch deck a run creates on a deployment is trashed and deleted forever by its id (`deck.info`, `deck.trash {id, baseRevision}`, `deck.remove {id, confirm: true, baseRevision}`) before the run returns; the bearer reaches every driver from `~/.config/turboslide/hosts.json` through a wrapper and is printed nowhere.
