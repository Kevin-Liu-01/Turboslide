# What the hosting costs and where the calls go

The cost audit of the sync round, written 2026-09-20 against production (https://turboslide.vercel.app, the return round plus the caret hotfix, deployed 2026-09-20 11:40 PDT) and the working tree of the product round. Every number below names its source: a file and line of the code, a run file under `audit-costs/runs/`, a metric read with `vercel metrics` on the personal project, a header read with curl, or a Vercel pricing page with the date it was read. Nothing was created, changed or deleted on Vercel or GitHub; the store was listed and read only; the five scratch decks the runs made were moved to the trash and deleted forever through the product and answer 404 on `/edit` and `/deck` (each run's `cleanup` row).

## 1. Method

- The code counts. The store calls of every route were read from `packages/store/src/blob-store.ts`, `presence-store.ts`, `access-store.ts`, `pulse.ts`, `packages/realtime/src/blob.ts`, `apps/studio/src/server/room.ts`, `write.ts`, `decks.ts`, `thumbs.ts`, `card-thumb.ts`, `export-jobs.ts` and the routes under `apps/studio/src/routes/api/`. The `@vercel/blob` SDK 2.8.0 was read to classify each call: `head()` is a GET on the API and counts as a simple operation; `get()` fetches the public host URL (`useCache: false` only adds `?cache=0` on a private store), so it is a CDN request, a simple operation on a miss and free on a hit; `put()`, `list()` and `copy()` are advanced operations; `del()` is free (`node_modules/.pnpm/@vercel+blob@2.8.0/node_modules/@vercel/blob/dist/index.js` lines 65 to 200; docs/vercel-blob/usage-and-pricing).
- The client rates. `measure.mjs` (this folder) ran playwright-core 1.62.1, headless Chromium, 1440 by 900, at human speed: a scratch deck from `/new` with its title typed, then one state per process. The five runs: `loads` (one load each of `/home`, `/decks`, `/deck/<id>`), `idle` (an editor tab alone for 3 minutes), `edit` (one edit every 5 s for 3 minutes, 36 edits, revision 37, "All changes saved"), `show` (`/deck/<id>?present=1` alone for 3 minutes) and `export` (File > Download > PDF; the first run stopped at the Download dialog, `shots/export-end.png`, the second pressed its Download button and read the file from the store). Every request the page made is in `runs/<mode>.json`; `runs/<mode>.summary.md` is the table per route.
- The production metrics. `vercel metrics` (read only) on `kl01s-projects/turboslide`, production, the last seven days (2026-09-13 to 2026-09-20): invocations, active CPU, GB-hours and provisioned memory by request path; requests and data transfer by path type; the external API count by host. The raw answers are in `metrics/`. The external API metric does not see the Blob SDK's calls (602 rows in seven days against tens of thousands of heads), so the Blob counts come from the code.
- The prices. Read 2026-09-20 from vercel.com/docs (the dates are the pages' own): Blob usage and pricing (updated 2026-09-08), Fluid compute pricing (2026-06-16), CDN pricing and usage (2026-09-14), regional pricing and the iad1 page (2026-09-14), the Hobby plan (2026-09-14), the Pro plan (2026-09-15), the plans overview (2026-08-11), function memory (2026-07-15).
- Secrets check (the synthesizer, 2026-09-20, judge-operations addition 15): the run JSON files under `audit-costs/runs/`, `audit-hosting/hosting-walk.json` and `audit-ordering/*.json` carry no `cookie`, `set-cookie` or `authorization` key and no `Bearer `, `ts_id=` or `vercel_blob_rw_` value (`grep -r -l -i -F` per pattern, every file count 0); the next round repeats the check before it publishes evidence.

## 8. The pulse, presence and the three stores, stated

- The pulse head is a simple operation ($0.40 per million), not an advanced one, and it is already the cheapest fresh read the public store offers: the public host serves every object for 30 days, ignores the query string and answers a conditional request 304 from its own cache (`headers/public-store-heads.txt`), so a cache busting query or an ETag never reaches the origin. A private store's `get` with `useCache: false` reaches the origin but is billed as a simple operation on every read plus Blob data transfer and fast origin transfer, so it saves nothing over `head`. What the pulse can save is its tick: 2 s only while an op landed on this instance in the last 30 s, 10 s otherwise, which keeps the second browser bound of 35 s (`docs/PRODUCT.md` 8.2).
- Presence on the blob tier costs 40 heads, 12 puts and 12 gets a minute per idle tab, and the heartbeat's authorization is the larger half: the access record and the identity index are trusted for 5 s (`access.ts` 66, 164) and the heartbeat comes every 5 s, so every heartbeat re-reads both.
- A KV or Edge Config head does not beat Blob per operation: Upstash Redis is $2 per million commands against $0.40 per million heads; Edge Config is a configuration store whose writes propagate in seconds and are capped, not a per deck pulse. Redis wins only by replacing the poll with pub/sub, which the code already has as the `redis` tier (`room.ts` 126 to 139) and which also fixes the per instance presence, sessions bus and rate limits; at 50 editor hours a day it is about 1.1 M commands a month, $1.20 beyond the free 500,000, plus whatever plan the team picks.
- A Postgres row store (Neon) against Blob for the log: at 50 editor hours a day the edits' advanced operations cost $1 to $5 a month, so Blob wins in dollars; at 500 hours they cost $65 to $180 a month, so Neon's $19 Launch plan wins, and it brings consistent reads (no etag proofs, no listing lag, no phantom folders), the listing and the per identity index as queries. It needs Kevin's approval on the Marketplace.

## 11. Summary

What a seller feels today. Nothing of the bill; the cost is Kevin's. What a seller does feel is what the same calls do to latency and to the store's rate limits: the `/decks` page that heads 65 decks and preloads eight editors before its cards settle (the 26 s listing of R1-F3), the "Reconnecting" title row when a burst of heads meets a 429, and a card thumbnail that lags a typing burst because Chromium is rendering the last one. A viewer of a show feels nothing and costs 25 s of a 2 GB function every 31 s for an agent bus nobody attached to.

The ten this round should do first, in this order: item 1 (no session on shows and viewers, no poll while hidden, the poll unheld; then the command frame on the stream), item 2 with item 3 (the team project, the store transfer, the personal address as a redirect; a decision and dashboard work, none of it code), item 4 with item 13 (the leases and the export job record read through the proof), item 5 (the heartbeat at 15 s when quiet and the records trusted for 60 s), item 6 (the card thumbnail once at rest), item 7 (no `listVersions` per edit), item 8 (the idle stream closed after 5 minutes), item 9 (the listing from one index record, preloads on intent), item 10 (the show on a published snapshot), item 12 (the pulse tick backing off). Together they take the 50 hour scenario from $102.58 to about $18 a month on Pro (the ten savings sum to $84.31 and overlap), most of it in the first item, and the personal project to nothing.

What to leave. Item 14 beyond the prune (fewer puts per edit changes the proof the listing and the pull rest on; $1 a month at 50 hours), item 11 until the load passes about 150 editor hours a day or a round wants consistent reads for their own sake, item 17 unless the team wants the redis tier for correctness, items 21 and 22 (cents). The stream slots, the client owned reopen, the pulse as one head per deck per instance, the export job record and the `BLOB_BUDGET` rule stay: the measurements found them doing what the focus round said, and the money is elsewhere.
