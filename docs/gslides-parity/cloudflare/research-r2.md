## 1. The answer

Yes to question 1: every one of the six `BlobClient` calls (`head`, `get`, `list`, `folders`, `put`, `del`, `packages/store/src/blob-store.ts` lines 153 to 168 as T3 reads them) has an S3 call that R2's S3 API page lists as implemented, reachable from a Vercel function with a key pair in the environment, and the two conditions the store relies on (a put refused when the name exists, a put conditional on the etag read) are `If-None-Match` and `If-Match` on `PutObject`, both listed and answered with a 412 (section 2). Three facts need a line of code or a day 0 measurement before the client is trusted: the single part etag as the body's md5, the AWS SDK's checksum default since 3.729.0, and the one write per second per key limit (2.3). On price, `head` and `get` are Class B at $0.36 per million after 10 million free a month, `put` and `list` are Class A at $4.50 per million after 1 million free, `del` is free, and egress is free (4.2).

## 2. Question 1: the hosted store over the S3 API from a Vercel function

### 2.1 The way in

The S3 compatible API is "available via the `https://<ACCOUNT_ID>.r2.cloudflarestorage.com` endpoint" (https://developers.cloudflare.com/r2/api/s3/api/, read 2026-10-01). The region is `auto`: "For R2 buckets, the region is `auto`. Empty values and `us-east-1` alias to `auto`" (the same page). Cloudflare's own AWS SDK v3 example constructs the client with `region: "auto"` ("Required by SDK but not used by R2"), the endpoint above and `credentials: { accessKeyId, secretAccessKey }` (https://developers.cloudflare.com/r2/examples/aws/aws-sdk-js-v3/, read 2026-10-01).

The key pair is an R2 API token. Account tokens "are tied to the Cloudflare account itself and can be used by any authorized system or user"; user tokens "become inactive if your user is removed from the account". The permission "Object Read & Write" "Allows the ability to read, write, and list objects in specific buckets", and "If you select the Object Read and Write or Object Read permissions, you can scope your token to a set of buckets". The Access Key ID is the token's `id` and the Secret Access Key "The SHA-256 hash of the API token `value`"; "You will not be able to access your Secret Access Key again after this step" (https://developers.cloudflare.com/r2/api/tokens/ and https://developers.cloudflare.com/r2/api/s3/tokens/, read 2026-10-01). The tokens page also names temporary credentials "via the Temporary Credentials API or locally by signing a JWT with the parent token's secret access key" without detail; the store needs the long lived pair alone. A Vercel function's outbound HTTPS to that endpoint is an ordinary fetch; Vercel's networking page lists no line for a function's outbound transfer (T3 3.5), and the function's wait on R2 is paid as its GB hours.

Multipart is never the store's path: a single part put goes to "5 GiB (single-part)" (https://developers.cloudflare.com/r2/platform/limits/, read 2026-10-01) and the largest object on record is a 64 MB bundle (`docs/HOSTING-MOVE.md` 39), while "ETags for objects uploaded via multipart differ from those uploaded with a single `PUT`" and "The ETag of the completed multipart object is the hash of the concatenated binary MD5 sums of all parts, followed by a hyphen and the number of parts" (https://developers.cloudflare.com/r2/objects/multipart-objects/, read 2026-10-01). The S3 client must therefore call `PutObject` with the whole body and never a multipart helper such as `@aws-sdk/lib-storage`'s `Upload`.

### 2.3 Four facts to settle before the client is trusted

1. The etag as the body's md5. The store's proof model keys `BlobEntry.version` to `quotedMd5` of the bytes (T3 1.3, `blob-store.ts` 446 to 449) and the migration compares etags across stores (`migrate.ts` header lines 11 to 13: "every copy verified by etag (Vercel Blob's etag is the md5 of the body, the fake's too)"). No R2 page read today states in one sentence that a single part `PutObject`'s etag is the md5. The nearest sentences: the multipart rule above, "The ETag of each part is the MD5 hash of that part's contents" (the multipart page), and the binding's `checksums` field, "The MD5 checksum will be included by default for non-multipart objects" (the Workers API reference). Day 0 puts known bytes to a scratch bucket and compares the `ETag` to `quotedMd5`, as T3 3.2 proposes; the fallback is a `version` the client computes from the bytes it puts, plus `Content-MD5` on every put (implemented on `PutObject`), which also makes R2 refuse a corrupted body.
2. The AWS SDK's checksum default. "Beginning with version 3.729.0 of the AWS SDK for JavaScript, the SDK provides default integrity protections by automatically calculating a `CRC32` checksum for uploads" (https://docs.aws.amazon.com/sdk-for-javascript/v3/developer-guide/s3-checksums.html, read 2026-10-01). The settings are `request_checksum_calculation` (`AWS_REQUEST_CHECKSUM_CALCULATION`) and `response_checksum_validation` (`AWS_RESPONSE_CHECKSUM_VALIDATION`), default `WHEN_SUPPORTED`, the other value `WHEN_REQUIRED`, "Checksum validation is performed only when required by the API operation" (https://docs.aws.amazon.com/sdkref/latest/guide/feature-dataintegrity.html, read 2026-10-01; the client option names are the camel case forms). R2's pages read today list `Content-MD5` on `PutObject`, "S3 putObject now supports sha256 and sha1 checksums" (changelog 2023-06-16) and "The CRC-64/NVME Checksum algorithm is now supported for both single and multipart objects" (2025-07-03), and name CRC32 nowhere; Cloudflare's own SDK example carries no checksum note. So the client sets both options to `WHEN_REQUIRED` and sends `Content-MD5` itself, or uses a small SigV4 signer and no SDK at all; which one is the build's choice, and day 0's scratch bucket put shows whether the default breaks.
3. One write per second per key. "Maximum concurrent writes to the same object name (key) | 1 per second" and "Concurrent writes to the same object name (key) at a higher rate return HTTP 429 (rate limited) responses" (the limits page). T3 3.3 lists the keys the store writes faster than that (`deck.json` when two instances commit inside a second, `pulse.json`, `presence.json`) and the two remedies (one retry of a 429 put after a second inside the 20 s document deadline, or the checkpointer spacing its records); the 429 must reach `isStoreBusy` (`packages/store/src/pulse.ts` 187 to 198) as a `retryAfter` or a message its regex reads, since the SDK's error shape differs from `@vercel/blob`'s.
4. `BlobEntry.url` is computed, never answered. The S3 API answers no public URL; the client builds `https://${TURBOSLIDE_PUBLIC_STORE_HOST}/${pathname}` for a public path and an unfetchable marker for a document, so `fetchFreshByQuery` (`access-store.ts` 355) fails closed (T3 3.2). Presigned URLs exist ("GET, HEAD, PUT, DELETE", "from 1 second to 7 days (604,800 seconds)") but "work with the S3 API domain (`<ACCOUNT_ID>.r2.cloudflarestorage.com`) and cannot be used with custom domains" (https://developers.cloudflare.com/r2/api/s3/presigned-urls/, read 2026-10-01); the store has no use for them, since a document is never readable by URL and the public set is served by section 3.

Where the bucket sits: a bucket's location is "set to Automatic by default", chosen "in the closest available region to the create bucket request based on the location of the caller"; the hints are `wnam`, `enam`, `weur`, `eeur`, `apac`, `oc`, "a best effort and not a guarantee" (https://developers.cloudflare.com/r2/reference/data-location/, read 2026-10-01). The functions run in `iad1` (`docs/HOSTING-MOVE.md` 18), so the bucket is created with the `enam` hint. The per call latency from `iad1` to the bucket is unmeasured (section 7); the commit is three sequential rounds plus the pulse (T3 1.3), so each millisecond of difference against the same region Blob store counts four times per commit.

The REST API limit on the page, "rate limited to 1,200 requests per five minutes across all R2 REST API operations on your account", is the Cloudflare management API (bucket creation, token management), not the S3 endpoint; the "50 per second" bucket management limit covers listing, not object reads and writes (T3 3.3).

## 3. Question 2: the public reads

The public set is what a browser reads by URL: twins under `decks/<id>/assets/`, thumbnails under `.thumbs/`, exports, bundles, builds and avatars (T3 1.3 and 3.4). The documents never are (`docs/hosting.md` 907 to 915 at `HEAD`, layout v2). R2 offers three ways to serve a public set, and the Vercel function is a fourth.

### 3.1 `r2.dev`

"Public access through `r2.dev` subdomains is rate-limited and should only be used for development purposes" and "To use features like WAF custom rules, caching, access controls, or Bot Management, you must configure your bucket behind a custom domain" (https://developers.cloudflare.com/r2/buckets/public-buckets/, read 2026-10-01). The limit: the `r2.dev` endpoint "has a variable rate limit applied to it" and "If you exceed the rate limit (hundreds of requests/second), requests to your r2.dev endpoint will be temporarily throttled and you will receive a 429 Too Many Requests response" (the limits page). "Avoid creating a CNAME record pointing to the `r2.dev` subdomain. This is an unsupported access path." Egress through `r2.dev` is free (the pricing page). Not for production; usable for a preview.

### 3.2 A custom domain on the bucket

"The domain being used must have been added as a zone in the same account as the R2 bucket" (the public buckets page). `turboslide.com`'s nameservers are `dns1.registrar-servers.com` and `dns2.registrar-servers.com`, `www` is a CNAME to `5661780b11730745.vercel-dns-016.com` and the apex answers `216.150.1.1` (`dig NS turboslide.com`, `dig CNAME www.turboslide.com`, `dig turboslide.com`, 2026-10-01). The zone is not on Cloudflare, and moving it is Kevin's act alone, named here and not scheduled: it changes where every record of the production domain is served from, and `docs/hosting.md` 802 to 804 at `HEAD` keeps DNS outside the account boundary. A custom domain on a zone Kevin already holds on Cloudflare (T3 3.4 names `gtx.dev` on the General Translation account) is the same decision in another form, since the bucket must then live in that account.

What a custom domain buys: "Domain access through a custom domain allows you to use Cloudflare Cache to accelerate access to your R2 bucket", "By default, only certain file types are cached. To cache all files in your bucket, you must set a Cache Everything page rule" (the public buckets page). The default list includes `.png`, `.jpg`, `.svg`, `.webp`, `.pdf`, `.zip` and `.pptx` and excludes `.json`, with edge TTLs "200, 206, 301 | 120m", "302, 303 | 20m", "404, 410 | 3m" and "The Cloudflare CDN does not cache HTML or JSON by default" (https://developers.cloudflare.com/cache/concepts/default-cache-behavior/, read 2026-10-01). The twins, thumbnails and avatars are digest named and never overwritten (T3 1.2), so a cache in front of them is right; the consistency page's caveat, "An object you delete from R2, but that is still cached, will still be available" and a cached 404 persists until the TTL, bites only overwritten or deleted keys, which the public set does not have except the export prune. Whether a request served from Cloudflare's cache is billed as a Class B operation is stated on no page read today (T3's open item stands); the consistency page says Worker bindings and the S3 API "do not transit through the cache", which places the cache in front of R2 and not inside it. Up to "100" custom domains per bucket (the limits page); "public buckets do not let you list the bucket contents at the root of your (sub) domain" (the public buckets page). "Disable public access to your r2.dev subdomain when using products like WAF or Cloudflare Access" (the same page).

### 3.3 A Worker on `workers.dev` with the bucket bound

No zone is needed: a Worker reached on its `workers.dev` hostname reads the bucket through a binding and serves the public prefixes alone, as T3 3.4 item 3 lays out (the prefixes, `Cache-Control` from `httpMetadata`, `Content-Disposition: attachment` on `download=1`, the headers the assets route sets, every other prefix refused). Workers Free is "100,000 per day" requests and "10 milliseconds of CPU time per invocation"; past a limit "further operations of that type will fail with an error". Workers Paid is "$5 USD per month" with "10 million included per month" requests, "30 million CPU milliseconds included per month", then "+$0.30 per additional million" requests and "+$0.02 per additional million CPU milliseconds" (https://developers.cloudflare.com/workers/platform/pricing/, read 2026-10-01). R2's charges are separate from the Workers plan; the Workers pricing page prices R2 by storage and operation class and says nothing about a binding call counting as a Workers request.

Two facts shape this path. First, every read through the Worker is a Class B operation on the bucket: the Cache API page grants functional caching to custom domains, "Workers deployed to custom domains have access to functional `cache` operations", and grants nothing to `workers.dev`, whose one mention is about cache keys including the query string (https://developers.cloudflare.com/workers/runtime-apis/cache/, read 2026-10-01); so on `workers.dev` a twin read by 1,000 browsers is 1,000 `get` calls on the binding, where a custom domain with Cache Everything would serve 999 from cache. At $0.36 per million after 10 million free that is the price of not moving the zone, and section 4 sizes it. Second, the request count: a gate day on a hosted preview reads twins and thumbnails by the hundred thousand (`research-costs-actual.md` 32: 1.52 M CDN hits and 6.19 M misses on the personal project since 2026-09-01, most of them the gates), which would pass 100,000 a day and fail reads for the rest of the day; `docs/REALTIME.md` 19 rule 1 keeps the whole matrix on the local tier, and at seller traffic (18 production requests in three quiet hours, the same line) the free plan is not approached. The fact that would force Workers Paid is therefore a pipeline habit, not a seller number.

### 3.4 The Vercel function streams the body

The fourth path is the one `TURBOSLIDE_BLOB_ACCESS=private` already names: the assets route streams the twin through the function instead of answering a 302 (`docs/hosting.md` 340 to 342 at `HEAD`, "not measured"). It costs a function invocation, provisioned memory for the stream, Vercel's Fast Data Transfer to the browser and a Class B `GetObject`, and it holds no Cloudflare hostname at all; it is the fallback if neither 3.2 nor 3.3 is wanted on day one, and `docs/SYNC.md` 4.3's reading that provisioned memory is the bill argues against it as a destination.

### 3.5 CORS and the download flag

CORS is set on the bucket in the dashboard ("under CORS Policy, select Add CORS policy"), by `npx wrangler r2 bucket cors set <BUCKET_NAME> --file cors.json`, or through the S3 API's `PutBucketCors` (implemented per the S3 API page; a Class A operation, once). A rule carries `AllowedOrigins`, `AllowedMethods`, `AllowedHeaders`, `ExposeHeaders`, `MaxAgeSeconds`; "Custom domains connected to an R2 bucket with a CORS policy automatically return CORS response headers", and for presigned URLs "you still need to configure CORS when making requests from a browser" (https://developers.cloudflare.com/r2/buckets/cors/, read 2026-10-01). The page states no cap on the number of rules and does not address `r2.dev`. On the Worker path CORS is the Worker's own headers, as the assets route's are today (`headers.ts` 77 to 95 as T3 reads them).

The export links append `?download=1` because "Vercel Blob honours `download=1`" (`apps/studio/src/server/export-jobs.ts` 367 to 370; `export-batch.ts` 589). R2 has no such query on a public bucket in the pages read today (the S3 API page lists no `response-content-disposition` parameter as read). Two replacements: the Worker reads `download=1` and sets `Content-Disposition: attachment` (T3 3.4), or the export puts set `Content-Disposition` at write time, which `PutObject` implements and a custom domain or `r2.dev` serves back as stored; the second holds without a Worker and fits exports, which are only ever downloaded.

On R2 a simple operation is a Class B one, an advanced one is Class A, deletes are free on both, and the transfer line goes.

## 5. Question 4: the migration and the public URL rewrite

### 5.1 Cloudflare's tools do not read Vercel Blob

Super Slurper's sources are "Amazon S3, Cloudflare R2, Google Cloud Storage (GCS), All S3-compatible storage providers", with "Access Key ID and Secret Access Key" for S3 compatible ones (tested: Backblaze B2, DigitalOcean Spaces, Scaleway, Wasabi); it preserves custom metadata, overwrites by default or skips, skips "Objects greater than 1 TB", runs from the dashboard's data migration page, and "ETags are not guaranteed to be equal when an object is migrated using Super Slurper" (https://developers.cloudflare.com/r2/data-migration/super-slurper/, read 2026-10-01).
