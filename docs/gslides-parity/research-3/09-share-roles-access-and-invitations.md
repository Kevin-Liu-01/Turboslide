# Share roles, access records, link tokens and invitations

Report 09 of the Turboslide round three research set, written 2026-09-13 against `main` at `61b16e4`. It designs the access record that decides who may do what to a deck, the role and capability matrix per route, link sharing with revocable tokens, invitations by email without Google accounts, request access, ownership transfer, the home page filtered by grants, the agent and CLI story under roles, the action table, and the migration from today's open deployment. Report 01 section 5 recorded Google's Share dialog; report 03 decided that roles bind to accounts or links and never to an anonymous id (03 B4); report 04 stated the security requirements (F1, F2, F8, F21, F22, 8.1). This report turns those into one design.

Rules followed: plain technical English, sentence case, no em dashes, no metaphors, no trailing periods on headings. No Google icon or artwork is reproduced. No account was signed in; every external fact comes from a public page read on 2026-09-13. Every Turboslide fact is read from the code at `61b16e4` and cited by file and line. Facts the sibling reports verified are cited by report number and section and not repeated.

## How to read this report

- Source keys resolve in the Sources section: L for a local report or file, G for a Google fact as report 01 or research/10 recorded it, W3C, MDN, RFC, OWASP, BA for better-auth, V for Vercel, N for Notion, FG for Figma, LN for Linear.
- "Principal" is an identity as report 03 defines it: an anonymous id in a sealed cookie (03 B2) or a signed in account (03 Part C). "Grant" is a role given to a principal or to an email. "Link" is a general access token. "Record" is the access record of section 1.
- A capability name in `code` is one of the names section 8 fixes for `authorize()`.
- "Checkout" is a clone with `decks/` on disk and the file store (`packages/store/src/select.ts:67-92`); "hosted" is the Blob backend on Vercel.

## Decisions

1. One access record per deck, `access.json`, beside `deck.json` in the store. On Blob it lives in the private store of 04 P9 under `decks/<id>/access.json`, is written with `ifMatch` like the manifest (`packages/store/src/blob-store.ts:986-1024`), is excluded from the document mirror and from bundles like `leases.json`, and is cached in Redis for 60 s with invalidation on write. On a checkout it lives at `decks/<id>/.turboslide/access.json`, gitignored (`.gitignore` line 3) and never committed, because a committed record in a public repository publishes email addresses and because a clone is a new store with a new owner (section 1).
2. Roles are owner, editor, commenter and viewer, as Google's (01 section 5). A fifth position, the link visitor, holds the link's role and is never named in a grant (03 B4). An agent acts as its token's owner with the token's scopes intersected (04 8.7).
3. General access has three modes: `restricted`, `link` (a token in the URL carries a role) and `open` (no token; the legacy mode every deck created before round three starts in, and the mode the Prototemplate embed depends on, SPEC 0.25). New decks start `restricted` with the creator as owner, as Google's do.
4. The link token is at least 128 bits from `crypto.getRandomValues`, stored as a SHA-256 hash with its role, revocable one by one, rotated by Stop sharing, and carried in the query string as `?k=`. The fragment was rejected because the server renders `/deck/:id` and must authorize before it renders, and because the hash already carries the slide grammar `#NN` and `#s/<id>` (section 3).
5. Publish to web is a second token, `?p=`, that opens only the player (present mode or the embed protocol), never the editor, always at the current revision; Stop publishing revokes it and the URL answers 410 (section 3).
6. Notes are read by editors and owners only; skipped slides are read by editors, commenters and owners. This narrows 04 F21 by one role for notes and departs from Google, where a viewer opening the editor sees the notes pane by implication (research/10 A15); the sales workflow of research/10 C2 is the reason (section 2).
7. `/edit` for a viewer or commenter opens the editor in Viewing mode with the role's menus and a View only button that requests edit access, as Google does (01 section 1). `/deck` and `/embed` for a deck the caller may not read answer one 404 page, the same for a missing deck, offering Request access with an optional message and, for anonymous people, an email field (section 2).
8. Invitations bind to an email; the grant activates when a session with that verified email arrives (03 Part C). The invitation mail carries the deck link and the message, never a capability. Pending invitations expire after 30 days; per person expiry is offered to every owner up to one year (section 4).
9. Request access creates a pending request the owner sees as a dot on Share and a Review banner in the dialog (01 section 2); the response can notify the requester; every answer to a requester is the same sentence whether or not the deck exists (section 4).
10. Email collaborators ships after invitations, behind the same Resend account and the invite rate limits, because an open mail relay is the abuse case; the message field on an invitation covers the rep's need first (section 4).
11. The home page reads a per identity index (`users/<principalId>/decks.json` in the private store, heads cached in Redis) instead of syncing every deck (04 F7); Owned by me, Shared with me, Recent and Trash are four views of that index (section 5).
12. Agent tokens are records owned by an identity with scopes, through better-auth's API key plugin; `TURBOSLIDE_TOKEN` stays the bootstrap admin token that mints the first record and names the deployment admin. A person signs in from the terminal with the device authorization flow (RFC 8628, better-auth plugin) and the CLI stores an API key, not a session (section 6).
13. On a checkout the CLI over files and the MCP server over stdio are always the owner: a process that can write the folder holds the deck. The dev server enforces the record for HTTP visitors when a record exists and stays open to localhost when none does (section 6).
14. Every capability check is one server function, `authorize(ctx, deckId, capability)`, called at the top of every server function and route before the store is touched (04 F1, OWASP), answering 401 without identity, 403 with identity and no right, and 404 when the deck must not be shown to exist (section 8).
15. Rollout: anonymous sessions and server derived authors first (03 J item 1, 04 P1), the private store for `access.json` and the index next (04 P9's first half), then `authorize()` in a shadow mode that logs denials for a week without refusing, then enforcement with every existing deck in `open: editor` until its owner claims it (section 11).

## 1 The access record

### 1.1 Shape

One JSON document per deck. Times are ISO 8601 strings like every stamp the store writes (`packages/store/src/templates.ts:317-327`).

```json
{
  "schemaVersion": 1,
  "deckId": "q4-review",
  "owner": "usr_01J...",
  "pendingOwner": {
    "principalId": null,
    "email": "ana@example.com",
    "askedAt": "...",
    "askedBy": "usr_01J..."
  },
  "createdAt": "2026-09-13T10:00:00.000Z",
  "createdBy": "usr_01J...",
  "generalAccess": { "mode": "link", "role": "viewer" },
  "links": [
    {
      "id": "lnk_...",
      "hash": "sha256:...",
      "role": "viewer",
      "createdAt": "...",
      "createdBy": "usr_...",
      "revokedAt": null,
      "expiresAt": null,
      "label": "Prospect deck"
    }
  ],
  "publish": {
    "hash": "sha256:...",
    "publishedAt": "...",
    "publishedBy": "usr_...",
    "revokedAt": null
  },
  "grants": [
    {
      "principalId": "usr_02K...",
      "email": null,
      "role": "editor",
      "invitedBy": "usr_01J...",
      "invitedAt": "...",
      "acceptedAt": "...",
      "expiresAt": null
    },
    {
      "principalId": null,
      "email": "lee@example.com",
      "role": "commenter",
      "invitedBy": "usr_01J...",
      "invitedAt": "...",
      "acceptedAt": null,
      "expiresAt": "2026-10-13T10:00:00.000Z",
      "message": "Please review slides 4 and 9"
    }
  ],
  "requests": [
    {
      "id": "req_...",
      "principalId": "anon_...",
      "email": "sam@example.com",
      "role": "editor",
      "message": "I need to fix the pricing slide",
      "askedAt": "...",
      "respondedAt": null
    }
  ],
  "settings": { "editorsCanShare": true, "viewersCanDownload": true, "allowHtmlBlocks": false },
  "revision": 7
}
```

Field rules:

- `owner` is a principal id, or `null` for an unowned deck (1.4). `createdBy` is the principal that created the record, the deck's creator on a new deck and the migration on an old one.
- `generalAccess.mode` is `restricted`, `link` or `open`; `role` is `viewer`, `commenter` or `editor` and is meaningless under `restricted`. Under `link` the role applies to the bearer of a live link token; the links list may hold several tokens with several roles at once (a viewer link for prospects and a commenter link for the agency), which Google does not offer and which the W3C recommends so one link can be revoked without the others (W3C section 5.1). Under `open` the role applies to anyone who reaches the deck by id, with no token, which is today's behaviour (`apps/studio/src/routes/deck.$deckId.tsx:33-40`, `edit.$deckId.tsx:354-361`).
- A link stores the hash of its token, never the token; the token is shown once when created or rotated, and again to whoever holds the URL. `revokedAt` set or `expiresAt` in the past means the token is dead; `share.get` returns dead links for thirty days so the dialog can say "Link rotated on <date>".
- `publish` is one token with the same fields; `null` when unpublished.
- A grant names a principal or an email, never both live at once: an email grant becomes a principal grant when a session with that verified email arrives, and the email is dropped from the grant at that moment (privacy, 03 Part G). `acceptedAt` is `null` until then. `message` is the inviter's message, kept until acceptance for the resend path.
- A request names the requester's principal (anonymous ids included) and an email, which anonymous requesters must give (section 4). Requests are removed seven days after `respondedAt` is set.
- `settings.editorsCanShare` and `settings.viewersCanDownload` are Google's two gear switches (01 section 5, rows "Editors sharing" and "Download, print, copy"). `settings.allowHtmlBlocks` is the owner switch of 04 F4's policy.
- `revision` counts writes to the record, for the CLI's `--base-revision` and the 409 shape every mutating action already has (`packages/schema/src/actions.ts:1-6`).

Nothing of this enters `deck.json` (`packages/schema/src/deck.ts:72-106`) or the bundle (`docs/deck-transfer.md` section 1: leases and `.turboslide/` never travel), so a deck moved with `deck pull` or `deck push` arrives without its grants and the receiving store gives it an owner of its own (section 6).

Every write reads the record with its etag, applies the change, and puts it back with `ifMatch` (V1 "Conditional writes": the put fails with `BlobPreconditionFailedError` when another process changed the blob), which is the protocol the manifest uses (`blob-store.ts:986-1024`, mapped to `BlobPreconditionError` at `blob-vercel.ts:157`). A failed precondition re-reads and retries once, then answers 409 with the current record, the same shape as a stale `baseRevision`.

### 1.4 Decks that exist before round three

At `61b16e4` no deck has an owner: the manifest has no owner field (`deck.ts:72-106`), `DeckHead` has none (`templates.ts:317-327`), and the collection has no permission on any call (`packages/store/src/hosted.ts:53-83`). Production held 15 decks on 2026-09-13 (07 section 13).

- An access read for a deck with no `access.json` synthesizes a record in memory: `owner: null`, `generalAccess: { mode: 'open', role: 'editor' }`, no links, no grants, default settings. Nothing is written until someone changes it. This is exactly today's behaviour, so no link breaks on the day roles land (SPEC.md line 45, decision 0.25).
- The editor shows a banner on an unowned deck: "This presentation has no owner yet. Claim it to decide who can open and edit it." with a Claim button for signed in people (anonymous people are told to sign in first, because an anonymous owner of a shared team deck is a cookie, 03 B4). `share.claim` sets `owner`, keeps `generalAccess` at `open: viewer` so every view link and the Prototemplate embed keep working, and turns editing by link off; the claimer then tightens or loosens access in the dialog.
- The deployment admin may assign an owner to any unowned deck (`admin.assignOwner`) and may claim on behalf of the team, which is how the gt-brand deck gets Kevin as owner.
- After the rollout window of section 11, remaining unowned decks are claimed by the admin.

### 1.5 The deployment admin

The admin is a signed in account with the admin role of better-auth's admin plugin (BA2: `adminRoles` default `["admin"]`, `adminUserIds`, `setRole`, `userHasPermission`). It is asserted in two ways, either sufficient:

- `TURBOSLIDE_ADMIN_EMAILS`, a comma separated list in the project environment; a sign in whose verified email is on the list receives the admin role. This survives a wiped identity database and needs no request.
- `admin.bootstrap`, an HTTP only action gated by the static bearer `TURBOSLIDE_TOKEN` (which 04 F12 keeps as the bootstrap admin token), input `{ email }`, which sets the role on the account with that email and mints the first API key record for it (section 6). The CLI form is `turboslide admin bootstrap --to <url> --email <email>` with the token from `~/.config/turboslide/hosts.json` (`apps/cli/src/hosts.ts:98-109`).

The admin's rights: read every record, list every deck (`account.decks --all`), claim or assign unowned decks, act as owner on any deck with every action logged as `via: 'admin'` (section 8), and nothing else. The admin never writes as another person: an admin's edit carries the admin's own principal in `Author`.

### 1.6 On a checkout

The file store is one folder on one machine. Without a record, every caller is the owner: the CLI (`apps/cli/src/cli.ts:260-262` resolves the author from `--author`, `TURBOSLIDE_AUTHOR`, `$USER`), the MCP server over stdio (the same process), and the dev server's own page on localhost (`packages/agent/src/http/auth.ts:75-95` admits localhost without a token). `share.*` actions read the synthesized open record and write `.turboslide/access.json` on the first change, with the caller as owner. With a record present, the dev server applies it to HTTP visitors (a colleague on the LAN when the dev server listens beyond loopback, the case 04 F11 and F13 harden) and to window actions; the CLI and stdio stay owner because they hold the folder. Sign in on a checkout exists only when the local identity store of 03 D2 (`node:sqlite` under `.turboslide/`) is configured; without it, an email grant on a checkout stays pending, and `share.invite` prints the deck link for the person to send by hand (section 7, local behaviour).

### 3.2 The token

- 16 bytes from `crypto.getRandomValues`, base64url, 22 characters; 128 bits is the floor 04 F22 set and is above the 64 bit floor 03 B2 cites for an identifier that must not be guessed. The W3C asks for "an unguessable unique identifier such as a UUID" (W3C section 5.2); a v4 UUID is 122 bits, so 128 bits matches. The id of a link (`lnk_...`) is a separate short id the dialog uses to name it; the token is never the id.
- Stored as `sha256:` of the token. A leak of the record then leaks no live link (the same reason 03 C2 sets `storeToken: "hashed"` for magic links).
- Mode bound: the role is a field of the stored link. A token grants exactly the role stored beside its hash on the day it is presented, so changing a link's role changes what its holders get without rotating it, and rotating it kills every copy in circulation.
- Revocable one by one (`share.revokeLink`), rotated (`share.rotateLink` revokes and mints), and rotated wholesale by Stop sharing (which sets `restricted` and revokes every link). Expiry per link (`expiresAt`) is offered because the W3C asks that "Capability URLs should expire" (W3C section 5.1); Google has no per link expiry for files (01 section 5, intro) and Figma offers link expiration on Enterprise only (FG1). The dialog offers none, 7 days, 30 days, 90 days, a date.
- A dead token answers the 404 page of section 2, not 410: the W3C allows "either a `410 Gone` or a `404 Not Found`" (W3C section 5.1), and 404 does not confirm that a link ever existed. The published player is the one place 410 is used (3.5), because a published URL is public by definition and a `410` tells an embedding page to stop retrying (RFC 9110 section 15.5.11).

Decision: the query string, `?k=` for links and `?p=` for the published player. What the query costs and how it is paid:

- Referer: the W3C's advice is that pages reached by a capability URL "should not include links to third-party websites" and otherwise use `rel="noreferrer"` (W3C section 5.1). Decks carry links (`run.link`, 04 F4); 04 F4's fix step 3 renders every link with `rel="noopener noreferrer"`, and 04 section 8.3 sets a `Referrer-Policy` on every response, so an outbound click from a view link carries at most the origin. The page's own subresources are same origin.
- Logs: the URL "appears within application logs, such as within web servers and in browser history" (W3C section 4.1). Turboslide's own log lines (04 section 8.11) log the hash of the token, never the token. Whether Vercel's runtime log records the query string is not verified (Unverified); the platform keeps runtime logs one day on Pro (04 F20). Accepted, with the mitigation that a link is revocable.
- Search engines: "The path under which capability URLs are found should be listed within `robots.txt`" (W3C section 5.2); `robots.txt` cannot match a query, so every response served through `?k=` or `?p=` carries `X-Robots-Tag: noindex` in addition to the route level `noindex` meta (`apps/studio/src/routes/__root.tsx:34-40`).
- Copy link copies the token: intended. The toolbar's Copy link copies `window.location.href` (`packages/chrome/src/Toolbar.tsx:488-505`); with `?author=` gone (03 J item 1) the copied URL is the deck, the slide hash and, when the tab was opened by a link, the token, which is what the person means to hand on.

## 4 People and invitations without Google accounts

### 4.1 Invite by email

`share.invite { deckId, emails, role, message?, notify }` writes one grant per address with `principalId: null`, `email`, `role`, `invitedBy`, `invitedAt`, `expiresAt` (for the invitation, thirty days), and `message`. If an account with that verified email already exists, the grant is bound to its principal at once and the person sees the deck under Shared with me on their next load; nothing in the answer says which case happened (section 8, email enumeration). When `notify` is on, one mail per address goes through the Resend account of 03 C2 (`resend.emails.send`, a verified sending domain, Free 100 a day or Pro 50,000 a month): subject "<inviter> shared "<title>" with you", the message, the role in a sentence ("You can comment"), and one button Open that links to `/deck/<id>` with no token. Google's dialog offers the same message field and notify checkbox (01 section 5, "Add people").

The recipient's path:

- Anonymous on arrival: `/deck/<id>` answers the 404 page (the deck is restricted) with a line "Invited by email? Sign in with the address the invitation went to." and the magic link and one time code form of 03 C2 prefilled with nothing (the page does not know who they are).
- After sign in with that email (verified by the link or the code, 03 Part C), the session's email matches the pending grant, the grant is bound to the principal, the email field is cleared, `acceptedAt` is stamped, and the deck opens at the role. better-auth's organization plugin follows the same rule, accepting an invitation only for a user whose email matches (BA1).
- A recipient who declines to sign in holds whatever the general access gives, which for a restricted deck is nothing. This is the answer to 03 J1 item 5's second half: roles by email need a sign in; roles by link do not.
- Expiry of the invitation: thirty days, then the pending grant is dropped by the next write of the record and the people list shows it no longer. Google's invitation expiry is not stated on the pages read (Unverified); better-auth's organization invitations "expire after 48 hours (2 days)" by default (BA1, `invitationExpiresIn`), which is too short for a sales cycle. Resend re-stamps the same grant (`share.invite` on an address already pending).

### 4.2 Per person expiry, remove, change role, the switches

- `share.setExpiry { deckId, who, expiresAt | null }` for any grant, at most one year ahead, as Google's "Add expiration" chooses "a date within one year" (01 section 5, "Expiry"); Google offers it to eligible work or school accounts only, Turboslide to every owner and sharing editor. An expired grant reads as no grant; the row stays visible for seven days with "Expired".
- `share.remove { deckId, who }` deletes a grant. Google's page warns that "Anyone who could open the file may already hold a copy" (01 section 5, "Remove access"); the dialog says the same in one line under the confirmation.
- `share.setRole { deckId, who, role }` switches Viewer, Commenter and Editor; setting the owner's row is refused (transfer is its own action).
- `settings.editorsCanShare` off stops editors from every write of 1.3 except publish (Google: editors can still publish, research/10 A6 G10).
- `settings.viewersCanDownload` off: what Turboslide enforces is the export routes and server functions (`syncExport`, `startBatchedExport`, `runBuild`, `bundleDownloadTicket`, `copyDeck`) refusing viewers and commenters with 403, the Download, Print preview and Make a copy rows hidden for those roles, and the print route's Download as PDF and Print hidden. What it cannot enforce: a screenshot, the browser's own print command, copying text from the rendered DOM, or saving the page; Google states the same limit, "you can't stop how others share the file content in other ways" (G4 via research/10 A10). The dialog's sentence under the switch says so.

### 4.3 Ownership transfer

`share.transferOwnership { deckId, to }` where `to` is an email or a principal id of a signed in account: the target is raised to editor if below, `pendingOwner` is set, and a mail asks them to accept, as Google does (01 section 5, "Transfer ownership": the pending owner is emailed, raised to Editor, may accept or decline, the original owner stays owner until acceptance and becomes an Editor after). `share.acceptOwnership { deckId }` by the pending owner sets `owner`, moves the previous owner to a grant with role editor, clears `pendingOwner`, and updates both identities' indexes (section 5). `share.declineOwnership { deckId }` clears `pendingOwner` and keeps the editor grant. Transfer to an anonymous principal is refused: an anonymous owner is a cookie (03 B4), and a team deck must survive a cleared browser. Drive's `pendingowner:me` search (01 section 5) becomes a "Pending ownership" row at the top of Shared with me.

- The requester's page is the 404 page of section 2 with the form: a role (Viewer default, Commenter, Editor), an optional message, an email field for anonymous requesters (required, because the owner's answer must reach someone and a granted role must bind to an email), and Request access. ## 5 The home page and the collection

### 5.1 The index

Today `/decks` calls `listDecks` (`apps/studio/src/routes/decks.index.tsx:53-57`; `decks.ts:201-203`), which on Blob syncs every deck of the store four at a time on every visit (`blob-store.ts:1032-1042`), and Recent is the browser's `turboslide:opened` key (`decks.index.tsx:66, 93-101`). 04 F7 names the listing amplification.

The index: one document per identity in the private store, `users/<principalId>/decks.json`, `{ owned: [deckId], shared: [{ deckId, role, since }], trashed: [{ deckId, at }], recent: [{ deckId, at }] }`, written with `ifMatch`. It changes when a deck is created or copied (owned), a grant is bound or removed or changes role (shared), a deck is trashed, restored or removed, ownership transfers, or a deck is opened (recent, at most once per hour per deck to bound writes). The heads the cards need (`DeckHead`, `templates.ts:317-327`, plus the appearance and first slide `deckCardFacts` reads, `decks.ts:189-191`) are cached in Redis under `head:<deckId>`, written by the commit path on every write of the deck (the writer already holds the manifest, docs/hosting.md lines 148-178), so a rename by another person shows on the next load without a sync. On a miss the page reads `deck.json` for that id, one simple operation (V3 "Simple operations").

The anonymous identity gets an index too, keyed by its principal id; Recent for anonymous visitors stays in the browser as well, because the cookie and the local storage key are lost together (03 B2). When an anonymous identity links to an account (03 E2), its index is merged into the account's.

### 5.3 Changes to the hosted interface

`HostedDecks` (`packages/store/src/hosted.ts:53-83`) gains, on every backend:

### 5.4 When the owner goes away

- Account deletion: 03 Part G's `beforeDelete` refuses while the person owns decks that other people hold grants on, until each is transferred (4.3) or trashed; decks with no other grant holder are trashed with the account. Trashed decks of a deleted account show "Deleted account" as the owner (03 E2's render rule) and can be deleted forever by the admin only; SPEC 0.24 forbids a schedule (`decks.trash.tsx:22-24`), so nothing sweeps them.
- An anonymous owner clears cookies: the owner principal still exists in the record and nobody holds it. The deck is not unowned in the sense of 1.4 (that would reopen it to everyone); it stays as it was, and the ways back are a link the person kept (a `link: editor` URL from Copy link), a Request access from a new session that the admin answers after checking out of band, or `admin.assignOwner`. The mitigation is upstream: the editor shows, on a deck owned by the anonymous session, the persistent line "Not signed in. Sign in, or copy an edit link, to get back to this presentation from another browser", and the sign in path links the anonymous id to the account so the deck follows (03 E2).

## 6 Agents, the CLI and the checkout

### 6.1 Agent tokens as records

04 F12's fix (token records with id, name, owner, scopes, created, last used, revoked, stored hashed with a `ts_` prefix) maps onto better-auth's API key plugin: keys with a prefix, hashed storage, `expiresIn`, `rateLimitEnabled`, `rateLimitMax`, `rateLimitTimeWindow`, `permissions`, `metadata`, secondary storage lookups, and "Sessions from API keys" through `apiKeyHeaders` and `enableSessionForAPIKeys` (BA4). Turboslide's mapping:

- `permissions` carries the scopes `read`, `comment`, `write`, `export`, `share`, `admin`; a key's rights on a deck are the owner's role intersected with them (section 2). A key with `admin` on an admin's account is the deployment's admin key.
- `apiKeyHeaders` is `Authorization` with the `Bearer` prefix stripped, so `requireAgentAuth` (`apps/studio/src/server/auth.ts:27-31`) resolves a record and a principal instead of comparing one static string (`packages/agent/src/http/auth.ts:75-87`). `TURBOSLIDE_TOKEN` stays valid as the bootstrap admin token for `admin.bootstrap` and for nothing else after the first records exist; the manifest's `auth` summary (`auth.ts:98-105`) gains `mode: 'api-key'`.
- The author of an agent write is `{ kind: 'agent', name: record.name, runId, principalId: record.ownerId }`, derived on the server (04 F2); `x-turboslide-author` (`auth.ts:108-113`) carries the `runId` only and `?author=` is ignored (04 8.7).
- Per key rate limits from the plugin sit beside 04 7.5's quotas; the key's `lastUsed` and `metadata.lastDeck` feed the activity feed.
- `account.tokens.create`, `account.tokens.list`, `account.tokens.revoke` are the actions (transports `window`, `cli`, `http`); a key is shown once.

### 6.2 A person signs in from the terminal

The device authorization flow (RFC 8628) through better-auth's plugin: `POST /device/code` returns a device code and a user code, the person opens `/device` and enters the code (default `verificationUri: "/device"`, `userCodeLength: 8`, `expiresIn: "30m"`, `interval: "5s"`), the CLI polls `POST /device/token` handling `authorization_pending`, `slow_down` and `expired_token` (BA3; RFC 8628 section 3.5: wait at least `interval` seconds, add five on `slow_down`). RFC 8628 asks that the user code "SHOULD have enough entropy that, when combined with rate-limiting and other mitigations, a brute-force attack becomes infeasible" and gives the example of "an 8-character base 20 user code" with a limit of five attempts (RFC 8628 section 5.1); the verification page therefore allows five attempts per code and is behind 04's R8 and R9 on `/auth/*`.

`turboslide login --to <url>` runs the flow, then, with the session token it received, calls `account.tokens.create { name: "<hostname> CLI", scopes: [...] }` and stores the API key in `hosts.json` under the origin (`apps/cli/src/hosts.ts:74-90`, mode 0600) with `kind: 'api-key'` and the principal's display name; the session token is discarded. The CLI never holds a browser session; a revoked key is one row in the profile dialog. `turboslide logout --to <url>` revokes the key and removes the row. Magic link or code from the terminal is not offered: the mail opens in a browser anyway, and the device flow puts the browser step where it belongs.

### 6.3 Pull, push and list under roles

- `deck pull` (`packages/schema/src/actions.ts:657-682`; `GET /api/decks/:id/bundle`) needs `history`, because the bundle carries `versions/<n>.json` and the notes (docs/deck-transfer.md section 1); a viewer's or commenter's key is refused with 403 and the message "Pull needs edit access; ask the owner, or open the presentation in the browser".
- `deck push` (`actions.ts:619-656`; `POST /api/decks/bundle`) to a new id creates a deck owned by the key's principal, `restricted`. With `--replace` it needs `write` on the target and rewrites the version log, so the imported records' author is stamped as the importer (04 F16) and the access record of the target is kept, not replaced (the bundle carries none).
- The bundle tickets the page mints (`bundle.ts:27-53`; `bundle-core.ts:46-51`) carry the minting identity in the ticket body and are checked against `export` and `write` on the subject deck; the upload ticket's subject `*` becomes the identity, so a ticket can no longer replace any deck.
- `deck.list` (`actions.ts:683-701`) answers the caller's `owned` and `shared` decks with the role on each head (`deckHeadSchema`, `actions.ts:335-345`, gains `owner` and `role`); `--all` is admin only. The MCP `deck_list` tool answers the same.

### 6.4 MCP sessions bound to an identity

An MCP session is one server per `mcp-session-id`, created at initialize with the deck and the author from the request (`packages/mcp/src/http.ts:107-140`; `apps/studio/src/routes/mcp.ts:24-47`). Round three binds the session to the key record resolved at initialize: the principal, the scopes and the name are session facts, every tool call runs `authorize()` for the session's deck, and a revoked key closes the session on its next request with the SDK's 404 error (`http.ts:149-151` today for an unknown session). Sessions per key are capped at 16 (04 7.5). Over stdio on a checkout the session is the owner (1.6).

## 8 Security and privacy cross checks with 04, and the layout shift rules of 05

### 8.1 The authorize signature

```ts

  | 'read'
  | 'readSkipped'
  | 'readNotes'
  | 'comment'
  | 'write'
  | 'history'
  | 'export'
  | 'exportNotes'
  | 'share'
  | 'settings'

  | 'copy'
```

Rules, each traceable to OWASP's authorization sheet (OWASP1): deny by default (a missing record on a hosted store is `restricted` with no owner only during the migration window of section 11; afterwards a missing record is a 404); validate on every request (the call sits first in every server function of `write.ts`, `decks.ts`, `download.ts`, `bundle.ts`, `render.ts`, `sessions.ts`, `agent-actions.ts` and in `handleActionRequest` and the MCP tool wrapper); server side only (the menu hiding of 2.3 is a convenience, never the check); lookup ids give nothing when guessed (the 404 page); exit safely (one `refuse()` path, `packages/agent/src/http/errors.ts`, bodies without detail); log every denial (04 8.11's line with `identity`, `deckId`, `action`, `status`, `reason`). The published token grants `read` in present mode only, whatever the capability asked; a link token grants its stored role's cells of the matrix; a grant its role; the owner everything; the admin everything with `via: 'admin'`.

### 8.4 Enumeration and the emails

- Deck ids are slugs of titles or dated drafts (`templates.ts:186-197`; `apps/studio/src/server/root.ts:343-351` per 04 F22), so existence must not be confirmed by the page: one page and one status for missing and restricted (8.2), one sentence from `share.requestAccess` (4.4), and the same timing (the request handler runs the same code path whether the deck exists, writing nothing in the missing case).
- Email enumeration on invite: the answer never distinguishes an address with an account from one without (4.1); the people list shows the email as typed until acceptance in both cases (03 Part H: "a consistent message for both existent and non-existent accounts").
- Where emails live: pending grants and requests in `access.json` in the private store; the identity table (03 Part G). They leave the record when the grant binds, is removed or expires, and seven days after a request is answered. Logs carry principal ids and hashed IPs, never emails (03 Part G; 04 8.11). `share.get` returns emails only to callers with `share`.
- CSRF: every share action is a POST server function under the existing middleware (04 8.2; `apps/studio/src/start.ts:12-18` per 07 section 1.3) or an agent route with the Origin and Content-Type checks of 04 F13; `share.requestAccess` over HTTP without a bearer is the one exception, protected by the rate limits above and by having no effect beyond a pending row.
