## 1. The asks and the decisions

### 1.1 Kevin's words, verbatim

"make turboslide super secure with data and authh, super performannt, and bullet proof and do a massive codebase cleanup, rewrite any backennd logic into rustm" (2026-10-08).

The standing rules that bind this round: "make sure turboslide is super optimized and super cheap to run while being fully featured and super performant"; "make sure to actually test our features and make sure they work"; one shared component or module for any cross cutting standard; plain technical English in every word a person reads; no word a person reads names another company's slides app.

### 1.2 What each ask means in this codebase

1. **Data and auth security.** Today production does not enforce its access model. Every decision runs in shadow mode (DATA-1), and every document sits on a public Blob store (DATA-2). The agent surface `/mcp` accepts any API key for any deck (AUTH-2). A slide's CSS can carry a script into every viewer's page (WEB-1, WEBV-1). The Worker serves raw SQL over the accounts database behind one bearer shared by preview and production (AUTH-3). The ask means four things. The access model is enforced at every entry point with one context builder. Documents leave the public store. Every secret is per environment and narrow. Every sink that writes deck content into a page treats that content as untrusted.
2. **Performance.** Clicks and typing already measure well (perf.md section 6). The problems are elsewhere. Store cost grows with a deck's history (PERF-1 to PERF-3). The editor loader is a serial chain (PERF-4). Pages ship code they do not use (PERF-8 to PERF-12). Cold starts write 30 MB of fonts (PERF-6). The admission clones and validates the whole document for every typed entry (RUST-1). The ask means costs that stay flat as decks and histories grow, with each one pinned by a budget.
3. **Reliability: nothing a person makes is lost, and every failure is handled.** The normal path is durable (reliability.md "What holds"). The losses are on recovery paths: a checkpoint answer lost and committed twice (RELIABILITY-1), the three two-typer losses (RELIABILITY-2 to 4), the pending store's Apply (RELIABILITY-5, 6), the oversized change (RELIABILITY-7), the object's failed close and dropped tails (RELIABILITY-8 to 11). There is also no backup and no alert that reaches a person (RELIABILITY-13, 14). The ask means each recovery path keeps every word exactly once, and each failure produces a sentence for the person and a line someone reads.
4. **A large cleanup.** 70 percent of the tracked tree and 94 percent of its history is the evidence folder (CLEANUP-5). There are 48 dead exports and 508 needless ones (CLEANUP-9). Thirteen hand written constant time comparisons exist (CLEANUP-1), and one job is often done two to four times (CLEANUP-11). Infrastructure Kevin ruled out still has code paths (CLEANUP-6). Five specs, the Worker's tests and the Rust tests run in no gate (CLEANUP-3). The ask means one module per job, nothing in the tree that nothing reads, and gates that catch drift.
5. **Backend logic in Rust.** Section 6 gives every module a verdict. The research overturns most of the orchestrator's starting position. The one CPU hot path is algorithmic and is fixed in TypeScript 300 to 470 times over. serde_json in wasm is slower than V8 at the boundary. One TypeScript source shared by the browser, the function and the Durable Object is what makes them converge. Auth stays on better-auth. The Rust work this round is the existing crate (phase 1). Kevin can overrule this (question 10).

### 1.3 The decisions

1. H1 to H3 (section 3) ship first. No lane edits a file listed for a hotfix until that hotfix is on `origin/main`.
2. K1 and K2 are the first lanes. Each needs Kevin for a step no agent may take: creating a paid store, setting secrets, running a production migration. The code half of each lands before his step and after it, as section 4 lists.
3. Severity 4 and 3 security fixes go through the guard first, then severity 4 and 3 reliability fixes, then the rest by severity (section 5).
4. One mechanism per push. Each push is small enough to roll back alone with the guard's promote back.
5. A security finding a verifier refuted is dropped as a finding. Any fix it still warrants rides with the finding that needs it (AUTH-1 with AV-1 in H2; DATA-3's residual in SD#3). Findings the verifiers found that the audits missed are counted and assigned.
6. Rust: no backend port this round. Phase 0 is the TypeScript work that removes the measured cost (lane RT). Phase 1 is the crate (lane N). Phase 2 has triggers (section 6.4).
7. One shared module for each cross cutting standard this round touches: `safeEqual` (SA#1), the error reporter (O#2), the deck listing (C#7), the rewrite rule (RT#3, RC#2), the limiter (SA#3), and the zip, sha256, `writeAtomic`, `requireSlug` and sign in modules (C#5, C#6).
8. Every fix is pinned by a test, a matrix row, a hosted smoke row or a budget (section 8). A lane runs the feature rows its push touches on a local server before it commits (section 9).

### 2.3 Corrections the verifiers made, which bind the fixes

- AUTH-2 is broader than first stated: `/mcp` skips the key's scope check as well as the deck's authorize.
- AUTH-3: the separate preview D1 already exists (`turboslide-accounts-preview`, `apps/realtime-worker/wrangler.jsonc` 96 to 100) and `BETTER_AUTH_SECRET` is already per environment (`realtime-env.mjs` 130 to 133). What is shared is the pair in `room.env` (`realtime-env.mjs` 134), which `worker-secrets` and `do` push to both environments. K2 fixes that pair and narrows `/db`.
- AUTH-4 is a severity 3 the moment mail turns on. With `TURBOSLIDE_MAIL=off` on production it is latent. SA#2 lands either way.
- DATA-1: the stranger cannot change sharing even in shadow mode (the record functions re-check standing). Production has Google sign in, so flipping to enforce without DATA-V4's fix locks owners out. H3 carries both.
- DATA-2: the migration as built leaves `assets/`, `exports/`, `bundles/` and `u/` public, keeps `legacyAssetKey` (the id padded with zeros), makes `.thumbs/` private while the render route answers a 302 to it, and leaves 30 day cache headers on the public copies. K1 covers all four.
- WEB-1: `sanitizeCss` alone does not close the breakout. Rejecting `<` in CSS at write time and at render time, for both `ext.import.css` and html block `css`, does. H1 carries this.
- WEB-2: dompurify's two advisories are low, and seroval reaches the tree through `@tanstack/react-devtools`, which `apps/studio/package.json` lists under `dependencies`.

### 2.4 SPEC-1, read for this spec

`GET https://www.turboslide.com/home` at 18:50 UTC (load 131) answered from the CDN (`x-vercel-cache: HIT`, `age: 1233`) with these headers only: `accept-ranges`, `access-control-allow-origin: *`, `age`, `cache-control: public, max-age=0, must-revalidate`, `content-disposition`, `content-type`, `date`, `etag`, `last-modified`, `server`, the short `strict-transport-security: max-age=63072000`, `x-vercel-cache` and `x-vercel-id`. There was no `content-security-policy` of either kind, no `x-frame-options`, no `x-content-type-options` and no `cross-origin-opener-policy`. The body carries `nonce="5ZZPgb7nGEIlUqCaQ+1M4A=="` on 52 tags, the same for every visitor. `GET /docs` at 18:59 UTC (load 143) had the same header set (`x-vercel-cache: MISS`) and one nonce on 53 tags. `/decks` and `/signin` carried the app's headers (`content-security-policy-report-only`, `x-frame-options: DENY`, `nosniff`, COOP). The cause: the prerendered files are served by Vercel's static layer, and `ROUTE_RULES` (`vite.deploy.config.ts` 252 to 272) give them `cache-control` alone. The security headers come from the request middleware, which never runs for a static file.

So the landing and every docs page can be framed by any site. They also fall outside WEB-3's site-wide CSP plan, which only reaches responses the function writes. Severity 2, a missing defence on public pages that hold no deck content. Fix (W#3): route rules for `/home`, `/docs/**`, `/`, `/favicon.ico` and `/robots.txt` carry `x-content-type-options: nosniff`, `x-frame-options: DENY`, `cross-origin-opener-policy: same-origin`, `referrer-policy: strict-origin-when-cross-origin` and the long HSTS value. The prerendered pages also carry a static CSP that names the build's own nonce: a static page holds no injected content, so a fixed nonce there carries no risk, and the build writes it with `frame-ancestors 'none'`. Pin: the row `security.static-pages.headers` (8.2) and the hosted smoke rows `static headers /home` and `static headers /docs` (8.4).

### 6.2 Phase 0, this round, in TypeScript (lane RT)

RT#3 (one rewrite rule), RT#5 (incremental admission), RT#10 (deck cap) and RT#16 (Text memo). The parity method for RT#5: 2,000 seeded random mutation sequences (mulberry32 seeds recorded) on GT and on the 850 slide copy, comparing today's `landCandidate` with the new one for equal `ok`, `reason`, `message` and resulting document. The flag is `TURBOSLIDE_ADMISSION=incremental|full|shadow`, where `shadow` runs the full path on 1 percent of entries and logs any disagreement. The production default is `incremental` once the parity test and a week of `shadow` on the preview read zero disagreements. The gain measured on the prototype: 16.3 ms to 0.051 ms per entry on GT, and 122 ms to 0.261 ms on 850 slides.

### 6.3 Phase 1, this round, the crate (lane N)

Scope: N#1 (napi out, wasm the crate's one output), N#4 (the native CI job), N#5 (the dither port if and only if a frame misses 16 ms at a load under 24), N#6 (DSSIM restructured). The parity method is the crate's existing rule, made general. The TypeScript stays the reference. The Rust passes the same vitest suite through the backend selector (`packages/effects/src/select.ts`). A seeded comparison checks outputs byte for byte, or DSSIM within 1e-9. CI runs it with `TURBOSLIDE_NATIVE_REQUIRED=1`. The flag is the existing `TURBOSLIDE_EFFECTS_BACKEND=typescript|wasm|auto`, with `describeBackends()` reporting which ran. The measurable gain of phase 1 is a smaller build, a parity gate that runs on push, and a binary whose hash is checked. It makes no user-facing speed claim.

### 6.4 Phase 2, later, each with its trigger

- Image decode, resize, encode and SVG raster in the crate's wasm (`image`, `png`, `zune-jpeg`, `resvg`), replacing sharp where N-API is missing. Trigger: the app moves onto Workers (`docs/CLOUDFLARE.md` stage 2).
- The logo sanitizer on `roxmltree` in wasm. Trigger: N#2 finds a parser defect.
- A document core in Rust (reducer, transforms, validator) compiled to wasm and run by the browser, the function and the object alike, never as a server-only copy. Trigger: a measured cost that phase 0 cannot meet on a mid range laptop or in the object, read at a load under 24.

Never: auth, the Blob store, Chromium orchestration, the MCP server, SSR.

### 6.5 Where the research overturns the orchestrator's starting position

The starting position was that Rust buys speed and correctness in the admission and transforms, the schema's validation and migrations, export and image work, and that auth and runtime glue should stay. The research keeps the second half and the image work. It overturns the rest, for the reasons in 6.1: the admission's cost is algorithmic, the wasm boundary is slower than V8 for this document, export is Chromium-bound, and a server-only Rust copy of the document core would be a second implementation the browser cannot share. The framing's statement that the crate is "loaded through napi in the Vercel function" is also incorrect: no Linux addon was ever built, and production's function runs the TypeScript stages (CLEANUP-7, RUST-3). Kevin can overrule this with question 10.
