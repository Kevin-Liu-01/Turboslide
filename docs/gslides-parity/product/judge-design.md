# Judge design: the product round specification

Written 2026-09-19 by the design and engineering judge of the product round against `docs/PRODUCT.md` and the five audits under `docs/gslides-parity/product/` (`audit-seller.md`, `audit-interface.md`, `audit-brand.md`, `audit-gaps.md`, `audit-assist.md`), read on the shared checkout at `6e15d60`. Every file and line named below was read on that commit with read only commands; the branch `round-five/integration` was read with `git show` and `git ls-tree` only. No source file was touched, no git write command ran, no browser was driven, and nothing was installed. The model route's parameters were checked against the current Claude API reference of 2026-06-24.

## Verdict

Revise. The document is the right shape: it reads the five audits into one ranked plan, keeps the four measurement words, gives almost every item a row and a driver, keeps the sync engine out, and states the assist's budget and guardrails. It fails on size, on lane ownership, on four engineering claims that the tree contradicts, and on an acceptance rule that builds two flakes into its own gate. The rejections below name each with the file that proves it; the additions name what the document must add before the lanes start.

## Rejections

1. Section 1, the size. "About two days of the pipeline" is not honest. The return round added 166 rows, most of them flag flips of built features plus about ten fixes, and took one pipeline day (`7d19326` 2026-09-18 17:32 to `6e15d60` 2026-09-19 18:06); the focus round took three. This round builds 31 friction items, about twenty token and state rules, a brand record with a renderer, three actions, an eight section panel and export masters, a 26 family font port, a template index port with a fifteen slide Sales pitch rebuild, two dialogs and a pane, a 24 module PPTX import port, an assist with a server function, a panel, four cards, two actions and quotas, the identity changes, and 133 drivers in four new spec files and four new probe modules. B5 alone carries 37 rows and B1 51 rows over about 55 files.

2. Section 7, lane ownership is not disjoint where the second table says nothing. `text.format-options.padding-grid` is in B1's rows and in B2's "every `text.*` row" while its files split (`FormatOptions.css` to B1, `FormatOptions.tsx` and `inspector/fitting.tsx` to B2). `formatting.bold.pressed-follows-selection` needs `packages/chrome/src/editor-shell.ts` (`factsOf`, named in section 3.1), which no lane owns. The heading swatch fix behind `brand.colors.palette-row` lives in `ToolbarTail.tsx` 285 to 291 and 534 to 539 (audit-brand 11), and the shared table gives B5 that file for the Font slot only. `text.link.slide-target` needs `packages/viewer/src/present/` (section 2 rank 19), which no lane owns. `packages/chrome/src/Thumb.tsx` (section 3.6) has no owner.

3. Section 7, B7. The claim that `apps/studio/vite.deploy.config.ts` "already names `fonts/assets/*/*`" is false: line 117's `PACKAGES_PATTERN` names `fonts/assets/InterVariable.woff2` alone. The 26 families under `packages/fonts/assets/<id>/` would not reach the function, so `fonts.export.pdf-face`, `fonts.export.editable-names-face` and the `brand.export.*` rows would go red for a packaging reason and park `fonts` and `brand` whole.

4. Section 8.2, the unparkable list. `formatting` is listed as unparkable, but `scripts/probes/core-matrix.mjs` `UNPARKABLE_FEATURES` (lines 103 to 116) and `docs/RETURN.md` section 1 rule 2 make `formatting` parkable. `formatting.bold.pressed-follows-selection` is a chrome behaviour filed under `formatting`; a red run of it would park every formatting row the return round brought back instead of blocking the ship, the opposite of what the document says happens.

The criterion "with text selected the Font dropdown is the first control" couples an unparkable `chrome` row to the parkable `fonts` feature; when the ship's rule parks `fonts`, the control draws the read only family of section 3.4 and the chrome row goes red and blocks the ship.

6. Section 8.1, the `today` column. The severity then feeds the ship rule.

7. Sections 6.3 and 8.1, `assist.quota.429`. The row drives a memory counter on production, where `apps/studio/src/server/ratelimit.ts` 456 to 468 says the quotas count per instance and Fluid compute spreads one caller's requests across instances (section 6.3 says the same), so the seventh ask answers 429 on some runs and 200 on others; the row is flaky by design, and FOCUS.md 6.2 makes one flaky row fail the ship.

8. Section 8.2, the flake class. The assist rows call `claude-opus-5` on production under 20 s bounds, and a model latency or availability miss is "a row red once whose mechanism is anything else", which fails the ship until a rerun after a named code change; the carve out names the blob tier class alone. `decks.card.thumbnail-slide-1` (a render worker capture and a listing within 10 s) sits in the same gap. The gate would hunt a third party's latency.

9. 10. Sections 6.2 and 6.4, `assist.accept { cardId }`. Accept by id implies a server side card store between propose and accept, and the document names none; on Fluid compute without Redis (the finding of item 7) an in memory store misses across instances. 11. Section 6.3, the WAF rule. 12. Sections 3.1 and 3.7, drawn once in both appearances. 13. Sections 4.1, 6.1 and 8.1, the control id contract. 14. Section 6.4, the guardrails have no acceptance. The action allowlist, the `safeParse` and id validation before a card, the `baseRevision` re base or drop, the `assist` kill switch and the `readOnly` refusal have no row and no named unit test, while the rows of 8.1 drive only the happy paths; and the reason the card is the gate (slide text is untrusted input to the model) is not stated, so nothing forbids a prompt that treats a slide's text as an instruction.
