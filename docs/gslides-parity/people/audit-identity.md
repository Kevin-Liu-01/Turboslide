# Identity audit

The identity model of Turboslide as the tree at `8ceb6294` (branch `people/round`, 2026-09-29) holds it, read from `packages/identity/src`, `apps/studio/src/server/auth`, the room and write servers, the chrome's presence and dialog files, and the documents that define it (SPEC-3 sections 0.17 to 0.23, 2.4, 4.1, 4.8, 7; `docs/security.md` sections 2 and 9; `docs/PRODUCT.md` section 2 rank 4). Line numbers are the tree's. The measured numbers come from a script run against the package and the chrome renderers on this machine with Node 24 (`--experimental-strip-types`), not committed.

## 1. What exists

### 1.1 The principal

A principal is the unit every record attributes work to. Three id formats and nothing else (`packages/identity/src/ids.ts` 1 to 9, 13 to 19):

- `anon_<uuid>`: an anonymous browser. A v4 UUID minted by the server into a sealed cookie.
- `usr_<id>`: a signed in account. The identity store's user id, 1 to 64 URL safe characters.
- `agent:<tokenId>`: an agent acting through an API key record.

`parsePrincipalId` (46 to 60) classifies an id without a lookup. Everything that attributes work stores one of these and never a name (7 to 9). The name, the mark and the trust state are computed at render time by `resolvePrincipal` (`resolve.ts` 139 to 211).

The anonymous browser. The cookie is `__Host-ts_id`, `Secure; HttpOnly; SameSite=Lax; Path=/; Max-Age=400 days` (`apps/studio/src/server/auth/session.ts` 21 to 24, 174 to 188); on plain http off localhost the name falls back to `ts_id` (169 to 171). The value is `v1.<payload>.<mac>`, an HMAC-SHA256 over `<principalId>.<issuedAt>` under `TURBOSLIDE_SESSION_SECRET` (74 to 91). `readPrincipal` (196 to 205) returns `{ id, kind: 'anonymous', admin: false }` or null; `ensurePrincipal` (226 to 244) mints a fresh id when the cookie is absent or does not verify and never for a request that carries `Authorization`. The request middleware mints on the first request (`middleware.ts` 31 to 45). "Two visitors are two people from the first request; clearing cookies makes a new visitor" (`session.ts` 4 to 5). `account.forget` mints a new id and a fresh record and sets the cookie (`actions.ts` 417 to 428).

The principal record. `principal:<id>` holds `{ principalId, label, name?, avatar, linkGrants[], notificationSettings, livePointers, createdAt, lastSeenAt }` (`packages/identity/src/principal.ts` 52 to 64) with a 90 day sliding TTL re-armed by every `touch` (19, 216 to 223). The label is stored at creation (`newPrincipalRecord`, 69 to 83). The store is Redis when the deployment has a Redis client and a JSON file per principal under `<stateDir>/principals/` otherwise (`apps/studio/src/server/auth/principal.ts` 104 to 110; `identity.ts` 189 to 205). A checkout writes `.turboslide/principals/`. The browser mirrors nothing of the record today apart from one flag (see 1.4).

The order a request is identified in (`apps/studio/src/server/auth/identity.ts` 8 to 16, 456 to 641): a bearer (an API key record, the static bootstrap token, the per checkout token), then a better-auth session with the anonymous cookie beside it linked to the account, then the anonymous cookie with its record's typed name or label, then a minted principal. The bootstrap and checkout bearers act as `agent:bootstrap` and `agent:checkout` with `admin: true` (430 to 442). The room routes have a second, narrower reader (1.6).

The account. Sign in is better-auth 1.7.4 with a magic link and a six digit code in one mail, the device authorization flow for the CLI, GitHub when its two variables are set, no passwords, passkeys off until the address is final (`better-auth.ts` 1 to 8, 78 to 87, 235 to 268). Sessions are 7 days idle, refreshed daily, fresh for 10 minutes (40 to 42, 183 to 188). The database is Postgres behind `DATABASE_URL`, `node:sqlite` behind `TURBOSLIDE_AUTH_DB` on a checkout, none otherwise (`db.ts` 44 to 66); with none, `runtime.auth` is null (`identity.ts` 214 to 215, 230), `methods.available` is false (`better-auth.ts` 78 to 86), the account menu has no Sign in row (`packages/chrome/src/presence/AccountMenu.tsx` 11 to 16) and the name prompt has no Sign in link (`dialogs/NamePrompt.tsx` 126 to 142, from `write.ts` 394 to 395). A hosted process refuses the SQLite variable (`db.ts` 52 to 55). better-auth's user row is `{ id, name, email, emailVerified, image }` (`schema.ts` 23 to 31); Turboslide's own tables are `ts_alias`, `ts_api_key`, `ts_profile`, `ts_mail`, `ts_quota` (7 to 17, 137 to 143). `accountFacts` (`identity.ts` 313 to 336) reads the user row and the profile; `admin` is the profile flag or membership of `TURBOSLIDE_ADMIN_EMAILS` (334; `profile.ts` 183 to 193). On session creation the account's principal record is touched into being, the admin flag is set from the variable, the anonymous cookie beside the session is linked, and pending invitations bind when the address is verified (`identity.ts` 373 to 390). Deleting an account marks the profile deleted, removes every alias, deletes the account's principal record and revokes its keys (392 to 398). `ensureUserByEmail` creates a user row with `name: ''` and `emailVerified: 1` for the admin paths (`actions.ts` 259 to 288).

The agent. `agent:<tokenId>` is the record of an API key (`ts_api_key`, `schema.ts` 75 to 92: name, prefix, start, sha256 hash, owner, scopes, expiry, last use, revocation). A bearer resolves to its owner as the principal and the key as `AgentContext { tokenId, ownerId, scopes, name, runId? }` (`identity.ts` 467 to 500; `packages/identity/src/access.ts` 65 to 71). Its rights are the owner's role intersected with the scopes (`access.ts` 129 to 150, 322 to 326); it never transfers or follows (148 to 149, 331 to 334). The run id is shown only when it is 1 to 32 characters of `[A-Za-z0-9._-]` (`resolve.ts` 93 to 99). An agent's mark is the dashed 50 percent plate with a centred square and no hue (`marks.ts` 105 to 107; `marks-render.ts` 121 to 124, 191 to 203).

### 1.2 The alias

An alias is one row `ts_alias { anonymousId, userId, linkedAt }` (`schema.ts` 69 to 73, 147 to 159). It is written when a signed in session first arrives in a browser that carries an anonymous cookie (`identity.ts` 385 to 387, 544 to 545) and by `linkAnonymous` (357 to 371), which also merges the anonymous record into the account's record once (`alias.ts` 101 to 120: the union of link grants by link id, the typed name and the avatar when the account's record has none). The link is one way and first wins: a second `link` for the same anonymous id is a no-op (`alias.ts` 27 to 38, 70 to 74). History is never rewritten; `resolvePrincipal` is meant to render an aliased anonymous id as the account from then on (`alias.ts` 1 to 6; `resolve.ts` 191 to 198). Two browsers linked to one account are two aliases and one person (`alias.ts` 5). Without a database the alias store is memory per process (`identity.ts` 217). `unlinkAll` removes every alias of an account on deletion (`alias.ts` 57 to 63).

### 1.3 The display name

A display name is the typed string on the principal record (`record.name`) or, for an account, better-auth's `user.name`. It is set by `account.setName` (`actions.ts` 313 to 339): the server runs `normalizeName` over the input with `taken` = the human author names of the current deck's version log other than the caller's and other than labels and `studio` (`namesInVersionLog`, 185 to 205); on success it writes `record.name`, writes the name onto the principal's deck index on the Blob store so every instance reads it (`access.ts` 222 to 234), forgets the room's identity cache, and for an account updates `user.name` (331 to 336). The prompt is `NamePromptDialog` (`dialogs/NamePrompt.tsx` 11 to 24): it fires on the first edit, comment or lease, floats at the bottom right with no scrim, is prefilled with the label, and offers Continue and a Sign in link when sign in exists. The first Share on a browser with no name opens the same dialog titled "Your name, shown to collaborators" with a Skip row (38 to 39, 85 to 95), and remembers in `localStorage` that it asked (`dialogs/Share.tsx` 211 to 220).

The rules (`packages/identity/src/names.ts` 1 to 22, 298 to 335): NFC, an unterminated bidi control refused, format and default ignorable code points stripped, whitespace collapsed, 1 to 40 code points with a letter or digit, no leading or trailing punctuation, every code point Identifier_Status Allowed, UTS 39 Moderately Restrictive with the mixed number check, the label grammar refused, a reserved list by skeleton (226 to 246), the LDNOOBW list for English plus the request's languages, then per deck uniqueness by case folded skeleton in both orders (327 to 333). Three refusal sentences (53 to 57).

The name is not verified. A typed name yields trust `guest` (`resolve.ts` 199 to 206); the tooltip reads "Not signed in. This name was typed, not verified." (33); the trust word beside it is "guest" (21 to 26; `IdentityChip.tsx` 88 to 90; `presence-model.ts` 98 to 100). An account's name is also typed. What `verified` attests is the email of the session (`resolve.ts` 34 to 36, 121 to 132: `displayName: profile.name.trim() || profile.email`, `trust: 'verified'`); the check badge of SPEC-3 0.19 does not exist in the chrome, the verified state carries no word (`TRUST_WORDS.verified = ''`, `resolve.ts` 24), and the profile dialog's sentence is the only surface that says "Signed in as <email>, verified" (`dialogs/Profile.tsx` 37 to 44; `menus/strings.ts` 239 to 241). `docs/PRODUCT.md` 665 records why the assist quota is not keyed to the name: "the name is typed by the seller and not verified, so it would be a quota anyone resets by retyping".

### 1.4 What tells two people with one name apart

- The principal id, always. Two people who type "Kevin" are two ids, two records, two hue slots and two marks. Nothing in a stored record is the name alone; `Author` carries `principalId` beside `name` (`room.ts` 379 to 395).
- Per deck uniqueness at the time of typing (`names.ts` 327 to 333). The second person to type "Kevin" on the same deck is refused with "That name is already in use in this presentation", provided the first "Kevin" has already authored a version record on that deck (the `taken` list is the version log, `actions.ts` 185 to 205). See defect 6 for what the list does not cover.
- The mark. The plate density comes from two hash bits (four greys, `marks.ts` 66 to 74); the glyph seed from four hash bytes; the initials from the name (53 to 63). Two "Kevin"s with the default initials variant differ only by the density of the Bayer field behind a "K", one of four values.
- The hue, on live surfaces only. Six slots, preferred by `sha256(principalId)[0] % 6` and granted by the room to the least used slot when the preferred one is held (`hues.ts` 48 to 73; `room.ts` 2056 to 2061). Two people can hold one slot once six are present.
- The label suffix "(2)" for two anonymous principals with one label (`labels.ts` 125 to 143) is implemented and never called (defect 7).
- The trust word. "Kevin" (a label cannot be "Kevin") against "Kevin · guest" against "Kevin" with a verified tooltip.

### 1.5 The identity mark

One `MarkSpec` per principal (`packages/identity/src/marks.ts` 20 to 35): variant (`initials | glyph | dither | picture | agent`), initials, density 1 to 4, glyphSeed, pictureUrl, presenter, self, hue, trust, and the accessible label. `markSpec` (90 to 125): an agent is the agent variant with no hue; a picture needs a `pictureUrl` from the caller, else it falls to initials; glyph and dither keep no initials; initials come from the builder's typed letters or from `initialsFor` (a label gives one letter, a name the first letter of its first two words or the first two letters of one word). The salt "Another" rerolls is XORed into the glyph seed (72). The hue is null unless the caller passes the room's granted slot, so comments, version history and Show changes never colour (9 to 11).

How the hue derives: six hex values that pass 3:1 against `#070707`, `#ffffff` and `#f2f2f0` (`hues.ts` 1 to 9, 22 to 29); the slot is `sha256(principalId)[0] % 6 + 1` (49 to 52); a room grants the preferred slot or the least used one (59 to 73); the grant lives on the presence entry so every client draws the same colour (11 to 14; `room.ts` 2077 to 2094 writes `hueSlot: slot - 1` and the computed mark on the roster entry).

How the glyph and the plate derive: `markHash` (`marks.ts` 66 to 74) takes `density = (digest[8] & 3) + 1` and `glyphSeed = uint32(digest[12..15]) ^ salt`. The package renderer (`marks-render.ts`): the chip is a square of `size`; the plate is the chip less a 1 px border ring (117 to 119, 136 to 142); the initials plate lights `density` eighths of an 8 by 8 Bayer screen in 2 px cells aligned to the plate's top left (146 to 154); the glyph variant is a 5 by 5 grid of cells inside the plate with a 1 px inset, each empty or one of five glyphs, mirrored left to right, from an xorshift32 stream over the seed (56 to 84, 156 to 173); the dither variant is a Bayer dithered ramp whose centre, angle and curve come from the seed (86 to 96, 175 to 189); the agent plate is a 50 percent field with a centred square (191 to 203); a presenter gains a triangle at the bottom right over a 1 px paper gap (209 to 221). The SVG (302 to 359) draws the plate, the picture, the cells as one path, the initials at 11, 8 or 7 px in Inter 500 (289 to 295), the border in ink for the own chip and `#8a8a88` (light) or `#5c5c5a` (dark) otherwise (41 to 46, 347 to 351), and a 2 px stripe in the hue on live surfaces (352 to 356). The one bit PNG shares the raster (`marks-png.ts` 18 to 21).

The chrome draws its own copy. `IdentityChip` (`packages/chrome/src/presence/IdentityChip.tsx` 105 to 177) renders a `span.ts-chip` with a CSS border (`presence.css` 12 to 24: `box-sizing: border-box; border: 1px solid var(--pt-edge)`, ink for `.is-self`, dashed for `.is-agent`), an inner SVG of `size - 2` (`mark-svg.ts` 29 to 31) with one `rect` per lit cell from `markCells` (169 to 182), the initials as a text node with a 2 px paper stroke (`presence.css` 49 to 57), the stripe and the presenter triangle as absolutely positioned elements (60 to 82), and the two ring halo over a picture as a box shadow (85 to 92). The cell rules live in `mark-svg.ts` (`bayerCells` 39 to 58, `glyphGrid` 61 to 77, `glyphCells` 80 to 123, `ditherCells` 126 to 155, `agentCells` 158 to 166); the file says it predates the package's renderer and that `IdentityChip` "switches to the package's renderer when it lands" (8 to 11). Sizes are 24, 16 and 14 (`MARK_SIZES`, `marks-render.ts` 32), a 12 px chip by a CSS override on the filmstrip (`Sidebar.css` 703 to 711; `FilmstripMarks.tsx` 74 to 77), and the builder's 32, 64 and 256 px previews scale the 24 px grid (`dialogs/AvatarBuilder.tsx` 43 to 66). The mark reaches the chrome either as `identity.mark` from the server (the presence entry, `room.ts` 2093) or is computed on the client from the view with `avatar: { variant: 'initials' }` (`IdentityChip.tsx` 42 to 76).

The picture. `account.setAvatar` with `variant: 'picture'` refuses an anonymous principal with "Sign in to upload a picture" (`avatar.ts` 279 to 286), counts ten uploads a day per identity (288 to 294), sniffs the bytes (JPEG, PNG, WebP, GIF; SVG and HEIF refused, 50 to 69), decodes with sharp under `limitInputPixels` and `failOn: 'error'`, rotates, crops, resizes to 32, 64, 128 and 256 px WebP plus one 256 px PNG, strips metadata (103 to 169), stores under `u/<avatarKey>/<sha256>-<size>.<ext>` on the public Blob store hosted or `.turboslide/users/` on a checkout, and rotates the key with the old prefix deleted (295 to 313). The choice is written on `ts_profile` and on the account's principal record (308 to 310).

The avatar choice (`principal.ts` 27 to 43): `{ variant, initials?, salt?, picture? }`. For an account the resolver reads it from the account's principal record (`identity.ts` 345 to 352: `record?.avatar`); the `ts_profile.avatar` column is written (`profile.ts` 94 to 106; `actions.ts` 370 to 373) and never read for rendering.

### 1.6 Resolution and who sees whom

`resolvePrincipal` (`resolve.ts` 139 to 211): an id of no known format renders as itself with trust `guest` (146 to 158, the round one and two author names); an agent id renders as the token's name or "Agent" (160 to 174); a `usr_` id renders as its profile, or "Deleted account" when the profile is missing or deleted (176 to 190, 101 to 133); an anonymous id renders as the aliased account's profile when the alias table names one, else as its record's typed name (`guest`) or label (`label`) (191 to 210). `toIdentityView` (231 to 248) carries `name` only when the trust is not `label`, and `email` only when the caller passes `showEmail`.

Two server resolvers exist. `apps/studio/src/server/auth/identity.ts` `resolveIdentity` (653 to 692) prefetches the record, the alias, the account profile and the token and is called by `identityViewFor` (695 to 723), which only `account.me` calls (`actions.ts` 148). `apps/studio/src/server/room.ts` `resolveIdentity` (398 to 407) passes `alias: () => null, account: () => null` and is what `authorOf` (389), the presence roster (`cachedIdentity`, 2050), the editor's own identity on load (`write.ts` 360 to 363, 380 to 389) and `resolvePrincipalId` (410 to 415) use. `room.requestIdentity` (`room.ts` 309 to 377) reads the bearer and the anonymous cookie only; it never asks better-auth for a session, so on the room routes (the editor load, ops, stream, presence, comments, sessions: `write.ts` 333, 606, 754; `sessions.server.ts` 35; `room.ts` 962; `routes/api/decks.$deckId.ops.ts` 67) a signed in person is their anonymous cookie. The session is consulted by the actions dispatcher (`server/actions.ts` 696) and the share exchange (`routes/s.$token.ts` 71).

The chrome's own index (`apps/studio/src/editor/controller.tsx` 542 to 588): a comment author or a mention outside the roster is drawn from the stored `{ principalId, label, kind }` of the comment with trust decided by the id prefix (`usr_` is `verified`, `agent:` is `agent`, else `label`); the roster's entries and the caller override by id. A version record's author is the identities map entry by id, else the stored `author.name` as a guest, else "Earlier edits" (`packages/chrome/src/versions-model.ts` 41 to 60). The Share dialog derives a grantee's view from the id prefix and `labelFor` alone (`dialogs/Share.tsx` 277 to 285, 306 to 311).

Who sees whom (`room.ts` 2129 to 2144; `presence-model.ts` 83 to 95): a reader admitted by a link or by the open mode sees a `verified` person as the role word ("An editor", "The owner", "A commenter", "A viewer") with the role word's initial on the plate, unless the owner's `showNamesToLinkVisitors` switch is on (default false, 2218); labels, typed names and agents pass through to everyone. The roster row shows the name, the trust word, the role word or "by link", the slide, and "(you)" for the own row (`RosterMenu.tsx` 105 to 187). The version history shows "You" for the own records (`VersionsPanel.tsx` 160 to 168). The accessible name of a chip is the name and the trust word (`IdentityChip.tsx` 92 to 97).

### 1.7 Authorization and the deployment today

`decide` (`access.ts` 273 to 337) works over `Principal { id, kind: 'anonymous' | 'account', email?, admin }` (57 to 62): deny by default, one 404 for a missing and a restricted deck, 403 with the capability, 401 for no identity, 410 for a revoked publish token; the owner everything, a grant its role, a link its stored role and never the sharing, trash, publish, transfer or follow cells (153 to 162, 330), the legacy open mode as a link, an agent its owner's role intersected with its scopes, the deployment admin everything (328). Follow needs an account principal (331 to 334). A deck without a record is `open: editor` until R8 (17 to 19, 282 to 286). `authorize()` wraps it with the mode (`apps/studio/src/server/authorize.ts` 69 to 87; `docs/security.md` 43 to 72).

Production's environment (`docs/HOSTING-MOVE.md` 20; `docs/gslides-parity/VERIFICATION-3.md` 845, 1046; `VERIFICATION-4.md` 307): `TURBOSLIDE_AUTHORIZE`, `TURBOSLIDE_MAIL` (set to `off`), `TURBOSLIDE_REALTIME=blob`, the two secrets, the public store host, the Blob token; not set: `DATABASE_URL`, `REDIS_URL`, `RESEND_API_KEY`, `TURBOSLIDE_MAIL_FROM`, `BETTER_AUTH_SECRET`. What that implies for accounts today:

- No `DATABASE_URL`: the auth database is `none` (`db.ts` 62 to 65), `runtime.auth` is null, `keys` is `noApiKeyStore`, aliases and profiles are memory per instance (`identity.ts` 214 to 219). There are no accounts, no API key records, no sessions and no `usr_` principals on production. Every person is an anonymous principal (`docs/PRODUCT.md` 365: "On today's deployment every seller is an anonymous principal until sign in lands"). The Sign in row and the name prompt's Sign in link are absent. The only bearer is `TURBOSLIDE_TOKEN`, the bootstrap admin (`identity.ts` 502 to 518).
- `TURBOSLIDE_MAIL=off`: `selectMail` answers `off` (`mail/mailer.ts` 65 to 68) and `offMailer` drops every mail with one warning (252 to 268); the sign in handler answers the same whether or not a mail left (`better-auth.ts` 149 to 156). So even with a database no magic link, code, invitation, access request, transfer or digest mail would reach anyone. The mail off state is also the reason SPEC-3 804 names GitHub as the only sign in until a sending domain exists, and GitHub's two variables are not set either.
- `TURBOSLIDE_AUTHORIZE=shadow`: a denial is logged as `authorize.deny` and the call proceeds with the legacy role (`docs/security.md` 64; `authorize.ts` 76 to 81). Every deck without a record is an open editor deck to anyone with the address. The identity of a request matters for attribution and quotas, not for refusal. The You need access page hides its request form while the deployment has no sign in provider (`docs/PRODUCT.md` 139).
- No `REDIS_URL`: the principal store is the file store under the instance's state folder (`auth/principal.ts` 104 to 110). On Vercel that folder does not outlive the instance. The typed name survives through the deck index on the Blob store (`room.ts` 357 to 366; `access.ts` 222 to 234); the avatar choice and the notification setting do not (defect 5).

## 2. Defects

1. The mark's field touches the border. The plate begins at the pixel inside the 1 px ring (`marks-render.ts` 117 to 119: `origin: 1, extent: size - 2`) and the initials, dither and agent fields fill it from its first pixel (146 to 154, 175 to 189, 191 to 203). The chrome does the same: the inner SVG is `size - 2` wide inside a `border-box` span with a 1 px CSS border (`IdentityChip.tsx` 116 to 117, 149 to 152; `presence.css` 16 to 19), and `bayerCells` and `ditherCells` start at `x: 0, y: 0` (`mark-svg.ts` 48 to 53, 145 to 150). A picture abuts the border the same way (`IdentityChip.tsx` 146 to 147: `width={plate}`, `object-fit: cover`). Only the glyph variant keeps a 1 px inset (`marks-render.ts` 158 to 160; `mark-svg.ts` 88 to 89). Measured at 24 px on three anonymous ids: the densest initials plate has 44 of its 144 ink pixels on the plate's outer ring, the lightest 22 of 72; the dither plate 31 to 53 (package) and 34 to 68 (chrome). Ink on the ring merges with the `--pt-edge` border, so the chip reads as a ragged square and the ring stops reading as a border. The fix is one rule in both renderers: a 1 px paper gap between the ring and the field, so the field's plate is `origin: 2, extent: size - 4` (the presenter badge and the stripe already sit inside it), or the chrome's `.ts-chip` takes `padding: 1px` with a `size - 4` plate. The 12 px chip then has an 8 px field. `marks-render.test.ts` and `presence-model.test.ts` recount.

2. The chrome and the package draw different marks for the glyph and dither variants. The package's `glyphGrid` is an xorshift32 stream with `word % 3` empty cells and `(word >>> 8) % 5` glyphs (`marks-render.ts` 56 to 84); the chrome's takes three bits per cell from a rotation of the seed with 0 and 6 to 7 empty (`mark-svg.ts` 61 to 77). The package's ramp parameters come from a seeded stream (`rampParams`, 86 to 96); the chrome's from the seed's four bytes directly (`ditherCells`, 130 to 134) with a different curve range and angle span. Measured at 24 px on three ids: the glyph plates share 22 to 48 ink pixels of 130 to 192; the dither plates share 108 of 124, 152 of 318 and 191 of 240. The initials plates agree pixel for pixel. So `turboslide account me --avatar-png`, the PPTX comment author list and any export that embeds a chip show one mark and the chrome another for the same person. The chrome file records the intent to switch (`mark-svg.ts` 8 to 11); the switch never happened.

3. Sign in does not reach the deck surfaces. `room.requestIdentity` (`room.ts` 309 to 377) reads the bearer and the anonymous cookie and never the better-auth session; `room.resolveIdentity` (398 to 407) resolves with `alias: () => null, account: () => null`. Consequences, each from the code path: the editor's own identity on load is the cookie's record (`write.ts` 360 to 363, 380 to 389), so `signedIn` in the shell is false (`controller.tsx` 4231, `EditorRoot.tsx` 808) and the account menu's sentence stays "Not signed in" (`AccountMenu.tsx` 39 to 42); the presence entry of a signed in person carries the anonymous id with trust `guest` or `label` (`room.ts` 2033 to 2053, 2068 to 2098); version records are authored as the anonymous id with the typed name (`authorOf`, 379 to 395); an anonymous id linked to an account by the alias table (`alias.ts` 1 to 6) never renders as the account anywhere in the editor, which is what SPEC-3 2.4 and 7.4 promise ("a record written before a person signed in renders as the person afterwards"). The one path that sees the session and the alias is `account.me` (`actions.ts` 146 to 182; `server/actions.ts` 696). `accounts.spec.ts` asserts the alias row and the session (230 to 267) and never a rendered badge, so the gap is untested. A `usr_` id that did reach the room resolver would render as "Deleted account" (`resolve.ts` 176 to 190 with a null `account` lookup).

4. The verified state has no mark and no word. SPEC-3 0.19 names "verified (the check badge)". `TRUST_WORDS.verified` is the empty string (`resolve.ts` 24), `trustWordOf` returns a word for `guest` only (`IdentityChip.tsx` 88 to 90; `presence-model.ts` 98 to 100), `markSpec` draws nothing for trust (`marks.ts` 90 to 125), and `data-trust` on the chip has no rule in `presence.css`. A link visitor who reads a verified person's name under the owner's switch, or a grant holder, cannot tell a verified "Kevin" from a guest "Kevin" once the "guest" word is cut (the flag cuts it past 13 characters, `presence-model.ts` 135 to 140). The tooltip is the only carrier (`resolve.ts` 29 to 40) and the chrome's chip tooltip does not use it (`chipTipOf`, `presence-model.ts` 123 to 129 composes name, trust word, slide).

5. The avatar choice and the settings are per instance on production. The principal store is Redis or a file store (`auth/principal.ts` 104 to 110); production has no Redis (1.7). `account.setName` carries the name onto the Blob index (`actions.ts` 322 to 330; `access.ts` 230 to 234) and `room.requestIdentity` reads it back (`room.ts` 356 to 365), but `account.setAvatar` writes the record only (`actions.ts` 366 to 369), and the index update has a `name` field alone (`indexUpdates.name`, `access.ts` 232). A glyph or dither chosen on one instance is initials on the next and after every cold start; `notificationSettings` and `livePointers` go the same way. Two people who chose different plates can be shown with the same default plate.

6. Per deck name uniqueness reads one source. `taken` is the version log's human author names (`actions.ts` 185 to 205), skipping labels and `studio`. SPEC-3 7.2 names "the owner, the roster, the version log". A second "Kevin" is accepted while the first has only commented, is only present, or holds a grant and has not yet produced a version record; on a fresh deck the first checkpoint lands 2 s after the first edit (SPEC-3 0.3), so two people who type the same name in the same minute both keep it. The check also runs on the instance's own store; on the blob tier the version log is shared, so this part holds across instances. The check never runs when the name is set from `/decks` or the profile with no deck in the request (`facts.deckId` undefined returns `[]`, 189).

7. Two anonymous principals with one label are not told apart. `disambiguateLabels` (`labels.ts` 125 to 143) has no caller outside its test (a repository grep over `packages` and `apps`). The roster, the version history and the comments would show two "Titanium 471" rows with two marks whose only stored difference is the plate density (four values) and, on live surfaces, the hue. The label space is 57,280 (`labels.ts` 93 to 94); on a deck with twenty people the chance of one collision is about 0.3 percent, on a deployment's whole history it is certain.

8. The initials variant separates people by four greys. `density` is two hash bits (`marks.ts` 71). Two "Kevin"s on the default variant differ by the field's density alone, one chance in four of being identical, and at 14 px (the flag and the mention chip) a 1/8 and a 2/8 field are hard to tell apart. The glyph and dither variants carry 32 bits but are opt in through the builder, whose row is parked: the whole `title.account` submenu (Change name, Change avatar, Sign in, Sign out, Forget this browser, Sessions) is wrapped in `parked(...)` (`packages/chrome/src/menus/model.ts` 865 to 900, "parked whole (docs/FOCUS.md 3.2)") and `AccountMenu` lists only the rows `isPresent` admits (`AccountMenu.tsx` 38), so with the Advanced tools switch off the own chip's menu is its header sentence alone; the roster's own row is under the same switch (`RosterMenu.tsx` 70 to 71).

9. The Share dialog does not resolve people. `identityOf` (`dialogs/Share.tsx` 277 to 285) builds a grantee's view from the id prefix and `labelFor`; the grant rows read `nameOf(grant.principal)` which is the label for every anonymous grantee (472) and the email for an invitation. A grantee who typed a name shows as their label in the people list; a `usr_` grantee shows as a label with trust `verified` and no name. The owner row shows the same. "You" is the one resolved word (557 to 559).

10. The stored comment author is a label snapshot. `CommentAuthor` is `{ principalId, label, kind }` (`packages/schema/src/comments.ts` 140) and the chrome draws a past commenter from it with trust by id prefix (`controller.tsx` 542 to 555). A comment written under the label and a comment written after typing a name show two different words for one person in one thread; a name typed later never reaches the older comment. This is the design of SPEC-3 2.4 ("resolved at render time") inverted for comments.

11. The picture avatar is unreachable in practice. It needs an account (`avatar.ts` 286), which needs a database, which production does not have (1.7); the builder's Picture tab reads "Sign in to upload a picture" for everyone on production. On a checkout with `TURBOSLIDE_AUTH_DB` the path works.

12. Deletion leaves two readings. `onUserDeleted` deletes the account's principal record and every alias (`identity.ts` 392 to 398). After that a `usr_` authored record renders "Deleted account" (`resolve.ts` 180 to 189) while an anonymous authored record that was aliased to the same account renders its label again (`resolve.ts` 191 to 210 with no alias), so one deleted person is two authors in the version history. SPEC-3 7.4 asks for "Deleted account" on the principal.

13. The account's typed name is not run through the rules on every path. `account.setName` normalizes (`actions.ts` 319). The magic link, OTP and GitHub paths create the user row through better-auth with whatever `name` the provider or the library gives at creation (GitHub's display name on that path), and `resolvePrincipal` shows `profile.name.trim() || profile.email` (`resolve.ts` 124) with no rule applied and no per deck uniqueness. `ensureUserByEmail` writes `name: ''` (`actions.ts` 279), which renders as the email address itself.

14. The link visitor's role word initial reuses the person's mark. `rosterEntryForReader` (`room.ts` 2137 to 2143) keeps the verified person's `mark` (its density, its glyph seed, its hue) and only swaps the initials to the role word's initial. A link visitor who later gains a grant sees the same plate under a name and can pair the two, which is the disclosure 0.12 was meant to prevent; the plate should be the role's, not the person's.

15. The `guest` word is the only spoken difference between a typed name and a label on text surfaces. `displayWithTrust` (`resolve.ts` 250 to 256) and the flag (`presence-model.ts` 135 to 140) drop the word when the flag is full. A label such as "Cobalt 512" is refused as a typed name (`names.ts` 324, the label grammar), so a label and a name cannot collide; a typed "Cobalt" alone is refused too (`isLabelWord`, `labels.ts` 116 to 118). This part holds.

16. An unknown id format renders as text with trust `guest` (`resolve.ts` 146 to 158). Round one and two records carry an author name and no principal id (`versions-model.ts` 67 to 73 handles `studio`); any other legacy name (a typed `?author=` from before R1) shows as a person with the guest word and a mark computed from the name as if it were an id, and a live person who types that same name is a second person with the same word.

## 3. Gaps against the target

The target is the identity model of SPEC-3 sections 2.4, 4.1, 4.8 and 7 and `docs/PRODUCT.md` section 2 rank 4 (a typed display name the presence chips, the Share dialog and Version history show, with "You" on the own row) and section 9 (optional sign in that "names a person and owns their decks").

- Render time resolution through the alias table (2.4, 7.4) exists in the package and in `account.me` and reaches no deck surface (defect 3). The target's "old records render with the check badge" (SPEC-3 1194) has neither the resolution nor the badge (defect 4).
- Three trust states with marks (0.19). Two states have a mark difference (the agent's dashed ring); label, guest and verified share one mark family and differ by a word that appears on some surfaces (defects 4, 15).
- One mark per principal drawn by one function (4.1). Two functions draw it and they disagree for two of the four variants (defect 2). The chrome's file says so.
- The 1 px `--pt-edge` border around the plate (7.6, "a square plate with a 1 px --pt-edge border") is drawn, and the field runs into it (defect 1).
- The label collision suffix "(2)" (4.1) is unused (defect 7).
- Per deck uniqueness "against the owner and every named collaborator in the roster and the version log" (0.19, 7.2) reads the version log only (defect 6).
- The Share dialog showing the display name (rank 4) shows the label (defect 9).
- The typed name on `/decks` "Edited by Kevin" (`docs/PRODUCT.md` 157) is wired on the card (`routes/decks.index.tsx` 246 to 258 takes an optional `by`; 1250 to 1258 reads `updatedBy` off the card) and nothing fills it: a grep for `updatedBy` over `apps/studio/src` and `packages` finds no producer outside the route, so the line reads "Edited yesterday at 2:02 PM" with no author on every card.
- Sign in that names a person and owns their decks (section 9) is built and switched off: no database, no mail, no provider variables on production (1.7). Question 6 of `docs/PRODUCT.md` section 10 (line 658, the email link first) needs Resend and a sending domain, which `TURBOSLIDE_MAIL=off` records as absent.
- The avatar builder and the Change name row are reachable only under the Advanced tools switch (`menus/model.ts` 865 to 900; the focus round parked the account rows and `docs/PRODUCT.md` 646 leaves them there), and the Picture tab needs an account (defect 11). The name prompt on the first edit and the first Share is the one unparked path to a name; there is no unparked path to a plate.
- The mention picker listing present people and past commenters (SPEC-3 5.4; `docs/PRODUCT.md` 314) is the round after; today mentions list only the caller.
- Passkeys and GitHub (7.3) are off by environment.

## 4. Notes for the design

- Keep the id as the only truth and make one resolver. The room's `resolveIdentity` should take the alias and account lookups the auth runtime already has (`identity.ts` 653 to 692), with the 5 s identity cache it keeps (`room.ts` 2025 to 2053), and `room.requestIdentity` should read the session the way `auth/identity.ts` `requestIdentity` does (539 to 576), or the room routes should call that function. Until then no account feature is visible on a deck.
- One renderer. Delete `mark-svg.ts` and render `renderMarkSvg` (or its cells through `inkRects`) in `IdentityChip`; the builder's previews then scale the package's raster. Any change to the geometry (the border gap of defect 1) is made once.
- The border gap. A 1 px paper ring inside the edge ring at every size, including the 12 px chip, so the field is a figure inside a frame. The initials font sizes stay; the presenter badge and the stripe already sit inside the field. Over a picture the halo outside and the gap inside keep the picture from touching either ring.
- A verified mark. If the check badge of 0.19 stands, it is a 5 px ink square at the plate's top right over a 1 px paper gap, the presenter's triangle mirrored, drawn from `trust === 'verified'` in `renderMarkBits` so the CLI PNG and the exports carry it too. A word beside the name is not enough at 14 px.
- What separates two people with one name. The design should decide which channel is the primary one and make it survive the smallest chip: the plate (32 bits of glyph or dither by default instead of four greys), or a short id suffix on text surfaces ("Kevin · 471" from the label's number, which is stable per principal and already refused as a typed name), or the "(2)" suffix by first appearance on every list. The suffix by appearance changes across sessions; the label number does not.
- The Share dialog and the comments should take identity views from the server's resolver (the presence route already ships `mark`, `label` and `trust` per entry); the stored `CommentAuthor.label` can stay as the PPTX author fallback and stop being the rendered word.
- Per deck uniqueness needs the roster and the grants beside the version log, or it needs to be dropped in favour of the id suffix, since a check that runs once at typing time cannot hold across two instances typing at once.
- Production. Every account row in this note is dormant until `DATABASE_URL`, a mail path (`RESEND_API_KEY` and `TURBOSLIDE_MAIL_FROM`, or GitHub's two variables) and `REDIS_URL` for the principal store exist. A design that depends on sign in for the seller's hour should say so in its first line; a design that does not should carry the avatar choice on the deck index the way the name travels (`access.ts` 222 to 234), or move the principal record to the Blob store per principal.
