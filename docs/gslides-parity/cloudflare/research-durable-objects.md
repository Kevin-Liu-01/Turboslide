Written 2026-10-01 in the worktree `Turboslide-realtime` (branch `realtime/round`, `origin/main` at `c978bb43` plus a build round's uncommitted edits). It answers the six questions the Cloudflare design round put to W1: the free plan and Turboslide's consumption against it, what one object holds, connection limits, the wake and billing rules of an idle WebSocket, published latency, and what wrangler needs. Every Cloudflare page below was read on 2026-10-01 as its markdown twin (`<page>/index.md`, saved under the session scratchpad `cfdocs/`); the `dateModified` in each page's JSON-LD is given after the URL where the page carries one. The load model used throughout is the one `docs/REALTIME.md` section 2 adopts from `docs/SYNC.md` 4.3 (line 242: "One editor hour is 12 minutes of editing at one edit per 5 s and 48 idle minutes") and `research-options.md` section 6 (lines 103 to 106) counts per editor hour: 144 ops, about 1,440 caret and selection messages at 2 a second while editing, 576 heartbeats at 5 s while idle, about 2,200 messages sent per tab and the same number delivered, 300 bytes a message, a room of two on average, 30 day months (1,500 editor hours a month at 50 a day, 15,000 at 500). ## 0. The short answer

1. Yes. Durable Objects with hibernating WebSockets run on the Workers Free plan since 2025-04-07, SQLite backend only, with daily caps of 100,000 requests, 13,000 GB-s of duration, 5 million rows read, 100,000 rows written and 5 GB of storage, reset at 00:00 UTC, and an operation that passes a cap fails with an error for the rest of the day (section 1.1).
2. At 50 editor hours a day Turboslide fits every cap with room, if the object is written three ways: the 5 s heartbeat is answered by `setWebSocketAutoResponse`, no `setTimeout` or `setInterval` is left standing (alarms instead), and presence never touches SQLite. In that shape the day costs about 5 to 13 % of the request cap, under 1 % to 35 % of the duration cap and 8 to 22 % of the write cap (section 1.3).
3. At 500 editor hours a day the Free plan does not hold on its own: rows written reach 84 to 216 % of the cap because each op is one row and a delete counts as a write, requests reach 52 to 128 % depending on the alarm cadence, and duration passes the cap if any timer keeps the object awake while people edit. The Workers Paid plan ($5 a month minimum) makes every one of those an overage instead of a cutoff; at 500 hours it costs $5.45 to $17.95 a month by the published rates (section 1.4).
4. One fact forces the Paid plan before the numbers do, if Kevin wants production to never fail closed: on the Free plan "If you exceed any one of the free tier limits, further operations of that type will fail with an error" (pricing page line 30), and the Worker in front answers "Error 1027" after 100,000 requests in a day (Workers limits page line 171). A public `workers.dev` hostname lets anyone spend that budget by opening connections; the Worker's authorization check keeps the object's cap safe but not the Worker's own. Under `docs/FOCUS.md` 6.2 a core row red twice on production is a stop, and a daily cutoff would redden every realtime row at once (section 1.4).
5. No first party page read today publishes a WebSocket round trip to a Durable Object in milliseconds. Cloudflare says where the object runs (near the first request, never moved) and how fast its storage is (microseconds); the per frame figure stays `research-options.md` 5b's estimate until the preview measures it (section 5).
6. Wrangler 4.146.0 (npm, 2026-10-01) needs `name`, `main`, `compatibility_date`, a `durable_objects.bindings` entry and an `exports` entry with `storage: "sqlite"` (or the legacy `migrations` array, never both), `npx wrangler login` in a browser session or `CLOUDFLARE_API_TOKEN` plus `CLOUDFLARE_ACCOUNT_ID`, and one `npx wrangler deploy`, which provisions the namespace and prompts for the `workers.dev` subdomain. A Cloudflare account created through Sign in with Google has no password, and creating an API token requires setting one; and Sign in with Google is unavailable if an account already exists under that email (section 6).

### 1.2 Turboslide's day, counted per editor hour

Per editor hour, per tab, from the load model above:

- Incoming WebSocket messages to the object: 144 ops + 1,440 presence frames + 576 heartbeats = 2,160. At 20:1 that is 108 request units; with the heartbeat answered by `setWebSocketAutoResponse` (section 4) it is (144 + 1,440) / 20 = 79.
- Connection requests: one per connect. A WebSocket has no 240 to 290 s life (`STREAM_LIFETIME_MS`, `protocol.ts` 49, is the SSE stream's), so 1 to 3 an hour with network changes.
- Alarm invocations: one request and one row written each. The cadence is a design choice this note does not make: a 30 s debounce after the last op gives at most 24 an hour, an alarm every 5 s during the 12 editing minutes gives 144.
- Rows written: one per op if every op is a row (144), one per `setAlarm` (24 to 144), one per deleted row at compaction after the Blob checkpoint (0 to 144 because deletes count as writes), zero for presence if presence stays in memory and the socket attachment (section 2).
- Rows read: with the heartbeat auto-answered the object is never woken during the 48 idle minutes, so reads are the joins (a tail of the log, say up to 200 rows twice an hour) and rare wakes: under 500 an hour. Without the auto-response each heartbeat re-runs the constructor (section 4), 576 wakes an hour, and a constructor that reads 10 to 50 rows costs 5,760 to 28,800 rows an hour.
- Duration: three shapes of the same object. (a) Handlers only: about 1,584 events at about 2 ms plus about 24 Blob checkpoints at about 300 ms, about 10 s awake, 10 s × 0.125 GB = 1.3 GB-s, rounded to 1.5 below. (b) A `setTimeout` kept standing while people edit (the 80 ms presence batch written as a timer, a coalesce timer): the object is "idle, in-memory non-hibernateable" for the 12 editing minutes, 720 s × 0.125 GB = 90 GB-s (this is `research-options.md` 5b's figure). (c) A standing `setInterval` (a 30 s roster sweep written as an interval): awake the whole hour, 3,600 s × 0.125 GB = 450 GB-s. The room of two shares one object, so (b) and (c) are upper bounds ("shared across all requests active on an Object at once").
- Storage: 300 bytes × 144 ops = 43.2 KB an editor hour uncompacted.

Reading of the table. At 50 editor hours a day every row holds if the object is written in shape (a) or (b), with the heartbeat auto-answered and presence out of SQLite; shape (c) alone passes a cap. At 500 editor hours a day the binding row is rows written, not duration or requests: one row per op is the floor for an op that must be durable before the acknowledgement (`research-options.md` 5b: "every piece of state that matters must be in SQLite or on Blob before the answer goes out"), and compaction by `DELETE` doubles it. Whether `DROP TABLE` or `storage.deleteAll()` is counted as rows written is not stated on the pricing page and is left open (section 8). The pipeline's gate runs are not in the table: `docs/REALTIME.md` 1.1 rule 1 keeps the whole matrix on the local memory tier, and a hosted gate that opened tabs against the object would count every tab's connects, messages and alarms against the same daily caps (`research-costs-actual.md` section 2 found 200 to 750 GB hours on a gate day against 6 to 27 on a quiet one on Vercel).

### 1.4 Where the Paid plan is forced, and what it costs there

Three facts, each with its source:

1. The Free plan fails closed. "If you exceed any one of the free tier limits, further operations of that type will fail with an error" (pricing line 30); a Worker over 100,000 requests a day returns "Error 1027" (https://developers.cloudflare.com/workers/platform/limits/, dateModified 2026-09-05, line 171). On production that is every realtime row red until 00:00 UTC. The Paid plan has no daily cap ("No limit" on requests, Workers limits line 21) and bills overage.
2. The budget is spendable by strangers. A `workers.dev` hostname is public; each `Upgrade` request is one Worker request before any authorization runs, and the docs tell the Worker to "Validate requests in your Worker to avoid billing for invalid requests against a Durable Object" (https://developers.cloudflare.com/durable-objects/best-practices/websockets/, line 471), which protects the object's cap and not the Worker's.
3. At ten times today's load the rows written cap is passed in every shape (section 1.3).

At 50 editor hours a day the Paid plan costs $5.00 a month: 12,750 × 30 = 382,500 requests and 4,500 × 30 = 135,000 GB-s are inside the included million and 400,000; shape (c) would add one rounded million GB-s at $12.50. At 500 editor hours a day: requests 52,000 to 127,500 × 30 = 1.56 to 3.83 million, 0.56 to 2.83 million over, rounded to 1 to 3 million, $0.15 to $0.45; duration (a) 22,500 GB-s a month included, (b) 1.35 million, 950,000 over, rounded to 1 million, $12.50; rows written 2.5 to 6.5 million a month inside the 50 million included; storage inside the 5 GB-month. Total $5.15 to $17.95 a month, against `research-options.md` 5b's $18 to $85 at 500 hours (that note let the object stay awake the whole hour).

## 2. What the object can hold (question 2)

https://developers.cloudflare.com/durable-objects/platform/limits/ (dateModified 2026-06-01), the SQLite table, lines 20 to 33:

- "Number of Objects: Unlimited (within an account or of a given class)"; "Maximum Durable Object classes (per account): 500 (Workers Paid) / 100 (Free)"; "Storage per account: Unlimited (Workers Paid) / 5GB (Free)"; "Storage per class: Unlimited"; "Storage per Durable Object: 10 GB".
- "Key size / Value size: Key and value combined cannot exceed 2 MB"; "WebSocket message size: 32 MiB (only for received messages)"; "CPU per request: 30 seconds (default) / configurable to 5 minutes"; "Simultaneous outgoing connections/request: 6".
- The SQL limits the summarizer read from the same page: 100 columns a table, unlimited rows a table, 2 MB a row, 100 KB a SQL statement, 100 bound parameters a statement.
- The same page's FAQ contradicts its table on the free plan: "When a SQLite-backed Durable Object reaches its maximum storage limit (10 GB on Workers Paid, or 1 GB on the Free plan), write operations ... will fail with the following error: database or disk is full: SQLITE_FULL" (line 120), while "Read operations ... will continue to work, and DELETE operations will also succeed" (line 126). Either figure is far above a deck's log; the design should quote 1 GB per object on Free as the safe reading.
- Footnote 3: "Accounts on the Workers Free plan are limited to 5 GB total Durable Objects storage" (line 167), and "1 GB = 1,000,000,000 bytes" (line 165).

What that means for the two things the object must hold:

- The per deck op log: at 300 bytes an op a 2 MB row holds about 6,900 ops and a 100 KB statement about 330 bound ops, so a batch `INSERT` is chunked at 100 parameters; a whole deck snapshot as one row is not safe (a picture heavy deck's JSON can pass 2 MB) and snapshots stay on Blob as the version records do today (`research-options.md` 5b). SQLite rows read and written are reported per statement on the cursor ("rowsRead ... The final value is used for SQL billing", https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/, lines 256 to 259), so the cost probe can read them. Cursors must be consumed before the next `await` ("fully consume cursors synchronously before the next await", line 196). The storage API also offers point in time recovery "to any point in time in the past 30 days" (https://developers.cloudflare.com/durable-objects/best-practices/access-durable-objects-storage/, line 64).
- The presence roster: not in SQLite rows per frame (section 1.3 shows why). It lives in memory while the object is awake and is rebuilt on wake from `getWebSockets()` plus each socket's attachment: "serializeAttachment(value): Keeps a copy of value associated with the WebSocket connection", "Maximum serialized size is 16,384 bytes" (websockets page line 360); up to 10 tags of 256 characters per socket for `getWebSockets(tag)` (https://developers.cloudflare.com/durable-objects/api/state/, dateModified 2026-09-30, line 157). The identity fields `rosterEntryFor` adds (`room.ts` 2449 to 2489) fit an attachment; the pointer and drag frames are published and not stored, as `docs/REALTIME.md` 3.4 already decides for the redis tier.
- Memory: the object is billed for 128 MB (pricing line 69); the limits page carries no memory row, and the in-memory state page says memory is "measured per isolate (which can host multiple Durable Objects), not per object" (https://developers.cloudflare.com/durable-objects/reference/in-memory-state/, dateModified 2026-06-29, line 57) and "Because in-memory state is not preserved across eviction or hibernation, persist anything important to storage".

## 3. Connection limits (question 3)

- Per object: "The WebSocket Hibernation API permits a maximum of 32,768 WebSocket connections per Durable Object, but the CPU and memory usage of a given workload may further limit the practical number of simultaneous connections." (state page line 152). PartyKit's own doc puts its two tiers at "Without Hibernation: up to 100 connections per room" and "With Hibernation: up to 32,000 connections per room" (https://docs.partykit.io/guides/scaling-partykit-servers-with-hibernation/, read 2026-10-01), and notes `y-partykit` "doesn't currently support Hibernation".
- Per object throughput: "An individual Object has a soft limit of 1,000 requests per second" and "A Durable Object that receives too many requests will, after attempting to queue them, return an overloaded error to the caller" (limits lines 82 and 86). The 20:1 ratio "does not affect Durable Object metrics and analytics, which reflect actual usage" (pricing line 63), so the soft limit counts messages. Turboslide's worst room is 20 pointer publishers at the 15 a second cap (`protocol.ts` 40 and 55): 300 messages a second, under the soft limit.
- Per account: no page read today states a cap on open WebSocket connections per account. What bounds an account is the Worker's 100,000 requests a day on Free (one per upgrade), the 100 Workers and 100 Durable Object classes on Free (Workers limits line 30, DO limits line 24), and the six "Simultaneous outgoing connections/request" the object may hold while waiting for response headers (limits line 32; Workers limits line 205: "Each Worker invocation can have up to six connections simultaneously waiting for response headers", and "Outbound WebSocket connections also count toward this limit", line 214), which caps parallel Blob puts from one object at six.
- Message size: 32 MiB received (limits line 29; Workers WebSocket page: "WebSocket messages received by a Worker have a size limit of 32 MiB (33,554,432 bytes)").

## 4. Wake and billing rules for an idle WebSocket (question 4)

The lifecycle page (https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/, dateModified 2026-09-30) is the authority:

- States: "Active, in-memory", "Idle, in-memory non-hibernateable", "Idle, in-memory hibernateable ... Currently, it is after 10 seconds of inactivity while in this state", "Hibernated: The Durable Object is removed from memory. Hibernated WebSocket connections stay connected", "Inactive" (lines 33 to 37).
- The conditions, all of which must hold (lines 49 to 54): "No setTimeout/ setInterval scheduled callbacks are set"; "No I/O operation or promise passed to this.ctx.waitUntil() remains unfinished, and no outbound connection remains open"; "No WebSocket standard API is used"; "No request/event is still being processed". Then "After 10 seconds of no incoming request or event, and all the above conditions satisfied, the Durable Object will transition into the hibernated state" (line 56). A pending alarm is not in the list; alarms are the documented way "to guarantee that operations within a Durable Object will complete without relying on incoming requests to keep the Durable Object alive" (https://developers.cloudflare.com/durable-objects/api/alarms/, dateModified 2026-04-21, line 33).
- An object that cannot hibernate is evicted later: "after 70-140 seconds of inactivity ... the Durable Object will be evicted entirely from memory" (line 66). "Pending I/O and open outbound connections prevent a Durable Object from being evicted ... outbound fetch() requests ... pending setTimeout() and setInterval() timers. TCP sockets and outbound WebSockets also prevent eviction" (line 70); "Each operation prevents eviction until it completes or for up to 15 minutes from when it starts" (line 72); "While an operation prevents eviction, the Durable Object continues to incur duration charges" (line 74). A Blob `put` that hangs bills up to 15 minutes, 112.5 GB-s; the object's fetches need an abort timeout.
- Billing: "A Durable Object incurs charges only when it is actively running in-memory, or when it is idle in-memory and non-hibernateable" (line 82). The pricing page's version: "idle and eligible for hibernation are not billed for duration, even before the runtime has hibernated them" (line 35).
- What wakes a hibernated object: "In case of an incoming request or event while in the hibernated state, the constructor() will run again" (line 64); the websockets page: "When a message arrives, the Durable Object wakes up automatically" (line 42), "If an event occurs for a hibernated Durable Object, the runtime re-initializes it by calling the constructor. Minimize work in the constructor when using hibernation" (line 68); `acceptWebSocket`: "any incoming messages will be delivered by calling the Durable Object's webSocketMessage handler, and webSocketClose will be invoked upon disconnect" (state page line 148). Alarms wake it too: "if the Durable Object wakes up after being inactive, the constructor is invoked before the alarm handler" (alarms line 100). Each wake by a message costs one twentieth of a request; each alarm costs one request and one row written.
- What does not wake it: WebSocket protocol pings ("nor for incoming WebSocket protocol pings", pricing line 63) and an application ping matched by `setWebSocketAutoResponse`: "If a request is received matching the provided request then the auto-response will be returned without waking WebSockets in hibernation and incurring billable duration charges" (state page line 187); "Both request and response are limited to 2,048 characters each" (line 193); the example sets `new WebSocketRequestResponsePair("ping", "pong")` (https://developers.cloudflare.com/durable-objects/examples/websocket-hibernation-server/, lines 92 to 94). `getWebSocketAutoResponseTimestamp` tells the last time a socket was auto-answered, which is what a 30 s dimming rule (`docs/REALTIME.md` row `realtime.caret.dims-and-leaves`) can read on the next real event instead of a timer. For Turboslide the 5 s heartbeat (`PRESENCE_HEARTBEAT_MS`) has to be the literal auto-response string, or every heartbeat is a wake, a constructor run and a row read.
- What breaks hibernation outright: `ws.accept()` ("Calling accept() on a WebSocket in an Object will incur duration charges for the entire time the WebSocket is connected", pricing line 67); hibernation "is only supported when a Durable Object acts as a WebSocket server. Outbound WebSockets do not hibernate" (websockets page); "an open outbound WebSocket connection prevents eviction for up to 15 minutes" (line 340); "Events such as alarms, incoming requests, and scheduled callbacks prevent hibernation. This includes setTimeout and setInterval usage" (line 342).
- Alarm semantics: "Each Durable Object is able to schedule a single alarm at a time" (alarms line 23); "guaranteed at-least-once execution and are retried automatically when the alarm() handler throws", "exponential backoff starting at a 2 second delay from the first failure with up to 6 retries allowed" (lines 24 to 25); alarm handlers have "a maximum wall time of 15 minutes" (limits line 157). Local development: alarms "may fail after a hot reload" under `wrangler dev` (https://developers.cloudflare.com/durable-objects/platform/known-issues/, line 45), and before `wrangler@3.13.2` WebSockets did not hibernate locally (websockets line 232).
- `setHibernatableWebSocketEventTimeout` "sets the maximum amount of time in milliseconds that a WebSocket event can run for" (state page line 233), a guard for a handler that awaits a slow Blob put.

## 5. Latency in published measurements (question 5)

No page read today from Cloudflare publishes a round trip in milliseconds from a browser to a Durable Object over a WebSocket. What is published:

- Placement: "a Durable Object is automatically provisioned geographically close to where it is first requested, starts up quickly when needed, and shuts down when idle" (https://developers.cloudflare.com/durable-objects/concepts/what-are-durable-objects/, line 17); "By default, a Durable Object is instantiated in a data center close to where the initial get() request is made", "Durable Objects do not currently change locations after they are created", location hints `wnam, enam, sam, weur, eeur, apac, apac-ne, apac-se, oc, afr, me` are "a best effort and not a guarantee" (https://developers.cloudflare.com/durable-objects/reference/data-location/, dateModified 2026-06-26). A deck opened first from Europe keeps its object there for its life; the US seller who joins later pays the ocean on every frame. `idFromName` with a `locationHint` from the deck's owner region is the lever.
- The 2020 announcement (https://blog.cloudflare.com/introducing-workers-durable-objects/, 2020-09-28): "Cloudflare will automatically create the coordinator close to the users using it and minimize latency", "clients on the opposite side of the world from that location will experience moderate latency due to the inherent limitations of the speed of light".
- Storage: the 2021 post (https://blog.cloudflare.com/durable-objects-easy-fast-correct-choose-three/, published 2021-08-03) on the key value backend: "The get() might typically take a couple milliseconds", "The put(), however, will take much longer, probably tens of milliseconds"; the 2024 post (https://blog.cloudflare.com/sqlite-in-durable-objects/, 2024-09-26) on the SQLite backend: "Latency is effectively zero, because there is no communication barrier between the application and SQLite", "A query can complete in microseconds", and the write path runs behind output gates so "The application is able to work on constructing the response in parallel with the storage layer confirming the write". The admission path in the object (`admitOps`, `room.ts` 1693) is therefore in memory plus a local SQLite write, which is `research-options.md` 5b's "under 5 ms".
- Throughput: the soft limit of 1,000 requests a second per object (section 3) and the GA post's "Durable Objects can now serve hundreds of thousands of requests per second across objects, and hundreds of requests on a single object" (https://blog.cloudflare.com/durable-objects-ga/, 2021-11-15, no millisecond figure; the limits page's soft limit of 1,000 a second per object is the 2026 figure).
- Third party: the two community pages that carry numbers could not be read (section 9); a search engine snippet of a Discord thread claimed a 60 to 90 ms ping pong round trip and under 20 ms in the same colo, and this note does not rely on it.

So the per frame figure the realtime round carries, 10 to 30 ms a WebSocket frame in region and 120 to 170 ms keystroke to screen (`research-options.md` 5b, `docs/REALTIME.md` section 1), stays an estimate, and the row `realtime.keystroke.within-300ms` (`docs/REALTIME.md` section 2) measured on a preview is the first number anyone will have. One published fact bears on the method: the WebSocket protocol ping is answered at the edge, not by the object, so a ping pong round trip does not measure the object; the measurement has to be an application message the object answers (pricing line 63 on protocol pings; the dev.to note https://dev.to/petersg/your-websocket-ping-is-answered-by-the-edge-not-your-durable-object-2hh4 makes the same point without a number).

## 7. Findings, one line each

1. Durable Objects run on the Workers Free plan since 2025-04-07, SQLite only, 100,000 requests, 13,000 GB-s, 5 million rows read, 100,000 rows written a day and 5 GB in all, reset at 00:00 UTC (pricing lines 23, 30, 31, 41, 42, 88, 89; changelog 2025-04-07).
2. At 50 editor hours a day Turboslide uses 5 to 13 % of the request cap, under 1 % to 35 % of duration and 8 to 22 % of rows written, if the heartbeat is an auto-response, no timer stands and presence stays out of SQLite (section 1.3).
3. At 500 editor hours a day rows written reach 84 to 216 % of the free cap, because an op is a row and a delete is a write; the Free plan does not hold at ten times today's load without the Paid plan or a compaction that is not row deletes (section 1.3, pricing line 106).
4. A standing `setInterval` or `setTimeout` is the single most expensive line one can write: it turns 1.5 GB-s an editor hour into 90 or 450 and passes the free duration cap at 50 editor hours a day in the worst shape; a 30 s dimming rule must be an alarm or a read of `getWebSocketAutoResponseTimestamp` (lifecycle lines 51 and 56; state page line 217).
5. The 5 s heartbeat must be the literal `setWebSocketAutoResponse` pair, or it is 576 wakes, constructor runs and row reads an editor hour, 58 to 288 % of the free read cap at 500 hours (state page line 187; pricing line 65).
6. The Free plan fails closed for the day when any cap is passed, and the Worker's cap is spendable by anyone who can reach `workers.dev`; that is the fact that forces the Paid plan if production may never go red on a cutoff (pricing line 30; Workers limits line 171; websockets line 471).
7. The Paid plan at today's load is $5.00 a month and at ten times $5.15 to $17.95 (section 1.4), below `research-options.md` 5b's $18 to $85 because that note kept the object awake.
8. One object holds 32,768 hibernating WebSockets, a soft 1,000 requests a second, 10 GB (or 1 GB on Free by the FAQ sentence), 2 MB a row and 100 KB a statement; a deck snapshot is not a row and stays on Blob (state page line 152; limits lines 82, 120, table).
9. Presence survives hibernation only in the 16,384 byte attachment per socket and the tags; the roster is rebuilt from `getWebSockets()` on wake (websockets line 360; state page lines 157 and 167).
10. The object is created near the first request and never moves; a `locationHint` at `idFromName` is the only placement control and is best effort (data-location page).
11. No first party millisecond measurement of a browser to object WebSocket round trip was found on 2026-10-01; the design's 10 to 30 ms a frame is an estimate until the preview row measures it, and the measurement must be an application message because protocol pings are answered at the edge (pricing line 63).
12. A Durable Object lifecycle change deploys only with `wrangler deploy`, not `versions upload`; `exports` and `migrations` are mutually exclusive; the first deploy provisions the namespace and asks for the `workers.dev` subdomain (exports page lines 28, 150, 614; get-started line 251).
13. Sign in with Google creates a new Cloudflare account only when none exists under the email and is refused otherwise; a social login account must set a password before it can create an API token (login page lines 43, 66, 67).
14. `turboslide.com` is on Namecheap's nameservers and `www` points at Vercel DNS, so the Worker's hostname is `<name>.<subdomain>.workers.dev` until Kevin moves the zone, and the browser's WebSocket is cross origin to it (`dig NS` 2026-10-01).
15. Deletes, `setAlarm` and key value `put()`/`get()` are all rows written or read; the cost probe can read `rowsRead` and `rowsWritten` off each cursor (pricing lines 102 to 106; sqlite storage API lines 256 to 259).
