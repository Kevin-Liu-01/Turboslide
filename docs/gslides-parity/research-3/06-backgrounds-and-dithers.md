# Background images with dithers

Round three research and specification, reader dither. Written 2026-09-13 against `main` at 61b16e4. Every repository fact below was read from the checkout on that date; every external fact carries its URL and the date read in section 8. Where a page refused the fetch, the fact is marked as read through a search result or a third party page and listed in section 9.

Kevin's directive for this reader, verbatim: "add more features like being able to add images in background and apply dithers over those, those are some huge features we like".

## 0. Decisions in one page

1. The dither becomes a property of the object, not of the file. A `dither` field on the `picture` block (and on `shot`) describes a non destructive effect over the picture's continuous source, the way Google's Adjustments, Figma's image adjustments, Keynote's Adjust Image and Affinity's live filters are properties of the object with the original kept. The asset level `treatment` of round one stays as the record of the GT deck's committed twins and as what `asset.dither` re-runs; a block level dither never rewrites an asset.
2. One pipeline, three hosts. The pixels come from the effects package's existing stages (gray, crop, fit, tone LUT, ordered threshold, nearest upscale), extended with three patterns and a strength blend, run in the studio's worker for the live preview, in the headless sheet page for renders, PDF and the Perfect raster, and in Node for the Editable text picture and the standalone build. The three hosts run the same TypeScript stages, so the pixels agree cell for cell, which the existing worker versus `twoToneScreen` test already proves for the current pipeline.
3. Variant first, live second. The renderer writes the effect as data on the picture's image and prefers a materialized variant file (`assets/<asset>.dither-<key>.png`, a 1-bit or palette PNG keyed by a digest of the source bytes and the effect) when the asset record lists one; the runtime computes the effect on a canvas overlay only while a variant is missing or stale, which is the editing case. Export and the standalone build materialize first, so no exported pixel ever comes from a live canvas.
4. Under 100 ms by caching the fit. The costly stages (decode, crop, Lanczos fit to the screen size, blur) run once per source and crop and are cached in the worker; a slider move re-runs only the LUT, the threshold and the paint over 360,000 cells, which is a few milliseconds in plain JavaScript. The 120 ms debounce of the present Dither section drops to one animation frame with stale request dropping.
5. Vocabulary for sales users. The Format options section is titled Dither and shows: a toggle, Pattern (Bayer 8 by 8, Bayer 4 by 4, Blue noise, Random), Tone (Ink and paper, Three tones, Original colours), Cell (1, 2, 3 or 4 sheet pixels), Strength (0 to 100), Ink point, Paper point, Midtones, Invert, Light theme (Inverse or Same), and a disclosure named Advanced for Blur, Thicken, Channel and Seed. The numbers under the hood are the deck's black point, white point and gamma, unchanged.
6. Backgrounds get the same surface. Slide > Change background gains a Dither toggle on its Image row (it writes the covering picture's `dither` field) and a Material row that places a shader frame at the bottom of the stack through `material.capture`, with the same Dither toggle. The background picture stays the round two picture object at the bottom of the stack; nothing new is locked or unselectable, which is where Turboslide departs from Google on purpose.
7. Every control is an action. `picture.dither` (block level, every transport), `picture.materialize` (server side, writes variant files), `slide.setBackgroundPicture` and `slide.setBackgroundMaterial` (one write each), plus the existing `asset.dither`, `slide.setBackground` and `deck.setBackground`. The CLI, MCP and `window.turboslide.studio` handlers follow from `packages/schema/src/actions.ts` as every other action does.

## 1. What exists today

### 1.1 The effects package

`packages/effects` (description in its `package.json`: "bayer8, ditherRamp, the two-tone pipeline with the pinned Lanczos3, the tone LUT, the 1-bit PNG encoder, the plate metrics, exact, pixelmatch and DSSIM diffs; one API over the native addon, the wasm module and the TypeScript stages").

- `bayer.ts`: `bayer8(r, c)` is the deck's own permutation of 0 to 63 (the 4 by 4 matrix times four plus a quadrant offset, from `Prototemplate/deck/parts/tail.html` lines 100 to 103). The threshold of a cell is `int((m + 0.5) / 64 * 255)`, and a tone value lights the cell when it exceeds the threshold. `ditherGray(gray)` is the ordered dither to one bit.
- `pipeline.ts`: `twoToneScreenTypeScript` runs gray or one channel, padded crop, invert, minimum filter, Gaussian blur, cover fit to 800 by 450 with Pillow's Lanczos3 reproduced in fixed point, an unsharp band, autocontrast at 0.5 percent, the tone LUT (black point, white point, gamma with Python's half to even rounding) and the Bayer threshold. `TWO_TONE_SIZE` is 800 by 450 and `SHEET_SIZE` 1600 by 900.
- `two-tone.ts`: `twoTone(rgba, params, options)` dispatches the screen to the selected backend, applies polarity, scales 2x nearest (`cell` 2), encodes both twins as 1-bit PNGs and measures the plate metrics. `twoToneAtScale(bits, scale, cell)` gives the 2x export its 4 by 4 device pixel cells. `TwoToneParams` mirrors `Asset.treatment` for kind `two-tone`: crop, channel, invert, blur, autocontrast, black, white, gamma, minFilter, unsharp, polarity, cell 2, bayer 8, resampler lanczos3.
- `select.ts` and `backend.ts`: the backend order is native (napi), wasm, TypeScript; `TURBOSLIDE_EFFECTS_BACKEND` pins one and naming an unbuilt backend is an error. Polarity, the nearest upscale, the PNG encoder and the metrics stay in TypeScript because they are integer operations that cannot disagree.
- `metrics.ts`: `litFraction`, `plateClear(bits, plate, cell)` (lit cells under the plate, in the 30 px band, and the nearest lit cell), `PLATE_BOXES` (opener `[137, 500, 740, 271]`, mood `[851, 539, 612, 232]`, closing `[137, 129, 720, 271]`), and two warnings: a uniform screen when the lit fraction is above 0.92 or below 0.08, and a blank twin below 0.02 or above 0.98.
- `png1.ts`: a 1-bit PNG encoder in plain Node, grayscale bit depth 1 by default or a two entry palette with the exact ink and paper; measured at 12 ms for 3200 by 1800 (the module header, citing the slides report section 3.2).
- `ramp.ts`: the Dither slide's live ramp (`rampInk`, `RAMP_COLORS` dark ground `#070707` cell `#f2f2f0`, light ground `#ffffff` cell `#070707`), drawn by `packages/viewer/src/dither.ts` `drawAllDither` on every `canvas.dither`.
- `tone.ts`: Pillow's L conversion in 16 bit fixed point (`(r * 19595 + g * 38470 + b * 7471 + 32768) >> 16`), `autocontrastLut`, `toneLut(black, white, gamma)`.
- `io.ts`: decode through sharp to RGBA; `encodePngRgba`; `writePng1`.
- Fixtures: `fixtures/two-tone/` holds the approved Prototemplate and Glyphfield opener pair read back to 800 by 450 screens (both twins round trip with no cell changed) and a golden of the whole pipeline; `fixtures/pillow/` pins each stage against Pillow. `two-tone.test.ts` requires agreement at or above 0.995 against the recorded pair and records 0.99976 against the lost source render.

### 1.3 Assets and the two-tone treatment

`packages/schema/src/assets.ts`: an `Asset` has `id`, `role` (opener, mood, capture, detail, thumb, render, icon, logo, frame, other), `alt`, `twins` (`{ light, dark }` or `{ neutral }`, relative paths under `assets/`), `size`, `scale` 1, 2 or 3, `source` (kind `material`, `capture`, `photo` or `file`), an optional `treatment` (`two-tone` with the pipeline's parameters, or `continuous` with a JPEG quality of 88, 92 or 95), an optional `sourceFile` (the continuous original `asset add --two-tone` keeps as `assets/<id>.source.<ext>`, absent for the imported deck), `credit`, `inline` (native, resample-1280, two-color, pass-through) and `metrics` (`litFraction`, `plateClear`).

The gt-brand deck (`decks/gt-brand/deck.json`) holds 115 assets, 16 with a two-tone treatment: nine mood photographs, six openers cut from renders and the liquid metal capture. Their twins are 1600 by 900 JPEGs at scale 1 (the import kept the deck's files; `docs/deck-transfer.md` notes JPEG twins are stored), the light twin the exact inverse of the dark one, with recorded parameters in these ranges: black point 0 to 140, white point 210 to 235, gamma 0.8 to 1.2, blur 0 or 0.6, lit fraction 2.4 to 43.6 percent. `mood-rosetta` is typical: crop `[0, 300, 1539, 1166]` of the 1800 px source, blur 0.6, black 140, white 230, gamma 0.9, dark ground, lit 8.9 percent, credit "Photograph: Hans Hillewaert, CC BY-SA 4.0". None of the 16 has a `sourceFile`, so the Dither section shows their committed twins and recorded metrics without a live preview.

How they were made is recorded in the Prototemplate deck's `shots/OPENERS.md` (checkout at `/Users/kevinliu/repos/Prototemplate/deck/shots/OPENERS.md`, 302 lines): the photograph pipeline scales Commons downloads to 1800 px on the long side, converts to gray (or one channel), crops, optionally blurs, fits to 800 by 450 with Lanczos, autocontrasts at 0.5 percent, clips to the black and white points, applies gamma, dithers with the 8 by 8 Bayer matrix at thresholds `(m + 0.5) / 64`, scales 2x nearest to 1600 by 900 and picks polarity by the dominant field ("The dominant field decides, not the background"). The shader pipeline is the same on 3200 by 1800 captures. The licensing note says the dithered files are adaptations, so share-alike sources need the credit on the plate; Turboslide's `asset/credit-on-plate` rule carries that.

### 1.7 The gaps this round closes

1. A dither is a property of a file, so two pictures of one asset share one treatment, a strength cannot be tried without rewriting twins, and every slider commit is a file write (a Blob put per commit on the hosted store).
2. The imported deck has no continuous sources, so its 16 dithered pictures cannot be re-toned in the app.
3. The only pattern is Bayer 8 by 8 and the only cell is 2 sheet pixels; there is no strength, no blue noise and no three tone or colour mode.
4. The Dither controls speak the pipeline's language (black point, polarity, min filter) and sit behind Tools > Advanced; a sales user editing a background never meets them.
5. The Background dialog has no dither and no material row; a shader background is reachable only through Insert > Material or the CLI.
6. The preview is 120 ms after the last change plus a full pipeline run per request, so a slider drag is not live.
7. A 1x JPEG twin upscales bilinearly in a 2x export ("the browser at 2x shows a bilinear upscale of the 1x twin", `AGENTS.md`), so the deck's cells blur at 2x wherever the raster is shot rather than regenerated.

## 2. What Google Slides does

Read from Google's help pages and the Slides API reference (section 8, sources G1 to G5) on 2026-09-13.

Change background. The menu path is Slide, then Change background. The dialog has a Color row (a colour box opening the picker) and an Image row with a Choose button; Done applies to the selected slide and Add to theme to the whole presentation (G1). Google's page lists images "from Google Drive or your computer (.gif, .jpg, or .png files under 50 MB)" (G1). Third party pages list the picker's tabs as upload, camera, by URL, Photos, Drive and a Google image search (G6, G7); Google's own page names only Drive and the computer, so the wider list is unverified against Google. Google's definitions: a theme is "A preset group of colors, fonts, background, and layouts", a background is "The picture or color behind your slide's content", a layout is "The way your text and images are arranged on a slide" (G1). The label of the reset button ("Reset to theme") is reported by third parties and not confirmed by a Google page (round one's research/03 recorded the same gap).

The API model. `PageProperties.pageBackgroundFill` is a `PageBackgroundFill` with `propertyState`, `solidFill` or `stretchedPictureFill`; a `StretchedPictureFill` is "The page or page element is filled entirely with the specified picture. The picture is stretched to fit its container", with a read only `size` and a `contentUrl` with a 30 minute lifetime (G3). So Google's background image is a stretched fill with no crop, no object handles and no adjustments. On the canvas a background image cannot be selected, moved or deleted; a 2026 third party guide describes it as "the most extreme form of locking available in Google Slides" (G8; third party). Turboslide's round two decision 0.74 keeps the background picture an object on purpose, which is a deliberate departure from Google, requested by directive (3).

Image effects. Google's image editing page lists Crop, the mask shapes under the arrow next to Crop, and in Format options: "Opacity: How much of the slide shows behind the image", "Brightness", "Contrast" and "Recolor: Change the color of your image", with the sentence "You'll see your changes as you edit" (G2). Reset image returns "to the original photo you added to the file" (G2). The API's `ImageProperties` carries `cropProperties`, `transparency` in [0, 1], `brightness` and `contrast` in [-1, 1], `recolor` (names NONE, LIGHT1 to LIGHT10, DARK1 to DARK10, GRAYSCALE, NEGATIVE, SEPIA, CUSTOM, with read only recolor stops), `outline`, `shadow` and `link`; transparency, brightness, contrast, crop and shadow are read only in the API (G4). Google has no dither, halftone or posterise; Recolor is its only tonal effect, a set of gradient maps built from the theme palette. Round two's SPEC-2 section 12 left Recolor and Reflection for later.

What this fixes in the design: the Dither section sits where Google's Recolor sits in the sidebar (between Picture or Adjustments and Drop shadow), behaves like Google's Adjustments (non destructive, live, with a Reset), and never bakes into the file the user uploaded. The Background dialog keeps Google's rows and buttons and adds two rows Google does not have.

The dither literature (W1, W2, B1, B2): ordered dithering compares each pixel to a tiled threshold map, is "simple to implement" and "suitable for use in animations" because neighbouring pixels do not interact, and the Bayer matrix gives "a very distinctive cross-hatch pattern" while blue noise matrices from the void and cluster method give "a look closer to that of an error diffusion dither" (W2). Error diffusion (Floyd-Steinberg, Jarvis-Judice-Ninke, Stucki, Atkinson) spreads the quantisation error to neighbours sequentially, gives very fine grain, is not tileable and cannot be evaluated per cell (W2). Blue noise "concentrates energy at high frequencies while suppressing low frequencies", tiles well because "The absence of strong low-frequency content helps a lot in terms of tiling", and free textures from 16 by 16 to 1024 by 1024 are CC0 (B1). Obra Dinn rendered at 800 by 450, the same screen size the deck dithers at (the secondary sources O1 and O2 report the two patterns and the sphere mapping; the 800 by 450 figure is from the search summary of Pope's devlog and is not verified against the post).

Vocabulary decision. The controls use the words the tools above share and the deck's own names where they already exist:

## 4. The specification

### 4.1 The field

`PictureDither` joins `pictureToolFields` in `packages/schema/src/blocks.ts`, so `shot` and `picture` both take it (a tile grid, a pair or a details grid do not this round).

```ts
/** A non destructive dither over a picture's continuous source (research-3 06, section 4). */
export type PictureDither = {
  /** The threshold pattern; bayer8 is the deck's screen. */
  pattern: 'bayer8' | 'bayer4' | 'blue64' | 'random';
  /** Ink and paper (the deck's two tone), three tones (ink, mid, paper), or the picture's own colours posterised. */
  tone?: 'two' | 'three' | 'original';
  /** Colour steps for tone 'original', 2 to 7. */
  steps?: number;
  /** Cell size in sheet pixels; 2 is the deck's 2 by 2 cell. */
  cell?: 1 | 2 | 3 | 4;
  /** The dithered plane's opacity over the continuous picture, 0 to 1; 1 is the pure two tone. */
  strength?: number;
  /** The deck's tone LUT: values at or below black become ink, at or above white paper; gamma below 1 lifts mid tones. */
  black?: number;
  white?: number;
  gamma?: number;
  /** Source inversion before the tone stages (a light render). */
  invert?: boolean;
  /** Which theme the positive image serves; auto picks by the lit fraction as the deck's rule did; same shows one image in both themes. */
  polarity?: 'auto' | 'dark-ground' | 'light-ground' | 'same';
  /** The photograph pipeline's optional filters, in source pixels of the 1800 px scaled source. */
  blur?: number;
  minFilter?: number;
  channel?: 'gray' | 'r' | 'g' | 'b';
  /** The hash seed of pattern 'random'; the default is 0 so two writers agree. */
  seed?: number;
};
```

Defaults when a field is absent: `tone` two, `steps` 4, `cell` 2, `strength` 1, `black` 0, `white` 255, `gamma` 1, `invert` false, `polarity` auto, `blur` 0, `minFilter` 0, `channel` gray, `seed` 0. `autocontrast` stays the deck's fixed 0.5 percent and is not a field; `bayer`, `resampler` and the screen size are constants of the pipeline as they are today. The zod schema mirrors the type with `annotate` groups so the generated inspector rows and the window API get `label`, `control` and `help` as every other field does (`black` min 0 max 255, `gamma` 0.25 to 4, `strength` 0 to 1, `steps` int 2 to 7, `cell` literal 1, 2, 3, 4).

The Dither toggle in the interface is the presence of the field: on writes `{ pattern: 'bayer8' }` (every other value a default), off removes the field. `block.resetImage` removes `dither` along with `trim`, `mask` and `adjust`, which matches Google's Reset image returning to the original photo.

What the field does not do: it never rewrites the asset's twins, so the GT deck's 16 committed treatments stay as they are, and `asset.dither` and the asset level `treatment` stay for them and for the CLI's batch regeneration. A block level `dither` over an asset that already carries a two-tone `treatment` and no `sourceFile` is refused by the validator with the message "the asset has no continuous source (sourceFile); the committed twins are already dithered", because dithering a dithered twin is meaningless. Section 6.3 gives those 16 assets a route to sources.

### 4.2 The pipeline

One function in `packages/effects/src/dither.ts`, browser safe (no encoder import), shared by the worker, the sheet runtime and Node:

```
ditherPicture(source: RgbaImage, box: Box, view: { w, h }, dither: PictureDither, theme, adjust?)
  1. cover fit of the source's trimmed region (the block's trim, then the cover crop of object-fit cover
     at the object's aspect) to the screen size (w / cell) by (h / cell), through the pinned Lanczos3
     (fitCover, cropPadded), after gray or one channel, invert, minFilter and blur     [cached: toneBase]
  2. autocontrast 0.5, then the tone LUT (black, white, gamma)                        [LUT]
  3. adjustments: brightness and contrast of block.adjust as the CSS filter formulas on the 0 to 1 value,
     gray' = clamp(((gray * (1 + b)) - 0.5) * (1 + c) + 0.5)                          [LUT, folded into 2]
  4. threshold against the pattern: bayer8 (the deck's table), bayer4 (the 4 by 4 matrix, thresholds
     (m + 0.5) / 16), blue64 (a 64 by 64 CC0 texture pinned by sha256 in the package, tiled, thresholds
     (v + 0.5) / 256), random (a 32 bit integer hash of (x, y, seed), tiled never, deterministic everywhere)
     for tone 'two' and 'three'; for 'original' the pattern offsets each channel before rounding to
     `steps` levels (the classic ordered posterise)                                     [per cell]
  5. polarity: auto picks dark-ground when the positive's lit fraction is under 0.5, light-ground
     otherwise (the deck's rule made mechanical); the light twin is the inverse unless 'same'
  6. paint: the theme's ink and paper (tokens.ts: light paper #ffffff ink #070707; dark paper #070707
     ink #f2f2f0), three tones with the theme's titanium #8a8f98 as the middle, or the posterised
     colours; every cell `cell` sheet pixels square by nearest upscale (scaleNearest), or
     cell * scale device pixels at an export scale (twoToneAtScale's rule)
  7. strength under 1: the painted plane over the continuous picture at opacity `strength`;
     at 1 the picture is not drawn at all
```

Stage 1 is the deck's pipeline with two changes: the fit runs on the trimmed cover region so the picture's crop tool (Google's crop handles, `block.crop`) and `position` decide what the dither sees, and the screen size follows the object's box and cell (1600 by 900 at cell 2 is 800 by 450, the deck's screen; a 400 by 225 picture at cell 2 is 200 by 113). Stages 2 to 4 are the deck's pipeline unchanged for `bayer8`, tone `two`, strength 1, so a picture object over a source with the recorded parameters regenerates the deck's cells; the parity test of section 7 pins that.

The Rust crate (`crates/turboslide-native`) gains the same stages behind the same `EffectsBackend` so the native and wasm backends stay ahead of TypeScript for the batch paths; the TypeScript stages remain the reference, as `pipeline.ts` is today.

### 4.3 The live preview under 100 ms

The present worker runs every stage per request and the section waits 120 ms. The budget is met by splitting the pipeline at the cache line marked above:

- `toneBase` (stage 1) depends on the source, trim, position, box aspect, cell, channel, invert, blur and minFilter. It is computed once and held in the worker as a `GrayImage` at screen size (360,000 bytes at 800 by 450). It changes when the picture is cropped or resized, which is a drag with its own budget, and stays fixed under every tone and pattern slider.
- Stages 2 to 7 run on every slider event: two LUT passes and one threshold pass over 360,000 cells plus a paint into an `ImageData` of 1600 by 900 by 4. In plain JavaScript this is a few milliseconds; the existing worker paints a twin this way already (`paintTwin`). The result returns as a transferred `ImageBitmap` and is drawn on the picture's canvas overlay (section 4.4) in one `drawImage`.
- Requests carry an id and the worker drops any request older than the newest before starting it, so a drag never queues. The section posts on every input event (no debounce) and the stage draws the newest frame. The slider is the commit boundary: `block.set /dither` is written on pointer up (the pattern of `SliderField.onCommit` in `picture.tsx`), so the store sees one write per drag.
- The source decode and the first `toneBase` fit are the one slow step (the 1800 px source through Lanczos to 800 by 450 in JavaScript). It runs when the section opens or the Dither toggle turns on; the toggle shows the first frame when it lands. The wasm backend built through `backendFromNative(wrapWasmModule(...))` (already designed for a browser worker in `backend.ts`) makes this step faster and is optional.

Acceptance measures, on Kevin's machine and in the e2e budget: from the pointer event on a Strength or Ink point slider to the overlay's `drawImage`, under 100 ms at the 95th percentile over 200 events on the 1800 px Rosetta source; the first frame after the toggle under 600 ms. Both numbers are recorded in VERIFICATION-3 with the browser and the backend.

### 4.4 The renderer path: canvas overlay and precomputed variant, and why both

The string renderer stays one function shared by every surface. `renderPicture` writes the effect and its digest as data on the picture root, and prefers a variant file:

```
<div class="picture" data-dither='{"pattern":"bayer8","black":140,...}' data-dither-key="sha256:…" data-dither-state="variant|live">
  <img class="picture-img" src="assets/mood-rosetta.dither-3f9c….png" data-light="…" data-dark="…" alt="…">
  <canvas class="picture-dither" hidden></canvas>        (only in a live render, RenderOptions.live)
</div>
```

The rule: when `deck.assets[asset].variants[key]` names files for the theme (section 4.5), `src` and the twin attributes point at them and the state is `variant`; the picture needs no script, which is what the standalone build, the CLI render, the PDF page and the Perfect raster read. When no variant exists for the key (a slider moved since the last materialization), the image shows the continuous twin, the state is `live`, and the runtime module (`packages/render/src/dither-runtime.ts`, the pattern of `drawAllDither` and `MaterialMount`) computes the effect in the worker and draws it on the `canvas.picture-dither` overlay at `position: absolute; inset: 0; image-rendering: pixelated`. The overlay is sized to the screen (w / cell by h / cell) and CSS scales it, so a 2x device shows exact 2 by 2 device pixel cells per screen cell at cell 1, and 4 by 4 at cell 2, which is `twoToneAtScale`'s rule with no second buffer.

Why a client canvas at all: the editing loop needs a frame per slider event and cannot write a file per event; a canvas overlay is how the deck's own Dither slide and the live shader mounts already work, so the studio's runtime has the shape.

Why a precomputed variant at all: the string renderer cannot dither, the standalone build ships one classic script and inlines assets by rule, the PDF and the Perfect raster shoot a page and must not depend on a worker having finished, the Editable text PPTX needs bytes in Node, and a viewer without JavaScript (or with WebGL off) still needs the picture. A variant is also small: a two tone 800 by 450 screen as a 1-bit PNG is about 4 KB (the fixture pair measured "about 4 KB each"), so the standalone budget is untouched, and it is exact by construction.

Why not the Paper image dithering shader as the pixel source: its luminance is float and its grid is in screen space (`u_pxSize` "linked to the screen space"), so its cells do not fall on the sheet grid and its thresholds do not reproduce the deck's integer pipeline; a preview from it would change on commit. It stays available as a future `paper:image-dithering` catalog entry for people who want the animated shader look on a picture, credited as Paper's.

Determinism rule (SPEC 5.3): the worker, the sheet runtime and Node share `ditherPicture`; a test decodes the fixture source, runs the function in Node and in the worker (through `previewTwoTone`'s harness) and asserts equal bits; the blue noise texture and the random hash are pinned by digest so no host can drift.

### 4.5 Variants on the asset record

Materialized files are recorded on the asset, not on the block, because two pictures with the same source and effect share one file:

```ts
export type AssetVariant = {
  /** sha256 of (sourceFile bytes digest, the resolved PictureDither, cell, screen size) */
  key: string;
  twins: AssetTwins;              // assets/<id>.dither-<key12>-light.png, -dark.png, or neutral for 'same'
  size: [number, number];         // the sheet pixels the file covers
  scale: 1 | 2;                   // cells are cell * scale file pixels
  metrics?: AssetMetrics;         // lit fraction; plate clearance when a plate group sits over it
  producedAt: string;
};
Asset.variants?: Record<string, AssetVariant>;
```

`picture.materialize` (section 5) writes the files and the record in one `asset.set`. A variant whose key no picture references any more is pruned by the same action with `--prune`, and by the export's materialization pass. The standalone build inlines a variant under the `two-color` rule when its tone is two (a 1-bit PNG with the theme's exact ink and paper through `Png1Options.palette`) and under `native` otherwise.

### 4.6 The two export paths

Perfect PPTX (the page raster). The exporter materializes every referenced variant before the shoot (`picture.materialize` for the deck, idempotent), so every page is shot in state `variant` and no page depends on a worker. A two tone background picture with only text over it stays a two colour page or a palette page and encodes as it does today (1-bit or palette PNG, exact); a `strength` under 1 makes the page continuous and it follows the JPEG or truecolor rule. At the 2x export the variant's cells are `cell * 2` device pixels through the nearest rule, so the page carries crisp 4 by 4 cells at cell 2 rather than the bilinear blow up of a 1x twin that the deck's imported JPEGs produce today; the report's `residual` lists `dither: <slideId>#<blockId> <key12> <state>` per dithered picture and `perfect` stays at or under 0.001.

Editable text PPTX (native shapes). The picture object's raster comes from the same materialized variant: a covering picture at the bottom of the stack travels as `slide.background = { data }` with the variant's bytes (the form of SPEC-2 2.6.4), and a picture at its box as a picture at its box; the file is the 1-bit or palette PNG when tone is two, so the package shrinks against today's RGBA raster. Trim, mask and adjust already reach the file through the raster; the dither joins them, and a `strength` under 1 composites in Node with sharp (`composite` of the painted plane over the continuous twin at the given opacity) before placement. The residual line names the block as `dither:` next to `background-picture:`.

PDF, standalone HTML, JPEG and TXT: the PDF prints the page in Chromium, which reads the variant; the picture regions are reported and never gated, as today. The standalone build inlines variants by the rule above and carries the dither runtime only when a referenced picture has no variant, which the build refuses with "materialize first" rather than shipping a slow page. JPEG is the page raster. TXT is unchanged.

## 6. Storage, hosting, security and hygiene

### 6.1 File layout

```
decks/<id>/assets/<asset>.source.<ext>              the continuous source, 1800 px long side (exists)
decks/<id>/assets/<asset>.dither-<key12>-light.png  a variant twin, 1-bit or palette PNG, 1x or 2x cells
decks/<id>/assets/<asset>.dither-<key12>-dark.png
decks/<id>/assets/<asset>.dither-<key12>.png        a 'same' polarity variant, one neutral file
```

Variants are committed under `assets/` like twins and frames (SPEC 4.1 "never under a git-ignored cache"); a checkout renders with no build step. The deck bundle (`docs/deck-transfer.md`) packs them with the twins; the bundle reader's allowlist already admits png.

### 6.2 Sizes and costs

A two tone variant at cell 2 is about 4 KB (the fixture pair); at cell 1, about 30 KB; a 2x variant of a two tone picture stays a 1-bit PNG four times the cells, about 16 KB at cell 2. A `strength` under 1 or tone `original` produces a palette or truecolor PNG, bounded by the continuous twin's size. The GT deck's 16 dithered pictures materialized once at both scales add under 1 MB against its 30 MB of twins.

Materialization is CPU: decode plus Lanczos plus encode, measured at 12 ms for the encoder alone and well under a second per picture in Node at 1800 px sources. It runs on the host that exports (the studio function or the render worker), inside the export budgets the security reader specifies; `picture.materialize` from the window is rate limited with the other server side window actions, and a deck with more than 64 dithered pictures materializes through the render worker's queue rather than the function.

### 6.3 Sources for the imported deck

The GT deck's 16 dithered assets have no `sourceFile`, so the block level dither is refused on them until a source lands (section 4.1). `asset.add --replace-source <id> <file>` (a new flag) attaches a continuous source to an existing asset without touching its twins, and `asset dither --verify-cells` then confirms the recorded treatment regenerates the committed cells (the M5 acceptance already does this where a source exists). The mood photographs' sources are Wikimedia Commons files named in `ext.provenance.source` and can be fetched through the existing allowlist (`commons.wikimedia.org`, `upload.wikimedia.org`); the six direction openers and the liquid metal capture regenerate from their recipes (`material.capture`, `asset.capture`) as OPENERS.md records.

### 6.4 Security

The `dither` field is JSON validated by zod on every transport with ranges (no unbounded numbers, `steps` and `cell` as literals, `seed` a 32 bit integer); an oversized `blur` or `minFilter` is refused (blur at most 8 px, min filter at most 9) because both cost time proportional to the radius. Variant file names are derived from the digest and the asset id (a slug), never from user text; the assets route's confinement (`assetPathWithin`, `isAssetRelative`) applies unchanged. Sources come through `asset.add` only (sharp decode, 25 MB cap, the host allowlist against SSRF, the 1800 px scale that bounds every later stage); SVG sources are rasterised by sharp at intake and never served as SVG for a dithered picture. The worker receives an `ImageBitmap` from the same origin's assets route and posts bitmaps back; no HTML or CSS is generated from the field. The security reader's rate limits cover `picture.materialize` and `slide.setBackgroundMaterial` as capture class actions.

### 6.5 Layout shift

The picture root carries its box from `pos` and the overlay canvas is absolutely positioned inside it, so toggling the dither, swapping a variant for a live frame or the reverse moves nothing. The Background dialog's thumbnail has a fixed 96 by 54 box before the image loads. The Dither section's rows have fixed heights (the slider row of `SliderField`), and the metrics line reserves one line when unmeasured ("not measured"), which is the layout reader's rule applied here.

### 6.6 The hosted twin push

On the Blob backend the store's `write()` pushes documents and not twins; `slide.import` pushes the twins it copies explicitly, and the asset actions register over a `FileStore` of the deck folder on the studio. Whether a twin written by `asset.add` on a hosted instance reaches the Blob store today, and by which call, was not established from the code read for this report and is listed in section 9. The variants of this round use whichever path the twins use; the hosting reader's document is the place to settle it, and the acceptance in section 7 includes a hosted round trip (add a picture, dither it, materialize, open the deck on a second instance, see the variant) so the gap cannot stay hidden.
