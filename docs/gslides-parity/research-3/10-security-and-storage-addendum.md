Report 10 of the Turboslide Google Slides parity round three, written 2026-09-13 against commit `61b16e4`. Report 04 is the threat model of the code as it stands; it names the round three surfaces in one line each and does not model them. ## 1. Summary

The one fact this report establishes from the code (Part 2, section 5.1): on the Blob backend, a picture added from the editor never reaches the Blob store. `insertPicture` converts the file to a data URL and calls `asset.add` over the window transport (`packages/viewer/src/Editor.tsx:2418-2445`); the studio runs it server side through the `runDeckAction` server function (`apps/studio/src/server/agent-actions.ts:74-126`); the asset actions are registered over the plain `FileStore` of the instance's mirror folder (`apps/studio/src/server/actions.ts:101-106,335-357,567`), which writes the twin bytes with `fs.writeFile` (`packages/headless/src/capture/shared.ts:248-257`, `intake.ts:213`) and commits the `asset.set` record through `FileStore.write` (`packages/materials/src/actions.ts:70-101`, `packages/store/src/file-store.ts:218-256`). Nothing in that path calls the Blob client. The next `BlobStore.write` from the same instance carries the asset record to the store inside `deck.json` and the snapshot, but never the twin bytes (the mirror manages documents only, `packages/store/src/blob-store.ts:149-157`) and never the `asset.set` version record (the write pushes only its own record, `blob-store.ts:684-687`). The picture shows on the instance that received it until that instance recycles, answers 404 on every other instance (`blob-store.ts:1162-1172`, `apps/studio/src/routes/decks.$deckId.assets.$.ts:36-48`), and leaves a hole in the version chain on the store. The same holds for `asset.dither`, `material.capture` and the variants 06 designs, because they write through the same `deps.store.dir` (`materials/actions.ts:110,152,176,193`, `materials/capture.ts:389-390,411,441-445`). Report 06 section 6.6 and 07 section 16 listed this as unverified and owned by nobody; it is F49 (High) here and P11 closes it.

The second fact: a picture above about 3.3 MB cannot be uploaded from the editor on the hosted instance at all. The data URL travels in a server function body, Vercel caps a function's request body at 4.5 MB and answers `413 FUNCTION_PAYLOAD_TOO_LARGE` (V4), base64 expands bytes by four thirds, and the editor's own cap is 25 MB (`packages/viewer/src/clipboard.ts:292`, the notice "Pictures up to 25 MB" at `Editor.tsx:617`). Kevin's background photographs are the pictures this affects. F51 (Medium) and P12 (client uploads to a private store, then the sharp pipeline) close it; section 5.3 has the flow, the limits and the cost.

The new findings, in the order of 04's severity scale:

- High: F49 (hosted asset writes are lost), F24 (stream exhaustion against the 1,024 descriptors per instance), F26 (`clientId` and `opId` are unbound to the session), F31 (presence identity spoofing), F33 (Redis command budget as a cost attack, and Upstash is outside Vercel's spend cap), F38 (a mention that sends an email as a spam vector from General Translation's domain), F40 (share links as capability URLs in Referer, logs and history), F44 (display name impersonation), F47 (share and comment window handlers callable by any same origin script).
- Medium: F25 (stream open without a role check, and unbounded `Last-Event-ID` replay), F27 (document growth through valid operations), F28 (transform CPU), F30 (the CSRF filter does not cover the new server routes), F32 (roster as a privacy leak to anonymous viewers), F34 (Lua lock starvation and key namespaces), F35 (eviction and the loss window), F36 (checkpointer stalls), F37 (comment bodies, links and caps), F39 (notification inbox exhaustion), F41 (request access spam and email enumeration), F42 (sign in limits keyed per email as well as per IP), F43 (avatar path enumeration, CORP, old files), F45 (agent presence names), F46 (WebSocket upgrade authentication), F48 (the local checkout with several browsers), F50 (public twins overwritten in place under a one month CDN cache), F51 (the 3.3 MB ceiling), F52 (untrusted upload bytes must never land on the public store), F53 (materialize and material capture as CPU).
- Low: F29 (the reject message as an oracle).

The storage decisions (Part 2, section 5.2): two Blob stores as P9 proposes, private for every document class (deck, slides, versions, snapshots, leases, the access record, comments, notifications, continuous sources, recipe sidecars, uploads in flight, exports, bundles) and public for the files a browser `<img>` loads (twins, dither variants, material frames, thumbnails, avatars). File names inside a deck stay deterministic and relative (`assets/<file>`), as the document, the bundle, the standalone build and the asset route already require; unguessability comes from one random 128 bit segment per deck in the public pathname (`d/<deckId>/<assetKey>/<file>`) and per person for avatars (`u/<avatarKey>/<file>`), recorded in the private access record and the profile, rotated when access is revoked. Nothing on the public store is ever overwritten: every regenerated twin, variant, frame or avatar gets a digest in its name and the record points at the new file, because Vercel caches a public blob for a month by default and cannot be told to cache it for less than a minute (V6, V7). Continuous sources are private (licensed photographs at full resolution are not something a link should hand out) and are read only by the server side dither and materialize paths.

The plan (Part 4): P11 (fix the asset write path, no design dependency, lands with P0), P12 (client uploads), P13 (stream, ops and presence hardening), P14 (Redis and the checkpointer), P15 (comments, mentions and notifications), P16 (share links, requests and invitations), P17 (avatars and display names), P18 (the storage map, extending P9), P19 (WebSockets), P20 (window handler binding), P21 (local checkout), P22 (logging fields and retention jobs), P23 (the smoke and e2e rows).

### 3.2 Findings F24 onward

Each finding names the evidence or the designing report's section, the severity, an exploit sketch, the fix and the verification.

#### The stream route

**F24 Stream exhaustion against the instance's descriptors, and reconnect storms. High.**

Evidence: 02 7.7 puts `GET /api/decks/<id>/stream` on the catch all function rule (300 s, 2 GB); Vercel gives an instance "1,024 file descriptors shared across all concurrent executions" including the runtime's own (V4); a stream ends at the 300 s maximum duration, which counts streamed responses (V4); Vercel decides which warm instance takes a connection (02 7.11 risk 1). Nothing in 02 caps streams per identity, per IP or per instance.

Exploit sketch: a script opens `EventSource` connections to one deck from one browser; each holds a descriptor for the response and one for the Redis subscription if the instance subscribes per stream. A few hundred from one IP, or a few dozen from a handful of IPs, take an instance to the limit and every function on that instance fails with "too many open files", including the writes of unrelated decks. Without limits, the 300 s boundary itself produces a synchronized reconnect of every tab every five minutes, which is a self inflicted burst.

Fix: one Redis subscription per instance per deck, never per stream (02 7.3 already says the instance writes into its open streams). Cap streams per identity at 4 (anonymous) and 8 (signed in), per IP at 16, per instance at 256 with a `503` and `Retry-After` beyond it; count them in Redis (`INCR` with a TTL of 320 s on `deck:<id>:streams:<identity>`) and decrement on close. Stagger the client's reconnect: the server sends `retry` with a random value between 1,000 and 4,000 ms (the WHATWG field, W5) and closes streams at a random point between 240 and 290 s so tabs do not reconnect together. Send the comment heartbeat every 15 s (02 7.2, W5). A stream open is one function invocation, so R12 rate limits opens per IP at the edge.

Verification: `apps/studio/e2e/security.spec.ts` opens 9 streams from one context and asserts the ninth is refused; a preview load test opens 300 streams to one deck and asserts the write path of another deck still answers; 02 7.12 item 2 measures descriptors per stream from `/proc/self/fd`.

**F25 Stream open without a role check, and unbounded replay. Medium.**

Evidence: 02 7.2 describes `hello`, `ops` since the client's position and `resync` when the position is older than the retention window, and 02 7.7 hands the stream the cookie of 03. A stream carries every admitted operation, that is the document and every keystroke; it is a read of the deck and must be authorized as one (OWASP authorization sheet: check "on every request for the specific object", O2). `Last-Event-ID` is a client header (W5) and names a `seq` the client chooses.

Exploit sketch: a viewer role or a visitor with a guessed deck id opens the stream and reads the deck as it is typed, including slides the viewer may not see (skipped slides and notes, F21). A client sends `Last-Event-ID: 0` on every reconnect and makes the instance read the whole retained stream (10,000 entries, 02 7.1) each time.

Fix: `authorize(session, deckId, 'read')` at stream open, the same call as the page loader; the stream filters events by role (a viewer receives checkpoints and presence, never raw operations; a commenter receives operations for the slides it may read; notes fields are stripped for both, per F21); `Last-Event-ID` older than the head minus 2,000 entries answers `resync` at once instead of a replay; replay reads are capped at 2,000 entries and 1 MB per open. The stream's deck id is the route parameter, the role comes from the access record, never from the query.

Verification: e2e: a second context with a view link opens the stream and receives no `op` events while the first types; `Last-Event-ID: 0` on a deck with 5,000 retained entries answers `resync` within one event.

#### The ops POST

**F26 clientId and opId are unbound to the session. High.**

Evidence: 02 7.2, "`clientId` is a per tab UUID; `opId` is `clientId:counter`; the server deduplicates a re-sent `opId` after a reconnect"; 02 7.3 admits operations under the author of the request; nothing binds `clientId` to the session that opened the stream.

Exploit sketch: an editor of the deck (or a same origin script, F47) posts operations with another tab's `clientId`. The other tab receives its "own" admitted operations it never sent and reconciles its pending queue against them (02 7.4), which can drop its real pending operations or apply the attacker's content as the victim's prediction. Dedup by `opId` alone lets an attacker who knows a victim's next `opId` post first, so the victim's real operation is dropped as a duplicate. In the version log every such operation is attributed to the victim's author.

Fix: the server issues `clientId` in the `hello` event as a random 128 bit value bound in Redis to the session id and the deck (`deck:<id>:client:<clientId> = <sessionId>`, TTL 320 s refreshed by presence); an ops POST whose `clientId` is not bound to the posting session is refused with 403 and logged; `opId` dedup is scoped to `(deckId, clientId)` and remembered for the retention window only. The author of an admitted operation is derived from the session (04 F2 fix), never from the body. `base.seq` older than the retention window is refused with 409 and `resync`.

Verification: `security.spec.ts` posts an op with the other context's `clientId` and asserts 403 and no event on either stream; a unit test on the admission function rejects an `opId` already seen for the pair and accepts the same counter from another `clientId`.

**F27 Document growth through valid operations. Medium.**

Evidence: 02 7.2 caps one POST at 64 entries and 256 kB; 02 7.10 rate limits 60 operations per second per client; 04 7.5 sets deck caps (500 slides, 400 blocks per slide, 200 KB per slide document, 5 MB per `html` block, 25 MB of documents per deck) and says they are enforced in `applyWrite`. At 60 operations per second an editor writes 15 MB of text per second if each operation is a 256 kB `slide.replace`.

Exploit sketch: a loop of `block.insert` with maximal text on one slide until the slide document is 200 KB and the deck 25 MB; then the checkpointer pushes a 25 MB snapshot every 2 to 10 s (02 7.1), which is Blob transfer and function memory; then every collaborator's tab applies 15 MB per second of operations.

Fix: the caps of 04 7.5 checked at admission before the transform (a slide whose serialized size would pass 200 KB rejects the operation with the reason "slide too large"); a byte budget per identity per minute on the ops route (2 MB anonymous, 8 MB signed in) counted in Redis; a per deck budget (16 MB per minute) so a room cannot grow the snapshot faster than the checkpointer commits; the checkpointer refuses to commit a document over 25 MB and the room goes read only with a notice.

Verification: unit tests on admission with a 201 KB slide; e2e: the 65th entry in a POST and the 257th kB are refused with 400 before any transform; the load test of P13 shows the per minute byte budget holding.

**F28 Transform CPU as a denial of service. Medium.**

Evidence: 02 7.3 transforms each incoming operation from `base.seq` to the head; 02 3.3 transforms text operations against the operations since base; the client chooses `base.seq`.

Exploit sketch: a client posts 64 text operations per POST with `base.seq` 2,000 behind the head against a busy Text; each operation transforms against 2,000 entries; at 60 POSTs per second the function spends its CPU transforming and every other room on the instance slows. Active CPU is billed (V9).

Fix: refuse `base.seq` more than 500 entries behind the head with 409 and `resync` (the client then reloads and rebases); cap the transform work per POST at 64 entries times 500 as an explicit budget and reject beyond it; the OWASP denial of service sheet's rule against input based resource allocation applies (O1).

Verification: a unit test times the transform of 64 operations against 500 entries on the fixture deck's longest Text under 20 ms; e2e: `base.seq` 600 behind answers 409.

**F29 The reject message as an oracle. Low.**

Evidence: 02 7.2 `reject { opId, reason, mutations }` and 7.5 "returned to its author with its content and a reason".

Exploit sketch: a commenter posts a `block.set` against a slide id it cannot read; the reason ("the target must exist", "the slide is locked by an agent", the validator's pointer) reveals whether the slide exists and what shape it has.

Fix: a fixed set of reasons (`stale`, `invalid`, `forbidden`, `too-large`, `locked`), the validator's pointer only for slides the author may read, and 403 before validation for a slide outside the author's role.

Verification: unit test on the reason table.

**F30 The CSRF filter does not cover the new server routes. Medium.**

Evidence: `apps/studio/src/start.ts:14-16` filters `createCsrfMiddleware` to `handlerType === 'serverFn'` (04 section 3.3); 02 7.7 makes ops and presence plain server routes and says the filter must widen "or the routes made server functions"; the comment, share, upload token and avatar routes of 03, 08 and 09 will be server routes for the same reason (a route path the WAF can see, 04 7.4).

Exploit sketch: a page on another site posts a form with `enctype="text/plain"` to `/api/decks/<id>/ops`; the cookie of 03 rides along under `SameSite=Lax` for a top level navigation POST only if the site uses `Lax` on a POST, which browsers do not send for cross site POSTs; the risk is the header free JSON POST from a subresource fetch with credentials where `SameSite=Lax` already blocks the cookie. The finding is defense in depth: without the filter, a future `SameSite=None` or a browser without `Lax` defaults exposes every state change.

Fix: widen the filter to every route under `/api/decks/*/{stream,ops,presence}`, `/api/comments/*`, `/api/share/*`, `/api/upload/*`, `/api/avatar/*`, `/api/notify/*`, `/auth/*`, while keeping `/api/actions`, `/api/agent`, `/mcp`, the export and bundle routes on their bearer and ticket rules (04 F13 for their own Origin check); require `Content-Type: application/json` on every JSON route; keep `SameSite=Lax` and `__Host-` on the cookie (03 B2).

Verification: `security.spec.ts` posts to `/api/decks/<id>/ops` from a page on a second origin served by the test and asserts 403; the same with `text/plain`.

#### Presence

**F31 Spoofed identity and display name, and cursor flooding. High.**

Evidence: 02 4 lists the presence state (`clientId`, the author identity, active slide, selection, pointer, follow target, `clock`), 02 7.6 the POST per 80 ms batch, 02 7.11 risk 8 "validate presence state with a schema (display names render as text, never HTML)". The identity inside the state is client supplied in that description.

Exploit sketch: a visitor posts a presence state with the display name and avatar of a colleague and the active slide of a prospect's title slide; the roster shows two of that colleague; the "being edited by" outline and the filmstrip marker attribute the attacker's selection to the colleague. A loop posts 1,000 pointer positions per second and every tab redraws 1,000 cursors.

#### Redis

**F33 Command budget exhaustion as a cost attack, and the spend cap does not cover it. High.**

Evidence: 02 2.5 and 7.10: Upstash pay as you go at $0.20 per 100,000 commands, up to 3 commands per operation, 19 million commands per month at the load model; Upstash's free tier is 500,000 commands per month, pay as you go has unlimited commands with a storage cap of 100 GB, the fixed 250 MB plan is $10 per month with 10,000 commands per second, and "You can set a maximum monthly budget for your database" on pay as you go with notifications at 70 and 90 percent (U1). Exploit sketch: on pay as you go, a script posts 60 operations per second per client from 50 clients for a weekend: 3 commands times 60 times 50 times 172,800 s is 1.5 billion commands, about $3,000, and the Vercel spend cap never triggers because the Marketplace bill is separate. On the free tier the same script spends the month's 500,000 commands in under a minute and the room falls to the Blob tier (02 7.7) for everyone.

**F34 Lua lock starvation and key namespaces. Medium.**

Evidence: 02 7.3, "A Lua script reads `deck:<id>:head`, and when it equals the head the function transformed against, appends the entries with `XADD`, increments the head, and publishes; otherwise it returns the entries since the function's head so the function transforms once more and retries. ... After two failed attempts the function takes a 200 ms lock and retries under it." Redis "guarantees the script's atomic execution. While executing the script, all server activities are blocked during its entire runtime" (RD1). Keys are `deck:<id>:ops`, `deck:<id>:head`, `deck:<id>:ckpt` where `<id>` is a slug (`packages/schema/src/ids.ts:13` per 04 section 5).

Exploit sketch: one busy client keeps the head moving so a slower instance never wins the compare and append; after two attempts it takes the 200 ms lock, which is itself a `SET NX PX`; under contention every instance queues on the lock and the room's latency is the lock's TTL. A script that returns "the entries since the function's head" copies a large range through the single Redis thread on every miss and blocks every other database command on the shard for that time. A deck id that is a prefix of another (`gt`, `gt-brand`) shares no key, but a key built from a client supplied string outside the slug check would.

Fix: the compare and append script returns only the count and the new head on a miss, never the entries (the function reads them with `XRANGE` outside the script); scripts stay under a few hundred microseconds and the 250 MB plan's 10,000 commands per second is the ceiling; the lock uses a per acquirer random token and releases only its own token (`GET` then `DEL` in a script); the lock TTL is 2,000 ms and a holder that sees the TTL expire abandons the checkpoint; every Redis key is built from the slug validated deck id and a fixed suffix list, and the key builder is one function with a test; presence keys are `deck:<id>:presence` and `deck:<id>:roster`, session bindings `deck:<id>:client:<clientId>`, budgets `q:<identity>:<name>:<day>`.

Verification: a test with two fake instances contending 1,000 appends converges with no lost entry and a maximum wait under 50 ms; the key builder test refuses any id outside the slug pattern.

**F35 Eviction and the loss window. Medium.**

Evidence: 02 7.11 risk 2 (stream loss, the two level acknowledgement, the Blob tier as fallback); Upstash: "By default eviction is disabled, and Upstash Redis will reject write operations once the maximum data size limit has been reached", and when enabled the policy is "optimistic-volatile", which evicts keys with a TTL first and then "additional non-volatile keys are randomly chosen for eviction" (U2).

Exploit sketch: with eviction on, the ops stream (no TTL) can be evicted under storage pressure from presence and budget keys, and every un-checkpointed operation is lost at the server; with eviction off, the database refuses writes at 250 MB and every room falls to the Blob tier at once. An attacker fills the store with presence states (up to 64 block ids and a selection each) from many clients.

Fix: eviction off (the default), so the failure is a refused write the client sees, never a silent loss; the stream trimmed after every checkpoint to `MAXLEN ~ 10000` (02 7.1) and the retention measured in bytes as well (16 MB per deck); presence values capped at 2 KB and expiring at 120 s (02 4); a storage alert at 60 percent of the plan; the client's `revAck` rule kept (02 7.1) so a refused or lost append is resent against Blob.

Verification: a unit test on the presence schema's size; a preview run with a 250 MB plan and 3 decks records the stream's byte size per hour under continuous typing (02 7.12 item 6 extended).

### 5.2 Where every file class lives

The two store plan of 04 P9, made concrete. "Private" is a private Blob store (files "cannot be accessed via public URLs", every read and write authenticated, OIDC by default, delivered through a function or a presigned URL; V1, V8). "Public" is a public Blob store (URL `https://<store-id>.public.blob.vercel-storage.com/<pathname>`, served with `content-security-policy: default-src "none"`, `x-frame-options: DENY`, `x-content-type-options: nosniff` and a content disposition; V7, V8). Naming: "deterministic" means the pathname derives from the deck id and the file's relative name; "keyed" means the pathname carries the deck's or the person's random 128 bit segment; "digest" means the file name carries a content digest and is never overwritten. The CDN staleness rule is the same for every public class: never overwrite, digest names, `allowOverwrite: false`, default cache (V7). Private classes are read with `useCache: false` where a read must see the latest write (V1) and with the default cache where the name is immutable.

Decisions the table records:

1. Deterministic names inside the deck, unguessable prefix outside it. 06's variant names, the bundle's relative paths (docs/deck-transfer.md section 1), the standalone build's inline rule (`packages/render/src/standalone.ts:1-3,20-21`) and the asset route's confinement (`hosted.ts:130-134`, `schema/assets.ts:117-123`) all work on `assets/<file>` relative paths, and 04 P9's `addRandomSuffix` would break all four (a suffix Vercel appends is not the name the record holds). The reconciliation is the `assetKey`: one random 128 bit value per deck, generated at deck creation, stored in the private access record, placed in the public pathname between the deck id and the relative name. The page receives the keyed prefix as `assetBase` only after `authorize(read)`. Revoking access to a deck rotates the key (a `copy` per file, an advanced operation, plus a `del`; for the GT deck's 202 twins that is 202 advanced operations, about $0.001, done in the background with the record pointing at the new prefix once the copies exist). A viewer who was removed keeps the old URLs in the browser cache until they expire and nothing else; the TAG's rule that capability URLs be revocable is met at the deck level (W4).
2. Continuous sources are private. They are the licensed originals at 1800 px (`intake.ts:167-171`), never rendered by a browser (the renderer reads twins and variants), and needed only by server side re-dithering, materialization and the Node export paths. SPEC 11 already says the GT deck's photographs move to a private overlay if the repository stays public (04 section 3.2); the private store is that overlay hosted.
3. Thumbnails are the same confidentiality class as twins (a viewer sees both), so they live on the public store under the deck's key, which makes the cross instance cache `docs/hosting.md` section 8 asks for and keeps function delivery out of the highest volume read. The trigger (a render on a miss) stays behind authorization and the quotas of 04 7.5.
4. Exports and bundles move to the private store and are handed out through the existing HMAC download tokens or presigned GETs. Vercel's presigned GET is served through the CDN, expires per URL (`validUntil`, capped to the delegation's, at most 7 days), can bypass the cache with `useCache: false`, and is produced by `presignUrl` from a token `issueSignedToken` mints on the server (V1, V2). The CLI's `deck pull` already follows a `302` (docs/deck-transfer.md section 2).
5. Nothing on the public store is overwritten (F50).

What Vercel's private store costs per delivery, from the pricing page (V5): private delivery through a function pays Blob Data Transfer plus Fast Origin Transfer on a cache miss for the function's fetch and Fast Data Transfer plus Fast Origin Transfer for the function's answer, and Vercel does not recommend private stores for files over 100 MB unless traffic is low; public delivery pays Blob Data Transfer plus Fast Origin Transfer on a miss, and Blob Data Transfer "is 3x more cost-efficient than Fast Data Transfer on average". Both stores price storage, operations and uploads the same. The decision above puts every browser loaded file on the public store for that reason and every document on the private one, where the reader is the function.

### 5.3 The large upload path

The flow, replacing the data URL path above 3 MB on the hosted instance and keeping it below and on a checkout:

1. The editor picks a file (`pickPicture`, `edit.$deckId.tsx:2497-2510`) and checks size and type in the browser: at most 25 MB anonymous and 50 MB signed in (section 3.3), `image/jpeg`, `image/png`, `image/webp`, `image/gif` only (SVG is refused on hosted per 04 F5). Under 3 MB and on a checkout the existing `asset.add { file: <dataUrl> }` path runs unchanged.
2. Above 3 MB on a hosted instance the editor calls `uploadPresigned(name, file, { access: 'private', handleUploadUrl: '/api/upload/picture' })` from `@vercel/blob/client`. The route runs `handleUploadPresigned` with `getSignedToken` that calls `authorize(session, deckId, 'write')`, checks the per identity upload quota, and returns `issueSignedToken({ pathname: 'uploads/<principalId>/<uuid>', operations: ['put'], allowedContentTypes: [the four types], maximumSizeInBytes: <the identity's cap>, validUntil: now + 10 min })` with `urlOptions { addRandomSuffix: false, allowOverwrite: false, cacheControlMaxAge: 60 }`. The route sets `BLOB_WEBHOOK_PUBLIC_KEY` for the callback signature and works with OIDC, without `BLOB_READ_WRITE_TOKEN` in flight (V2). The constraints "enforce constraints on the upload at the CDN, so the URL is safe to hand to a client even if the client controls the request body" (V2). Uploads through client paths incur no data transfer charge (V5).
3. The browser PUTs the bytes to the presigned URL. `onUploadCompleted` is not relied on (it does not work on a checkout without a tunnel, V2, and a checkout uses the data URL path anyway); the editor calls `asset.add { upload: 'uploads/<principalId>/<uuid>', role, alt, id }` over the window transport when the PUT returns.
4. `asset.add` with `upload` reads the object through the SDK `get(pathname, { access: 'private' })` by pathname, never by a URL (so no host allowlist and no SSRF question), sniffs magic bytes (`sniffImage`), decodes with sharp under `limitInputPixels` and `failOn: 'error'` with HEIF and AVIF blocked (04 F17), re-encodes to the twin sizes (04 8.5), writes the twins to the public store under the deck's key with digest names (F50, through `putAsset` of P11), the source to the private store when the treatment keeps one, commits `asset.set` through the hosted store, and deletes the upload object. A source over 25 MB that decodes is kept; the twin the browser loads is bounded by the sheet's pixel size.
5. The standalone build and the exporters read what they read today: the exporter's Node paths through `ensureAssets` and `pullAssets` (`blob-store.ts:846-861`, extended to the keyed public prefix and the private source prefix), the standalone build through the inline rule from the same local files, the Chromium page raster through the asset route's `302` or the keyed URL as `assetBase`.

Limits: 3 MB for the data URL path (a 3 MB file is a 4.0 MB data URL, under the 4.5 MB cap with the JSON envelope); 25 MB anonymous and 50 MB signed in for the presigned path; a token valid 10 minutes; one upload in flight per identity per deck; the daily caps of section 3.3; uploads not claimed by an `asset.add` within 24 h swept by a scheduled prune (a `list` on `uploads/` prefix, an advanced operation, once a day).

Blob operations and cost per 20 MB upload: one `put` by the presigned PUT (advanced), one `get` by the function (a simple operation on a cache miss plus 20 MB of Blob Data Transfer at $0.05 per GB in `iad1`, V5), one `del` (free), one or two twin `put` calls (advanced), one source `put` when kept (advanced), and the `asset.set` commit at four `put` calls plus one `list` (02 1.3). In total about nine advanced operations ($0.000045) and $0.001 of transfer, with sharp CPU of about one second (Active CPU at $0.128 per hour in `iad1`, V9: $0.00004). A hundred such uploads a day cost about $0.11 a day in transfer and operations.

### 6.2 The GDPR treatment of presence data and hashed IPs, extending 03 Part G

The GDPR defines personal data as "any information relating to an identified or identifiable natural person" (G1 Article 4(1)) and pseudonymisation as processing "in such a manner that the personal data can no longer be attributed to a specific data subject without the use of additional information" kept separately (G1 Article 4(5)); Recital 26 states that pseudonymised data "which could be attributed to a natural person by the use of additional information should be considered to be information on an identifiable natural person" (G2). Article 5(1)(b), (c) and (e) require purpose limitation, data minimisation and storage limitation (G3).

Presence data (display name, avatar reference, active slide, selection, pointer position, follow target) is personal data of a signed in person and pseudonymous data of an anonymous one (the sealed id is the additional information). It is processed for one purpose, showing collaborators where others are, and it lives in Redis with a 120 s expiry (02 4), is never written to Blob, never enters the version log, and appears in the security log only as counts (`presence.reject` carries the identity and a count, never the state). A person who closes the tab is gone from the roster within 30 s and from Redis within 120 s; there is nothing to erase.

The ops stream in Redis carries every keystroke including text that was deleted a moment later. It is retained for the window of 02 7.1 (10,000 entries or 24 hours) and trimmed after each checkpoint; the checkpointer coalesces bursts into version records (02 7.1), so the version log holds what a person committed, as it does today. An erasure request under Article 17 is handled as 03 Part G says: the display of the person's principal id becomes "Deleted account", the avatar and profile are removed, and the version bytes stay because rewriting the chain would break every deck the person touched; the privacy text says so.

IP addresses are hashed with HMAC-SHA256 under a salt that rotates daily and is discarded after 48 hours. While the salt exists the hash is pseudonymised data (linkable within the day, reversible only by whoever holds the salt and the address); once the salt is gone the value cannot be attributed to anyone and serves only as a same day correlation key in the 30 day Drain. Rate limit counters keyed on the raw IP live in Redis with a TTL at most one hour (the longest WAF or quota window), which is the minimum the function needs. The WAF's own logs are Vercel's and follow Vercel's retention (04 S13, S14). Email addresses appear in logs only as principal ids or as the same keyed hash when the person has no account (an invitation to an address that never signed up).
