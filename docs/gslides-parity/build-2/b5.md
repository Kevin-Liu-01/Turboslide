## 2. Decisions taken

1. **Hierarchy nodes.** A hierarchy of n levels has one node on top and two on every level
   below (2n minus 1 labelled nodes), each joined to the node above in its column (the top node
   for the second level). One node per level would be a column, not a hierarchy; a binary tree
   of five levels is 31 boxes. `DiagramTemplate.nodes(count)` names the labelled node count so
   the test of 11.5 ("as many text blocks as items") reads it per type; for every other type it
   is the count.
2. **The timeline's labels are ink in every style.** They sit on the paper under the rule, not on
   a fill, so the `ink` style's paper text would vanish; the dots of the outline style are filled
   paper so the rule does not show through them.
3. **The styles are tones, not colours.** Google's panel offers colour variants; the GT theme has
   one palette, so the three styles are Outline (ink strokes), Plate (plate fill) and Ink (ink
   fill with paper text), and a person recolours the members afterwards with the group tail.
4. **Plans carry `blockId` and the fields; the caller adds `slideId` and `baseRevision`.** The
   seams list fixes `tablePlan`'s input as "the action inputs of section 3" over a block; the
   shell's `menuActionPlan` has the facts and the sections have their props, so `tableWriteInput`
   and `chartWriteInput` spread them at the call. B3's `editor-shell.ts` imports `tablePlan`
   already (line 40 at 16:06), so the signature stayed exactly as the seams list has it.
5. **The Format options slot contract.** B3's `EditorShellInput.formatSlots` names a
   `FormatOptionsSlots` type in `FormatOptions.tsx` that is not written yet. The two sections take
   a structural props shape (`block`, `slide: { id }`, `revision`, `dispatch`, `selection?`,
   `editor?`, `busy?`, `onNotice?`) and export `chartFormatSlot(props)` and
   `tableFormatSlot(props)`, which narrow the block and draw nothing for another type, so
   whatever shape B3 gives the slot, `{ chart: chartFormatSlot, table: tableFormatSlot }` fits
   as long as those fields are present (request 1).
6. **The Table section keeps the generated rows.** The round one Table section (header row,
   columns, fill, vertical alignment) stays generated from the annotations; this section is the
   round two additions of section 5 and mounts under it. Header row is drawn again here as a
   checkbox because it is the first thing a sales user looks for.
7. **The grid's Tab.** Section 10 says Tab and the arrows move between cells; the grid uses a
   roving tab index (one cell in the tab order) and takes Tab and Shift+Tab itself while the
   active cell is inside the grid, leaving the section's other controls reachable from the first
   and last cell.
8. **`nextCell` is offered, not wired.** The viewer's `nextCellPointer` (`packages/viewer/src/InlineText.tsx`,
   B4's file) walks every cell including the covered ones; `table-tools.ts` `nextCell` skips
   them and lands on the anchor once (request 4).
9. **The specs drive the UI where it exists and the action where it does not.** Three of the
   surfaces 11.6 names are other builders' and land at merge 2; a spec that only failed until
   then would prove nothing this day, and a spec that skipped would not prove the writes. Each
   test records which path ran in its annotations, so the verifier sees at once whether the
   UI path was exercised.
