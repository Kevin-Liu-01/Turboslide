### 1.4 The thumbnail cache and the render route (0.31, 3.2; item 3)

`apps/studio/src/server/thumbs.ts` (rewritten), `routes/api/render.$slideId.ts`, `warm.ts` (unchanged), `root.ts`:

- The disk cache is keyed by stamp, `<state>/thumbs/<deckId>/<stamp>/<theme>@<width>/<slideId>.png`; the store cache is `decks/<deckId>/.thumbs/<stamp>/...` with `cacheControlMaxAge` of a year, through `exportBlobClient()` on the `blob` tier and nothing on `file` and `tmp`. `slideStamp` is the server's copy of the editor's arithmetic (asserted equal in `thumbs.test.ts`).
- `getThumbnail(request, { blob, access })`: the disk, then the store under the asked stamp (`r`, else the slide's current stamp), then, for a request without `r`, the newest stored stamp of the slide answered at once with the current one rendered behind the response (`afterResponse`, `@vercel/functions` `waitUntil` when a request context exists, a detached promise on a checkout), then the render (the worker's screenshot downsized, written to disk, put to the store, the retention prune behind the response). A stored answer on a public store is a 302 to the Blob URL (`kind: 'stored'`); on a private store (`TURBOSLIDE_BLOB_ACCESS=private`, or the layout v2 documents token, whose split client routes `.thumbs/` with the documents) the body is streamed. Headers: `public, max-age=31536000, immutable` with `r`, `public, s-maxage=60, stale-while-revalidate=86400` without; `x-turboslide-stamp`, `-fresh`, `-source`, `-cached`, `-revision`, `-thumb`, the etag by stamp. The signed URL of SPEC-3 8.13 (`s`, the grant) is verified before any of this as before.
- The route reads `r` through `isThumbStamp` (eight hex digits, a revision, or a short opaque name) and passes it; `revisionInUrl` is `r !== null`.
- `warmThumbs` writes each slide under its current stamp on disk and in the store (one render job, Chromium launched once) and skips the slides the store already holds.
- The sweep of `root.ts` (`revisionEntries`): a numbered thumbs folder is dead below the newest number as before; a stamp folder is never dead by age (the current stamp is not knowable from the folder's name) and the byte budget evicts it oldest first. `root.test.ts` gains the row.
- `thumbs.test.ts` (new): the header set per URL shape, the 302 and the body, the stamp grammar, the store access rule, the stamp arithmetic, the pathname round trip and the retention (the fourth stamp evicts the first at every width; the light theme is another set).

## 6. Findings for the integrator and the verifier

1. A spec that re-seeds its scratch deck on disk and reopens the same deck id on a live dev server sees the previous run's room: the memory channel keeps the room per deck id for the process, so the second run's editor loads the earlier run's document (the reordered slides of `filmstrip.spec.ts` test 2, the size 22 of `undo.spec.ts`'s redo). The first run on a fresh server passes; a rerun needs a restart or a new deck id per run. Not this build's doing (round three's channel), recorded because the acceptance runs the four specs against one server; `check.mjs` step 21 starts its own server, so the chain is unaffected. A `deckId` with a run suffix in the four specs (the way `e2e-canvas-<id>` does it) is the durable fix and sits in B3's `editor.spec.ts` too.
2. The DOM budget rows read CDP `Performance.getMetrics` `Nodes`, which counts detached nodes until garbage collection. Clone first with a two way window keeps the live DOM at about 1,900 elements on `/edit/gt-brand` through three scroll passes (section 5) while the CDP figure swings between 4,700 and 16,300 and reads 5,770 after a forced collection. The row cannot prove SPEC-4 0.41 as written; a live count (`document.querySelectorAll('*').length`, or CDP after `HeapProfiler.collectGarbage`) would. Request R14. With the live count, `/edit` sits at 1,860 against the 1,500 budget with the spec's `200% 0px` margin (27 of 85 cards hold a clone of about 45 elements each); `100% 0px` would land about 1,500 and `50% 0px` about 1,300, a one constant change (`NEAR_ROOT_MARGIN`) the integrator or Kevin decides against 0.41's fixed margin.
3. The filmstrip's frame rows on the dev server are below the baseline's 119 fps (section 5). Two causes this builder can name: the development bundle (React's dev build, unbundled modules) and the clone mounts as cards enter the window (each mount renders about 45 elements and applies the theme). The verifier measured 119 fps on a production build whose clones were replaced by captures early; the node-server build's step 31 is the number that counts. If it misses, the next lever is a smaller window (item 2) or deferring the clone mount of an entering card to an idle callback.
4. `/present/gt-brand` cold CLS 0.4022 in the perf run is the presenter under B3's rewrite (the popup's own page; nothing of this build touches it); recorded so nobody attributes it here.
5. `warmThumbnails` from `shell-bridge.tsx` (B3's file) still fires on `density === 'thumbs'` for the filmstrip; the controller ignores it outside grid mode, so the call costs one no op. B3 may drop the density condition.
6. The hosted smoke and step 31 will see `x-turboslide-source` and `x-turboslide-stamp` on every thumbnail answer, and a 302 for a stored capture on the `blob` tier; the verifier's row "one render per stamp" reads `x-turboslide-cached: 1` or `source: blob` on the second request.
