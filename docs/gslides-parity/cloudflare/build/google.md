# Google sign in by hand: the recipe for the D1 placement

Written 2026-10-01 by lane R4 of the Cloudflare phase (`docs/CLOUDFLARE.md` section 4, 2.1's hand row `accounts.google-roundtrip`, 4.4, section 6 steps 13 and 16; `docs/REALTIME.md` 4.5 to 4.6 and section 7 where CLOUDFLARE.md does not change them), from the realtime round's recipe `docs/gslides-parity/realtime/build/google.md`, which it replaces. The code side is on the branch: the Google provider in `apps/studio/src/server/auth/better-auth.ts`, the dialog's Google button first, the four local rows in `apps/studio/e2e/accounts.spec.ts`, the unit rows in `better-auth.test.ts`; and, since this phase, the account database on D1 through the realtime Worker (`auth/db.ts` `TURBOSLIDE_ACCOUNTS=d1`, `auth/d1-proxy-dialect.ts`, the principal records in `ts_principal`, `build/r4.md` "Cloudflare phase"). What remains is the orchestrator's through Kevin's Google session with the stops of section 6, and Kevin's own sign in, because Google issues no authorization code to a test, so the round trip is read by hand.

The placement in one sentence (CLOUDFLARE.md 4.1): the identity runtime, the auth routes, the cookies and the Google callback stay on Vercel and `www.turboslide.com`; the database is D1 `turboslide-accounts` bound to the Worker `turboslide-realtime`, reached by the function through the Worker's bearer routes `POST /db/query` and `POST /db/batch`; no Upstash, no Neon, no `REDIS_URL`, no `DATABASE_URL`. Nothing of the Google side moves: the redirect URI is still `https://www.turboslide.com/api/auth/callback/google`, so no `workers.dev` host is ever an authorized domain.

## 2. What the build does with the client and the database

- The authorization request asks for `openid email profile`, `prompt=select_account`, PKCE (`code_challenge`, `S256`), no `access_type=offline`, no `consent`: nothing calls a Google API after the sign in, so there is no refresh token and no verification to run.
- The redirect URI is `<origin>/api/auth/callback/google`, built from the request's Host when it is on the list `www.turboslide.com`, `turboslide.com`, `turboslide.vercel.app`, `localhost:*`, `127.0.0.1:*` (`TURBOSLIDE_AUTH_HOSTS` replaces the list; `TURBOSLIDE_PUBLIC_ORIGIN` is the hosted fallback for a Host off it). A preview deployment's host (`<deployment>.vercel.app`) is off the list, and Google's redirect URIs match exactly, so a preview never completes a Google sign in; the preview's accounts rows are the four local rows with the e2e mail mode (CLOUDFLARE.md 4.3).
- The account is keyed on Google's `sub`; the email is used for the linking rule alone (an existing email account links when both addresses are verified; Google is not a trusted provider).
- The rows better-auth writes (`user`, `account`, `session`, `verification`) and Turboslide's (`ts_alias`, `ts_profile`, `ts_principal`, `ts_quota`, `ts_api_key`, `ts_mail`, `ts_schema`) live on D1, one database for every Vercel instance; the function posts each statement to the Worker's `/db/query` under the room bearer, about fifteen statements inside the callback (`read-auth.md` 4.2), which is the 0.75 to 1.7 s the design expects the callback to add and the hand row's clock reads (bound 5 s; a reading over 3 s is the trigger for 7.3's identity runtime on the Worker).
- The anonymous person's decks and comments follow them: the callback request carries the `SameSite=Lax` identity cookie, the session hook writes the alias row (`ts_alias`), the principal records merge once on D1 (`ts_principal`), and every record under the anonymous id renders as the account with the check badge and the word "signed in". Google's `name` wins at render; Change name renames the account.
- The limiter holds `/sign-in/social` and `/callback/google` at 10 per minute per address in the library (per instance) under the WAF rule R8's 10 per 60 s per IP.

## 3. The hand row `accounts.google-roundtrip`, in two places

### 3.1 On a checkout, `http://localhost:4321`, with the real client against the preview Worker's D1

The client's redirect URI for localhost is on port 4321 (step 3 B7), so this runs on that port alone, by the one who holds 4321 (the integrator or the verifier, AGENTS.md dev server rules). A wrapper reads `~/.config/turboslide/google-oauth.env` and `~/.config/turboslide/room.env` into the process's environment and prints nothing (the shape of `~/.config/turboslide/with-tokens.mjs`); nothing echoes a value. The database is the preview Worker's D1, so the row reads the proxy's latency to a real Worker (CLOUDFLARE.md 2.1), and the realtime tier is forced to `memory`, because an unforced `TURBOSLIDE_ROOM_HOST` would select the `do` channel against a Worker whose `TURBOSLIDE_APP_ORIGIN` cannot reach `localhost` (3.6.1).

1. From `apps/studio`, through the wrapper: `TURBOSLIDE_STORE=tmp TURBOSLIDE_OVERLAY_DIR=<a folder under .turboslide/> TURBOSLIDE_REALTIME=memory TURBOSLIDE_LOCAL_OPEN=1 TURBOSLIDE_ACCOUNTS=d1 TURBOSLIDE_ROOM_HOST=turboslide-realtime-preview.kk23907751.workers.dev TURBOSLIDE_MAIL=off TURBOSLIDE_SESSION_SECRET=<32 or more characters> TURBOSLIDE_DOWNLOAD_SECRET=<32 or more characters> node_modules/.bin/vite dev --port 4321 --strictPort`, with `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `TURBOSLIDE_ROOM_SECRET` and `TURBOSLIDE_ROOM_BEARER` in the environment from the two files. No `TURBOSLIDE_AUTH_DB` (the explicit engine wins anyway). `TURBOSLIDE_MAIL=off` makes the dialog read as production will: no email field, Google first and focused. The server's first request runs the two migration sets through the proxy once (a few dozen statements) and writes the `ts_schema` version row; a second server over the same database makes one statement.
2. In a browser with no Turboslide cookies: open `http://localhost:4321/new`, type a title (the deck is created), name yourself through the own chip's menu (Change name), and read your anonymous id: `window.turboslide.studio.describe().state.identity.principalId` in the console, an `anon_…` value. Keep it.
3. Own chip menu, Sign in: the dialog shows Continue with Google first. Start a stopwatch at the click; the account chooser shows `turboslide.com` and asks for the basic profile only (no Gmail scopes, no "unverified app" page for the basic scopes). Choose an account.
4. You return to the same deck. The page reloads; the own chip carries the check badge and the word "signed in"; the account menu's head reads "Signed in as <the Google address>"; the deck is still yours. Stop the clock at the badge: the verifier records the wall time from Google's redirect to the editor's reload with the badge (bound 5 s).
5. The alias row, read from the preview Worker's D1 by the verifier, never by hand typing a value: `cd apps/realtime-worker && pnpm exec wrangler d1 execute turboslide-accounts-preview --remote --env preview --json --command "select userId from ts_alias where anonymousId = '<the anon_ id of step 2>'"` answers one row with the account's id; or, with the room host and bearer in the environment, `TURBOSLIDE_ACCOUNTS=d1 node apps/studio/e2e/identity-seed.mts alias - <the anon_ id>` answers `{ "userId": "<the account's id>" }` through the Worker's `/db/query` (the seed's d1 mode, `build/r4.md`). The badge in a second browser: open the deck's share link in a second browser (or a private window); your chip there carries the badge and the name Google reported.
6. Sign out from the account menu; Forget this browser; stop the server. The scratch rows stay in the preview database (a preview database, not production's).

### 3.2 On production, `https://www.turboslide.com`, after section 6 step 16

1. A browser with no Turboslide cookies: `https://www.turboslide.com/new`, type a title, name yourself, read the anonymous id as in 3.1 step 2.
2. Sign in with Google from the own chip's menu; return to the deck; read the badge and "Signed in as" as in 3.1 step 4, with the clock. The first sign in with `kevin@generaltranslation.com` is the admin (`TURBOSLIDE_ADMIN_EMAILS`).
3. A second browser opens the same deck through its editor link: your chip carries the badge and Google's name. The alias is read through the surfaces (the badge, the name, the deck still listed under your account on `/decks`); a read of production's D1 (`wrangler d1 execute turboslide-accounts --remote --json --command "select count(*) as n from ts_alias"`) is a count and never a row's values.
4. The scratch deck leaves by its id, never by a sweep: `deck.info`, `deck.trash {id, baseRevision}`, `deck.remove {id, confirm: true, baseRevision}` through `POST /api/actions/<action>?deck=<id>` with the bearer from `~/.config/turboslide/hosts.json` through the wrapper (or File > Move to trash and Delete forever from `/decks` in the signed in browser).
5. The function log: no `[better-auth] Base URL is not set` line after the deploy; a sign in is three requests on `/api/auth/` (the POST, the callback GET, `get-session`), under the WAF's 10 per 60 s; the Worker's `GET /db/counters` before and after the sign in gives the statement count of one sign in for `cost.d1.writes` (the design's 5 to 8 rows written).

## 4. What is not in this round, and why (design-google-login.md section 9; CLOUDFLARE.md 7.3)

- `linkSocial` from the Profile dialog (an email account adding Google later): one client call and one row, the round after.
- The Google picture as an avatar source: `user.image` is written and nothing reads it.
- A fixed preview alias: Google's redirect URIs match exactly, so a preview deployment's host cannot complete a sign in; Google is verified on localhost and production only.
- `hd` (a Workspace domain restriction): sellers sign in from any Google account.
- Passkeys: the plugin is not in the checkout and the rpID cannot move once set.
- The `/privacy` and `/terms` pages Google calls required for an external production app, and the brand verification that puts the name on the consent screen: the round after, with the links filled in Branding then.
