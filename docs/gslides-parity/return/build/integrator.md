### 1. The mechanism, and why the transport is the fix

The integrator's hand probe (section 8 above) named it: `file.download.zip`, `.html`, `.jpg` and `.png` ran as an anchor click with `download=""` on a same origin address the server had signed (a bundle ticket, a one time download token, a render grant), and an anchor's download request is the browser's, not the page's. It carries none of the page's request headers, so on a preview it met Vercel Authentication; the wall answers a redirect to `vercel.com`, a same origin address that redirects to another origin loses its `download` attribute, and the tab navigated away from the editor. The PDF and the PowerPoint pass on a preview because their files come from the public Blob host. The same transport hides every refusal from a seller on production too: a route that answers 401, 404 or 429 to an anchor ends as a cancelled download the page never hears of (b7.md B7-R5 read `download.path: canceled` for a 401; return-drive.md rows 13 to 16 read "canceled" before the first byte for the web page), so the snackbar said "The web page is ready" over a download that did not happen.

The change (`packages/chrome/src/download.ts`, new, exported as `@turboslide/chrome/download`; `packages/chrome/src/__tests__/download.test.ts`, 10 tests): `downloadFromPage(url)` fetches a same origin address from the page with its cookies (and whatever headers the browser attaches to the page's requests, which is how Playwright's `extraHTTPHeaders` reach it), reads the bytes, and saves them from a blob address through one anchor click named from `content-disposition` (`filename*`, then `filename`, then the address's last segment when it carries an extension, then the caller's name; path separators and quotes never reach the name). A response that is not ok rejects with the server's own sentence (`error.message` of the JSON body, else "The file could not be downloaded (HTTP <status>)" with a short plain body appended) and clicks nothing, so the caller's snackbar names the refusal. An address on another origin (the Blob host's stored copies) keeps the anchor click, which needs no CORS and buffers nothing; a page request that itself fails (the network, a redirect the fetch may not read) falls back to the anchor click, the old path. The callers: `packages/chrome/src/EditorShell.tsx` (the `render.slide` branch: `downloadFromPage(first, { name })` for a same origin picture, `window.open` for another origin as before; the `.then` callback is `async` so a refusal reaches the `.catch` that says it), `apps/studio/src/editor/controller.tsx` (`triggerDownload` is now `async` and delegates; its callers in `export.run`, `build.run` and `downloadArtifact` await it inside their try blocks, so a refusal publishes to the report card and the shell says it), `apps/studio/src/editor/EditorRoot.tsx` (`deck.pack` awaits the download before answering "The bundle is at", so a refused ticket is said instead). `apps/studio/e2e/core/lib.ts`'s refusal regex gains "could not be downloaded"; `apps/studio/e2e/core/export.spec.ts` says the transport in its header and each of the four rows reads that the editor is still the page after the file arrived. The decks page's and the print page's own `triggerDownload` copies are untouched (their rows passed on the preview; `decks.card.download` reads the route through the API context).

The blob tier budget is untouched: a download is one fetch per click of the row, no timer, no store poll.
