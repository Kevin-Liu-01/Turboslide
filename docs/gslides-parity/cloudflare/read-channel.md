# T1: the realtime channel seam

Reader T1 of the Cloudflare design round, written 2026-10-01 in the worktree `Turboslide-realtime` (branch `realtime/round`, `HEAD` at `c978bb43` equal to `origin/main`, plus the uncommitted edits of the realtime build round: lanes R1 to R6 editing at the time of reading). Every line number below is `c978bb43`'s unless it says "working tree"; a working tree hunk is cited by the function it lands in, since its numbers move while the lanes edit. This note reads code and docs and fetched no product page; every price or platform claim it repeats is a research note's and is cited by note and section. The DNS check the round asked for was run: `dig NS turboslide.com +short` answered `dns1.registrar-servers.com` and `dns2.registrar-servers.com` and `dig CNAME www.turboslide.com +short` answered `5661780b11730745.vercel-dns-016.com` (read 2026-10-01), so the zone is at the registrar and the site's host is Vercel's; a Worker lives on its `workers.dev` hostname, which is a different site from `www.turboslide.com` for cookies and `Origin`.

The question the note answers: if the deck's order and roster lived in a Durable Object (one object per deck, tabs on WebSockets, the version records still on Blob), what in this tree changes, what stays, which invariants the object must restate, which client rules survive, and what R1 and R2 are moving under the design right now.

## 1. What the channel interface requires, and what the room assumes beyond it

### 1.1 The interface

`RealtimeChannel` (`packages/realtime/src/channel.ts` 291 to 338) is one object per process with: `tier` (one of `memory`, `redis`, `blob`, 10); `append(deckId, base, entries, { token? })` (298 to 303), a compare and append that answers `{ ok: true, entries }` with the seq assigned from 1, or `{ ok: false, head, count, locked? }` and never the entries (99 to 106); `since(deckId, seq, limit)` (305); `head(deckId)` (307); `subscribe(deckId, listener, { passive?, clientId? })` (317; 242 to 253), one subscription per instance per deck delivering `op`, `presence`, `leave` and every published event in stream order; `publish(deckId, event)` (319); `trim(deckId, { minSeq?, maxEntries? })` (321; 266 to 271); `presence` with `set`, `roster`, `leave(clock?)`, `bind`, `owner` (273 to 289); `lock`, `heartbeat`, `unlock` on a key with a token and `staleMs` (324 to 328; 255 to 262); `budget(key, cost, limit, windowMs)` fixed windows (333); `flag(name)` on by default (335); `close` (337). The working tree adds `bus?: DropBus` (channel.ts, the `RealtimeChannel` type; `packages/realtime/src/bus.ts` 38 to 45, untracked), optional so the blob tier carries none.

The wire types the channel carries: `Entry` (56 to 94) with `seq`, `rev` (the revision the entry followed), `clientId`, `opId`, `mutations` or `comment`, `at`, `covers?` (the blob tier's folded op ids, 85) and `note?` (93); `RoomEvent` (193 to 236): `hello` with `seq`, `revision`, `clientId`, `role`, `clients`, `editing`, `tier`, `covered?` (194 to 212), `ops`, `op`, `checkpoint` (174 to 190, `external?: true` at 189), `presence`, `leave`, `reject` with a fixed reason (171), `inbox`, `access`, `resync`, `store` (blob only, 230 to 236). `protocol.ts` is the zod of every frame: `entrySchema` strict (158 to 175), `opsPostSchema` (198 to 222), `presencePostSchema` (264 to 266) refusing identity fields as `unknown_field`, `rosterEntrySchema` (292 to 295), `roomEventSchema` (319 to 361) with `tier: z.enum(REALTIME_TIERS)` at 328, the SSE framing `sseFrame`, `sseComment`, `sseRetry`, `parseSseBlock`, `roomEventOf` (370 to 442). A frame that fails the schema is dropped by the client (`roomEventOf` 440 to 441).

### 1.2 What the contract pins

`channel-contract.ts` runs over memory and redis (the blob tier has its own `blob.test.ts`): seq from 1 and `since` paging (112 to 136); a stale base answers `head` and `count`, never entries (138 to 149); the append lock makes other writers yield with `locked: true` and expires by TTL (151 to 171); every admitted op reaches every instance's listeners in order (173 to 196); `publish` reaches the other instance (198 to 216); `trim` by `minSeq` and `maxEntries`, the head never moves back (218 to 230); the roster keeps the newer clock, expires rows, announces `presence` and `leave` (232 to 266); a binding lives its TTL and refuses an id outside the 32 hex grammar (268 to 279); the checkpoint lock is taken, refreshed, broken after `staleMs` and freed by TTL (281 to 302); a fixed window budget answers the time to the window's end (304 to 316); flags read on by default and refuse an unknown name (318 to 323); a deck id that is not a slug is a TypeError on every call (325 to 330). The working tree adds the drop bus case (skipped on blob; `channel-contract.ts` diff after 265).

### 1.3 What the room assumes beyond the interface

These are the facts a fourth implementation inherits whether or not the interface says them.

1. The admitting process holds a live document per deck and keeps it at the channel's head. `createRoom` (`apps/studio/src/server/room.ts` 773 to 1035) loads the store at the last checkpoint (`coveredSeq`, 777 to 783), then `syncLive` (794 to 824) reads `channel.head` and pages `channel.since` to apply the entries after `live.seq`; the passive subscription (850 to 880) applies each `op` in order or calls `syncLive` on a gap, and a `checkpoint` sets the revision (`external: true` reloads from the store, 870 to 874). On the blob tier `syncLive` reads the store instead (795 to 800).
2. The admission runs in the Vercel function, against that live document, before `append`. `admitOps` (1693 to 1927): the binding (1697), four budgets through `channel.budget` with keys from `keys.ts` (1712 to 1750), the base window (`checkBaseWindow`, `admission.ts` 73 to 77; 1764 to 1773), the landed entries by `channel.since` (1779 to 1784), the dedupe of a resent op id against the last 2,000 entries of the stream (1789 to 1805), `transformEntry` (1485 to 1509) with the tie rule (`landedOf` 1462 to 1470), the reducer and the validator in `landCandidate` (1596 to 1642), the undo of a refused sibling (`undoOfSplices` 1584 to 1593), then `appendWithRetry` (`admission.ts` 167 to 233) with a transform hook that re-runs the same steps after a moved head (1850 to 1886). The channel is the order; the function is the transformer. The blob tier's `admitOnBlob` (2094 to 2347) is the same shape over the store's records.
3. The checkpointer runs on the admitting instance and writes the version log through the store. `createCheckpointer` (`apps/studio/src/server/checkpoint.ts` 145 to 343) takes `deck:<id>:ckpt` with `channel.lock` and a 1 s heartbeat (214 to 224), reads `covered` from the records (183 to 187; working tree: re-read under the lock after a `store.sync`), pages `channel.since` to the head (233 to 240), coalesces per author and run (`coalesce.ts` 1 to 29) and commits each run with `store.write(..., { ops: { fromSeq, toSeq }, force: true })` (190 to 210), publishes one `checkpoint` (284 to 296) and trims to 10,000 (297 to 300; `STREAM_RETAIN_ENTRIES` 37). Triggers: 2 s idle, 10 s hard, 2,000 entries or 1 MB (24 to 31), at once for an agent write (`admitOps` 1906 to 1907). The commit at 196 to 204 passes no `origin` (grep of `origin` over `checkpoint.ts` and `coalesce.ts` finds none), so a record of the memory and redis tiers carries no `origin`; section 3 item 3 reads this against the invariants.
4. The follower assumes a store watch and the follow lock. `follow` (890 to 990) reads the records above the live revision that are not this instance's own (`ownRevisions`, 784, 839 to 844, 897), takes `deck:<id>:follow` (902), checks the stream tail for `store:<n>` (912 to 915), appends a replayable record as an entry with `clientId: 'store'` (938 to 947) or announces an external checkpoint (992 to 1007); it is driven by `store.watch` (1009 to 1016), which is `fs.watch` on a checkout and the mirror's head poll on the Blob store (`blob.ts` 4 to 6). Off on the blob tier (891).
5. The server write enters the same order from the function. `admitServerWrite` (3281 to 3471): a `version.restore` or the blob tier goes through `store.write` and `room.follow()` (3287 to 3345); otherwise the base is checked against the live document (3346 to 3377), the write is placed by `landCandidate` (3379 to 3390), appended with `clientId: 'server'` (3391 to 3425; working tree `serverClientId` answers `agent:<principalId>` for an agent author), then the checkpointer is forced up to ten times 100 ms apart until the record that covers the seq exists (3443 to 3470). The dispatchers reach it through `roomBackedStore` (1126 to 1180, `storeDeps.store` of `deckDispatcher`), the editor's `writeDeck` through `write.ts` 844 to 850, and the HTTP route flushes the room before an agent read (`routes/api/actions.$action.ts` 99 to 112; `flushRoom` 1088 to 1112).
6. The reads that take the live document ahead of the store: `liveIfOpen` (1061 to 1070) for the viewer and print payloads (`decks.ts` 855 to 863, `liveServesRead` 828 to 833), `roomBackedStore.read` and `revision` (1139 to 1145) for the agent, and the editor's loader and resync read, which opens the room and reads `liveAtLeast` (`write.ts` 442 to 454; `liveAtLeast` 1965 to 2003 is a no op on the stream tiers, 1972). These assume the function can build the live document from the channel.

The identity and the decision are the function's. `requestIdentity` (352 to 439) reads the bearer (357 to 368), the localhost agent (369 to 382), the sealed anonymous cookie (385, 390 to 396) or the better-auth session (386, 450 onward); `decideFor` (716 to 726) is `authorize()` over that context; the stream's reader facts come from the access record and a second `authorize` (`viewerFacts` 2602 to 2617). ## 2. The exact places an external authority changes

The model: one Durable Object per deck orders the ops, holds the live document and the roster, and every tab holds a WebSocket to it; the version records stay on Blob; the Vercel app keeps the pages, the loaders, the exports, the actions and the agent HTTP routes (`research-options.md` 5b; `docs/REALTIME.md` section 6 first item). Each item names what today's code does and what moves.

1. Who admits. Today the function decides with `decideFor` over `requestIdentity` (1.3 item 7) and the object cannot read the identity from a cookie: the socket goes to a `workers.dev` host, another site, and the sealed anonymous cookie (`room.ts` 385) and the better-auth session (386) do not travel there. The replacement is a ticket minted by a Vercel route (the editor's loader at `write.ts` 403 to 490 already runs `requestIdentity` and `decideFor`): the deck id, the principal id, the identity string the budgets key on, the role, `via`, `showNames`, `readComments` (the `ViewerFacts` of 2500 to 2508), the client id (so `mintClientId`'s MAC stays the function's, 2663), an expiry, signed with an HMAC under a secret both sides hold (the shape of `clientIdMac` 2647 to 2652), carried on the socket's first frame or URL. The object verifies the signature and admits the socket; the 60 s recheck (route 70) becomes the ticket's expiry plus a refresh frame the client fetches from the Vercel route, and the `access` event's recheck (route 166 to 177, 195) becomes the Vercel share routes telling the object `access changed` so it closes or re-tickets its sockets. The `Origin` check of the CSRF filter (`apps/studio/src/start.ts` 19 to 20, 43 to 44; `refuseCrossSite` 3165 to 3184) moves into the Worker's upgrade handler with the allowed host list (`docs/REALTIME.md` 4.1 names `TURBOSLIDE_AUTH_HOSTS` with the same four hosts). The slot caps (1.3 item 9) become the object's count of sockets per identity and address; `retire` and the tab token lose their reason (the object sees every socket of the deck).
2. Who transforms. Today the function (1.3 item 2). In the object: `admitOps`' loop ports as the memory tier's path (`research-options.md` 5b: "the admission code of room.ts runs inside the object unchanged in shape"), which needs `transformEntry`, `rewritesText`, `landedOf`, `landCandidate`, `reanchorAll`, `undoOfSplices`, `betweenEntries`, `refusalIssue`, the working tree's `yieldConcurrentConversion`, and `appendShifts` (1217 to 1244) for the comment anchors, split out of `room.ts` into a module without `node:crypto` and `ioredis` (`room.ts` 1 and 3). The schema's reducer, transform and validator import no `node:` (1.3 item 8). The budgets (`admitOps` 1712 to 1750) become the object's counters with the same keys (`keys.ts` 106 to 128).
3. Who writes the version log. Today the checkpointer on the admitting instance through `store.write` (1.3 item 3), whose Blob store carries a `node:fs` mirror (`blob-store.ts` 24 to 34). Two options, both to be named by the design: (a) the object posts its coalesced writes to a Vercel route (`POST /api/decks/:id/checkpoint`, the reverse of today's bearer path) that runs `store.write` with `ops: { fromSeq, toSeq }` and answers the record; the object then publishes the `checkpoint` and trims its SQLite; (b) the object writes Blob itself, which means porting the manifest put with `ifMatch`, the snapshot per commit and the record layout (`docs/SYNC.md` 3.1, 3.5, 3.6) to a fetch only client. (a) is the smaller change and keeps `docs/SYNC.md` invariant 1's commit point in one module; it puts one HTTP round trip on the agent write path (item 4). The checkpoint lock (`checkpoint.ts` 214 to 224) and the working tree's `knownCovered` re-read exist for two instances and are moot in one object; `coveredSeq` (106 to 112) still seeds the object from the records at its first wake.
4. How the agent HTTP write enters the order. Today `actions.$action.ts` → `deckDispatcher` → `roomBackedStore.write` (1146 to 1178) → `admitServerWrite` (3346 to 3470) in the function, then a forced checkpoint and a wait for the record. With the object: the Vercel route forwards the write to the object (`fetch` to the object's stub through the Worker, under a bearer the Worker checks), the object admits it in order with `author.kind: 'agent'` and `clientId: agent:<principalId>` (working tree `serverClientId`; `docs/REALTIME.md` 3.3), fans it out as an `op`, and must commit the record before the answer returns because `writeDeck` and the agent surface answer `{ revision, record, seq }` (`ServerWriteResult` 3251 to 3261) and `deck.trash { baseRevision }` compares store revisions: so item 3's path runs synchronously for an agent write, as `checkpointer.run({ force: true })` does today (3443 to 3455). `version.restore` keeps today's rule (3287: never through the stream): the Vercel route writes the store and then tells the object `external checkpoint at revision n`, which is today's `announceExternal` (992 to 1007) with the object as the publisher.
5. How the room follows the external order. Today the function's live document follows the channel (1.3 item 1) and the store (item 4). With the object there is no live document in the function; the reads of 1.3 item 6 must ask the object (`GET` on the object for the document at the head, with `atLeast` and `since` as `readEditorDeckFn` takes them, `write.ts` 405 to 419) or ask it to checkpoint and then read the store. `liveIfOpen` (1061) answering null means "the store", which is behind by up to the checkpoint interval (`checkpoint.ts` 25 to 27); `flushRoom` (1088) becomes "ask the object to commit now". The follower's trigger (1.3 item 4) becomes a call from every Vercel code path that writes the store outside the room (the CLI on a checkout stays the memory tier's), since the object has no `fs.watch` and no free poll.
6. What the client sends. Today three HTTP surfaces: `GET /stream` with `since`, `retire`, `tab` and `last-event-id`, answering SSE frames, `x-turboslide-client`, a 503 `too_many_streams` with `retry-after` and the minted `clientId` (route 86 to 313; the transport at `controller.tsx` 320 to 422); `POST /ops` with `OpsPost` answering `{ ok, entries, rejected, head, revision, between? }` or `400`, `403 client_unbound`, `404`, `409 resync | contended`, `413`, `415`, `429` with `retry-after`, `503 store_busy | store_timeout`, plus `x-turboslide-revision` (`decks.$deckId.ops.ts` 40 to 154; transport 423 to 456 with a 30 s deadline at 500); `POST /presence` with `PresencePost`, `?leave=1` under `keepalive`, answering `{ ok, hueSlot, role }`, `{ ok, dropped }`, `400 unknown_field`, `403 client_unbound` (`decks.$deckId.presence.ts` 45 to 126; transport 457 to 464). Over one socket: up frames `{ t: 'ops', req, ...OpsPost }`, `{ t: 'presence', ...PresencePost }`, `{ t: 'leave', clock }`; down frames every `RoomEvent` plus `{ t: 'ack', req, ...OpsResponse }` so `transport.postOps` keeps its promise shape (`RoomTransport` `room-client.ts` 177 to 181). The transport is injected (`RoomClientOptions.transport` 341; `fake-transport.ts` exists), so the room client's state machine needs no change if the ack carries the same fields, including `between` (60 to 76) and `retryAfterMs` (83). The ops POST while the stream is down (`flush` 1449 to 1456 gates on `clientId` and `bound`, not `connected`) has no path when the socket is the only transport: the Worker keeps `POST /ops` and `POST /presence` as HTTP to the same object (a Durable Object serves `fetch`), or the client queues until the hello (section 4 item 3 reads the cost of each).
7. What the hello and the resync become. Today hello is built in the route from the roster, `room.live()`, `room.revision()`, `room.covered()`, the editing ceiling and the reader filter (route 222 to 236); the replay is `replayFor` (2764 to 2790) paging `channel.since` by 256 up to 2,000 entries or 1 MB, `resync` when the position is above the head or more than 2,000 behind (`replayPlan` `admission.ts` 85 to 89), and in the working tree when the first page's first seq is not `position + 1` (`replayFor`, the trim and the hand off case; `docs/REALTIME.md` 3.7). In the object: the same plan over its SQLite tail (10,000 retained after a checkpoint, `checkpoint.ts` 37); hello's `tier` is a fourth word, and the client's parser is strict (`protocol.ts` 328 with `REALTIME_TIERS` `channel.ts` 10; `roomEventOf` 440 drops a frame that fails), so the client that knows the word deploys before the object sends it. The working tree's client rule "a hello whose tier differs from the last one's resyncs at `hello.revision`" (`room-client.ts`, the hello handler; `build/r1.md` R1-R2a) makes the flip one reload per open tab. The resync read (`readEditorDeckFn` `write.ts` 442 to 490: `roomFor`, `liveAtLeast`, `originsSince` over the store's records) must read the object's document, since the store is behind by the checkpoint interval and `room.live()` is the stream's head today (1.3 item 6).
8. What the object must hold durably. The memory tier's `Room` (`memory.ts` 28 to 34: `entries`, `head`, `listeners`, `roster`, `bindings`) is process memory; an object is evicted and reconstructed (`research-options.md` 5b, failure modes), so `entries` since the last checkpoint and `head` go to SQLite before the ack, and the live document is rebuilt by `syncLive`'s cold path (794 to 824: the store at the last checkpoint plus `since`). The roster may stay in memory with the socket attachments (a tab re-sends its state on the hello, `room-client.ts` 1337 to 1338); the budgets and the flags are per object.
9. What the object does not give. The cross instance cache drops of the working tree's bus (section 5 item 2) are among Vercel functions; an object holds no subscription from a function. The access record cache, the index row cache and the identity cache keep their 5 s TTLs (1.3 item 10) unless another carrier drops them (Cloudflare KV or Redis, the account database reader's seam). The principal records (working tree `bindIdentityRedis`, the file store per instance without Redis) and the row `realtime.departed-guest.name-stable` are the same seam. The card thumbnail's two triggers (`decks.$deckId.ops.ts` 137 `scheduleCardThumb`; the stream close at route 142 to 149) are Chromium work in the function and lose their hook when the ops stop passing through it: the object calls a Vercel route, or the checkpoint route of item 3 schedules it.
10. The branches on `room.tier === 'blob'` that a fourth tier must be read against: `admitOps` 1751, `syncLive` 795, `follow` 891, `stopWatch` 1010, `covered` 1027, `flushRoom` 1098, `roomBackedStore` 1136, `liveAtLeast` 1972, `admitServerWrite` 3287, `room-client.ts` 874, 900, 1003, 1055, 1228, 1262 and 1491. Each reads "the store is the live document"; an object tier reads like memory and redis on the client and like neither on the server, since the function holds no room.

## 3. The invariants and which ones the object must restate

`docs/SYNC.md` 3.11 (177 to 191 at `c978bb43`) and `docs/REALTIME.md` 3.9 (116 to 118).

1. One ordered log per deck; the manifest put with `ifMatch` is the one commit point. Restate: the object's stream is the order and the record log's commit point stays the store's manifest put, written by the checkpoint route of 2.3; an op answered at seq n is in SQLite before the ack.
2. Transform before place on every tier; the answer carries the placed mutations. Restate: in the object, with the module split of 2.2; the tie rule rides the up frame as `insertTie` (`protocol.ts` 188 to 202).
3. Every record names its origin; an op id is admitted at most once within 2,000 of the head. On the stream tiers the second half holds through the tail dedupe (`admitOps` 1789 to 1805) and the first half does not: `checkpoint.ts` `commit` (196 to 204) passes no `origin`, so `docs/REALTIME.md` 3.2's sentence that the redis tier's record "carries `origin: { clientId, opIds }`" is not what the tree does. The object's checkpoint write should carry `origin` from `CoalescedWrite.clientId` and `opIds` (`coalesce.ts` 17 to 29), which restores invariants 4 and 10's resync path for records written by the object.
4. The client acknowledges by op id. Holds on the stream tiers through `applyEntry`'s own path (`room-client.ts` 987 to 1027) and the answer (`flush` 1528 to 1529); transport independent.
5. Every text a person can type into is a text run. Schema; unchanged.
6. A reader receives every op its role may see with the notes stripped for a commenter and a viewer. Restate per socket in the object: `filterEventForReader` (2566 to 2599), `rosterEntryForReader` (2515 to 2539) and `stripNotes` (2542 to 2556) run with the ticket's facts of 2.1.
7. The head is read, never listed; on the stream tiers read on the hello and never polled (`REALTIME.md` 3.9). In the object the head is memory and SQLite; unchanged in meaning.
8. Every read of an overwritten path is proven. Store side; unchanged.
9. The stream opens at the client's position, the replay covers exactly the gap, `hello.covered` is the live seq, the answer's `between` fills what sits under an admitted entry. Restate for the object: the replay from SQLite with `replayPlan`, `covered` from the object's checkpoint state, `betweenEntries` (1351 to 1366, pure) over the object's entries.
10. Unacknowledged ops survive a reload and a replay whose first attempt committed is acknowledged, never committed again. The pending store is the client's (`pending-store.ts` 1 to 48); the dedupe is item 3's tail check in the object; the resync read's `origins` need item 3's fix.
11. Undo per author moves the inverse past every remote entry since it was recorded. Client side (`transformSince` 1970 to 1983); unchanged.
12. At most one timed store call per tick per open deck per instance while a stream is open and none otherwise; zero on the redis tier (`REALTIME.md` 3.9). In the object: zero from the functions; the object's own store calls are its checkpoints and the reads of 2.5, which the `cost.*` rows restate (`docs/REALTIME.md` section 2, `cost.editor-idle.calls` and `cost.editor-editing.calls` give the redis tier's ceilings; an object tier needs its own column).
13. Retention on a schedule: the prune every 20th commit rides the store's write path; the prune at the last stream's close is the blob channel's (`blob.ts` 448 to 467) and does not exist on the stream tiers; the object adds nothing here.

Two more the object must state, which the Redis rule of `docs/hosting.md` section 9 ("Redis must never hold the only copy of anything", 728 to 729) does not cover as written: the entries between the last checkpoint and the head are the only copy for up to the checkpoint interval and live in the object's SQLite, so the rule becomes "the object's storage holds entries for at most the checkpoint interval and at most 10,000 behind the last checkpoint before the store has them"; and the reconstruction after an eviction is `syncLive`'s cold path and must finish before the first socket's hello.

## 4. The client reconnect rules that survive a WebSocket

1. The client owns the reopen and the transport reconnects nothing (`OpenOptions.onError` `room-client.ts` 97 to 105; `openStream` 1674 to 1695; `reopenStream` 1704 to 1736). The wait is the server's `retry-after` or `retry:` up to 60 s, 8 s on a 403 or 404, else a ladder 500 ms doubling to 8 s (`reopenWaitMs` 1666 to 1672; `BACKOFF_MAX_MS` 199; `REOPEN_WAIT_MAX_MS` 218). Survives: a socket's `close` event with a code and an optional wait maps onto `StreamFailure` (113 to 126); a refused upgrade answers a status the transport reads as today (`controller.tsx` 371 to 385).
2. Every open carries `since` at the position and the replay fills the gap (1680; `replayFor`); the hello resets the backoff, marks connected and bound, and gates the first flush until the replay drains (`caughtUp` 1308, `noteCaughtUp` 1072 to 1076). Survives unchanged.

5. The gap watch: an entry buffered above the position for 8 s reopens the stream (`watchGap` 1150 to 1162; `GAP_REOPEN_MS` 230). Survives as a guard; a TCP socket from one object should not lose a frame, and the rule costs nothing when it never fires.
6. 10. The working tree's `helloTier` rule (the hello handler; `build/r1.md` R1-R2a) resyncs at `hello.revision` when the tier word changes, so the flip to an object tier and a rollback from it are one reload per tab. ## 6. Findings, one line each

1. The admission, the checkpointer, the follower and the server write all run in the Vercel function against a per instance live document built from the channel (`room.ts` 773 to 1035, 1693 to 1927, 3281 to 3471; `checkpoint.ts` 145 to 343); the channel is the order and the function is the transformer.
2. A Durable Object channel moves the transform, the reducer, the validator, the budgets and the roster into the object and leaves the function with no live document, so `liveIfOpen` (`room.ts` 1061), `roomBackedStore` (1126), `flushRoom` (1088) and the editor's resync read (`write.ts` 442 to 454) must reach the object or read a store the object checkpoints first.
3. The version log's writer is the store's `write` with a `node:fs` mirror (`checkpoint.ts` 196 to 204; `blob-store.ts` 24 to 34), so the object commits through a Vercel route or the Blob layout is ported to fetch; the agent write needs that commit before its answer (`room.ts` 3443 to 3470).
