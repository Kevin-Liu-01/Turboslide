# The hosting setup of the realtime round

The scripts and files under `scripts/hosting/` set up production for the realtime round's Cloudflare phase (`docs/CLOUDFLARE.md` sections 3.6, 3.7, 3.8, 4.4 and 6): the realtime channel on one Cloudflare Worker (`turboslide-realtime`, one SQLite backed Durable Object per deck over hibernating WebSockets, the tier word `do`), the accounts database D1 bound to that Worker and reached by the Vercel function through its bearer routes, the variables the `do` tier and Google sign in need on the General Translation team's Vercel project `turboslide-gt`, in the order that never breaks a deployment, and the production guard's reading of them. No Upstash, no Neon, no `REDIS_URL`, no `DATABASE_URL`, ever (`docs/CLOUDFLARE.md` 4.4); the redis tier of the first realtime round stays in the tree as code and is never deployed (5.1), and its subcommand is retired below. Nothing here creates a Cloudflare or Google resource, buys a plan, changes DNS or touches a console: the account steps are the orchestrator's in Kevin's session with the stops of section 6, the project setting of step 15 and the Google console are Kevin's, and every command below names the step that is missing. The runbook a reader follows is `docs/hosting.md` section 13; this page is the reference of the tools.

## `realtime-env.mjs`

`node scripts/hosting/realtime-env.mjs <subcommand> [options]`. The Vercel subcommands run from a repository root linked to `turboslide-gt` (`.vercel/project.json` names the project; `/Users/kevinliu/repos/Turboslide-vector` is the guard's) and set variables with `vercel env add <NAME> <environment> [--sensitive] --yes --scope general-translation` and the value on stdin; the Worker subcommands run the workspace's wrangler from `apps/realtime-worker` (`node_modules/.bin/wrangler`, never a global one) with a secret's value on stdin, or talk to the Worker's control routes under the room bearer. Values come from 600 files under `~/.config/turboslide/`, and the output names variables, environments, hosts and deck ids only: no value reaches the command line, the output or a log, and the CLIs' own output is scrubbed of every value read before a line of it is shown.

Options: `--dry-run` prints what the command would read, mint, set, remove, post or run and makes no call (no `vercel`, no `wrangler`, no network); `--environments production,preview` narrows the Vercel subcommands (both by default); `--env preview` names the preview Worker and its database for `drain`, `do-flag`, `worker-migrate` and `worker-secrets` (production by default); `--local` makes `worker-migrate` run against the local D1 of `wrangler dev`; `--host <worker host>` overrides the Worker's hostname for `drain` and `do-flag`; `--force` replaces a variable that is already present (otherwise a present variable is skipped by name; rotation is `docs/security.md` section 12's runbook); `--admin-emails <a,b>` overrides the `TURBOSLIDE_ADMIN_EMAILS` value (the default is `kevin@generaltranslation.com`; `google-oauth.env` may carry it as a key); `--wrangler <path>` and `--worker-dir <dir>` move the wrangler binary and the folder it runs from (the tests pass a fake); `--scope`, `--project`, `--cwd` and `--config-dir` move the defaults (`general-translation`, `turboslide-gt`, the current directory, `~/.config/turboslide`). Exit 0 when done or nothing to do, 1 when a precondition is absent (the output names the step), 2 on usage, a refusal or a failed command.

The rules the script holds:

- A Vercel subcommand's linked project (`--cwd`) must be `--project` (`turboslide-gt`); a real run from another root refuses before any read, a dry run says so and goes on. `turboslide.vercel.app` (the personal project) gets nothing by REALTIME.md default 7.6. A Worker subcommand needs no linked project.
- A file is read only when its mode lets nobody else read it (600 or stricter); a looser mode is refused with the `chmod 600` to run. The files and their keys: `room.env` (`<NAME>_PRODUCTION=` and `<NAME>_PREVIEW=` for `TURBOSLIDE_ROOM_SECRET`, `TURBOSLIDE_ROOM_BEARER` and `TURBOSLIDE_DB_BEARER`, minted by `mint`; the unsuffixed `TURBOSLIDE_ROOM_SECRET=` and `TURBOSLIDE_ROOM_BEARER=` are the shared pair of before AUTH-3, production's until its rotation and never sent to the preview), `better-auth.env` (`BETTER_AUTH_SECRET_PRODUCTION=`, `BETTER_AUTH_SECRET_PREVIEW=`; the script mints them), `google-oauth.env` (`GOOGLE_CLIENT_ID=`, `GOOGLE_CLIENT_SECRET=`, optionally `TURBOSLIDE_ADMIN_EMAILS=`; section 6 step 13), `mail.env` (`RESEND_API_KEY=`, `TURBOSLIDE_MAIL_FROM=`; Kevin writes it if he wants the email method), `vercel-bypass.env` (`VERCEL_AUTOMATION_BYPASS_SECRET=`; Kevin's project setting, step 15), and `cloudflare.env` (`CLOUDFLARE_ACCOUNT_ID=`, `CLOUDFLARE_WORKERS_SUBDOMAIN=`, `D1_ACCOUNTS_NAME=`, `D1_ACCOUNTS_ID=`, `D1_ACCOUNTS_PREVIEW_NAME=`, `D1_ACCOUNTS_PREVIEW_ID=`, `TURBOSLIDE_ROOM_HOST=`, `TURBOSLIDE_ROOM_HOST_PREVIEW=`; account facts and not secrets, so the hosts and the database names may appear in the output). One value per environment for every secret (AUTH-3, `docs/hosting.md` 13.8): a subcommand that would send a production value to the preview, or a database bearer equal to its environment's room bearer, refuses with exit 2; each environment's three values are the same on its Vercel environment and on its Worker's secrets.
- The value travels as the child's stdin and nowhere else (a bearer reaches the HTTP child of `drain`, `do-flag` and `db-unlisted` through its environment, never its arguments); `VERCEL_OIDC_TOKEN` is removed from every child's environment, as the guard does; `CLOUDFLARE_ACCOUNT_ID` from `cloudflare.env` reaches the wrangler child alone (no `account_id` in `wrangler.jsonc`).
- `do`, `database`, `google` and `flip` set nothing before their precondition reads true: they read `vercel env ls <environment> --json` (the `key` of every row; the JSON carries no value for a sensitive or encrypted row) and `/health`, and stop with exit 1 and the step's sentence otherwise.
- A remote wrangler command (`worker-migrate` without `--local`, `worker-secrets`) is the integrator's for the preview environment and the ship step's for production, by the round's rules; the script does not check who runs it.

The retired subcommand: `redis` (the first realtime round's step 1, which required `REDIS_URL` from an Upstash install) answers exit 2 with the reason: the redis tier stays in the tree and is never deployed, `REDIS_URL` and the Upstash pair are never set on either project, and the channel is the Worker. `database` no longer requires `DATABASE_URL`; it sets `TURBOSLIDE_ACCOUNTS=d1`.

`realtime-env.test.mjs` drives the parsers, the plan of every subcommand, the dry run (no call), a real run against a fake `vercel` on `PATH` and a fake wrangler (the value's bytes arrive on stdin and never in `argv`; the account id in the child's environment; no value in the output), the drain and the flag against a fake fetch, the private mode rule, the linked project refusal and the retired subcommand; `node_modules/.bin/vitest run --project scripts scripts/hosting` runs it.

## `production.json`

The tree's expectation of production's realtime tier: `{ "realtime": "blob" | "redis" | "do" }`. The guard reads it from the checked out sha (below): `do` makes the realtime rows join the seller path, deploys the Worker with every push and holds the sha while `TURBOSLIDE_ROOM_HOST` is absent from production's names; `redis` is never written by this phase's tooling (the word stays in the file's grammar for the tier that exists in code); `blob` or no file checks nothing. `flip --tier do` writes `do` and `rollback` writes `blob`, and the file is committed with the push that changes the environment, so a tree always says which tier production selects after that push. A missing or unreadable file reads as `blob`, the tier a hosted deployment without a channel selects on its own (`packages/realtime/src/select.ts`), so every sha before this round behaves as today.

## The guard patch

`docs/gslides-parity/cloudflare/build/guard.patch` is a unified diff against `~/.config/turboslide/gt-follow.sh` as it read on 2026-10-01 10:49 PDT (23,938 bytes, the version with the docs-only rule; `sha256` prefix `a3b6f5d305773fe7`). It replaces the first realtime round's patch (`docs/gslides-parity/realtime/build/guard.patch`, removed in this phase and never applied), is written against the same guard, and is applied by the ship step, never by a lane, after R5's push is deployed (the three row ids exist in the matrix from then on) and before R1's push (the first one that carries the Worker):

```sh
cd ~/.config/turboslide
cp gt-follow.sh gt-follow.sh.before-cloudflare
patch -p0 --dry-run < /Users/kevinliu/repos/Turboslide-realtime/docs/gslides-parity/cloudflare/build/guard.patch
patch -p0 < /Users/kevinliu/repos/Turboslide-realtime/docs/gslides-parity/cloudflare/build/guard.patch
bash -n gt-follow.sh
[ -d gt-follow.lock ] && echo "a pass is in flight; wait" || { pkill -f gt-follow.sh; (nohup ~/.config/turboslide/gt-follow.sh > /dev/null 2>&1 &); }
tail -1 gt-follow.log
```

The dry run says whether the hunks still fit a guard edited after that date; a rejected hunk means the guard is re-read and the patch rewritten, never forced. Before the first push that deploys the Worker, the guard's worktree needs the Worker's dependencies once: `pnpm install --frozen-lockfile` in `/Users/kevinliu/repos/Turboslide-vector` after it has checked out a sha that carries `apps/realtime-worker` (the loop does not install; a missing `apps/realtime-worker/node_modules/.bin/wrangler` is an error whose note names this command), and the keyring credential of `wrangler login` (section 6 step 7) or `CLOUDFLARE_API_TOKEN` in the loop's environment. The `README.md` beside the guard gains the section the patch's header names (`build/guard-readme-section.md`), by hand, after the apply.

What the patch changes, in the guard's own words (`docs/CLOUDFLARE.md` 5.6):

1. `REALTIME_ROWS=realtime.title.two-typers,realtime.caret.within-300ms,realtime.join.chip-within-1s` beside `SPEC_ROWS`; `WORKER_DIR=apps/realtime-worker`; `WORKER_PATHS_RE` (the paths whose change deploys the Worker: `apps/realtime-worker/**`, `packages/realtime/src/room-core.ts`, `frames.ts`); `ROOM_HOST_VARIABLE=TURBOSLIDE_ROOM_HOST`; `CF_ENV=$DIR/cloudflare.env`; and a start line that names them.
2. `env_names <environment>` (the `key` of every row of `vercel env ls <environment> --json --scope general-translation` from the worktree, never a value), `has_env_name <environment> <NAME>` (0 present, 1 absent, 2 unreadable), `tree_expects` (the `realtime` word of the checked out sha's `scripts/hosting/production.json`: `blob`, `redis` or `do`; `blob` when absent) and `spec_rows_for <origin>`: the spec rows for a check are `SPEC_ROWS`, plus `REALTIME_ROWS` only when the tree's matrix carries the first id, the tree expects `do` and the deployment's environment names (`preview` for a preview deployment, `production` for a `--check` of production) carry `TURBOSLIDE_ROOM_HOST`; otherwise the rows are skipped and the log says why.
3. `cf_env` and `cf_host <environment>`: the account id and the two hosts of `cloudflare.env` into shell variables (never exported; the account id reaches the wrangler child alone), the hosts of `docs/CLOUDFLARE.md` 3.1 as the defaults.
4. `worker_touched <base> <sha>` (a path of `WORKER_PATHS_RE` between the two; an empty or unknown base reads as touched), `worker_deploy <preview|production> <sha> <app origin> <out>` (`pnpm exec wrangler deploy --env preview|"" --var TURBOSLIDE_BUILD_COMMIT:<sha> [--var TURBOSLIDE_APP_ORIGIN:<url>]` from the worktree's `apps/realtime-worker`, the output scrubbed to a file under `guard/`), `worker_health <host> <sha> [<app origin>]` (`GET /health` with a 10 s deadline, three tries 10 s apart: `ok` true, the commit equal to the sha, the app origin equal when given) and `worker_rollback <previous sha> <current sha>` (the worktree checked out at the previous sha, the production Worker deployed with that stamp and read, the worktree put back).
5. `check()` runs the spec step over `spec_rows_for`'s rows and logs the note; the timing rerun narrows to the red ids as today.
6. `pass()`, after the Vercel preview deploy and the docs-only decision: when the push is not docs-only and the tree expects `do` or the push touched the Worker's paths, the preview Worker deploys with the preview URL as its app origin and `/health` must answer the sha and that URL before the check runs (an error otherwise). Before the production deploy of a green sha: a tree that expects `do` is held while `TURBOSLIDE_ROOM_HOST` is absent from the production environment names (the names unreadable is an error); then, on a pass that deployed the preview Worker, the production Worker deploys with `--env ""` (the top level environment named on purpose, since wrangler warns when several environments exist and none is named) and `/health` must answer the sha, else the previous sha's Worker is put back and the pass errors; then the Vercel production deploy as today. On a red production smoke, the previous sha's Worker is redeployed beside the promote back and the `held` line carries both sentences.

The patch adds `curl` and `pnpm` to the loop's dependencies beside `vercel`, `node`, `git` and `grep`. Its tests are `bash docs/gslides-parity/cloudflare/build/guard-patch-check.sh [<path to the guard>]`, whose readings are recorded in `docs/gslides-parity/realtime/build/r6.md`: `patch -p0 --dry-run` and the apply on a copy, `bash -n` on the result, and the helpers sourced from the patched copy and run against fakes on `PATH` (`vercel` answering `env ls --json` from a file, `pnpm` logging its argv and the account id, `curl` printing a `/health` body per host) and a fake worktree with a real git repository, each reading by its exit code and its note. The ship step runs it once more against the guard as it reads on the day before the apply.

Two dependencies the ship step clears before the first push whose tree expects `do`: the preview Worker's `VERCEL_AUTOMATION_BYPASS_SECRET` (Kevin's project setting, section 6 step 15, then `worker-secrets --env preview`), without which the object cannot read the seed route or post its checkpoints to a protected preview and the three realtime rows read red on every preview and hold the sha; and the orchestrator's step 14 (`do`, `database`), which puts `TURBOSLIDE_ROOM_HOST` among production's names.
