## HR-PS#1, the log floor (PERF-1)

Commit: the `HR-PS#1` commit on `harden/wave2`.

### What was wrong

A Blob mirror that held no record walked the deck's whole version log by number before it could answer a read or take a write: a `head` and a `get` per record ever written, at most 8 records at a time (`RECORD_WALK_BATCH`). The store never removes records, so the cost grew with the deck's history. Every deployment starts every instance without a mirror, and the guard deploys every push. perf.md measured 1,422 calls in 97 rounds at 708 records, and the object's checkpoint call gives up after 25 s, which the walk alone passes at about 3,700 records.

### What changed

- `packages/store/src/blob-store.ts`, the pull. A mirror that holds no record reads record 1 in the same round as the snapshot the manifest's etag names. A write's record moves the revision by one and takes the next number, so record 1's revision and the snapshot's revision give the newest record's number (`newestRecordNumber`, `versions.ts`). The mirror reads the 50 numbers up to it (`LOG_FLOOR_RECORDS`) in one parallel batch of `get` calls with no `head`, and the walk goes on from the number after them, which reads the named versions and holes since record 1. The lowest number of the batch is the mirror's log floor, kept in `.turboslide/log-floor.json` beside the mirror manifest.
- A record below the newest one known is read with one `get` (`fetchKnownRecord`): nothing writes such a number again, so the edge holds no miss a later write could hide behind. A body is accepted when it hashes to its etag and parses as the record of that number; anything else is read again the proven way, `head` first (`fetchRecord`, unchanged). A `get` reads the store's URL and not its API, so the batch is no burst against the API's rate limit.
- The older records come on demand (`extendLog`), 50 numbers at a time, newest first, in the deck's queue: `records()` and `listVersions()` read the whole log first, so the History panel, the room's covered sequence, the recovered writes check, `deck.info`'s counts and the agent's `since` answers see every record as before. `documentAt(n)` reads the records from version n up. `documentAtRevision` reads the whole log only when the revision's record is not among the newest. A write reads below the floor when it restores an older version or names an origin whose base sits below the floor (a queue replayed from long ago), so a restore rebuilds its version and a resend is answered with its record.
- The snapshot prune removes nothing on a mirror with a floor, because retention keeps every named version's snapshot and a mirror with a floor cannot see the named versions below it.
- The full walk stays as the repair path: `TURBOSLIDE_STORE_FULL_WALK=1` (`STORE_FULL_WALK_VARIABLE`, `BlobStoreOptions.fullWalk`). A mirror without a proven snapshot (a deck not written since the snapshot round) walks fully as before. So does a mirror whose batch finds no record while numbers below it are unread: a deck whose revision moved outside the store by more than 50.
- `apps/studio/src/server/bundle-core.ts`: `exportDeckBundle` calls `records()` before it packs the mirror folder. `packDeckDir` reads `versions/` from the folder itself, and a replace removes every stored file the bundle does not carry, so a bundle made from a mirror with a floor would have ended the deck's history on a pull and a push back. The pack is the one reader of the mirror's record files outside the store.

### Where the spec's text and the build differ

The spec says "the manifest names the newest record number". The build does not write the number anywhere. It reads it from record 1 and the snapshot the manifest already names. The reasons:

1. `deck.json` is a strict schema (`deckSchema` in `packages/schema/src/deck.ts`), so it cannot carry a field the release before would read.
2. The snapshot body could carry it. But the object's seed fetches a large deck's snapshot as a `DeckDocument` with no parse (`apps/realtime-worker/src/deck-room.ts` `seedDocument`), so an extra field would reach the object's live document and its `/document` answer.
3. A file of its own is one more put per commit, against PS#3's budget of 4 puts on the `do` tier.
4. A listing breaks the sync round's invariant 7 ("records are read by number"), and it lags.
5. Every snapshot already on production names no number, so a written number would leave every deck on the walk until its next commit.

Record 1 is the record the walk read first anyway. Nothing that the store writes changes, so 1.3 item 4 (b) asks nothing of this push.

### What the push leaves open

The read path is constant: `read()`, `revision()`, `write()`, `sync()`, the leases, the viewer at `/deck/<id>`, the thumbnails, the render and the exports. The callers that ask for the whole log still read it once per fresh instance, now as one `get` per record in rounds of 50 instead of a `head` and a `get` per record in rounds of up to 8. These are the room's open (`apps/studio/src/server/room.ts` 1046, `coveredSeq`), which the editor's and the presenter's loader run, the checkpoint's `knownCovered` (`checkpoint.ts` 274), the seed route and the loader's version list (`write.ts` 507). At 1,000 records the editor's first open is about 1,006 calls (a read, then `records()`) where it was 2,011, and it makes no `head` of the API per record. A read of the newest records for those four callers would make it constant. Their files belong to RT and PS#5 in wave 2 and 3 (4.13), so that is a request below, not part of this push.
