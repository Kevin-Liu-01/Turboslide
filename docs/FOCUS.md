## 1. Kevin's directive and the rule it sets

Kevin's directive of 2026-09-15, verbatim: "i think there are a bunch of features that donnt work like shapes. we can get rid of those for now and focus on teh features we need, that work, and that work well with every interaction tested." His standing words: "remember this is actually going to be used by majority sales in our org"; "make sure to actually test our slide features and make sure they work".

The rule this round sets, and every later round keeps:

A feature is in the product's default view only when every one of its interactions works on production and is in the test matrix.

What the rule means in practice:

1. "Works" means the interaction's matrix row passes when the row is driven against the preview and against production (section 6). An interaction that was never driven is not driven, and a feature with a not driven interaction is not in the default view until the row is driven and passes.
2. The default view is the core set of section 2: what a seller does weekly, per `07-sales-users.md` (the paragraph after the population table: "the sales user opens a deck that already exists, duplicates or deletes slides, replaces a logo or screenshot, retypes a name and a few numbers, reorders, hides the slides that do not apply, presents over a call, and sends a PDF or a link"). Everything else on production today is the parked set of section 3.
3. Parked means hidden behind one switch, Tools > Advanced tools, never deleted. A parked feature's rows leave the menu bar, the toolbar, the right click menus, Search the menus and the shortcuts dialog while the switch is off; its blocks still render when a deck carries them; its actions stay on the CLI, MCP, HTTP and window transports and are documented as advanced.
4. A core interaction that is broken or flaky today is fixed in this round (section 5). Every matrix row carries a `feature` field naming its section 2 feature, and the run computes from the file which features have a not driven or failed row; such a feature is parked for that ship and the ship note's parked list is rendered from the run, not typed. The switch itself (`surface.*`) is the mechanism of parking and cannot be parked: a failed or not driven `surface.*` row blocks the ship.
5. Nothing enters the default view by being built. It enters by its rows joining the matrix and passing on production first (section 8).

The audits behind this document, all on `ec61c6b` on 2026-09-15: decks 61 rows (`audit-decks.md`), slides 107 rows (`audit-slides.md`), text 61 rows (`audit-text.md`), pictures 67 rows (`audit-images.md`), arrange 78 rows (`audit-arrange.md`), shapes 50 rows of which 31 were driven (rows 1 to 30 and 35), rows 31 to 34 not driven because production draws the gallery plate where the named rows would be, and rows 36 to 50 not driven because the orchestrator's stop arrived at row 35 (`audit-shapes.md`; 15 is the count of presets inserted by click, row 24), present and share 50 rows (`audit-present.md`), export 51 rows (`audit-export.md`). ## 4. The shapes decision

Decision: a minimal set is kept and made to work in every interaction: Rectangle, Rounded rectangle and Ellipse as shape presets with hand written paths, Line and Arrow as line blocks, each with fill, border and text where the kind takes them. The four galleries, the block arrows, the callouts, the equation signs, Change shape and Mask image are parked until the geometry interpreter draws them and passes the canvas fidelity gate. Insert > Shape > Shapes lists Rectangle, Rounded rectangle and Ellipse as named rows and Insert > Line lists Line and Arrow.

The evidence:

1. Every preset draws as its bounding rectangle. `shapePath` in `packages/schema/src/shapes.ts` returns `M0,0 H{w} V{h} H0 Z` for every kind (lines 385 to 393 at `ec61c6b`), the docblock at 395 says "the whole box until the interpreter lands", the renderer's preset branch calls it (`packages/render/src/blocks/primitives.ts` 321 and 484), and the picker draws every glyph from `shapePath(48, 36)` (`packages/chrome/src/pickers/ShapePicker.tsx` 22 to 26) (`audit-orchestrator-shapes.md`). On production the 135 tiles of the four galleries were the same 28 by 21 px rectangle outline with the name only in a hover tooltip (`audit-shapes` rows 4 to 8, screenshots `01` to `04`), and the triangle, diamond, hexagon, star, cloud, right arrow, left right arrow, chevron, both callouts and both equation signs inserted as hairline rectangles carrying the right `data-shape` (`audit-shapes` rows 12 to 23 and 27 to 30). Only the rectangle and the ellipse drew their own outline (rows 9, 11, 25, 26). A seller who picks a callout and gets a box is worse off than a seller who finds no callout (`audit-shapes` summary, line 13).
2. The gallery counts on production (99, 26, 4, 6) differ from the shape table at `ec61c6b` (100, 20, 10, 6) (`audit-shapes` rows 4 to 7), so the built plate is not the table in the source.
3. The rounded rectangle's radius was not measured on production (`audit-shapes` row 10 recorded works with the radius unconfirmed) and cannot exist while `shapePath` returns the box; it needs its own path, as does any block arrow (`audit-orchestrator-shapes.md`, "Consequences"). The matrix row `shapes.insert.rounded-click` is therefore not driven, with the source reading in its evidence cell.
4. A fresh shape has no fill and a `var(--hair)` 1 px stroke, a faint outline on the dark theme (`audit-shapes` row 35, severity 1).
5. The battery on the kept kinds is not driven on `ec61c6b`. The shapes audit was stopped at row 35 before select, move, resize, rotate, fill, border, text, duplicate, delete, undo, Format options, lines, connectors, the exports and the reload (`audit-shapes` rows 36 to 49, each "not driven" with the reason). The production walk of hotfix 4, against `e2e6307`, passed the rectangle's move, its eight handles plain, with Shift and with Alt, the ring, Cmd+D, Delete, Cmd+Z and Cmd+Shift+Z (`hotfix-4.md` section 3.8, rows 771 to 782 and the rectangle's resize rows, none of which failed), and a line drawn by a drag with its end drag (row 54); those observations predate `ec61c6b` and the matrix records the rows as not driven with the walk as the last observation. No walk has driven fill, border, text in a shape, the arrow's head, the line tail or a shape through the exports (`audit-shapes` rows 40 to 42, 45 to 48). Only `shapes.select` was driven on `ec61c6b` (`audit-arrange` row 1 clicked a rectangle: chip "Shape", eight handles, the ring).
6. The named rows already exist in the model (`insert.shape.shapes.rectangle`, `.rounded`, `.ellipse`, `insert.shape.arrows.arrow`, `model.ts` 1217 to 1236) but production draws the `shapes` plate instead because the submenus carry `effect: shapeGrid(...)` (`model.ts` 1227 and 1237); the audit could not click a named row (`audit-shapes` rows 31 to 34).

What the minimal set requires before it ships in the default view: a rounded rectangle path and an ellipse path in `shapePath` for those two kinds (the rectangle keeps the box path), the `shapes` plate effect removed from `insert.shape.shapes` so the three named rows draw, `insert.shape.arrows` parked, a visible default look (a fill from the theme, or a stroke that reads on both themes), a text run opened by Enter or a double click on a shape (`audit-shapes` row 42: a fresh shape has no run), and every `shapes.*` and `lines.*` matrix row passing on the preview and on production. If any `shapes.*` row is not passing by the ship, the whole of Insert > Shape leaves the default view for that ship and the `lines` feature stands alone when its own rows pass; if a `lines.*` row is not passing, Line and Arrow leave too. The reasoning is Kevin's ("we can get rid of those for now") and the rule of section 1. The block arrow returns with the interpreter (SPEC-5 6.5, `docs/gslides-parity/SPEC-5.md` line 498), not before. The sales judgment's note that a rectangle and an ellipse without the rounded rectangle are worth keeping is recorded; the rule still parks the feature whole when one of its rows fails (section 8), so the rounded path is part of the work, not optional.

## 6. The test matrix

Every core interaction is a row with a stable id, `area.feature.interaction`, and a `feature` field. The matrix is the file `docs/gslides-parity/focus/core-matrix.json`; the table of 6.4 is rendered from it and the file is the source when the two differ. Every row records what production did on 2026-09-15 ("Today on production") and names the audit row or the file that saw it; a row the audits measured carries its time bound in the interaction text, so the pass criterion is fixed before the run and not chosen after it (5 s for a picture to land, 5 s for a listing, 5 s three of three for collaboration, 20 s for a comment, 30 s for a download).

### 6.1 What drives a row

- `probe --core`: `scripts/probes/editor-walk-probe.mjs` gains a `--core` flag beside `--base`, `--json`, `--shots`, `--quick` and `--headed` (lines 52 to 66). In `--core` mode a `step()` call that proves a matrix row carries the row's id as a tag (the `record` and `step` helpers at lines 78 to 104 gain the tag and write it as `id` in the JSON row); an untagged step is a setup step and runs as today. When a setup step fails, every later tagged step that depends on it is recorded as not driven with the reason "setup failed: <step>", and the run exits 1 (the cascade `audit-arrange` section 1 records, where run 3's rows after the paste row failed because the stage held another slide, becomes a not driven reason and a failed run, never a false failure of the dependent rows). A matrix id whose driver is `probe --core` and for which the run finds no tagged step is a failure of the run ("no step" exits 1), not a not driven row. The exit code is 1 when any tagged step fails or is not driven, unless the row's feature is in the ship's committed parked list (6.2). The walk keeps its human pace, its scratch deck from `/new` and its `finally` block (File > Move to trash, Delete forever, the 404, lines 3164 to 3243).
- `core/<area>.spec.ts`: Playwright specs under `apps/studio/e2e/core/`, run from the repository root with `PLAYWRIGHT_BASE_URL=<origin>` so the config defines no web server (`playwright.config.ts` 19 to 20 and 34 to 36), one worker (27), retries 0 (28), viewport 1440 by 900 (32). These carry the rows the probe cannot drive in one tab: the file chooser and the clipboard picture (`core/images.spec.ts`), two browser contexts (`core/share.spec.ts`, `core/present.spec.ts`, `core/slides.spec.ts` for the two tab paste), files checked on disk (`core/export.spec.ts`), the list and trash surfaces (`core/decks.spec.ts`) and the switch (`core/surface.spec.ts`). The rules for a core spec, so that it runs against production as written: no import from `node:fs` except to read a file the browser downloaded; no deck seeded from disk or from a fixture; no environment variable read other than `PLAYWRIGHT_BASE_URL` and `VERCEL_OIDC_TOKEN`; every observation through the page, `window.turboslide.studio.describe()`, the network and the download; every deck created from `/new` by the test itself and torn down in `afterEach` and in a `finally` through File > Move to trash, Delete forever on `/decks/trash` and a 404 check on `/edit/<id>`. The existing specs are not the pattern: `apps/studio/e2e/home.spec.ts` 272 to 338 reads the manifest from disk (`manifestOf`, `existsSync(join(DECKS, ...))`), `present.spec.ts` 16 to 45 seeds `decks/e2e-present` from a fixture, and `share.spec.ts` 24 decides its refusal rows from the runner's own `TURBOSLIDE_AUTHORIZE`; a core spec observes the production it is pointed at and nothing else. No spec clicks Empty trash (`audit-decks` row 54) or touches a deck it did not create. A setup write through the window API (the matrix's `setup` field: `block.insert` of a parked block, `deck.set` of the appearance) is made before the driven steps and is never counted as one.
- On a preview the probe and the specs send `VERCEL_OIDC_TOKEN` as `x-vercel-trusted-oidc-idp-token` (the probe's line 66); on production they send nothing. Under `.turboslide/e2e.lock`, one run at a time.

### 6.2 Acceptance

- The parked list is committed before the runs: `docs/gslides-parity/focus/ship-<commit>.json` with `{ "commit": "<sha>", "parkedFeatures": [...] }`. A run exits 1 when any core id is failed or not driven unless its feature is in that list; the `surface` feature cannot be listed.
- Before a ship, every core row of every feature not in the parked list passes on the preview built from the ship's commit and on production after the alias moves. A row with several checks (the eight handles, the two theme colours, the two decks of the card paste) passes only when every check passes.
- The run ledger: the ship note lists every run started against the preview and against production on the ship's commit, with its start time, origin, commit, deck id, counts and JSON path; no run is left out. A row passes only when it passes in the last run of each origin. A rerun happens only after a code change, named by its commit, or with a reason written in the ledger; a row that fails in one run and passes in a later run on a fresh deck with no code change between them is flaky and fails the ship. `retries` stays 0 (`playwright.config.ts` 28), no core spec calls `test.describe.configure({ retries })`, and the report's retry count is asserted to be zero. This is what closes the gap the audits saw between decks and runs (`audit-images` row 6 passed on two decks and broke on `3fma`; `audit-present` row 31 delivered in 2.4 s in run 2 and lost three edits in run 3; `audit-decks` row 37 failed three times on one card and passed on a fresh one).
- Not driven rows are listed in the ship note by id and reason and are never counted as passed; the ship note's parked list is rendered from the run's JSON by feature.
- `node scripts/probes/new-write-probe.mjs --base <origin>` and `node scripts/hosted-smoke.mjs <origin>` keep running as they did for hotfix 4 (`hotfix-4.md` section 3.8).

Every feature in the default view is driven end to end against the production deployment before a release, at human speed, and the release note carries the table of what passed. Features that are not yet tested that way are behind Tools > Advanced tools and are documented as advanced.
