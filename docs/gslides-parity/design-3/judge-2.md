The winner is proposal 3. The three proposals share one skeleton, because all three take report 02's operation stream, report 08's comment sidecar, report 09's access record, report 03's identity plan and report 06's dither field. What separates them is what they do at the seams I own. Proposal 3 adds two mutation ops and leaves `text.replace` alone; proposals 1 and 2 change the meaning of `text.replace`, and section 1 shows that this breaks the replay of every stored text record. Proposal 3 also names the storage migration as a procedure with a dual read window, lists the dependencies the integrator must add to the catalog, fixes the day one seams as types, and assigns files without overlap. Its weaknesses are scope (about 64 actions and a live storage migration in nine days), an integrator who owns the wiring of a 3,818 line route, a stale precondition about the MCP buffer, and a design written for engineers where proposal 2 writes for the rep.

## 1. What I verified in the code

The scores rest on these facts. Each names the file and line at `61b16e4`.

1. `text.replace` ranges are markup offsets. `packages/schema/src/mutations.ts:43` documents the op as "range is [start, end) in the markup string at `path`". The editor computes the range with `textDiff(from, to)` over two markup strings (`packages/viewer/src/InlineText.tsx:328-336`). `text.style` and `insertAt` use plain text offsets (`packages/schema/src/text.ts:495-500`, `:578`, `:645`). Two offset systems exist, as report 02 1.1 says.
2. The stored inverse of `text.replace` is a whole string replace in markup offsets. `packages/schema/src/reduce.ts:326-334` returns `{ op: 'text.replace', range: [0, next.length], text: current }`, where `next` and `current` are markup strings. Every version record since round one carries inverses of this shape.
3. Version history is rebuilt by replaying those inverses. `packages/store/src/versions.ts:146-170` (`documentAtVersion`) applies `record.inverse` of every later record, newest first, through `applyMutations`; the header at lines 3 to 5 says no snapshot is stored for this purpose and the chain must be contiguous. `version.restore` and the History panel read this function.
4. The Blob mirror replays forward records through the same reducer. `packages/store/src/blob-store.ts:443-455` applies every record above the base with `applyWrite` and the record's own `createdAt`, and it is the path `deck pull` and the proposed `deck follow` reuse.
5. Consequence for proposals 1 and 2. Both change `text.replace` ranges to plain text offsets (proposal 1 section 1.4, proposal 2 section 1.3) and both repeat report 02 3.3's sentence that "records already written keep their meaning because a record's mutations are replayed against the document as it was". The reducer, not the record, interprets the range. A stored inverse `[0, markupLength]` replayed under plain offsets throws the `RangeError` at `reduce.ts:318` whenever the markup is longer than its plain text (any run with a mark), and where the lengths agree the stored `text` (markup) is inserted as plain characters, so `*bold*` becomes six literal characters. `documentAtVersion` fails with "Cannot undo version n" for every deck with a text edit in its log, the Blob replay breaks on the same records, and `packages/store/src/versions.test.ts` and `file-store.test.ts` go red. Proposal 3 section 2.1 saw this and adds `text.splice` and `text.mark` as new union members, leaving `text.replace` as a whole value write at admission. That is the only one of the three that keeps the version log replayable, and it is the reason for the four point gap on architecture fit.
6. The hosted asset write defect is where report 10 F49 puts it. `apps/studio/src/server/actions.ts:507-508` opens the hosted `deckStore` and the plain `storeFor(deckId)` FileStore; line 567 passes the FileStore to `registerAssetActionsLazily`, so twins and the `asset.set` record land in one instance's mirror and never on Blob. All three proposals fix it on day one with `DeckStore.putAsset`; proposal 3 names the line.
7. The window transport already has a server side path. `apps/studio/src/server/agent-actions.ts:39-50` lists ten `SERVER_SIDE_WINDOW_ACTIONS` that run through `runDeckAction`. Proposal 3 section 1.6 extends this list by name; proposals 1 and 2 say "server side through `runDeckAction`" without naming the list. All three are correct; proposal 3 is the one a builder can act on.
8. The action table holds 105 ids (`packages/schema/src/actions.ts:99-205`), and an entry carries `group`, `mutates`, `transports`, `milestone`, `input`, `output`, `cli`, `mcp` and `example` (`:85-97`). `Milestone` ends at `GS2` and `ActionGroup` at `studio` (`:57-70`). Proposal 3's "105 to about 169" matches; proposal 1 adds 46 and proposal 2 about 70.
9. The MCP stdio buffer finding is closed at this commit. `VERIFICATION-2.md` section 14 records that the ship step closed finding 16 with 13: `tools/list` is served at 1.46 MB for 88 tools, and `apps/cli` `mcp.test.ts` carries the budgets. Proposal 3 decision 0.24 treats it as open; the precondition is stale but costs nothing. Neither proposal 1 nor 2 mentions the budget test that 46 to 70 new tools must pass.
10. Check step 21 has never run green. `VERIFICATION-2.md` finding 28 records that the round two Playwright specs of step 21 fail or do not run on the merged tree. `scripts/check.mjs:131-133` lists fifteen specs in that step. All three proposals add five or six specs to it and none makes step 21 green first.
11. `apps/studio` has no vitest project. `vitest.config.ts` at the root lists `packages/*`, `apps/cli`, `apps/render-worker` and `scripts`; its comment says the studio is covered by Playwright only. Proposal 3 puts the room client in `apps/studio/src/sync/**` "under the apps/studio vitest project the integrator adds", which is one config change; proposals 1 and 2 give the sync client no unit test home at all.
12. `jsdom` is a devDependency of `packages/chrome` and `packages/agent` only (`pnpm-workspace.yaml:42`, the two `package.json` files). All three run DOMPurify through jsdom in the admission path of the studio function; proposal 2 risk 13 is the only one that names the bundle cost.
13. The function rules. `apps/studio/vite.deploy.config.ts:128-132` sets a 300 s catch all and the 800 s, 3,009 MB `HEAVY` rule on `/api/export/**`, `/api/render/**` and `/_serverFn/**`. Proposal 3 section 2.3 places the stream routes on the catch all rule, which is right; the other two say the same in fewer words.
14. The rest of the shared skeleton checks out: the editor takes a ten minute lease (`packages/store/src/lease.ts:2`, `:92`); the session registry lives on `globalThis` (`apps/studio/src/server/sessions.ts:21-29`); the CSRF filter is `handlerType === 'serverFn'` (`apps/studio/src/start.ts:15`); `Author` is `{ kind, name, runId? }` with no principal (`mutations.ts:80`); the MCP server declares `resources: {}` without `subscribe` (`packages/mcp/src/server.ts:109`); `packages/effects` exports `two-tone`, `png1`, `bayer`, `tone`, `resample` and `pipeline` and imports `sharp` only in `io.ts`, so a browser safe `ditherPicture` beside them is feasible.

## 2. Proposal 1, Google faithful

Fidelity 9. This is the fullest Google surface of the three: the Follow stops and refusals as Google lists them, the four comment display modes and every chord, the three notification levels, Publish with Stop publishing, Transfer ownership with accept and decline, the version history rows, Activity with the comment trend, and the ephemeral chat. It marks each unverified Google fact where it uses it and lists them for Kevin.

Ease for sales 7. The click by click trace (section 9) is good and the presence slot, inbox plate and Share dot are in Google's positions. Two things cost it: comments are shown to viewers as Google shows them, so a prospect on a view link can read the manager's review thread unless the rep resolves or deletes it first; and the defaults claim ("Bayer 8 by 8, ink and paper, cell 2, strength 100" reproduce the GT look) is true for the pipeline's identity and not for a fresh photograph, whose GT treatment used black 0 to 140, white 210 to 235 and gamma 0.8 to 1.2 (report 06 1.3). Chat adds a surface a sales team did not ask for.

Architecture fit 5. The skeleton is right: the stream in front of the log, the checkpointer, two level acknowledgement, the sidecar, `authorize()`, `VersionRecord.ops`. The `text.replace` change of section 1.4 breaks `documentAtVersion` and the Blob replay (section 1 item 5), and the proposal asserts the opposite. Kill switches live in Vercel Global Config, a product beside Blob, Redis and Postgres. The file split puts `packages/store/src/**` on B1 except `blob-vercel.ts` on B6, while the two store split and `putAsset` span `blob-store.ts` and `blob-vercel.ts` together. B4 owns the 3,818 line edit route, the viewer overlay, the dither runtime and every layout shift fix in the routes at once.

Security 8. The plan of reports 04 and 10 is applied step by step with the WAF table, the per identity quotas, the three layer `html` block fix, the sandboxed frame in the standalone file, `safeFetch` with pinned DNS, the widened CSRF filter, the nonce CSP, the two stores under unguessable keys, structured logging and retention. It does not carry report 10 F47 (a per page nonce and a fresh session for share changes over the window transport) or the signed thumbnail URL of report 04 F6, both of which proposals 2 and 3 carry.

Buildability 5. About 438 agent hours plus an integrator and a verifier, with a cut line whose first entries are chat, the trend bar, `version.delete` and two avatar tabs. The `text.replace` change alone turns `packages/store` red on day three and forces a rework the plan has no time for. The proposal names no dependency additions for the integrator, gives the sync client no unit test home, and does not mention the MCP budget test that 46 new tools must pass.

## 4. Proposal 3, architecture first

Fidelity 8. Google's positions are kept for presence, Follow, the filmstrip marker, the caret and pointer, the comment card, panel, anchors, reactions, assignment and shortcuts, View > Live pointers and View > Mode, Notification settings, Activity, Publish to the web, request access, invitations and transfer. Chat, Q&A and Approvals are round four. The Photograph preset is Turboslide's own and is marked as such.

Ease for sales 8. The Photograph preset (black 120, white 230, gamma 0.9, the middle of the recorded ranges) is the honest one click GT look for a real photograph, where the other two proposals promise it from the identity LUT. The traces of section 10 cover the same five moments as proposal 2's. The offline design ("3 unsaved changes from this browser; Apply or Discard") is the best of the three for a rep on hotel wifi. What it lacks is proposal 2's discipline about where sign in appears and the fixed refusal sentences.

Architecture fit 9. Four truths with one owner each, and a sentence for what each never touches (the room never enters Blob or an export; identity is resolved at render time). The two new ops are additive, so `MUTATION_OPS` grows to seventeen and every stored record, `documentAtVersion` and the Blob replay keep working (section 1 items 1 to 5). `packages/realtime` is a framework free package with the key builder, the Lua script, the three implementations and a `protocol.ts` of zod schemas. `SERVER_SIDE_WINDOW_ACTIONS` is extended by name. The storage migration is a procedure: `meta.json` with `layout: 'v2'` and a cursor, `overwrite: false` copies with etag checks, an `assetKey` per deck, one `asset.set` per deck for the rewritten twins, a dual read window, batched deletes off the request path, a rollback flag before cutover, and the seed path writing private from the start. Kill switches are Redis keys with no third product. `deck follow` reuses the `pull()` replay path. Two warts: `preset` is stored on the block, which is derived state that goes stale after one slider drag; and the integrator owns the edit route, so the largest client wiring job sits with the person who also runs the merges.

Security 8. The same plan with a few additions the others lack: a cancel token minted with the export job, the download token spent set in Redis, the signed thumbnail URL, F47's nonce, a 16 MB per deck per minute admission budget, and risk 6, which says plainly that restricted decks stay readable from the public store until the cutover and orders the cutover before enforcement is announced. Two gaps: kill switches in Redis need a default table for the moment Redis is unreachable (`realtime` reads as off and falls to the `blob` tier, everything else reads as on), and jsdom's presence in the function bundle is not named.

Buildability 8. The day one seams are enumerated as types and files (the schema fields and ops, `RealtimeChannel` and `protocol.ts`, `authorize()` and `resolvePrincipal()`, the chrome contract in `editor-shell.ts`, the renderer's DOM classes), so five builders can type against them from day two. The catalog additions are listed for the integrator (`better-auth`, `@simplewebauthn/*`, `resend`, `ioredis` or `redis`, `@upstash/ratelimit`, `dompurify`, `kysely`, `pg`), which AGENTS.md requires. Ownership is disjoint across `apps/studio/src/server`, `apps/studio/src/routes`, `packages/render` and `packages/chrome`; I found no two builders on one file. The rollout R0 to R8 names dependencies and a verification per step, and R6 (sign in) and R7 (dithers) can land after R5 without blocking each other. The `mcp.test.ts` budgets are named. The costs: no hours estimate and no cut line, a live storage migration inside the round, and the edit route on the integrator.

## 5. Why proposal 3 wins from this seat

The three proposals agree on almost everything a user sees. The differences that decide a round from the store's seat are whether the version log stays replayable, whether the storage migration is a procedure or a sentence, whether the builders' files overlap, and whether the check chain stays green while about 60 actions land. Proposal 3 is the only one that passes the first test, the only one that writes the migration as steps with a rollback, the cleanest on ownership, and the only one that names the MCP budgets and the dependency list. Proposal 2 is the better product document and proposal 1 the better Google document; both must be grafted onto 3, not the other way around, because the graft direction that keeps the version log intact is the one that starts from 3.

## 7. What must not ship

1. The change of `text.replace` ranges from markup offsets to plain text offsets (proposal 1 section 1.4, proposal 2 section 1.3, report 02 3.3). It breaks `documentAtVersion` (`packages/store/src/versions.ts:168`) and the Blob replay (`packages/store/src/blob-store.ts:443-455`) for every stored text record, and the sentence that records keep their meaning is false because the reducer interprets the range. The synthesis takes proposal 3's `text.splice` and `text.mark`.
2. Kill switches in Vercel Global Config (proposals 1 and 2). A fourth product beside Blob, Redis and Postgres for eleven booleans; the synthesis takes Redis flags with a defaults table, or a committed flags document on a checkout.
3. Pending operations kept in memory only (proposal 2 section 1.7). A tab closed while offline loses its queue. The synthesis takes proposal 3's IndexedDB record with Apply or Discard on the next open.
4. The chat panel in this round (proposal 1). An ephemeral message channel with its own abuse surface and no store home; proposals 2 and 3 defer it and proposal 1's own cut line cuts it first.
5. The claim that the identity defaults (black 0, white 255, gamma 1) reproduce the GT deck's photograph look (proposals 1 and 2, sections 7.6 and 7.7). They reproduce the pipeline's identity; the deck's photographs were toned at black 0 to 140, white 210 to 235 and gamma 0.8 to 1.2. The synthesis ships proposal 3's Photograph preset and says what the defaults are.
6. Ownership overlaps: proposal 1's split of `blob-store.ts` (B1) from `blob-vercel.ts` (B6) across the two store change; proposal 2's `ToolbarTail.tsx` on B3 and B6 and `write.ts` shared by B1 and B2; proposal 3's edit route on the integrator.
7. A stored `preset` field on the picture block (proposal 3 section 8.1). Derived state on the document goes stale after one slider drag.
8. Five or six new Playwright specs added to check step 21 as it stands (all three). Step 21 has never run green on the merged tree (VERIFICATION-2 finding 28). The new specs join as their own numbered step with their own green requirement, and finding 28 is a separate fixer item, so a round three regression is distinguishable from a round two one.

## 8. Risks none of the three prices

1. The admission path loads the document at the last checkpoint and applies the stream since it "cached per instance by seq". On a cold instance that is a Blob read of `deck.json` and the touched slides plus up to 10,000 stream entries before the first transform. All three assume a warm instance; the preview run of report 02 7.12 must measure the cold case and the synthesis must state a cap on entries applied per admission.
2. The checkpointer coalesces "consecutive `text.splice` on one run into one splice" (or `text.replace`). When two authors interleave in one Text within one checkpoint window the coalescing must stay per author and per contiguous run, or the version record's inverse no longer undoes what that author did. Proposal 3's checkpointer test on a recorded typing session should include an interleaved session.
3. `comment.shift` entries are emitted by the server after a text op moves an anchor (all three). On the `blob` tier and on a checkout the shift runs inside `FileStore.write` under the lock; on the `redis` tier it is a second stream entry. The two tiers must produce the same thread file bytes for the same edit, and no proposal names that test.
4. The `open: editor` synthesis for a missing access record is today's behaviour and stays until a claim. All three accept it. The month between R4 and R8 in which anyone with a deck's address can still edit it should be on Kevin's decisions list with a date, not only in a risk row.
