# Layout shift audit and fix plan

Report 05 of the Turboslide round three research, written 2026-09-13 against the repository at commit `61b16e4`. It answers the fourth directive's "address all layout shifts": it names every source of layout shift the code can produce on `/new`, `/edit/:id`, `/deck/:id` (and `/embed/:id`, the same viewer), `/decks`, `/decks/trash`, `/present/:id`, `/print/:id` and the slideshow, in both appearances and at 1440, 1280 and 390 CSS pixels wide, gives the fix for each, and designs the Playwright measurement the verifier runs so the gate is a number and not an opinion.

Method: the routes, the chrome, the viewer, the fonts package, the theme's stage and sheet CSS, the renderer's image emission and the materials mount were read as source; no dev server was started and nothing was measured in a browser, as the task rules require. Every "counts" or "does not count" verdict below follows from the Layout Instability specification and the web.dev articles cited in the Sources section, applied to the CSS and the mount order the code shows. Where a verdict depends on a browser detail the pages read do not settle, the row says so and the Unverified section repeats it. Arithmetic on scores uses the formula in section 1 and the token sizes in `packages/chrome/src/tokens.css`; the numbers are estimates for ranking, and the verifier's script replaces them.

Rules followed: plain technical English, sentence case, no em dashes, no metaphors, no trailing periods on headings. Google Slides is named as the reference behaviour only; no Google artwork is reproduced. Every web source is listed with its URL and the date read (2026-09-13).

## 1 How layout shift is measured

### 1.1 The metric

Cumulative Layout Shift is "a measure of the largest burst of layout shift scores for every unexpected layout shift that occurs during the entire lifecycle of a page" (S1). A burst, the session window, is "one or more individual layout shifts occur in rapid succession with less than 1-second in between each shift and a maximum of 5 seconds for the total window duration" (S1); the web-vitals library implements it as `entry.startTime - lastSessionEntry.startTime < 1000 && entry.startTime - firstSessionEntry.startTime < 5000`, skips every entry with `hadRecentInput`, and reports the largest session's sum (S9, S10). The threshold is 0.1 at the 75th percentile of page loads (S1).

One entry's value is `impact fraction * distance fraction` (S1): the impact fraction is the area of the union of every unstable node's previous and current visual representation divided by the viewport area, and the distance fraction is the largest move divided by the viewport's larger dimension, capped at 1 (S3). The visual representation excludes "any points that lie outside of the viewport" (S3), so an element that moves while off screen costs nothing.

### 1.2 What counts and what does not

- A node is unstable when its starting point moves by the significance threshold or more in either axis between two frames; Chrome uses 3 pixels (S3). Moves under 3 px never produce an entry, so a font swap that changes a word by 2 px is invisible to the API and only a screenshot or a frame sampler sees it.
- "If a new element is added to the DOM or an existing element changes size, it doesn't count as a layout shift, as long as the change doesn't cause other visible elements to change their start position" (S1). A fixed banner that appears, a snackbar that mounts, a dialog over a scrim: none of these count by themselves.
- Transforms do not count: the specification considers "the starting point both with and without transforms, to ensure that a node is not made unstable solely due to a transform change" (S3). `transform`, `opacity` and `visibility` changes are free; a node with `opacity: 0` or `visibility` other than `visible` is never unstable (S3).
- Scrolling inside a scroll container does not make its content unstable "solely because of a scroll operation" (S3). A size change of one item inside a scroller that moves its siblings still counts for the siblings that are in the viewport.
- `hadRecentInput` is true when the last excluding input was less than 500 ms before the shift; excluding inputs are "mousedown, keydown, pointerdown, and change events", and "the mousemove and pointermove events are also not excluding inputs" (S3); scrolls are not excluding inputs either. An event that "directly changes the size of the viewport" is an excluding input (S3), so a window resize or a fullscreen toggle is never charged.
- Shifts inside an iframe are not reported to the parent's observer but do count in the metric with a weight equal to the frame's share of the viewport (S1, S3). Turboslide's `/embed` route is such a frame inside Prototemplate.

### 1.3 Attribution

Each `LayoutShift` entry carries `value`, `hadRecentInput`, `lastInputTime` and up to five `sources`, each with `node`, `previousRect` and `currentRect` in CSS pixels (S3, S4). "If all properties of previousRect are set to 0 this means that the element has shifted into view" (S4). "The element that moved is listed as the source, but it's possible these elements are only indirectly related to the root cause" (S4): a pushed sheet is the source, the panel that pushed it is the cause. The web-vitals attribution build exposes `largestShiftTarget`, `largestShiftSource`, `largestShiftValue`, `largestShiftTime`, `largestShiftEntry` and `loadState` (S9).

### 1.4 Lab tools

- The observer: `new PerformanceObserver(cb).observe({type: 'layout-shift', buffered: true})` (S1, S4). Playwright runs it in headless Chromium through `page.addInitScript`, which evaluates "after the document was created but before any of its scripts were run", on every navigation and in every attached frame (S11). Several published Playwright recipes sum the entries this way (S13).
- Lighthouse: "Avoid large layout shifts" lists the shifting elements with their contribution and a best guess of the cause (unsized media, a web font, an injected iframe); "Image elements do not have explicit width and height" and "Avoid non-composited animations" are the two supporting audits (S5, S6). "Lighthouse can only identify layout shifts that occurred during the initial page load" (S4), so it cannot audit a driven state such as an open panel.
- Chrome DevTools: the Performance panel's layout shift track, the "Layout shift culprits" insight naming unsized images, injected iframes, unoptimized animations and web fonts, and the "Layout Shift Regions" rendering setting (S4, S7).

### 1.5 The fixes the literature prescribes

Reserve the space before the content arrives: `width` and `height` attributes on every image and video, or `aspect-ratio`, "each image should use the same aspect ratio" in a `srcset` (S2); `min-height` or `aspect-ratio` for late content, and "removing the space set aside for elements can cause just as much CLS as inserting content" (S2); insert late content only after a user interaction or below the viewport (S2). Animate with `transform`, never `top`, `left`, `width` or `height` (S2). For fonts: "font-display: auto, font-display: block, font-display: swap, and font-display: fallback all have the potential to cause layout shifts when the font is swapped" (S12); `font-display: optional` avoids the swap at the cost of not using a late font (S2, S12); `size-adjust`, `ascent-override`, `descent-override` and `line-gap-override` let a local fallback face take the web font's metrics so the swap moves nothing (S8); a preloaded font needs `crossorigin` or "fonts preloaded without the crossorigin attribute will be fetched twice" (S14); fonts named only in an external stylesheet "aren't discovered until the browser downloads and parses the CSS files" (S14). `content-visibility: auto` needs `contain-intrinsic-size` or off screen items lay out as empty and "the size of the scrollbar will shift" (S15). `scrollbar-gutter: stable` keeps the gutter when overflow appears, for classic scrollbars only; "when using overlay scrollbars, the gutter will not be present" (S16).

### 2.2 Fonts

`packages/fonts/src/inter.css` declares two faces, `Inter` upright and `Inter` italic, both `font-weight: 100 900`, both `font-display: swap`, from `InterVariable.woff2` (352 240 bytes) and `InterVariable-Italic.woff2` (380 904 bytes). The chrome stacks are `'Inter', 'Helvetica Neue', Arial, sans-serif` for `--pt-display` and `--pt-text` (`tokens.css`); the sheet uses the theme's `--display` and `--text` on the same family. There is no `<link rel="preload" as="font">`, no fallback face with adjusted metrics, and the `@font-face` rules live in an external stylesheet, so on a cold cache every text on every route renders first in Helvetica Neue or Arial and re-lays out when Inter arrives. In production the files are content hashed (`InterVariable-DiVDrmQJ.woff2`), so a warm cache renders Inter at once and the swap shows only on a first visit, after a deploy that changes the hash, or in a fresh Playwright context, which is the case the verifier measures.

### 2.3 The shell's geometry

`.pt-viewer` is `position: fixed; inset: 0; display: grid` with the sidebar track `var(--pt-sb-w)` (208 px in outline density, 256 px in thumbnail density, 0 while closed or narrow) and the main region `minmax(0, 1fr)` (`ViewerShell.css`). The editor adds five rows at token heights: 44, 28, 40, `1fr`, 32 (`EditorShell.css`), a third column of 0 or `--pt-panel-w` 320 px for the right panel, and the notes slot as the second row of the canvas column. `body[data-shell]` sets `overflow: hidden` once a shell mounts, so the document never scrolls under a shell. Every chrome scroll region that carries `.pt-scroll` reserves its gutter (`scrollbar-gutter: stable`, `tokens.css`). The stage is measured by a `ResizeObserver` and the sheet is placed by `fitSheet()` through inline `left`, `top`, `width`, `height` with the 1600 by 900 stage scaled by `transform: scale(k)` (`Sheet.tsx`); the sheet is `visibility: hidden` until the first measurement.

## 4 Rules for the round three build

The rows above reduce to nine rules. The multiplayer, accounts and dither surfaces of round three are new chrome, so they are listed against the rules before they exist.

1. Geometry state is known at first paint. On a client rendered route, read localStorage, `matchMedia`, `innerWidth` and the platform in `useState` initializers. On a server rendered route, stamp the saved geometry on `<html>` from the boot script and let CSS carry the unsettled frame (D1), or move the preference to the server (a cookie now, the account later; L1). No mount effect may change a grid track, a row height, a column width or a document order.
2. Every `<img>` the renderer writes carries `width` and `height` from the asset's `size`, and every CSS rule that fixes one dimension leaves the other `auto` (E12). A round three background picture is a picture object at the bottom of the stack with a fixed box, so it is already safe; its dither is drawn on a canvas over the same box, never a second element in flow, and the original stays in the DOM at the same size.
3. Fonts: preload both Inter files with `crossorigin`; ship a metric matched fallback face; the sheet paints once, in Inter (G1). No new face is added to chrome in round three; avatars use the display face at a fixed size.
4. Late content lives in fixed or absolute layers, or in a slot whose size is reserved. The presence avatars in the title row get a fixed slot (`--pt-presence-w`, sized for the maximum shown, with a "+N" overflow chip) that exists whether zero or five collaborators are present, so a collaborator joining moves nothing; live cursors and selection outlines are absolute overlays in the stage's overlay layer and the filmstrip's cards (a badge inside the frame's box); comment anchors are absolute markers; the comments panel is the right panel (E6's one frame refit); notifications are the fixed snackbar and a fixed activity plate; the request access and sign in prompts are dialogs over the scrim; the avatar builder is a dialog whose preview box has a fixed size for every stage of the builder.
5. Text whose width follows state has a fixed box: the save words (E5), the presenter's timer, clock and status (P2, P3), a collaborator's name flag (an ellipsized fixed width), the comment count chip (tabular figures with `min-width`), the version history's relative times (tabular, fixed width).
6. Placeholders for `content-visibility: auto` derive from the container width in `cqw` (E10); every new list (comments, activity, versions by author) that uses it follows the same rule or sets no placeholder and no `content-visibility`.
7. Every scroll region carries `.pt-scroll`; documents that scroll set `scrollbar-gutter: stable` (G2, L5).
8. A measurement that decides chrome geometry runs before paint (`useLayoutEffect`) on client routes and becomes CSS (container queries) on server routes when the content is deterministic (D2, E3). A structural move that a click causes (a panel, the notes pane, the filmstrip) lands in one frame together with the refit it forces (E6).
9. Motion is `transform` and `opacity` only; the sidebar track animation stays the one exception and stays behind `data-settled` (E14). The collaborator cursor moves by transform; a "follow" jump changes the active slide (an absolute swap) and scrolls the filmstrip (a scroll), never a track.

## 5 Measurement design for the verifier

### 5.1 What is measured and where

The gate runs against the production build served by `vite preview` (`pnpm --filter @turboslide/studio build` then `preview --port 4321 --strictPort`), never the dev server: in development Vite injects component CSS from JavaScript after the module loads, which is a flash of unstyled chrome that production does not have, and the dev shell mounts the TanStack devtools with a second `Inter` face (`__root.tsx`). The `pnpm check` runner already starts and stops a server on 4321 with the log capped and takes `.turboslide/e2e.lock` (AGENTS.md dev server rules); the gate joins it as a step after the build step (step 6) so `apps/studio/dist` exists, with `PLAYWRIGHT_BASE_URL` pointing at the preview when a builder runs it on their own port. The hosted deployment is measured the same way by pointing the base URL at `https://turboslide.vercel.app` in a separate, non gating run recorded in `VERIFICATION-3.md`, because the host's function cold start lengthens the `ssr: false` blank period (E1) and the Blob store's latency changes the thumbnails' arrival.

The deck under test is `decks/gt-brand` (85 slides, sections, grammar figures with pictures, a material slide), plus the fixture deck `decks/fixture/gslides` for the canvas objects, seeded the way `apps/studio/e2e/home.spec.ts` seeds its scratch decks.

### 5.2 The observer

`context.addInitScript` installs, before any page script (S11), one script that:

- opens `new PerformanceObserver(record).observe({ type: 'layout-shift', buffered: true })` and keeps every entry in `window.__ts.shifts` as `{ startTime, value, hadRecentInput, lastInputTime, sources: [{ path, previousRect, currentRect }] }`, where `path` is the node's tag, id and classes plus up to four ancestors (the same shape `web-vitals` uses for `largestShiftTarget`, S9), computed at record time because the node may be detached by the time the test reads it;
- marks `performance.mark('ts:first-paint')` from the first `requestAnimationFrame`, `ts:fonts` from `document.fonts.ready`, `ts:hydrated` when a `MutationObserver` sees `.pt-viewer[data-settled]`, `[data-hydrated]` (the list routes) or `.ts-presenter` (the presenter), and `ts:state:<name>:start` and `:end` when the driver calls `window.__ts.mark(name, phase)` around each state;
- runs a frame sampler for the first 4 s after navigation and during every state: on each `requestAnimationFrame` it records `getBoundingClientRect()` and, for the print stage, `getComputedStyle(el).transform` of a fixed anchor list per route (`.pt-main`, `.pt-sb`, `.sheet`, `.ts-title-clock`, `.pt-bar-r`, `.ts-rpanel`, `.ts-notes`, `.ts-home-page`, `.ts-recent`, `.ts-presenter-stage`, `.ts-print-sheet .ts-stage`), so sub 3 px moves and transform only jumps (R1), which the API never reports, are caught, and so a pre hydration frame's geometry is known even though the API's `sources` cannot name the cause.

The script never touches `hadRecentInput` semantics: the driver's own clicks and keys are real Playwright input and set the flag, which the metric ignores (S1, S3); the gate therefore uses its own marks, not the flag, to decide which entries belong to which state.

### 5.3 The sessions and the numbers

For each run the script computes, from the recorded entries:

- `loadCls`: the web-vitals session algorithm (entries with `hadRecentInput` false, grouped while `start - last < 1000 && start - first < 5000`, the largest sum; S10) over the entries from navigation to `ts:hydrated` plus 3 s of idle; this is the number Lighthouse and the field would report;
- `loadEntries`: every entry in that window regardless of the flag, with sources, because a shift the flag excludes at load is still a defect when no rep has touched anything (the driver has not either; any flagged entry at load is a bug in the flagging or the test);
- per state `stateEntries`: every entry between the state's start and end marks, flagged or not, with its sources; the state's declaration in the script lists the sources it expects (for `panel`: `.sheet`, `.pt-main`; for `filmstrip`: `.sheet`, `.pt-main`, `.pt-sb`; for `notesOpen`: `.sheet`, `.ts-notes`) and the maximum number of frames in which entries may occur (1 for a cut, 14 for the 220 ms track animation);
- `fontEntries` and `imageEntries` for runs F and I: the entries whose sources are text containers or images, at load and in the states.

Gate: `loadCls === 0` and `loadEntries.length === 0` for every route, width, appearance and saved state variant; every state's entries have only expected sources and fit the frame budget; runs F and I report zero entries. The directive is zero measured shift, so there is no tolerance band; a row that a fix cannot remove (none is known) would need its own declared exception in the script with the reason.

- Routes: `/new`, `/edit/gt-brand`, `/deck/gt-brand`, `/embed/gt-brand` (and a local host page that frames it), `/decks`, `/decks/trash`, `/present/gt-brand`, `/print/gt-brand`, `/deck/gt-brand?present=1`.

### 5.5 Output and integration

The script (`scripts/layout-shift-audit.mjs`, `playwright-core` 1.62.1 from the root, run as `node scripts/layout-shift-audit.mjs --base http://localhost:4321 --out docs/gslides-parity/verification-3/layout-shift.json`) writes one JSON with a record per run (route, width, appearance, variant, network, `loadCls`, `loadEntries`, per state entries with sources and frame counts, the sampler's anchors with the frames where any rect changed), and a markdown summary table with the failing rows, each named by the audit id of section 3 through a source to id map in the script (for example a `.ts-title-clock` source in state `write` is E5). It exits non zero on any gate failure. `pnpm check` gains it as a step after the parity audit (step 20), with the same `needs: 'server'` handling; the builders run it against their own preview with `PLAYWRIGHT_BASE_URL` like the other specs.

Cross checks the verifier records but does not gate on: Lighthouse (`lighthouse <url> --only-audits=cumulative-layout-shift,layout-shifts,unsized-images,font-display,non-composited-animations --chrome-flags=--headless`) on the preview at 1440 and in its mobile preset, expected to list no shifting elements and no unsized images once E12 lands (S5, S6); a DevTools Performance recording with the "Layout shift culprits" insight for any failing row the JSON attributes poorly (S7).

### 5.6 What the design cannot do

The API does not report shifts inside a cross origin frame to its parent and Turboslide's `/embed` is same origin only when framed by a local host page; the Prototemplate host on another origin is measured from inside the frame with the frame as the page. Lighthouse measures load only. The frame sampler sees one frame in sixty; a shift that lands and reverts inside one frame is invisible to both the API and the sampler, which is acceptable because it is invisible to a rep as well. The gate runs in Chromium; Firefox and Safari have no Layout Instability API and are covered by the CSS reasoning of section 3 alone.

## 6 Unverified

- U1. Inter 4.001's vertical metrics and the `size-adjust` percentage against Arial and Helvetica Neue were not read in this session; `scripts/build-fonts.py` computes them from the shipped file and the test pins them. The report gives no numbers.
- U2. Whether Chromium charges a layout shift for an element clipped by an ancestor's `overflow: hidden` (the toolbar tail, E3, and the collapsed labels, D2). The specification clips the visual representation to the viewport (S3); none of the pages read states how ancestor clips are treated. Run B and the frame sampler settle it empirically.
- U3. Whether a React state update made inside a `ResizeObserver` callback paints in the same frame as the layout that triggered the observer (E6's one frame refit). The pages read do not cover React's scheduling; the frame sampler measures it.
- U4. Whether `calc()` may divide a length by a length to yield a `<number>` in the shipping Chromium (the CSS fit for D3 and R1). Not confirmed from a page read in this session; the inline script fallback does not depend on it.
- U5. Whether TanStack Start injects every route chunk's CSS into the server rendered head, so the server frame is fully styled (no flash of unstyled chrome on `/deck` and `/decks`). The built output has per chunk CSS files; run B (JavaScript blocked) versus the hydrated frame settles it.
- U6. Google Slides' own behaviour for the title row's save words slot, the canvas refit when Format options opens, and the filmstrip toggle's animation were not verified from a Google page in this session; they are named as the reference from product knowledge only.
- U7. The style Paper's `ShaderMount` gives the canvas it prepends inside the `.ts-material-live` wrapper over a picture; the wrapper is absolute with `overflow: hidden`, so a wrong canvas style cannot push flow content, but it could clip.
