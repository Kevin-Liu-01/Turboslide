## 2. Gaps

Ordered by weight.

1. **An unparkable feature carries a row the specification expects to stay flaky.** Section 2.1 writes of `realtime.share-link.every-instance`: "the row stays `flaky` in the matrix until the preview reads it green", and section 5.5 restates the acceptance rule from `docs/REALTIME.md` 5.5 and `docs/FOCUS.md` 6.2 (working copy 262 to 268): "every core row of every unparked feature green in the last run of each origin with `retries` zero; `realtime` and `setup` unparkable". A row that reads flaky on the preview fails the ship under that rule, and `realtime` cannot be parked. The specification names the one new mechanism (the refusal path re-read with `fresh: true`, 3.6.1 `access.ts` row) and says nothing about what the ship does when the row still reads red or flaky: hold the whole round, move the row out of `realtime` into a parkable feature, or change the rule. `design-a.md` section 8 left the row flaky and said so; `judge-3-operator.md` 2 item 7 said the working tree's `access.ts` must be re-read; neither resolved the acceptance conflict and the specification inherits it.

2. **The preview gate's recipe deploys the Worker before the URL it needs exists.** Section 5.5 item 2: "The integrator deploys the preview Worker once from the merged tree (`pnpm exec wrangler deploy --env preview --var TURBOSLIDE_APP_ORIGIN:<the Vercel preview url> ...`), then one Vercel preview with `vercel deploy ...`". The Vercel preview URL (`https://turboslide-<hash>-kl01s-projects.vercel.app`) is minted by that `vercel deploy`, so it cannot be a `--var` of a deploy that runs before it; and `TURBOSLIDE_APP_ORIGIN` is where the object posts `/api/decks/:id/checkpoint` and reads `/api/decks/:id/seed` (3.2, 3.6.2), so with the variable wrong no checkpoint lands and no realtime row can read green on the preview. The same ordering sits in 5.6 item 1 (the guard deploys the preview Worker "then the Vercel preview deploy as today"), and the guard makes one Vercel preview per push, each with a new URL, so the preview Worker must be re pointed per push or given a fixed target. The fix is one of: deploy Vercel first and the Worker second; a fixed preview alias on the Vercel project (which `docs/REALTIME.md` 4.6 lists as not done); or the Worker reading the app origin from the ticket's `org` claim per deck instead of a variable. None is written.

3. **The Worker's two control tables have no creation command and no seed.** Section 3.6.2 says `rt_open` and `rt_flags` are "created by the Worker's own migration on its first deploy, since the Worker reads them without the function" (4.2) and section 6 step 11 says "the Worker's own migration creates `rt_open` and `rt_flags`". A Worker runs no code at deploy; a migration is either `wrangler d1 migrations apply <db> --remote` from a `migrations/` folder (the command `design-b.md` 7 step 9 named and the specification dropped), `wrangler d1 execute <db> --remote --file <sql>`, or a `CREATE TABLE IF NOT EXISTS` on the first request through a guarded path. The runtime kill switch's hand fallback (3.8 item 1: `update rt_flags set v='off' where k='realtime'`) updates a row nobody inserts, and `/health` answers `realtime: 'on'` from a table that may not exist. Section 6 is the setup list and lacks the step; `realtime-env.mjs` has no `worker-migrate` subcommand in 3.6.1.

4. **The D1 hand row on localhost selects the `do` tier by accident.** Section 2.1, `accounts.google-roundtrip`: "first on `http://localhost:4321` with the real client against the preview Worker's D1 (`TURBOSLIDE_ACCOUNTS=d1`, `TURBOSLIDE_ROOM_HOST` the preview Worker)". By 3.6.1 (`select.ts`): "unforced, `TURBOSLIDE_ROOM_HOST` set selects `do` before the `REDIS_URL` check", so that local server would run its realtime channel against the preview Worker, whose `TURBOSLIDE_APP_ORIGIN` is a Vercel preview and whose checkpoint callbacks cannot reach `localhost:4321`. The recipe needs `TURBOSLIDE_REALTIME=memory` forced, or the accounts host split from the room host; the specification shares one pair (`TURBOSLIDE_ROOM_HOST`, `TURBOSLIDE_ROOM_BEARER`) between the channel and the database (4.2) and does not say so here. The same pair also means `do` forced "without both variables" (3.6.1) checks the host and the secret and not the bearer the function's every call to the Worker carries (3.3).

5. **The wake path rebuilds the whole document before a presence frame.** Section 3.2, "A wake after a pause": "the frame wakes the object (the constructor runs again) -> read the meta row, the doc rows (one per slide, 20 to 80 rows), the entries above covered -> rebuild the live document in memory -> admit the frame", and 3.4 item 7 says the constructor "rebuilds the live document and the roster ... and admits". A caret move or a slide change after a pause of more than 10 s is a presence frame that needs no document, yet pays 20 to 80 rows read and the JSON parse of a document of up to 25 MB (`CAPS.deckMaxBytes`, `admission.ts` 37) before it fans out, which is on the path of `realtime.caret.within-300ms`. `design-b.md` 2.4's last paragraph had the rule the specification grafted elsewhere and dropped here: "a woken object rebuilds its live document ... before it admits the first op after the wake, while presence, joins and the hello need no document and run at once". The specification should carry it, with the rebuild deferred to the first `ops` frame or the first `/document` read.

6. **The Worker request ceiling undercounts the D1 proxy.** Section 2.2, `cost.worker.requests`: "at most 60 requests to the Worker from one tab and its instance (2 connects, the HTTP belt, 6 function calls, at most 15 D1 proxy calls)". Section 4.1 says the proxy dialect "posts one compiled statement per `executeQuery`", a cache miss "costs 4 to 5 sequential statements on a loader", and "at most about 12 misses an hour per instance reach D1". Twelve misses at four to five statements each are 48 to 60 `/db/query` calls an hour per signed in session per instance, not 15, before the first instance of a deployment's boot migration check (one `/db/query` per cold instance, 4.2) and the migrations themselves ("a few dozen statements once"). The per day total still sits far under 100,000 at 50 editor hours, so no verdict changes, but the row's ceiling as written would hold the ship on a correct reading of the counters, and the fix is either the ceiling raised or the miss's four to five reads folded into one `/db/batch`, which 4.1 does not choose.

7. **The `/document` read on an object with no `doc` rows is unspecified.** Section 3.2's join flow has the loader `GET https://<worker>/rooms/<deck>/document (bearer, 2 s deadline) when the object answers, else store.read()`, and 3.4 item 7 says `doc` rows are dropped at the last socket's close. A loader on a deck nobody has open reaches an object with no rows; whether the object answers "no document" (so the loader reads the store itself) or itself reads the seed route first (a Vercel invocation nested inside a Vercel invocation with a 2 s deadline) is not written. 3.2 says the seed read happens "before any hello", which does not cover a `/document` GET.

8. **`version.save` is given two paths.** Section 3.4 item 8 keeps "the at once trigger for an agent write, `version.save` and the last socket's close", while 3.5 lists "`deckDispatcher`'s `version.save`" among the "Vercel code path[s] that write the manifest outside the checkpoint route" and call `POST /rooms/:id/external`. Both may be true in sequence (a flush through the object, then `saveVersion`'s own manifest write, then `/external`), and the order is not written; as it stands the two sentences describe different mechanisms for one action.

9. **The moved transport is more than an import line, and two sections disagree who asks.** Section 3.6.3: "`sseTransport` moves there from `controller.tsx` 325 to 466 by one import line the integrator lands at R3's request, since `controller.tsx` is R3's"; 5.1 R3 and 5.3: "the one import line for `transport.ts` is the integrator's at R2's request on day 0". The move deletes about 140 lines from R3's file (`controller.tsx` `HEAD` 325 to 466), which belongs in the integrator's seam commit beside `room-core.ts` and is not listed there (5.1's integrator paragraph names the seam commit as "the move into `room-core.ts` with re-exports").

10. **A risk the judges carried and the specification dropped: the isolate's memory.** `design-b.md` 10 item 4: "A Worker isolate holds 128 MB shared by the objects in it (W1 section 2's in memory state page), and this design holds a deck's document in the object's memory, up to the 25 MB cap; a picture heavy deck's JSON parsed as objects may be several times its byte size." The specification holds the live document in memory (3.6.2) and names no memory risk; `research-workers.md` section 1 quotes "Each isolate can consume up to 128 MB of memory" and the in memory state page as W1 cites it says memory is "measured per isolate (which can host multiple Durable Objects), not per object". Several open decks on one isolate is the case to name, with the preview's large deck row as the measurement.

11. **The security document's scope for the bearer SQL route is not named.** `POST /db/query { sql, params }` and `/db/batch` run any statement under `TURBOSLIDE_ROOM_BEARER` (3.6.2), the same secret that authorizes `/rooms/:id/write` and the object's checkpoint posts. One leaked value is the whole account database and every deck's order. Section 5.2 gives R4 "`docs/security.md` section 12's text" and R6 the table, with no sentence about what section 12 must say of this route (an allowlist of statement shapes, a separate bearer for `/db/*`, or the acceptance of one secret with its rotation runbook).

12. **Smaller omissions in section 6.** No `wrangler whoami` after step 7 to confirm the CLI is logged into the account Kevin named (W1 6.2 names the command); no `.dev.vars` or local D1 step for 5.4 (the local e2e second mode reads the OTP from Miniflare's D1 with `wrangler d1 execute --local --json`, which `design-b.md` 4.7 named and the specification's 4.3 gives only for `--remote`); no step that seeds `rt_flags.realtime = on` (item 3); the `database_id` of the preview database into the `env.preview` block is implied by step 9 and not written as its own line.

## 4. Asserted without a source, or with a source that does not say it

1. **The object's CPU limit per request on the Free plan.** The specification runs the reducer, the validator and the transform in the object (3.3) and parses a document of up to 25 MB on every wake (3.4 item 7) and never states the object's CPU budget. `research-durable-objects.md` section 2 quotes the Durable Objects limits page: "CPU per request: 30 seconds (default) / configurable to 5 minutes", with no plan column, while the Workers Free plan's "10 milliseconds of CPU time per invocation" (W1 1.1) is the Worker's row. Whether the Free plan's 10 ms applies to an object's request was read on no page the notes cite. `design-b.md` 10 item 3 named the question; the specification drops it. If the 10 ms applied to the object, the admission of a large deck and every wake would be over it and the Paid plan would be forced on day one; it belongs in section 1.3's list of facts that force Paid, as an open item with the day 0 probe that answers it.

2. **Point in time recovery of 30 days on the Free plan.** 3.9: "the storage API's point in time recovery covers 30 days (W1 section 2)". W1 quotes https://developers.cloudflare.com/durable-objects/best-practices/access-durable-objects-storage/ line 64 ("to any point in time in the past 30 days") with no plan qualifier; D1's Time Travel on the same account is "7 days (Free)" against "30 days (Workers Paid)" (`research-d1-auth.md` 1.1). Whether the object's 30 days hold on Free is unread.

3. **`serializeAttachment` writes cost nothing.** 3.2 and 3.3 rewrite each socket's attachment on every durable presence frame (a slide or selection change) and the cost rows count zero rows written and zero storage for it. W1 section 2 quotes the size cap (16,384 bytes) and nothing about billing; no page cited says whether an attachment write is a row written, a storage byte or free.

4. **"the dashboard has no API the pipeline reads this round"** (2.3, `setup.free-plan.caps`). Written as a product fact inside a driver cell; no note read Cloudflare's analytics API, so the sentence should say that none was read, not that none exists.

5. **The sign in callback's added latency is not carried.** 4.1 says a cache miss costs "4 to 5 sequential statements on a loader" and that one Worker hop plus one D1 statement is unmeasured (W2 open 1). `read-auth.md` 4.2 counts about 15 sequential statements inside the Google callback and prices them: "a remote database at L ms per statement adds about 15 × L to the callback: 75 ms at 5 ms, 450 ms at 30 ms, 1.5 s at 100 ms". With W2 1.3's measured floor of 50 to 116 ms from this machine to the API edge, the callback carries 0.75 to 1.7 s of added wait on the proxy dialect, which 4.1 does not say and `accounts.google-roundtrip` has no bound for.

6. **The 10 to 30 ms frame and 125 to 165 ms keystroke figures** are labeled as `research-options.md` 5b's estimate with no first party number (W1 section 5), which is right; they are listed here because 2.2's `cost.do.duration` ("1,584 handlers at about 2 ms", "144 checkpoint waits at about 0.7 s") and the break day arithmetic rest on the same unmeasured handler and commit times. The preview row replaces them, as the specification says.

7. **The 4 wakes per editor hour** of `cost.do.duration` (2.2) and section 1.3: `design-a.md` 6 said 4, `design-c.md` 6.1 said 12, `design-b.md` 6.1 said about 20. With presence frames arriving whenever either person moves after a pause over 10 s, 4 is the smallest of three guesses and none is sourced; the duration cap has room (5 percent at 50 editor hours), so the number decides nothing today.

8. **The claim that the client "deploys before any hello says it" needs deployment N in production before the Worker is ever selected** (3.7 item 1); the specification says so. Not unsourced; listed because the guard's TanStack Start advisory hold on `c978bb43` (`read-runtime.md` 1.1: the Vercel CLI refused `c978bb43` on 2026-10-01 and production is `f50b209d`) means no main sha deploys until the catalog moves or the override is set, and the specification's section 3.7 and 5.6 do not mention that the whole flip order waits on it.

## 5. Verdict

Revise. The design is complete in its data flows (eight drawn, each with a bound and a row), its rows (every `docs/REALTIME.md` section 2 row has a mechanism, a lane and a driver; the three `setup.*` rows and the `cost.*` rows have drivers), its lanes (six lanes with files, a merge order and the files two lanes share) and its free tier arithmetic (every cap matched against a per day count at 50 and 500 editor hours with the break day printed). The three largest items to fix before it binds:

1. The acceptance conflict of gap 1: an unparkable `realtime` feature with a row the specification expects to stay flaky, and no rule for the ship when it does.
2. The preview gate's ordering of gap 2: the preview Worker's `TURBOSLIDE_APP_ORIGIN` is set from a Vercel preview URL that does not exist until after the Worker deploy the recipe runs first, in 5.5 item 2 and 5.6 item 1, so no realtime row can read green on a preview as written.
3. The control tables of gap 3: `rt_open` and `rt_flags` have no creation command and `rt_flags.realtime` no seed, so the runtime kill switch and `/health` rest on tables nothing makes; with it, the `do` tier selection by accident in the D1 hand row (gap 4), which is one line.

After those, the eight citation drifts of section 1 and the two internal contradictions (`version.save`, the transport's requester) are an hour of edits.
